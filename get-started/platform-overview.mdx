The [introduction](./introduction) covered *why* Prisme.ai is a unified foundation rather than another silo. This page covers *how* that foundation is put together: the architecture underneath it, the development lifecycle on top of it, and the governance that runs through all of it.

## Three-tier architecture

Prisme.ai is layered so that each concern (infrastructure, models, and the Gen.AI platform itself) can evolve and scale independently.

<Frame>
  <img src="/images/architecture.png" alt="Prisme.ai three-tier architecture" />
</Frame>

### 1. Cloud & Infrastructure Layer
- Runs on any major cloud (GCP, AWS, Azure, OpenShift) or on-premises
- Provides the foundation for deploying and running Prisme.ai services
- Ensures security, scalability, and reliability, with no vendor lock-in

### 2. Language Models Layer
- Integrates multiple LLM providers: OpenAI, AWS Bedrock, Google Vertex AI, Mistral AI, and open-source/self-hosted models
- Manages model selection, routing, optimization, and fallback
- Handles multimodal capabilities where supported

### 3. Gen.AI Platform Layer (AI Products & Builder)
- The user-facing products and development tools
- Implements RAG, agentic workflows, and integrations
- Enables no-code, low-code, and full-code paths onto the same system

## Why event-driven

Prisme.ai is built on an **event-driven architecture**, and that choice is what makes the enterprise guarantees possible: it's not just a technical detail.

Every operation on the platform emits a **normalized event**: a consistent type, a **correlation ID**, and a timestamp. Because every action speaks the same language, the platform can:

- **Scale**: processing is asynchronous, so load spikes don't block the system
- **Observe**: events are historized and aggregated into analytics and usage statistics
- **Secure**: a single normalized stream is what security monitoring watches
- **Debug**: follow one correlation ID across every API call and tool execution to trace exactly what an agent did, and why

## The development lifecycle

On Prisme.ai, an agent or application isn't a one-off you configure and hope for the best. It follows a real engineering lifecycle: the same discipline you'd expect from any production software.

<Steps>
  <Step title="Iterate">
    Build and refine in a development environment. An agent's behavior is defined declaratively in a versioned config file (`index.yml`).
  </Step>
  <Step title="Validate">
    Test in the Playground, replay conversations, and inspect execution through the correlation ID.
  </Step>
  <Step title="Version (Git)">
    Commit your work to Git. Configuration-as-code means every change is reviewable and reproducible.
  </Step>
  <Step title="Review (Merge Request)">
    Open a merge request so changes are reviewed before they reach production: traceability and quality by default.
  </Step>
  <Step title="Deploy & Publish">
    Promote to the target environment, then publish the agent to your organization and generate an embed script to integrate it into websites or portals.
  </Step>
</Steps>

### Infrastructure as Code, for AI

Developing through Builder and VS Code is the equivalent of using Terraform for infrastructure: defining your agents and applications **as code** guarantees **reproducibility and consistency** across environments. Two deployment modes cover both speed and rigor:

## Governance runs through everything

Governance on Prisme.ai isn't a separate product you visit occasionally; it's woven into the foundation, and it works on **two levels**: a **central governance** defines platform-wide rules, and **each organization inherits from it** while adapting within those guardrails. Teams get agility; the enterprise keeps compliance.

The platform solves the cross-cutting concerns once, for everyone:

- **Multi-tenancy** separates organizations, teams, and environments, each inheriting central policy
- **SSO and centralized permissions**: one identity model across the whole platform
- **Audit logs**: every action recorded and traceable for security and compliance
- **Chargeback / rebilling**: usage attributed per organization for transparent cost allocation
- Every agent runs with a **service account**; you can **restrict the models and tools** it may call
- **Membership rules** (for example, based on email domain) automatically grant the right roles as people join
