This page tells you how much CPU and memory to give each Prisme.ai service, when to scale, and how to debug resource problems. Database resources are covered in [Databases](/self-hosting/databases/overview).

---

## Two reference variants

We ship two sets of resource defaults. Treat them as the **recommended lower and upper bounds for production**; your environment should land somewhere between the two, tuned to your actual load and use case.

| Variant | Use when |
|---------|----------|
| **Balanced** *(chart default)* | Up to a few hundred concurrent users, budget-sensitive. Each pod is sized for typical load, with HPA absorbing spikes. |
| **Performance** | Thousands of concurrent users, max throughput per pod. Requests are sized at the maximum each service can usefully consume on a 4 vCPU node; going higher on these nodes brings no gain. |

<Info>
  **Start at Balanced.** `Balanced` is now the chart default and the right starting point for a fresh install: high enough to run a real workload comfortably, low enough to avoid over-paying before you know your traffic shape. Move toward `Performance` (or somewhere in between) once you've observed your actual usage.
</Info>

### Trade-off in plain English

- **High requests** → fewer pods per node → idle CPU/RAM is wasted when pods aren't busy.
- **Low requests** → more pods per node → risk of a node being unable to provide CPU/RAM under load spikes.

Pick **Balanced** if your traffic is mostly steady and budget matters. Pick **Performance** if you need each pod to absorb large bursts on its own. Most production deployments end up at an intermediate point: **any value between Balanced and Performance is valid**, service by service, and there is no reason to copy either column verbatim once you have real data. You don't need Performance requests on day one if your user base will grow progressively.

### Right-sizing from observed usage

Once the platform is live, monitor per-pod CPU and memory and resize from data, not from these tables:

- **CPU request** → set to the **P95** of the pod's normal usage. CPU is compressible: the occasional P99 spike is absorbed by the node without breaking the workload, so paying for it as a permanent request wastes capacity.
- **Memory request** → set to the **P99** of the pod's normal usage. Memory is not compressible: exceeding the request risks eviction or OOMKill, so the request must comfortably cover the worst legitimate spike.
- **Memory limit** → keep close to the request (the chart defaults already do this) so a runaway pod is capped before it OOMs the node.
- **CPU limit** → don't set one (see [Why no CPU limit?](#why-no-cpu-limit) below).

Iterate: re-measure after a few weeks of steady traffic and after any major usage shift (new product enabled, big workspace migration, traffic doubled).

### Cluster size baseline

Our reference node is **4 vCPU / 16 GB RAM** (a common cloud baseline like AWS `m6i.xlarge`, GCP `n2-standard-4`, Azure `D4s_v5`). Once the cloud provider's reservations and the usual DaemonSets are subtracted, such a node leaves roughly **3.6–3.8 vCPU and ~14 GB** for Prisme.ai pods (see [Fitting the runtime on a node](#fitting-the-runtime-on-a-node)).

Scheduling the requests / limits below on these nodes gives:

| Variant | At HPA min | At HPA max | Recommended starting pool |
|---------|------------|------------|---------------------------|
| **Balanced** | ~8.4 vCPU requests / ~13 GB memory limits → 3 nodes | ~21.6 vCPU / ~41 GB → **6 nodes** | **5 nodes**, cluster autoscaler allowed to grow to 6+ |
| **Performance** | ~30.5 vCPU / ~29 GB → **10 nodes, with no spare room** | ~76 vCPU / ~72 GB → ~24 nodes | **12 nodes**, cluster autoscaler enabled |

How to read this table:

- **CPU is counted on requests, memory on limits.** CPU is compressible: the scheduler places pods on their requests and a busy pod is only slowed down. Memory is not: a pod exceeding its limit is killed, and a node whose pods together exceed its RAM evicts them. Plan node memory on the sum of the limits so you never overcommit it.
- **CPU is the constraint in both variants**; memory never is on 16 GB nodes.
- **Performance at HPA min fills 10 nodes exactly.** A Performance `runtime` pod takes almost a whole 4 vCPU node, and the remaining pods don't pack perfectly, so the leftover capacity is split into slivers too small to host another pod. 12 nodes leave room for two scale-outs (one extra `runtime` replica needs one free node) or a rolling update.
- **The starting pool is deliberately smaller than what HPA max needs.** Provisioning every node HPA could ever ask for would waste capacity most of the time; the **cluster autoscaler** adds nodes as HPA scales out and removes them afterwards. It is required in both variants. The `HPA max` values are themselves yours to raise (see [HPA](#horizontal-pod-autoscaling-hpa)), so no fixed node count can cover them.

These are starting points; the actual node count depends on your HPA targets, the database pods you co-locate, and any extra workloads. Pick the **node size** and the **pod IP range** from your expected scale up front: those two are the hardest settings to change later. Requests and HPA bounds can then be tuned at any time from your monitoring.

<Warning>
  **Keep at least one free node when a pod takes almost a whole node.** A rolling update (`helm upgrade`, `maxSurge`) or a node drain needs room for the new pod *before* the old one goes away. With Performance `runtime` (and, to a lesser extent, `crawler`) on 4 vCPU nodes, that room is a full empty node: without it, the new pod stays `Pending` until the cluster autoscaler provisions one, which takes a few minutes. The same delay applies to every `runtime` scale-out.
</Warning>

### Alternative: 8 vCPU nodes for Performance

On **8 vCPU / 32 GB** nodes (AWS `m6i.2xlarge`, GCP `n2-standard-8`, Azure `D8s_v5`), or compute-optimized **8 vCPU / 16 GB** nodes (Performance needs roughly 1 GB of memory limit per vCPU of request), the Performance variant fits in **5 nodes at HPA min and ~11 at HPA max**. A `runtime` pod then shares its node with other pods, so you can raise its CPU request to **4–4.5 vCPU** (the technical ceiling of 4 workers, see [Scaling `prismeai-runtime` workers](#scaling-prismeai-runtime-workers)).

| | 4 vCPU nodes *(reference)* | 8 vCPU nodes *(alternative)* |
|---|---|---|
| `runtime` Performance request | 3500m, one pod per node | 4000–4500m, shares the node |
| Bin-packing | Fragmented: leftover slivers per node | Better: fewer, larger nodes |
| Scale-out / rolling update | Each new `runtime` pod waits for a new node | Usually fits on an existing node |
| Cost of adding a node | Small increments | Larger increments; more idle capacity, especially for Balanced |
| Availability | Every cloud and most on-premise setups | Not always available on premise |

Both are supported. 4 vCPU nodes remain the reference, and Performance runs fine on them; 8 vCPU nodes are a comfort option for large, bursty loads, not a prerequisite.

## Why no CPU limit?

You'll notice the tables above have no CPU limit. **Don't set one** on Prisme.ai services.

- The Linux CFS scheduler already throttles pods that exceed their request when another pod on the same node needs that CPU.
- A CPU limit on top of that wastes free CPU: when the node has spare cycles and a pod could use them, the limit blocks it for no reason.
- In practice, CPU limits on Node.js workloads cause unnecessary tail-latency spikes and add zero protection.

Memory limits stay: memory is not compressible, so a runaway pod must be capped before it triggers OOM on the whole node.

## Horizontal Pod Autoscaling (HPA)

**Golden rule for production: at least 2 replicas of every core service**, and of `functions` and `crawler` in apps. Single-replica means a single bad pod, restart or node drain takes the service down.

<Note>
The `HPA max` values in the variant tables above are **starting points**, not ceilings. They were chosen to cover the typical load profile of each variant; review them against your own observed traffic and **raise them** when you see HPA sitting at max replicas during peaks or latency degrading. The right max replicas count is the one that comfortably absorbs your highest expected spike with headroom; treat the defaults as a starting baseline to tune.
</Note>

### Example HPA config

```yaml
prismeai-runtime:
  hpa:
    enabled: true
    minReplicas: 2
    maxReplicas: 5
    targetCPUUtilizationPercentage: 70
```

### Recommended targets

| Service group       | Target CPU | Notes |
|---------------------|------------|-------|
| api-gateway, workspaces, runtime, console | 70% | Standard CPU-bound services |
| events              | 70% CPU    | Pin clients via a consistent-hash header (or Istio `DestinationRule` on `user-agent`); events benefit from sticky sessions |
| functions           | 70% CPU    | Memory is the real constraint; over-provision memory before scaling |
| crawler             | 80% CPU + 80% memory | Heavy memory pressure during indexing |
| searchengine        | 70% CPU    | |

## Scaling `prismeai-runtime` workers

`prismeai-runtime` is the only platform service that runs multiple workers inside the same pod. The pod runs a **main thread** that receives HTTP calls from api-gateway and events from the broker and dispatches them to **N worker threads** which actually execute the automations. Adding workers raises the per-pod parallelism without spinning up new pods.

Configured via the **Helm value `prismeai-runtime.maxWorkers`** (which populates the `RUNNER_MAX_THREADS` env var inside the container). Default: `1`.

<Note>
The `runtime` resource numbers in the variant tables above are sized for a specific worker count: **3 workers** for Balanced, **4 workers** for Performance. If you change `maxWorkers`, re-derive the pod resources with the math below; keeping the defaults while bumping workers will starve each one.
</Note>

### Golden rule: scale workers and resources together

A worker is a Node.js thread; it competes for the pod's CPU and memory budget alongside the main thread. **Doubling `maxWorkers` without raising `resources.requests` / `resources.limits` halves what each worker gets** and you'll see latency degrade or workers OOMKilled.

The chart slices **75%** of `resources.limits.memory` across the workers (the other 25% goes to V8 metadata, native modules and the main thread). So sizing the pod is a two-step decision:

1. Pick how much heap **each worker needs** based on the workload it will execute. For production workloads, plan **500 MiB to 1 GiB per worker** depending on the automations they run (heavier templating, large payloads or heavy in-flight contexts push it toward 1 GiB).
2. Set `limits.memory` and `maxWorkers` together so the chart's auto-slice gives each worker that heap.

In practice you have two equivalent ways to think about it:

- **Top-down**: keep `limits.memory` fixed and lower `maxWorkers`; each worker's heap rises proportionally.
- **Bottom-up**: target a per-worker heap and raise `limits.memory` to fit `maxWorkers` of them, plus the 25% main-thread overhead.

Example: aiming for 4 workers at ~750 MiB heap each → `limits.memory ≈ 4 GiB`, `maxWorkers: 4` (this is the Performance default).

### CPU per worker

A worker (i.e. a Node.js thread) can use **at most one core**, and the main thread a small share on top. So **one core per worker plus ~0.5 for the main thread is the ceiling** a runtime pod can consume: about `4.5` vCPU for 4 workers. A request above that is wasted.

It is a ceiling, not a minimum. Automations spend much of their time waiting on I/O (LLM calls, HTTP fetches, databases), so workers rarely all burn a full core at once, and a request below one core per worker is normal: Balanced runs 3 workers on 2 vCPU. Size the request from the observed P95 usage, like any other service.

On a **4 vCPU node**, the 4.5 vCPU ceiling can't be requested: keep `maxWorkers: 4` and request what the node can actually give (3500m in the Performance table). Because Prisme.ai sets no CPU limit and a Performance `runtime` pod is alone on its node, a lower request doesn't take CPU away from the workers: they still use all the CPU the node has free. Dropping to 3 workers caps automation execution at 3 cores, whatever the node has free. With 4 workers, the pod also uses the remaining 0.5–0.7 vCPU of requestable CPU, and usually more: DaemonSets and system pods rarely consume their whole request, and that idle CPU goes to whoever needs it. A 4th worker also limits how much work waits behind a CPU-heavy automation: tasks are dispatched round-robin and each worker runs its automations concurrently on one event loop, so a worker busy with a heavy automation delays every task assigned to it. In return, each worker gets less heap and the pod opens more database connection pools. The 3-worker option pays off when you also lower the request (about `3` vCPU) so that a small pod can share the node.

### Fitting the runtime on a node

A pod is only scheduled if its request fits in what the node has left. On a 4 vCPU node, that is less than 4 vCPU:

```text
max runtime request = node allocatable CPU − requests of the DaemonSets on the node − requests of the pod's sidecars
```

- **Allocatable CPU** is the node's capacity minus what the cloud provider reserves for the kubelet and the OS: around 3.85–3.92 vCPU for a 4 vCPU node on AWS, GCP and Azure.
- **DaemonSets** run on every node: CNI, kube-proxy, CSI drivers, log and monitoring agents, security agents. A bare AWS node requests about 150m (`aws-node` + `kube-proxy`); managed monitoring or security agents can add a few hundred more.
- **Sidecars** injected in the `runtime` pod (for instance an Istio proxy, typically 100m) count in the pod's own request.

For example, a bare AWS node gives 3920m − 150m = 3770m, or 3670m with an Istio sidecar. The 3500m of the Performance table keeps a margin that fits a 4 vCPU node on the three major clouds. Check your own nodes:

```bash
kubectl describe node <node>
# "Allocatable:" → cpu
# "Non-terminated Pods:" → CPU Requests of every DaemonSet pod on that node
```

If what is left is clearly below 3.5 vCPU (many agents on every node), either lower the `runtime` request and `maxWorkers` together (see [CPU per worker](#cpu-per-worker)), or move to [8 vCPU nodes](#alternative-8-vcpu-nodes-for-performance).

### Node.js workers heap is auto-sized

Each worker thread has its own heap memory hard limit, configured via Node.js's `--max-old-space-size` option. You don't need to set `NODE_OPTIONS` manually; the chart auto-derives each worker's heap from `resources.limits.memory` and `maxWorkers`:

```text
maxOldSpaceSize = floor( memory_limit_in_Mi / maxWorkers × 0.75 )
```

## Resource Quotas and Limit Ranges

Apply quotas at the namespace level to prevent runaway consumption. The example below fits the **Balanced** `core` namespace at HPA max (~13 vCPU requests and ~16 GiB memory limits, or ~16 vCPU during a rollout). Size yours on your own HPA max, plus one extra pod per deployment for rolling updates: a quota that's too tight blocks scale-outs and rollouts. The Performance `core` namespace, for instance, requests ~18.5 vCPU at HPA min and ~46 vCPU / ~30 GiB of memory limits at HPA max, so it needs a `requests.cpu` of about `"56"` once rollouts are counted.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prismeai-core-quota
  namespace: prismeai-core
spec:
  hard:
    requests.cpu: "16"
    requests.memory: "32Gi"
    limits.memory: "64Gi"
    pods: "50"
```

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: prismeai-core-limits
  namespace: prismeai-core
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "250m"
        memory: "512Mi"
      default:
        memory: "1Gi"
```

## Troubleshooting

<AccordionGroup>

<Accordion title="Pods stuck Pending">
```bash
kubectl describe pod <pod> -n <namespace> | tail -30
kubectl describe nodes | grep -A 5 "Allocated resources"
```
- "0/N nodes available: Insufficient cpu/memory" → reduce requests, increase node size, or scale the node pool.
- `runtime` (or another large pod) `Pending` on every node, even an empty one → its request exceeds what a node can offer after DaemonSets; see [Fitting the runtime on a node](#fitting-the-runtime-on-a-node).
- "node(s) didn't match Pod's node affinity/selector" → check `tolerations` and `nodeSelector` against your node pool labels.
</Accordion>

<Accordion title="HPA pinned at maxReplicas">
```bash
kubectl get hpa -n <namespace>
kubectl describe hpa/<hpa> -n <namespace>
```
- Sustained 100% CPU on max replicas → raise `maxReplicas`, or move from Balanced to Performance variant for the affected service.
- Memory-bound service (e.g. `functions`) → raise memory request rather than replica count.
</Accordion>

<Accordion title="Pod OOMKilled">
```bash
kubectl logs <pod> -n <namespace> --previous
kubectl describe pod <pod> -n <namespace> | grep -i oom
```
- For `runtime`, check `BROKER_EMIT_MAXLEN`; very large events can spike memory.
- For `functions`, check `NODE_OPTIONS=--max-old-space-size=...` matches the container memory limit.
- Raise the memory request **and** limit together.
</Accordion>

<Accordion title="CPU throttling under load">
```bash
kubectl top pods -n <namespace>
```
- High CPU usage approaching the request, with growing latency → raise the CPU request (not a limit).
- Verify no CPU limit is set on Prisme.ai services.
</Accordion>

<Accordion title="Node saturation">
```bash
kubectl top nodes
kubectl describe nodes/<node>
```
- One node carrying disproportionate load → check pod anti-affinity on critical services, or rebalance with a rolling restart.
- Persistent saturation → scale the node pool or move to larger instances.
</Accordion>

<Accordion title="Frequent restarts after deployments">
```bash
kubectl get events -n <namespace> --sort-by=.lastTimestamp | tail -30
```
- Failing readiness probe right after rollout → check service dependencies (DB reachable, secrets mounted).
- Crash loop → `kubectl logs <pod> -n <namespace> --previous`.
- If the regression is in a new chart version, roll back: `helm rollback <release> <revision> -n <namespace>`; see [Helm install: Upgrade, rollback, uninstall](/self-hosting/kubernetes/helm#9-upgrade-rollback-uninstall).
</Accordion>

<Accordion title="Volume node affinity conflict">
Symptom in `kubectl get events`:
```
FailedScheduling   0/3 nodes are available: 1 Insufficient memory, 2 node(s) had volume node affinity conflict.
```
A pod with a `ReadWriteOnce` PVC can only be scheduled on the node where the volume lives. If that node is full and the others can't mount the volume, scheduling fails.

Fixes:
- Free CPU/memory on the node that hosts the volume (delete idle pods, scale a noisy neighbor down).
- Move to a **ReadWriteMany** storage class (EFS / Azure Files / Filestore / CephFS) for workloads that can be re-scheduled freely; see [Requirements](/self-hosting/requirements#filesystems).
- Add a node to the pool.
</Accordion>

<Accordion title="PersistentVolume nearly full">
Alerts: `KubePersistentVolumeFillingUp`, `KubePersistentVolumeFull`.

```bash
kubectl get pvc -A
kubectl describe pvc <pvc> -n <namespace>
```
- For Elasticsearch or OpenSearch, the most common cause is unbounded event growth; enable the `prismeai-events` cleanup job and tune retention. See [Elasticsearch: Events automated cleanup](/self-hosting/databases/elasticsearch#events-automated-cleanup).
- Expand the PVC if the storage class supports it (`kubectl edit pvc <pvc>` → bump `spec.resources.requests.storage`).
- Otherwise, snapshot + restore into a larger volume.
</Accordion>

</AccordionGroup>
