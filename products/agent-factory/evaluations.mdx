Evaluations help you systematically test your agent. Create test cases with expected outcomes, run them against your agent, and track quality over time.

## Why Evaluate?

Manual testing in the Playground is useful for exploration, but evaluations provide:

- **Consistency** - Same tests run the same way every time
- **Regression detection** - Know immediately if changes break something
- **Quality metrics** - Track scores over time
- **Documentation** - Test cases describe expected behavior

## The Evaluate Page

Open any agent and go to the **Evaluate** section. You'll see:

- **Test Cases** - Your collection of input/expected output pairs
- **Run History** - Past evaluation runs and their results
- **Current Run** - Real-time progress when an evaluation is running

## Creating Test Cases

A test case defines:

| Field | Description |
|-------|-------------|
| **Input** | The user message to send |
| **Expected Output** | What the agent should say or do |
| **Criteria** | Specific things to check (optional) |
| **Tags** | Categories for organizing tests |

### From Scratch

1. Click **Create Test Case**
2. Enter the user input
3. Describe the expected output
4. Add any specific criteria
5. Save

### From Playground

When you have a good conversation in the Playground:

1. Note the user message and agent response
2. Go to Evaluate and create a test case
3. Use the conversation as your baseline

### Import Bulk

For many test cases:

1. Click **Import**
2. Upload a JSON or CSV file with your test cases
3. Map the columns to fields
4. Import

## Writing Good Test Cases

### Be specific about expectations

Instead of "should be helpful", specify:

```
Expected: Agent should search the knowledge base and provide 
a step-by-step guide for resetting the password. Should include 
the link to the self-service portal.
```

### Cover different scenarios

Build a diverse test suite:

- Happy paths (common, expected use)
- Edge cases (unusual inputs)
- Error handling (what happens when things go wrong)
- Out of scope (things the agent shouldn't do)

### Use criteria for precision

Criteria let you check specific aspects:

| Criterion | What It Checks |
|-----------|----------------|
| `contains_link` | Response includes a URL |
| `mentions_product` | Specific product name appears |
| `polite_tone` | Response is professional |
| `under_100_words` | Response is concise |

### Tag for organization

Use tags to group related tests:

- `password-reset` - All password-related tests
- `billing` - Payment and subscription tests
- `edge-case` - Unusual scenarios
- `regression` - Tests for fixed bugs

## Running Evaluations

### Run All Tests

1. Click **Run Evaluation**
2. Wait for all tests to complete
3. Review results

### Run Single Test

To test one case:

1. Find the test case
2. Click the play button
3. See the result inline

### Run with Different Models

Compare how different models perform:

1. Click **Run Evaluation**
2. Select a different model from the dropdown
3. Compare results to previous runs

## Understanding Results

After a run completes, you'll see:

### Summary

- **Score** - Overall pass rate (0-100%)
- **Passed/Failed** - Count of each
- **Duration** - How long the run took

### Per-Test Results

For each test case:

| Field | Description |
|-------|-------------|
| **Status** | Pass or Fail |
| **Score** | How well it matched expectations (0-100) |
| **Actual Output** | What the agent actually said |
| **Feedback** | Explanation of scoring |

### Regression Detection

When you run multiple evaluations, the system detects:

- **Improvements** - Tests that now pass
- **Regressions** - Tests that used to pass but now fail
- **Score changes** - How individual test scores changed

## Working with History

### Compare Runs

Select two runs to see side-by-side comparison:

- Which tests changed status
- Score differences
- What's improved vs regressed

### Delete Runs

To remove old evaluation data:

1. Find the run in history
2. Click the delete button
3. Confirm

### Export Results

Export evaluation data for reporting:

1. Select a run
2. Click Export
3. Download as JSON or CSV

## Runs without a user

An evaluation run started from the **Evaluate** page or the API executes as the user who started it: calls to the agent and to the judge model authenticate as that user, and quota and cost are charged to that user's organization. Two background jobs start or resume runs that have no user:

- The stalled-run job checks every 2 minutes for runs that are still running but have stored nothing for more than 3 minutes (and for less than 24 hours). It resumes each of them from the first case that has no result.
- The nightly evaluation batch runs the test cases of every agent that has some. It ships disabled.

These runs authenticate to Agent Factory and to the LLM Gateway with an organization API key stored in the `AGENT_FACTORY_API_KEY` secret of the **Agent Evaluations** workspace. This section is for platform administrators, including operators of self-hosted deployments. Configure the key on every environment where agents are evaluated: without it, a stalled run is failed instead of resumed.

### Configure the organization API key

Before you begin, make sure that you have:

- The `orgs:apikeys:create` permission in the organization that owns the evaluated agents.
- Access to the secrets of the **Agent Evaluations** workspace in Builder. By default, only workspace owners can manage secrets.

To create the key and store it:

1. In Governance, start [creating an API key](/products/ai-governance/identity-access#creating-an-api-key) in the organization that owns the evaluated agents.
2. In the permission tree, grant `agent-factory:agents:read` and `llm-gateway:models:chat-completions`. Sending a message to an agent is authorized as a read of that agent, so the key needs no write permission.
3. Set the [scopes](/products/ai-governance/identity-access#scopes) `agent-factory:agents:*` and `llm-gateway:models:*`. To restrict the key further, list the ids of the evaluated agents and of the models they and the judge use instead of the wildcards.
4. Create the key and copy its value. The value starts with `iak_` and is displayed only once.
5. In Builder, open the **Agent Evaluations** workspace, then open **Settings** and select **Secrets**.
6. In the [Additional Secrets form](/products/ai-builder/module-secrets#additional-secrets-form), enter `AGENT_FACTORY_API_KEY` in **New key** and the key value in **New value**, then select **+**.
7. Select **Save Secrets**.

For self-hosted deployments that inject workspace secrets from [environment variables](/products/ai-builder/workspaces#environment-variables), you can set `WORKSPACE_SECRET_agent-evaluations_AGENT_FACTORY_API_KEY` instead. A secret saved in the workspace takes precedence over the environment variable.

When you [rotate the key](/products/ai-governance/identity-access#rotating-keys), the previous value stops working immediately: save the new value in `AGENT_FACTORY_API_KEY` right away.

### Verify runs without a user

Saving the secret does not start a run. Check the result the next time the stalled-run job resumes a run:

1. In Builder, open the [Activity](/products/ai-builder/activity) feed of the **Agent Evaluations** workspace.
2. Search for `EVAL_AUTH_NOT_CONFIGURED`. No `error` event with this code after the time you saved the secret means that the jobs found a usable key.
3. On the **Evaluate** page of an agent whose run was resumed, open **Run History**. The resumed run finishes, and its cases have results instead of `AGENT_ERROR` or `JUDGE_AUTH` errors.

### Limits of the organization API key

The key changes the identity that the agent, the judge, and the agent's tools see. Plan for these limits:

- **One organization**: Agent Factory grants the key only the agents of the key's organization. A run without a user on an agent of another organization fails with `403 Access denied`, stored as `AGENT_ERROR` on each case.
- **Nightly batch across organizations**: the nightly batch evaluates every agent that has test cases, whatever its organization. Before you enable it, restrict it to the agents of the key's organization. Otherwise the agents of every other organization fail with `403` each night.
- **Identity change on resume**: a run started by a user and resumed by the stalled-run job changes identity during the run. Cases run before the stall used the user's identity, and cases run after it use the key. Quota and cost of the resumed cases are charged to the key's organization. If the user's organization is not the key's organization, the resumed cases fail with `403` (`AGENT_ERROR`).
- **Tools**: the capabilities and tools that the agent calls receive the key's scopes, not a user session. A tool that requires a user session may fail in a run without a user.

### Troubleshoot runs without a user

#### `EVAL_AUTH_NOT_CONFIGURED`

- **Symptom**: the Activity feed of the **Agent Evaluations** workspace shows an `error` event `EVAL_AUTH_NOT_CONFIGURED`. A run has the status `failed`, with an error that starts with `EVAL_AUTH_NOT_CONFIGURED:`.
- **Cause**: the `AGENT_FACTORY_API_KEY` secret is missing, or its value is not an organization API key (it does not start with `iak_`). The jobs launch no case that would fail: the stalled-run job fails each run that still has cases to run, without writing any result, and the nightly batch stops before it creates any batch, run, or result.
- **Fix (platform administrator)**: [configure the organization API key](#configure-the-organization-api-key). A failed run is not resumed: start the evaluation again from the **Evaluate** page.
- **Verify**: [check that no new `EVAL_AUTH_NOT_CONFIGURED` event appears](#verify-runs-without-a-user).

#### Cases fail with `AGENT_ERROR` or `JUDGE_AUTH` in a resumed run

- **Symptom**: in a run resumed without a user, cases fail with `AGENT_ERROR` (agent call) or `JUDGE_AUTH` (judge call).
- **Cause**: if the error message names the `AGENT_FACTORY_API_KEY` secret, the secret was removed while the run was in progress. A `401` without this message means that the platform refused the key, for example because it expired or was rotated without updating the secret. A `403` means that the agent, or the user who started the run, belongs to another organization than the key (see [Limits of the organization API key](#limits-of-the-organization-api-key)).
- **Fix (platform administrator)**: save a valid key in `AGENT_FACTORY_API_KEY`, or rotate the key and save the new value. Then run the evaluation again from the **Evaluate** page.
- **Verify**: [check the next resumed run](#verify-runs-without-a-user).

## Best Practices

<AccordionGroup>
  <Accordion title="Run before publishing">
    Always run your full test suite before publishing changes. Catch regressions before users do.
  </Accordion>
  <Accordion title="Add tests for bugs">
    When you find and fix a bug, add a test case to prevent it from returning.
  </Accordion>
  <Accordion title="Review failures carefully">
    A failing test might mean the agent is wrong, or it might mean the test expectation needs updating.
  </Accordion>
  <Accordion title="Keep tests maintainable">
    Overly specific expectations break easily. Focus on what matters, not exact wording.
  </Accordion>
  <Accordion title="Test tool usage">
    Include tests that verify the agent uses the right tools for the right tasks.
  </Accordion>
</AccordionGroup>

## Advanced: Tool Expectations

For agents with tools, you can specify expected tool usage:

```json
{
  "input": "What's the weather in Paris?",
  "expected_tools": [
    { "name": "weather_lookup", "arguments": { "city": "Paris" } }
  ],
  "forbidden_tools": ["calendar"]
}
```

This checks that the agent:

- Calls the expected tools with correct arguments
- Doesn't call forbidden tools
