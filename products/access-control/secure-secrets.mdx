---
title: "Let members deposit their own credentials"
description: 'Workspace owner: write the secure_secrets rules that let each member store their own third-party credential, and let a scheduled automation replay those credentials through a dedicated role.'
---

Use this procedure when a workspace connects members' own third-party accounts, for example a connector that stores each member's OAuth refresh token so a scheduled synchronisation can use it later. When it succeeds, each member can write only their own credential, and only the automation calls you mark can read, rotate, or drop them.

Two rules are needed, and they are deliberately different:

| Rule | Applies to | May touch |
|---|---|---|
| A rule without `role` | Every member | `create` and `update` on one secret: their own, pinned to `${user.id}` |
| A rule with a dedicated role | An automation call that takes the role on with `assumeRole` | `read`, `create`, `update`, and `delete` on a whole family of secrets, such as every `spnRefresh_` token |

## Before you begin

- **Who:** an owner of the workspace.
- **Where:** Builder, in the workspace, **Settings**, **Security**, and the automations that read the credentials.
- **Requires:** the prefix of the secret names the connector uses, such as `spnRefresh_`. It must be at least six characters long, end with `_`, `-`, `:`, or `/`, and must not start with `prismeai_`.
- **Impact:** the role you declare can read and overwrite every credential in the family. See the warning in step 2.

## Write the rules

<Steps>
  <Step title="Let each member write their own credential">
    In **Settings**, **Security**, add a rule without `role` granting `create` and `update` on `secure_secrets`, with a `name` condition that pins the secret to the caller:

    ```yaml
    authorizations:
      rules:
        - action:
            - create
            - update
          subject: secure_secrets
          conditions:
            name:
              $regex: '^spnRefresh_[a-f0-9]{16}_${user.id}$'
    ```

    The `name` condition is what keeps members apart, so the platform refuses the rule unless it is either an exact string containing `${user.id}`, or a `$regex` that:

    - is anchored with `^` and `$`;
    - contains `${user.id}` exactly once;
    - uses only literal characters around it, plus at most one fixed-width character class such as `[a-f0-9]{16}`, so a connector can hold one credential per remote account.

    The width of the class must be fixed (`{16}`, never `+`, `*`, or `{1,16}`): with a variable width, two different account and user pairs could produce the same name.
  </Step>
  <Step title="Declare a role for the automation that replays them">
    Declare a role, without an `auth` block, and grant it the family of secrets:

    ```yaml
    authorizations:
      roles:
        tokenResolver: {}
      rules:
        # ...the rule from step 1
        - role: tokenResolver
          action:
            - read
            - create
            - update
            - delete
          subject: secure_secrets
          conditions:
            name:
              $regex: '^spnRefresh_'
    ```

    `create` and `update` let the automation store the new refresh token a provider returns when it rotates tokens. `delete` lets it drop a token the provider has revoked, so the member is asked to reconnect.

    <Warning>
    Anything holding this role can read and overwrite every credential in the family. Do not assign it to a person in **Sharing**, and do not give it an `auth` block: an API key bound to it would hand every member's credential to whoever holds the key. The platform does not prevent either.
    </Warning>
  </Step>
  <Step title="Save the rules">
    Select **Save Rules**. If a `name` condition does not meet the constraints above, the editor shows why, for example `Security rules on 'secure_secrets' must confine 'name' to the acting user: ...`.
  </Step>
  <Step title="Take the role on where the credential is read">
    In the automation, add `assumeRole` to the `run` instruction that reads the secret:

    ```yaml
    - run:
        function: secret.get
        assumeRole: tokenResolver
        parameters:
          name: 'spnRefresh_{{targetUserId}}'
          scope: workspace
    ```

    The role applies to that single call. It replaces the caller's rights for the call rather than adding to them, and it is not passed to the instructions that follow, to the automations this one calls, to an `emit`, or to another workspace. For the functions of the secrets module, see [Secrets module](/products/ai-builder/module-secrets).
  </Step>
</Steps>

## Verify the result

1. As a member, connect your third-party account through the connector, so it stores your credential.
2. Run the scheduled automation, or trigger it manually, and confirm in its activity that `secret.get` returns the credential instead of `{ error: "not_found" }`.
3. Remove `assumeRole` from a copy of the call and run it again. It returns `{ error: "not_found" }` with a message asking to declare a role, which proves the role is what grants the read.

## Limits that no rule can change

- `manage` cannot be granted on `secure_secrets`, and `delete` cannot be granted without a `role`.
- A rule without `role` that grants `read` applies to every member, who would then read each other's credentials. The platform accepts it but you should not write it.
- Secrets of `scope: user` belong to one person. A run without that person is refused before any rule is consulted.
- The `owner` role cannot be taken on with `assumeRole`. Declare a role that states what it opens. Taking on an undeclared role fails with `Unknown role '<role>': assumeRole only accepts a role declared in this workspace's security rules`.

## Undo the change

Remove the two rules and the role from **Settings**, **Security**, and select **Save Rules**. Members can no longer store credentials, and the automation can no longer read them. Credentials already stored stay in the workspace until an owner deletes them.
