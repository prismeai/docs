Use this page to look up the permissions an organization role can hold, how scopes restrict a role to specific resources, and what each system role grants. To create a role or assign one to a member, see [Create and assign organization roles](/products/access-control/manage-organization-roles). For how organization roles combine with resource sharing and workspace roles, see [How access control works](/products/access-control/overview).

## Permission format

A permission has three segments separated by colons: `product:resource:action`. For example, `storage:vector_stores:write` lets the holder create and edit knowledge bases.

A `*` replaces any segment and everything after it:

| Permission | Grants |
|---|---|
| `storage:vector_stores:*` | Every action on knowledge bases |
| `storage:*` | Every resource and action of the Storage product |
| `*` | Every permission of every product |

A permission alone does not reach a specific resource. The role also needs a [scope](#resource-scopes) on that resource, or the resource must be shared with the member.

## Permissions by product

The role editor in Governance groups permissions as a tree, product then resource then action. Checking a product or resource node saves the matching wildcard.

### Organization (`orgs`)

These permissions control the administration of the organization itself.

| Resource | Actions | Covers |
|---|---|---|
| `orgs` | `read`, `update`, `delete`, `manage`, `create` | The organization record. `orgs:create` lets the holder create organizations. |
| `orgs:members` | `create`, `read`, `update`, `delete`, `manage` | Inviting, listing, changing the role of, suspending, and removing members |
| `orgs:groups` | `create`, `read`, `update`, `delete`, `manage` | Groups |
| `orgs:groups:members` | `create`, `read`, `update`, `delete`, `manage` | Group membership |
| `orgs:invites` | `create`, `read`, `update`, `delete`, `manage` | Invitation codes |
| `orgs:subscriptions` | `create`, `read`, `update`, `delete`, `manage` | Subscriptions |
| `orgs:roles` | `create`, `read`, `update`, `delete`, `manage` | Organization roles |
| `orgs:apikeys` | `create`, `read`, `update`, `delete`, `manage` | Organization API keys |
| `orgs:branding` | `read`, `update`, `manage` | Branding |
| `orgs:navigation` | `read`, `update`, `manage` | Menu editor |
| `orgs:join-rules` | `read`, `update`, `manage` | Join rules |
| `orgs:auth` | `read`, `update`, `manage` | SSO providers and anonymous access |
| `orgs:service-accounts` | `create`, `read`, `update`, `delete`, `manage` | Service accounts |
| `orgs:audit` | `view` | The audit log |

`manage` covers every other action on the same resource.

<Note>
Reading roles and changing them are separate. Every system role except **Anonymous** and **Agent Standard** holds `orgs:roles:read`, which Governance needs to load the roles list. Creating, editing, or deleting a role requires `orgs:roles:manage` (or the matching `create`, `update`, `delete`), which only **Owner** holds by default.
</Note>

### LLM Gateway (`llm-gateway`)

| Permission | Covers |
|---|---|
| `llm-gateway:models:read` | Listing models |
| `llm-gateway:models:write` | Managing models |
| `llm-gateway:models:chat-completions` | Chat completions |

| `llm-gateway:models:audio-transcriptions` | Speech to text, used by [chat dictation](/products/ai-securechat/dictation) |

<Warning>
A role that holds `llm-gateway:models:read` or `llm-gateway:models:chat-completions` does not hold `llm-gateway:models:audio-transcriptions`. To let the holders of a custom role dictate, check **Use Audio Transcriptions** under **LLM Gateway** in the role editor. When the platform and the organization have no transcription model, this permission is not checked. See [Dictate a message, for administrators](/products/ai-securechat/dictation#for-administrators).
</Warning>

### Account (`account`)

These permissions control self-service features of a member's own account. Every system role except **Anonymous** and **Agent Standard** holds them; remove one from a role to withhold the feature from its holders.

| Permission | Covers |
|---|---|
| `account:access-tokens:use` | Personal access tokens, and with them the Builder MCP server, the SDK, and the browser extension |
| `account:demo-mode:use` | The demo mode toggle |

### Permissions outside the tree

System roles also use `secure-chat:*` (Chat) and `builder:*` (Builder). The role editor shows permissions it does not list in its tree under **Custom Permissions**, where you can also add app-specific permissions in the `scope:action` format.

## Permissions that wildcards do not cover

Three resources sit apart from the `agents` resource on purpose, so that a wildcard on agents never grants them:

- `agent-factory:traces:read`: someone allowed to change an agent is not thereby allowed to read what its users sent it.
- `agent-factory:sharing:cross-org`: editing agents never implies exposing them outside the organization.
- `<product>:apikeys:*`: an administrator can let a role share agents, knowledge bases, or collections without letting it create keys that bill the organization. These permissions are checked even for the owner of the resource.

`agent-factory:agents:*` grants none of them. A product wildcard such as `agent-factory:*` grants all three for that product, and `*` grants everything.

When you allow a role to create API keys, also allow it to revoke them (`<product>:apikeys:delete`), so that a leaked key can always be revoked.

## Resource scopes

Scopes restrict a role to specific resources. A scope is written `product:resource:id`:

```json
{
  "scopes": [
    "agent-factory:agents:agent_abc123",
    "storage:vector_stores:kb_xyz",
    "llm-gateway:models:gpt-4o"
  ]
}
```

| Scope | Reaches |
|---|---|
| `*` | Every resource of every product |
| `agent-factory:*` | Every resource of the product |
| `agent-factory:agents:*` | Every agent |
| `agent-factory:agents:agent_abc123` | One agent |
| None | No resource through the role. The member reaches only the resources they own or that are shared with them. |

Scopes restrict resources such as agents, knowledge bases, collections, and models. They do not apply to `orgs`, `ai-governance-v2`, `ai-insights-v2`, and `account`, whose permissions are not tied to individual resources. API key resources (`apikeys`) only accept the wildcard scope.

A role, an organization API key, or a service account whose scopes name specific resources of a product, without a wildcard for the resource type, cannot create resources of that product. For example, a key scoped to one knowledge base cannot create a knowledge base.

## System roles

Every organization has these roles. Their slug identifies them in APIs, join rules, and environment variables.

| Role | Slug | Permissions | Scopes |
|---|---|---|---|
| **Owner** | `org:owner` | `*` | `*` |
| **Admin** | `org:admin` | `orgs:members:manage`, `orgs:roles:read`, `orgs:groups:manage`, `orgs:groups:members:manage`, `orgs:branding:manage`, `orgs:navigation:manage`, `orgs:invites:manage`, `orgs:join-rules:manage`, `orgs:apikeys:manage`, `orgs:auth:manage`, `users:manage`, `agent-factory:*`, `builder:*`, `storage:*`, `ai-collection-v3:*`, `ai-insights-v2:*`, `ai-governance-v2:*`, `llm-gateway:*`, `account:*` | `*` |
| **Member** | `org:member` | The member base: `orgs:roles:read`, `users:read`, `orgs:groups:read`, `orgs:members:read`, `agent-factory:agents:read`, `agent-factory:agents:explore`, `secure-chat:*`, `llm-gateway:models:read`, `llm-gateway:models:audio-transcriptions`, `account:access-tokens:use`, `account:demo-mode:use` | None |
| **Agent Maker** | `agent-maker` | The member base, plus `agent-factory:agents:*`, `agent-factory:apikeys:*`, `storage:*` | None |
| **Builder** | `builder` | The member base, plus `agent-factory:agents:*`, `agent-factory:apikeys:*`, `storage:*`, `builder:*` | None |
| **Agent Standard** | `agent-standard` | `llm-gateway:models:chat-completions`, `tools:*` | None |
| **Anonymous** | `org:anonymous` | `agent-factory:agents:read` | None |

- **Owner** cannot be edited. The person who creates an organization becomes its **Owner**.
- **Agent Standard** is meant for [service accounts](/products/ai-governance/identity-access#service-accounts) used by agents.
- **Anonymous** applies to [anonymous sessions](/products/agent-factory/overview#embedding-for-anonymous-visitors) opened on an organization that allows them. The organization can choose another role for anonymous sessions.

### Customizing system roles

Every system role except **Owner** can be edited per organization. Saving a system role stores an override for that organization, which fully replaces the system definition. As a consequence, permissions added to a system role by a later platform release do not reach an organization that has already edited that role: an administrator has to add them to the override.

On self-hosted deployments, the `ORG_ADDITIONAL_SYSTEM_ROLES` environment variable of the API gateway replaces the **Agent Maker**, **Builder**, and **Agent Standard** roles with the list it declares, as a JSON array of objects with `slug`, `name`, `description`, and `permissions`.
