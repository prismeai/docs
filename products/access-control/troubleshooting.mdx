---
title: 'Troubleshoot access denied errors'
description: 'Find why a member, an API key, or an automation is refused access in Prisme.ai, from the exact error message, and who can fix it.'
---

Use this page when someone is refused access they expect, or has access they should not. Each entry starts from the error message or symptom. For how the layers fit together, see [How access control works](/products/access-control/overview).

Before anything else, confirm **which organization the person is active in**. Organization roles apply only in the active organization, and each browser tab keeps its own.

## Organization products

### `Access denied: missing permission '<product>:<resource>:<action>'`

**Cause:** the person's role in the active organization does not hold the permission named in the message. Sharing the resource with them does not compensate: the organization permission is required first.

**Owner:** organization administrator. Changing a role requires the **Owner** role or `orgs:roles:manage`.

**Resolution:**

1. In Governance, select **Members** and note the person's role.
2. Select **Roles**, open that role, and check whether it holds the permission from the message, or a wildcard covering it.
3. Either assign a role that holds it, or add it to the role. See [Create and assign organization roles](/products/access-control/manage-organization-roles).
4. Ask the person to reload the page and repeat the action.

### A shared agent or knowledge base is refused, or opens read-only

**Cause:** one of the two conditions is missing. The person's organization role must hold the action (for example `agent-factory:agents:write` to edit), **and** they must reach the resource through a scope or a share whose role includes the action. A share as **Reader** never allows editing, and a share as **Editor** does not allow editing to a **Member**, whose role has no write permission.

**Owner:** the owner of the resource for the share; the organization administrator for the role.

**Resolution:** open the resource's sharing dialog and check the person's role there, then check their organization role as in the previous entry. When several shares reach the person (direct, group, organization), the most privileged one applies.

### A product does not appear in the menu

**Cause:** the person is active in another organization, or their role holds no permission for the product, such as `builder:*` for Builder or `agent-factory:agents:read` for Agent Factory.

**Owner:** organization administrator.

**Resolution:** ask the person to switch to the right organization. If the product is still missing, assign a role that includes it, such as **Agent Maker** or **Builder**. See [Organization roles and permissions](/products/access-control/organization-roles#system-roles).

### `Reading organization roles is not permitted`

**Cause:** the administrator's role does not hold `orgs:roles:read`, so Governance cannot load the roles list. Inviting members, bulk adding, importing roles, and changing roles are unavailable.

**Owner:** organization **Owner**.

**Resolution:** add `orgs:roles:read` to the role. Every system role that administers members holds it by default; a custom role or an edited system role can miss it.

### `Unauthorized` or `Authentication required`

**Cause:** the request carries no valid session, personal access token, API key, or service account token.

**Owner:** the caller.

**Resolution:** sign in again, or check that the token or key is sent and not expired or revoked. A personal access token also requires `account:access-tokens:use` in the caller's role.

### A platform administrator cannot act on a resource

**Cause:** the resource belongs to another organization than the one the administrator is active in, or the product applies a check of its own.

**Owner:** platform administrator.

**Resolution:** switch to the organization that owns the resource. If the action is still refused, read the product's automation activity to see which check failed, and give the administrator a role holding the permission in that organization.

## Builder workspaces

### A person cannot open a workspace

**Cause:** the workspace is not shared with them. Organization roles, including **Admin** and **Builder**, grant no access to a workspace.

**Owner:** an owner of the workspace.

**Resolution:** in the workspace, select **Settings**, **Sharing**, and add the person with a role. See [Control access to a workspace](/products/access-control/workspace-roles#share-the-workspace).

### `This user could not be found`

**Cause:** the person has never signed in to the platform, or does not belong to your organization. Only members who have signed in at least once can be added to a workspace.

**Owner:** the person, then the workspace owner.

**Resolution:** ask the person to sign in once, then add them again.

### An endpoint returns HTTP 403 with `ForbiddenError`

**Cause:** the automation declares an `authorizations.action`, and no rule lets the caller's role execute automations carrying that key.

**Owner:** an owner of the workspace.

**Resolution:** see [Restrict who can run an automation](/products/access-control/protect-automations#troubleshooting).

### Saving the security rules fails

**Cause:** a rule is invalid, for example `Unknown custom role '<role>' referenced in a rule` or `Forbidden subjectType 'secrets' found in security rules`. The previous rules stay in effect.

**Owner:** an owner of the workspace.

**Resolution:** look up the message in [Workspace security rules reference: validation errors](/products/access-control/workspace-rules-reference#validation-errors), fix the YAML, and save again.

### A user has more access than expected

**Cause:** usually one of these:

- a rule without `role`, which applies to everyone, anonymous visitors included;
- an `auth` block that assigns a role to every user of an identity provider;
- an automation with an endpoint or event trigger and no `authorizations.action`, which anyone can execute;
- a grant written below a denial, which overrides it.

**Owner:** an owner of the workspace.

**Resolution:** review the rules in that order. Add a `role` to broad rules, narrow `auth` blocks with `conditions`, and add `authorizations.action` to automations. See [Precedence](/products/access-control/workspace-rules-reference#precedence).

### An attached file is ignored, or a user cannot read back a file they uploaded

**Cause:** the security rules of the **Storage** workspace are missing the rule that lets a user read their own files. Without it, a file uploaded by someone who is not an owner is ignored. Organization owners are never affected, which makes the symptom look specific to some users.

**Owner:** platform administrator.

**Resolution:**

1. In Builder, open the **Storage** workspace, then **Settings**, **Security**.
2. If this rule is absent, add it and select **Save Rules**:

   ```yaml
   - action: read
     subject: files
     conditions:
       createdBy: '{{user.id}}'
     reason: Anyone can read its own files
   ```

3. Attach a file in a conversation as a user who is not an owner, and confirm the agent reads it.

The rule ships with the Storage workspace and is applied on install and upgrade, so a workspace missing it has drifted from the release.

### `secret.get` returns `{ error: "not_found" }` in a scheduled run

**Cause:** the run has no user, so it reaches a workspace secret only under a role it takes on with `assumeRole`, and that role must hold `read` on a `name` family covering the secret.

**Owner:** an owner of the workspace.

**Resolution:** see [Let members deposit their own credentials](/products/access-control/secure-secrets).
