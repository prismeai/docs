---
title: "Secrets Module"
description: "Securely store and retrieve sensitive values at runtime"
---

The **secrets** module lets automations securely store and retrieve sensitive values (API keys, tokens, credentials) at runtime. Values are encrypted at rest and never exposed as plaintext in automation outputs or logs.

This page documents two things:

- The **runtime API** (`secrets.set`, `secrets.get`, `secrets.delete`) for automations.
- The **Settings → Secrets** form in the Builder UI, which is where workspace-level secrets are typically configured before any automation runs.

## Settings → Secrets form

Open **Settings → Secrets** in the Builder. The form has two sections.

### Schema-defined secrets

The top section is generated from the workspace's secret **schema**, declared in `index.yml`:

```yaml
secrets:
  schema:
    openaiApiKey:
      type: string
      description: API key for the OpenAI integration
    notionToken:
      type: string
      description: Notion integration token
```

Every property of the schema is rendered as an input field. These are the "main" secrets of the workspace: they have known names, automations reference them as `{{secret.<name>}}`, and someone (usually the workspace author) committed the schema to source control.

Typing a value and clicking **Save Secrets** posts the new values to `POST /workspaces/{id}/secrets`. Values are stored encrypted; the form never reads back plaintext (an empty field means "leave the existing value untouched", not "clear the value").

### Additional Secrets form

The "Additional Secrets" section underneath is for secrets that **are not declared in the schema**. The label "Additional" is intentional: these are extras beyond the schema-defined set.

| Field | Notes |
|---|---|
| **New key** | The variable name. Will be readable from automations as `{{secret.<key>}}`. |
| **New value** | Hidden by default (password input). The eye icon toggles visibility. |
| **+** button | Adds the pair to the in-memory list. The secret is not persisted until you press Save Secrets. |
| Delete (per row) | Removes the row from the in-memory list. |
| **Save Secrets** | Persists the schema values *and* the additional secrets in one call. |

Use the Additional form when:
- You are prototyping and have not yet committed a schema.
- You need an environment-specific override (e.g. a per-deploy webhook URL) that should not appear in source.
- You want a one-off value usable from a single automation without touching `index.yml`.

Once a name stabilizes, promote it to the schema so the next workspace clone has the documentation built in.

<Warning>
The "Additional Secrets" form persists plaintext values to the workspace's encrypted secret store. It is **not** a temporary scratchpad; entries survive reloads and pulls (unless overwritten by a pulled `index.yml`).
</Warning>

## Runtime API

For automations that need to **create** or **rotate** secrets at runtime (OAuth tokens, refresh tokens, per-user credentials), the `secrets` module exposes `set`, `get`, and `delete`.

### How it works

1. `secrets.set` and `secrets.get` return an opaque **secret reference** (a `$secret:...` string), not the actual value.
2. When this reference is used inside a `fetch` instruction (in the URL, headers, body, query, or auth fields), the platform automatically resolves it to the real value just before the HTTP call.
3. The resolved value is redacted from all logs and events.

Secret references are short-lived (a few minutes). Always call `secrets.get` right before using the reference; do not store it for later reuse.

### Scopes

| Scope | Description |
|---|---|
| `workspace` | Belongs to the workspace, not to whoever triggers the automation. Readable by workspace editors, or by any per-name access rule (`secure_secrets`) that matches the caller. |
| `user` | Belongs to one user. Only ever reachable by a run that carries **that** user's context. There is no way to read a `user` secret from a run without a user — see below. |

## Access model — who can read a secret

Whether `secrets.get` (and `set`/`delete`) succeeds depends on **three** independent things:

1. **The scope** requested — `user` or `workspace`.
2. **Whether the run carries an authenticated user** — i.e. `ctx.source.userId` is set. Interactive runs (a user clicking in the UI, an API call with a user token, a page render) carry a user. Cron/schedule triggers, anonymous webhooks, `emit`-triggered runs, and in-process cross-workspace calls do **not**.
3. **Whether a cross-workspace delegation is declared** — only relevant to `workspace` secrets reached from a run with no user (see [Delegated secrets](#delegated-secrets-cross-workspace)).

### Access matrix

| Scope | Run | Result |
|---|---|---|
| `user` | Authenticated (user present) | ✅ Reads **that user's own** secret. |
| `user` | No user (cron, schedule, anonymous webhook, cross-workspace call) | ❌ Returns `{ error: "user_required" }`. **No delegation, no self-delegation, no configuration changes this** — a `user` secret is unreachable without its user. |
| `workspace` | Authenticated, with the right role or a matching `secure_secrets` rule | ✅ Normal RBAC read. |
| `workspace` | No user, **no** cross-workspace hop (e.g. a plain cron on the workspace itself) | ❌ Returns `{ error: "not_found" }`. The secret exists but is invisible — a user-less run holds no role. |
| `workspace` | No user, cross-workspace hop, caller **and** name declared as delegated | ✅ Delegated read (runs "as the workspace itself"). |
| `workspace` | No user, cross-workspace hop, but **not** declared | ❌ `{ error: "not_found" }`, with a message naming the two declarations to add. |
| `workspace` | Arrives over HTTP (e.g. an anonymous webhook call) | ❌ Delegation is refused for any HTTP-borne run, even with no user. |

`set` and `delete` follow the **same** rules as `get`, so a delegated run that can read a rotating token can also store its replacement and delete a dead one — reading without writing would be a half-feature (the run would burn the token and fail on the next pass).

### Delegated secrets (cross-workspace)

By default a `workspace` secret is invisible to any run without a user: reads resolve RBAC against the caller, and a user-less trigger holds no role, so it sees nothing. **Delegation** is the one way to open a specific `workspace` secret to a specific *other* workspace, for runs that carry no user.

It is gated by two facts, **neither of which the caller can forge**:

- The **name** is on the workspace's delegated list.
- The **calling workspace** (`sourceWorkspaceId`, stamped by the runtime itself on every outgoing call — a DSUL author cannot override it) is on the workspace's delegated caller list.

Both facts live in two reserved workspace secrets, written by the platform:

| Reserved key | Holds |
|---|---|
| `prismeai_delegated_secrets` | Comma-separated secret-name patterns a caller may read (a literal name, or a single trailing `*`). |
| `prismeai_delegated_secret_callers` | Comma-separated workspace **ids** allowed to read them. |

<Warning>
These two keys use the reserved `prismeai_` prefix, so a **workspace owner can neither write nor even see them** — only a platform SuperAdmin can. The party being authorised must not be able to author its own authorisation. **You never write these keys by hand.** Instead you declare an ordinary write rule in your workspace's `security.yml`, and the platform *derives* the delegation from it at import / publish.
</Warning>

#### Declaring it: a `secure_secrets` write rule

A connector opens delegation by granting its members the right to **write** their own token — a `secure_secrets` rule in the workspace's `security.yml`. Example (Figma connector):

```yaml
# security.yml
authorizations:
  rules:
    - action:
        - create
        - update
      subject: secure_secrets
      conditions:
        name:
          $regex: '^figRefresh_${user.id}$'
      reason: |
        A member connecting their own account deposits the refresh token that a
        scheduled sync will later replay.
```

The platform validates this rule strictly and **forces** two conditions you do not write — `workspaceId` (the current workspace) and `scope: workspace`. The rule must obey:

| Requirement | Why |
|---|---|
| `subject: secure_secrets` | Targets the encrypted runtime store (`secrets.set` / `get`). |
| `action`: only `create` / `update` | **Read, delete and manage are refused.** A workspace may grant *depositing* a credential, never reading a value back — the runtime consumes it through a `$secret:` ref, it is never returned to a caller. |
| `name` **confines to the acting user** | Otherwise one rule would let any member overwrite another's credential. Use `{$regex: '^<head>${user.id}<suffix>$'}` — anchored at both ends, `${user.id}` present exactly once, only literal characters around it, plus **at most one** fixed-width character class (e.g. `[a-f0-9]{16}`) for connectors holding several credentials per person. |
| not `inverted` | An `inverted: true` rule is a DENY — a delegation is never derived from a prohibition. |

<Warning>
Use the **`$regex` form**, not a plain string. A plain-string `name` is only *substring*-checked for `${user.id}` (its exact-match nature is what confines it) — and, crucially, **only a `$regex` rule produces a delegation at all**: the derivation reads `conditions.name.$regex`, so a plain-string rule grants the write-only deposit but yields **no** cross-workspace delegation.
</Warning>

A connector holding several credentials per remote account carries a discriminator with the fixed-width class (SharePoint):

```yaml
    - action: [create, update]
      subject: secure_secrets
      conditions:
        name:
          $regex: '^spnRefresh_[a-f0-9]{16}_${user.id}$'
```

The width must be fixed (`{16}`, never `+` / `*` / `{n,m}`) and the class must sit **before** `${user.id}`: a variable-width segment next to the id would let two different `(account, user)` pairs spell the same name.

#### What the platform derives

At each import / publish the platform reads every qualifying `secure_secrets` rule and derives one delegated **name pattern** per rule — the literal head of the regex, up to the first metacharacter, plus a trailing `*`:

| `security.yml` `name.$regex` | Derived pattern | Note |
|---|---|---|
| `^figRefresh_${user.id}$` | `figRefresh_*` | literal head, ends on `_` |
| `^spnRefresh_[a-f0-9]{16}_${user.id}$` | `spnRefresh_*` | head taken up to the first `[` |
| `^a${user.id}$` | *(nothing)* | head too short — `a*` would match `apiKey_stripe` |
| `^[a-z]+_${user.id}$` | *(nothing)* | no literal head — a bare `*` would delegate every secret |
| `^prismeai_…${user.id}$` | *(nothing)* | reserved prefix, refused on both sides |

For a head to be accepted it must be **at least 6 characters, end on `_` or `-`**, carry no comma or whitespace, and not start with `prismeai_`. Real connector prefixes (`figRefresh_`, `spnRefresh_`, `gwsRefresh_`) clear this easily. The resulting `figRefresh_*` deliberately matches **every** user's `figRefresh_<id>` — that breadth is the point: a scheduled sync must be able to reach any connected user's token.

#### Who may read them — the callers

The delegated caller list is **platform configuration**, not per-workspace DSUL: it comes from the `DELEGATED_SECRET_CALLERS` environment variable (default `knowledge-sync`), a list of workspace **slugs** resolved to ids at write time (a slug is mutable and reusable, so only the resolved id is what the runtime trusts). A caller slug absent on the instance is skipped, not an error.

#### Revoking

Delegation is **derived state**: remove the `secure_secrets` rule from `security.yml`, and the next import derives nothing, so the platform deletes both reserved keys. A workspace that delegates nothing — the vast majority — never has them written at all.

---

A run reaching a secret this way must **also** carry no user and no HTTP origin. The only runs that qualify are the scheduler and in-process cross-workspace calls; a forged identity would necessarily arrive over HTTP, which is refused.

<Note>
Per-user connector tokens (OAuth refresh tokens, etc.) are **not** stored as `user` secrets. They are `workspace` secrets whose **name embeds the user id** (`figRefresh_<id>`) and are guarded by the `secure_secrets` rule above. That is why delegation — which only ever touches `workspace` secrets — is what lets a scheduled sync replay a given user's token.
</Note>

### Self-delegation

A workspace **can** delegate to itself, but two things are required — declaring itself is not enough on its own:

1. The declarations must name the workspace as its **own** caller (still SuperAdmin-written / derived from `secure_secrets`).
2. The run must actually make a **cross-workspace hop to itself** — the self-webhook pattern (`fetch` to one of the workspace's own automations), which stamps `sourceWorkspaceId` to the workspace's own id.

A **plain schedule with no hop** carries no `sourceWorkspaceId` at all, so it can never reach a `workspace` secret this way, however it is declared. A relayed call (A → B → the workspace) is also refused: the grant is non-transitive, so only a call the workspace initiated for itself — where both ids are the same workspace — is tolerated.

### Functions

### set: Store or update a secret

```yaml
- run:
    module: secrets
    function: set
    parameters:
      name: myApiKey
      value: "sk-live-abc123"
      scope: workspace
    output: secretRef
```

| Parameter | Type | Required | Description |
|---|---|---|---|
| `name` | string | yes | Unique name for the secret (within its scope) |
| `value` | any | yes | The value to encrypt and store |
| `scope` | `user` \| `workspace` | yes | Storage scope |
| `ttl` | number | no | Time-to-live in seconds. The secret expires and becomes unreadable after this duration. |

Returns a `$secret:...` reference string. If a secret with the same name and scope already exists, it is updated.

### get: Retrieve a secret reference

```yaml
- run:
    module: secrets
    function: get
    parameters:
      name: myApiKey
      scope: workspace
    output: secretRef
```

| Parameter | Type | Required | Description |
|---|---|---|---|
| `name` | string | yes | Name of the secret to retrieve |
| `scope` | `user` \| `workspace` | yes | Storage scope |

Returns a `$secret:...` reference string, or `{ error: "not_found" }` if the secret does not exist (or has expired).

### delete: Remove a secret

```yaml
- run:
    module: secrets
    function: delete
    parameters:
      name: myApiKey
      scope: workspace
    output: result
```

| Parameter | Type | Required | Description |
|---|---|---|---|
| `name` | string | yes | Name of the secret to delete |
| `scope` | `user` \| `workspace` | yes | Storage scope |

Returns `{ deleted: true }` on success, or `{ error: "not_found" }`.

### Using secret references in fetch

Pass the reference returned by `set` or `get` wherever a sensitive value is needed in a `fetch` instruction. The platform resolves it transparently:

```yaml
do:
  # 1. Retrieve the secret reference
  - run:
      module: secrets
      function: get
      parameters:
        name: myApiKey
        scope: workspace
      output: secretRef

  # 2. Use it in a fetch: the platform injects the real value at execution time
  - fetch:
      url: https://api.example.com/data
      method: GET
      headers:
        Authorization: "Bearer {{secretRef}}"
      output: apiResponse
```

Resolution is supported in these `fetch` fields: `url`, `headers`, `body`, `query`, and `auth` (including `auth.awsv4`).

<Warning>
Secret references expire after a few minutes. Always retrieve the reference (`secrets.get`) in the same automation run where you use it.
</Warning>

### Complete example: storing and using an OAuth token

```yaml
slug: call-with-oauth
name: Call API with OAuth token
do:
  # Authenticate and get a token
  - fetch:
      url: https://auth.example.com/oauth/token
      method: POST
      body:
        grant_type: client_credentials
        client_id: "{{config.clientId}}"
        client_secret: "{{secret.clientSecret}}"
      output: authResponse

  # Store the token as a workspace secret with a 1-hour TTL
  - run:
      module: secrets
      function: set
      parameters:
        name: oauthToken
        value: "{{authResponse.access_token}}"
        scope: workspace
        ttl: 3600
      output: tokenRef

  # Use the token in subsequent API calls
  - fetch:
      url: https://api.example.com/resources
      method: GET
      headers:
        Authorization: "Bearer {{tokenRef}}"
      output: resources
```

### Error handling

All three functions return an error object instead of throwing when the error is actionable:

| Error | Returned by | Meaning |
|---|---|---|
| `{ error: "not_found" }` | `get`, `delete` | No secret with that name/scope exists (or it has expired), **or** it exists but the run cannot reach it — a user-less run on a `workspace` secret with no matching delegation. When the run looks like an undeclared delegation, the accompanying `message` names the two `prismeai_delegated_*` keys to add (a SuperAdmin action) and states this is *not* an expired user token. |
| `{ error: "user_required" }` | `set`, `get`, `delete` | `scope: user` was used but there is no user context (e.g. cron trigger). No delegation can substitute for the missing user. |

Use `onError` or a `conditions` block to handle these:

```yaml
- run:
    module: secrets
    function: get
    parameters:
      name: myApiKey
      scope: workspace
    onError: continue
    output: result
- conditions:
    '{{result.error}}':
      - emit:
          event: secret-missing
          payload:
            message: "Secret myApiKey not found"
```
