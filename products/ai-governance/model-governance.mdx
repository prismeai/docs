AI model access is one of the cross-cutting concerns the platform handles once, and Model Governance is where you shape it: control which AI models are available to your organization, set usage policies, configure routing strategies, and monitor consumption. The same controls also underpin the platform's LLM resilience story, letting you downgrade or fail over across providers when a model or cloud is unavailable. Access these features from **Agents Controls** in the sidebar.

## Models Configuration

### Allowed Models

By default, organizations can use all models enabled by the platform administrator. You can restrict this to a specific list.

1. Go to **Agents Controls > Models**
2. Toggle **Restrict Models**
3. Select which models to allow
4. Click **Save**

### Default Models

Set the default models used when agents don't specify one:

| Setting | Description |
|---------|-------------|
| **Default Completion Model** | Used for chat and text generation |
| **Default Embedding Model** | Used for vector embeddings |

### Quota Policy

Configure what happens when quota limits are reached:

| Policy | Behavior |
|--------|----------|
| **Hard Block** | Requests fail with quota exceeded error |
| **Soft Downgrade** | Fall back to a cheaper model |

### Downgrade Mapping

When using soft downgrade, configure which models to substitute:

```
claude-3-opus → claude-3-sonnet
gpt-4 → gpt-3.5-turbo
```

This ensures continuity when expensive models hit quota limits.

### Failover Mapping

Configure automatic failover when a model is unavailable:

```
claude-3-sonnet → claude-3-haiku
gpt-4 → gpt-4-turbo
```

Failover activates when the primary model returns errors, not for quota limits.

**Failover behavior:**
- **5xx errors**: switches to the failover model from the mapping, or falls back to the default completion model (with linear backoff 1s, 2s, 3s...)
- **429 rate limits**: retries the same model after a 5s backoff
- **Other 4xx errors**: returned immediately without retry
- Up to 3 attempts (configurable, hard cap of 10)
- Failover models are validated against governance access controls before use
- Failover only applies to **non-streaming** requests

## Model Routing

The LLM Gateway supports intelligent model routing: selecting the best model for a request based on configurable strategies. Use `model: "auto"` in API calls to trigger routing.

### Routing Strategies

| Strategy | Description |
|----------|-------------|
| **Disabled** | No automatic routing; use specified model |
| **Rules** | Rule-based routing: first matching rule wins |
| **LLM Classifier** | Use a cheap LLM to classify the request and map category to model |
| **Capabilities** | Query model catalog for enabled models matching required tags |
| **Cost Optimized** | Same as capabilities but iterates cost tiers (`low` → `medium` → `high`) to pick cheapest match |
| **Hybrid** | Try rules first, fall back to LLM classifier if no rule matches |

### Rule-Based Routing

Define conditions to route requests to different models:

```yaml
routing:
  strategy: rules
  rules:
    - condition: messages_count
      operator: "<"
      threshold: 5
      model: claude-3-haiku
    - condition: messages_count
      operator: ">="
      threshold: 5
      model: claude-3-sonnet
```

The only supported condition type is `messages_count` with operators `<`, `>`, `<=`, `>=`, `=`. If the selected model is blocked by governance, routing falls back to the default.

<Note>
For load testing, the gateway also exposes built-in fake models that return instant responses without calling a provider. They bypass the routing, quota and failover logic described above — see [Mock Models](./mock-models).
</Note>

### Using `auto`

Once a routing strategy is configured for your organization, send `model: "auto"` in the request body and the LLM Gateway selects the model for you. This is the supported way to consume routing today: through the **REST API** and through **MCP tools** that call the gateway.

```bash
curl https://{host}/v2/workspaces/slug:llm-gateway/webhooks/v1/chat/completions \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto",
    "messages": [{ "role": "user", "content": "Summarize this contract clause..." }]
  }'
```

The gateway resolves `auto` against the strategy defined in **Agents Controls**, enforces the governance allowlists, and returns the completion from the model it selected. If routing cannot resolve a model, it falls back to the organization's default completion model. The response reports the model that actually served the request, so you can confirm which one was chosen.

For an LLM Classifier strategy, the routing configuration maps a classified category to a target model:

```yaml
routing:
  strategy: llm_classifier
  classifier_model: claude-3-haiku
  categories: [coding, legal, general]
  model_map:
    coding: claude-3-5-sonnet
    legal: claude-3-opus
    general: claude-3-haiku
```

<Note>
`auto` is currently an **API and MCP capability**. Selecting `auto` from the chat model picker, or from an agent's model dropdown in the interface, is being rolled out progressively and is not yet a supported end user path. Do not add `auto` manually to the organization's **Models** list to expose it in chat: a streamed chat request routed this way may stay in a loading state. Until interface support ships, keep a concrete model (for example Haiku 4.5) selected in chat, and use `auto` through the API or MCP.
</Note>

## Model pricing

Every cost figure the platform shows you — Total Cost and Cost by Model in [Observability → LLM](/products/ai-governance/observability#llm-tab), the Cost ($) series in [Insights → Consumption](/products/ai-insights/consumption#llm-requests), the `llm.cost.monthly` quota metric above — is computed from prices **you** enter in the model catalog. The platform ships no price list and reads no provider invoice.

### How a cost is calculated

On every call, the LLM Gateway multiplies the tokens actually consumed by the model's catalog prices:

```
cost = prompt_tokens     × input_per_1m_tokens  / 1 000 000
     + completion_tokens × output_per_1m_tokens / 1 000 000
```

The result is rounded to 6 decimals and emitted on the `analytics.llm.completion` event, which is what every dashboard aggregates.

There is **no multiplier and no margin** anywhere in the chain. A displayed cost is tokens × your catalog price, and nothing else. If a dashboard total is off by a factor, the prices in the catalog are off by that same factor — that is the only place the discrepancy can come from.

### Prices are environment data, not a platform default

Prices are configuration, like credentials or quotas: each environment carries its own, and a platform administrator enters them. The providers' public list prices are a reasonable starting point. If you buy through a negotiated contract, a reseller, or committed-use discounts, enter **your contractual prices** instead — otherwise the dashboards report list price while you are billed something else.

<Warning>
**A model with no price costs 0, silently.** The gateway computes a cost only when **both** the input and the output price are set. Otherwise the cost is `0` — no error, no warning, no badge. The model keeps working, and it appears free in every dashboard, in the per-user chargeback table, and against the `llm.cost.monthly` quota.

Scale mistakes are just as quiet. The fields are **per 1M tokens**: entering a per-1K price there understates every cost by a factor of 1000, and nothing flags it.

Embedding models use the input price only; leaving their output price empty is normal and does not zero the cost.
</Warning>

### Costs are never recalculated

A cost is frozen at the moment of the call and stored on the event. Correcting a price changes **future calls only** — history keeps whatever it was computed with. There is no backfill, so a period priced wrongly stays wrong in the dashboards. Fix the price as soon as you notice it, and treat the affected window as known-bad rather than waiting for it to correct itself.

### Currency

Dashboards label costs `$`. The platform performs no conversion: whatever number you enter is the number displayed. If your contract is in euros, entering euro prices makes every dashboard read euros under a `$` sign — pick one currency per environment and stay with it.

### Setting prices in Govern

Reserved to platform superadmins.

1. Go to **Govern → Models** and open the **Models** tab.
2. Click the model to open it.
3. In the **Pricing** block (**Tarification** in the French interface), fill **Input (per 1M tokens)** and **Output (per 1M tokens)**.
4. Save.

Both fields take the price of **one million** tokens. For a model listed at $2.50 per million input tokens and $10.00 per million output tokens, enter `2.5` and `10`.

### Setting prices by API

```http
PATCH {api}/v2/workspaces/slug:llm-gateway/webhooks/v1/models/{model_id}
```

```json
{
  "pricing": {
    "input_per_1m_tokens": 2.5,
    "output_per_1m_tokens": 10
  }
}
```

The model cache is flushed automatically, so the new price applies to the next call.

<Note>
The PATCH **replaces the whole `pricing` object** — it does not merge field by field. Always send both keys, even when changing one: sending only `output_per_1m_tokens` drops the input price, and the model silently falls back to a cost of 0.
</Note>

<Warning>
**Bulk import replaces the entire catalog.** Importing a JSON catalog from the **⋮** menu (and `PUT /v1/models`) is a wholesale replacement, not a merge: **every model absent from the file is deleted**, and the prices carried by the file overwrite the ones in place.

Import files therefore carry the *source* environment's prices. After importing from another environment — staging into production, or one tenant into another — re-check prices model by model before trusting any dashboard.
</Warning>

### `cost_tier` is a label, not a price

Do not confuse pricing with the **Cost tier** field (`low` / `medium` / `high`) in the model's Metrics block. The tier drives the [Cost Optimized routing strategy](#routing-strategies) and the soft-downgrade policy, and it is what end users see in the model picker. It never enters the cost calculation.

The two are independent in the data but must stay consistent in practice: a model priced at the top of your catalog and tagged `low` will be picked first by cost-optimized routing and read as cheap by everyone choosing a model. Set the tier from the prices, and revisit it whenever prices change. See [Available Models → Cost tiers](/products/ai-governance/available-models#cost-tiers).

### Checklist after adding or importing models

- Every enabled `completion` model has **both** prices set.
- Prices are per **1M** tokens, in a single currency across the environment.
- Every embedding model has its input price set.
- Each `cost_tier` is consistent with the model's actual prices.
- Run one test call per model, then confirm a **non-zero** cost for it in Observability → LLM. A model sitting at 0 after a real call has no price.

## Reference catalogue (recommended metrics)

The LLM Gateway ships a **reference catalogue**: Prisme.ai's recommended values for the Metrics block of each known model. It covers completion and embedding models, and is maintained with the platform: it changes only when the LLM Gateway workspace is updated.

For each model, an entry carries:

| Field | Content |
|---|---|
| `key` | Canonical model id, e.g. `claude-sonnet-4-6` |
| `aliases` | Known deployment ids for the same model, e.g. `vertex-claude-sonnet-4-6` |
| `suggested` | Recommended `eco_score`, `cost_tier`, `energy_per_token`, `pue_profile` (completion models only) |
| `reference_pricing` | Indicative provider list price, in USD. **Never written** to your models: see [Prices are environment data](#prices-are-environment-data-not-a-platform-default) |
| `spec` | Type, context window, capabilities, and embedding dimensions |

The response also states its `methodology_version`, `source` and `verified_at` date. `energy_per_token` follows the method described in [Carbon Footprint](/products/ai-governance/carbon-footprint); `eco_score` and `cost_tier` are tiers derived from energy and from the reference price.

```http
GET {api}/v2/workspaces/slug:llm-gateway/webhooks/v1/models/catalog
```

Reading the catalogue changes nothing in your environment.

### Using the catalogue in Govern

Reserved to platform superadmins, in **Govern → Models**.

**In the model form.** Open a model, or add one:

- The **Catalogue model** select (**Modèle catalogue** in the French interface), at the top of the form, links the model to a catalogue entry. When it is empty, it is pre-selected by matching the model id, and re-matched as you type the id, until you pick an entry yourself. Choose **None** to unlink the model.
- Next to each metric (Eco score, Cost tier, Energy/Token, PUE profile), the training date and the context window, a **Prisme.ai suggestion** badge shows the recommended value when yours differs. **Apply** copies it into the field. A suggestion bar does the same for capabilities, listing only the flags that differ.
- On a new model, the fields you have not touched are pre-filled from the linked entry.
- An info icon on the **Pricing** heading shows the entry's reference price. It is indicative only and is never copied into your prices.

Nothing is saved until you save the model.

**From the ⋮ menu, Update from catalogue** (**Mettre à jour depuis le catalogue**) opens a window with two sections:

- **To update** runs the [sync](#aligning-an-environment-with-the-catalogue) as a dry run and lists, per model, each metric that differs, as old value → recommended value, along with the models about to be linked to an entry. **Apply** on a row applies that model only; **Apply all** applies every row.
- **Add models** lists the [model ids declared but not registered](#models-declared-but-not-registered). Pick the catalogue entry for each (one is pre-selected by matching) and add the model in one click: it is created with the entry's spec and recommended metrics. Set its prices afterwards — they are not filled in (see [Model pricing](#model-pricing)).

<Warning>
**Apply all overwrites the four metrics on every listed model**, including values you set on purpose. Check the old → new table first, and use the per-row **Apply** when only some models should change.
</Warning>

### Linking a model to the catalogue: `catalog_id`

Each model can carry a `catalog_id`, the `key` of its catalogue entry. Model ids differ from one environment to the next (`az-gpt-4o`, `vertex-claude-sonnet-4-6`…), so the link is resolved **once by name** and then stored. From then on, everything joins on `catalog_id` without re-matching names.

In Govern, it is the **Catalogue model** select of the model form. By API, set it when creating or editing a model (`POST /v1/models`, `PATCH /v1/models/{model_id}`): a string of at most 128 characters. Send `null` to unlink the model.

### Aligning an environment with the catalogue

`POST /v1/models/catalog/sync` brings the Metrics block of the environment's models in line with the catalogue. It is what the **To update** section of **Update from catalogue** runs. It works in two steps per model:

1. **Back-fill `catalog_id`** when the model has none. The model id is matched against catalogue keys and aliases, ignoring case and separators (`-`, `.`, `_`, `:`, spaces), then again after stripping common deployment prefixes (`az-`, `azure-`, `vertex-`, `gcp-`, `bedrock-`, `aws-`, `openai-`, `oai-`, `ovh-`). An exact match always wins over a looser one.
2. **Apply the recommended metrics** of the entry found by `catalog_id`. Only the selected `metrics` fields are updated; pricing and every other field are left as they are. Embedding entries carry no recommended metrics, so embedding models only get their `catalog_id`.

```http
POST {api}/v2/workspaces/slug:llm-gateway/webhooks/v1/models/catalog/sync
```

```json
{
  "dry_run": true,
  "model_ids": ["az-gpt-4o", "vertex-claude-sonnet-4-6"],
  "fields": ["eco_score", "energy_per_token"]
}
```

| Body field | Default | Effect |
|---|---|---|
| `dry_run` | `true` | Report what would change, write nothing. Send `false` to apply. |
| `model_ids` | all models | Restrict the sync to these models. |
| `fields` | the four metrics | Restrict which `metrics` fields are updated. |

The response lists what was (or would be) done:

```json
{
  "dry_run": true,
  "summary": { "total": 2, "backfilled": 1, "patched": 1, "unchanged": 1, "unmatched": 0 },
  "backfilled": [
    { "model_id": "az-gpt-4o", "catalog_id": "gpt-4o", "match": "alias" }
  ],
  "patched": [
    {
      "model_id": "vertex-claude-sonnet-4-6",
      "catalog_id": "claude-sonnet-4-6",
      "fields": ["energy_per_token"],
      "before": { "energy_per_token": 0.00001 },
      "after": { "energy_per_token": 0.000016 }
    }
  ],
  "unmatched": []
}
```

`match` tells how the back-fill resolved the id: `exact`, `alias`, `strong` (after prefix stripping) or `strong_alias`. A model listed in `unmatched` has no catalogue entry; set its metrics by hand.

<Warning>
**Run a dry run first, and read it.** With `"dry_run": false`, the sync overwrites the selected metrics on every matched model, including values you set on purpose. Use `fields` and `model_ids` to keep it to what you mean to change. The model cache is flushed for each updated model, so the new values apply to the next call.
</Warning>

### Models declared but not registered

`GET /v1/models/unregistered` lists the model ids declared in the gateway's provider configuration that are not yet registered as models in your environment, each with its provider (`openai`, `azure`, `openailike`, `anthropic`, `vertex`, `bedrock`). It feeds the **Add models** section of **Update from catalogue**. Only the ids are returned, never the provider credentials.

The sync and the unregistered list require write access to models; reading the reference catalogue requires read access.

## Model Lifecycle: Hidden vs Disabled

A platform administrator can manage a model's availability at three levels of severity. Each level has a different effect on what the LLM Gateway accepts, what surfaces in UI pickers, and whether the model is auto-pruned from organization allowlists.  
"LLM Gateway" designates the product responsible for llm calls execution and authorization, whether through API calls or chat front-end.  

### State matrix

| Flag | Set by | LLM Gateway | Org "Allowed models" panel | Agent-level pickers | Auto-pruned from `org.allowed_models` |
|------|--------|---------|----------------------------|---------------------|---------------------------------------|
| **Visible & enabled** (default) | n/a | ✅ Accepted | ✅ Shown | ✅ Shown | n/a |
| **Hidden** (`display.hidden: true`) | Platform admin | ✅ Still accepted via the org allowlist entry | ✅ Still shown; admin can decide to keep or remove it | ❌ Filtered out | ❌ Stays |
| **Disabled** (`enabled: false`) | Platform admin | ❌ Rejected (`MODEL_NOT_ALLOWED`) | ❌ Filtered out | ❌ Filtered out | ✅ Removed |
| **Deleted** (removed from catalog) | Platform admin | ❌ Rejected | ❌ Gone | ❌ Gone | ✅ Removed |

### Why hidden is not the same as disabled

The `hidden` flag exists specifically to **deprecate a model from UI selection without breaking direct API usage or existing agents that already point to it**. Saving the organization's `Allowed models` panel without a hidden model would effectively forbid it, so hidden models are left in the list, only filtered out of agent-level dropdowns. An agent that had selected a model before it became hidden keeps using it, and API consumers calling `/chat/completions` with that `model_id` keep working.

If a model truly must be retired, use **Disabled** (or delete it from the catalog) to prevent any agent from using it.  

### Warnings surfaced in the Agent Creator

When you open an agent whose currently-configured model is no longer fully usable, the model picker surfaces one of two messages:

- 🔴 **Error (model unusable)**: the model has been deleted, disabled at platform level, or removed from the org / agent allowlist. The agent will fail to process any request until you select another model.
- 🟡 **Warning (model hidden)**: the model has only been hidden at platform level. The agent still works for now, but you're no longer expected to pick this model; please switch to another one.

The current model is always shown even when filtered out so you can always see what is configured, but does not appear in models picker to force you choose another one.

## Model Access Control

When a request arrives, the LLM Gateway validates the requested model against three sequential allowlists:

1. **Org allowlist**: Is the model in the organization's allowed models? (if the list exists and has entries)
2. **Agent allowlist**: Is the model in the agent's allowed models? (passed by agent-factory)
3. **API key scopes**: Is the model allowed by the API key's scopes?

Each check is skipped if the corresponding list is empty or absent. If any check fails, the behavior depends on the quota policy:
- **Soft Downgrade**: silently swaps to the default completion model
- **Hard Block** (default): returns a `403` error with `MODEL_NOT_ALLOWED`

## Carbon Footprint Tracking

Every LLM call includes an estimated environmental impact in the response:

```json
{
  "usage": {
    "carbon": {
      "energy": { "value": 0.000012, "unit": "kWh" },
      "gwp": { "value": 0.0000057, "unit": "kgCO2eq" }
    }
  }
}
```

The calculation considers GPU energy per token, server overhead, datacenter PUE (Power Usage Effectiveness), and regional emission factors. Results include uncertainty margins (+/- 20%).

| PUE Profile | Multiplier |
|-------------|-----------|
| Efficient | 1.1 |
| Average (default) | 1.58 |
| Inefficient | 2.0 |

Carbon data is included in analytics events and powers the observability dashboards.

## Supported Providers

The LLM Gateway abstracts multiple providers behind a unified API:

| Provider | Models | Notes |
|----------|--------|-------|
| OpenAI | GPT-5, GPT-4o, o3-mini, embeddings, DALL-E 3 | Direct API |
| Azure OpenAI | GPT-5, GPT-4o, embeddings, Claude (via Azure AI) | Multiple resource configs |
| OpenAI-compatible | Gemini, DeepSeek, Mistral, Cerebras, OVH, Linagora | Via `openailike` provider type |
| Anthropic | Claude Sonnet 4.5, Claude 3.7 Sonnet, Claude 3.5 Sonnet | Native API; optional custom `endpoint` + selectable `auth_scheme` for self-hosted / compatible / non-standard Azure hosts |
| Google Vertex AI | Gemini 2.5/3, Imagen 4.0, text-embedding-005 | Via model aliases + service account. Tool calling is supported on Gemini 3.x models |
| AWS Bedrock | Claude, Titan, Cohere, Nova, Llama | Multiple region/credential sets |

All providers are normalized to the OpenAI API format for chat completions and streaming (SSE).

### Provider Options

Every provider block in the LLM Gateway config exposes a uniform `options` object that lets you reshape the request just before it hits the upstream endpoint, without changing application code. Three options are supported, all consumed by the same path inside `fetchLLM`:

| Option | What it does | Applies to |
|--------|--------------|------------|
| `options.parameterAliases` | Renames request body keys (e.g. `max_tokens` → `max_completion_tokens` for providers that adopted the new OpenAI name) | All providers |
| `options.excludeParameters` | Drops request body keys the upstream rejects (e.g. `top_p` for models that don't support it) | All providers |
| `options.headers` | Attaches arbitrary HTTP headers (tenant tags, gateway subscription keys, correlation IDs…) | All providers |

The same three options are also exposed in the **Agents Controls → Providers** UI for every provider type. Backwards-compatible: any option you omit is a no-op.

<Note>
Provider options are configured **per-provider** in the workspace that owns the provider config: **LLM Gateway** (`providers.<provider>.options.*`) for the current LLM Gateway architecture, or **AI Knowledge** (`llm.<provider>.options.*`) for the legacy AI Knowledge stack. The OpenAI app instance is a pass-through and is **not** the configuration surface; editing it directly there has no effect on traffic that flows through the gateway.
</Note>

#### `parameterAliases`

Each entry is a `{ from, to }` pair. When a key matching `from` is present in the request body, it is renamed to `to` (the value is preserved, the old key is dropped). Typical use: a provider exposes the OpenAI Chat Completions surface but renamed `max_tokens` to `max_completion_tokens`.

```yaml
options:
  parameterAliases:
    - from: max_tokens
      to: max_completion_tokens
```

#### `excludeParameters`

Each entry is a body key name to delete before the request is sent. Typical use: a model rejects `top_p` or `presence_penalty` and you want to keep your app code provider-agnostic instead of conditionally stripping.

```yaml
options:
  excludeParameters:
    - top_p
    - presence_penalty
```

Excluding `stream` is a special case: it doesn't only drop the key from the body, it **forces the provider into non-streaming mode**. Use it when an upstream endpoint advertises SSE but doesn't handle it reliably. The gateway then issues a plain request and returns the full completion at once, while the calling agent keeps its usual response shape.

```yaml
options:
  excludeParameters:
    - stream
```

#### `headers`

A map of `name → value` HTTP header pairs attached to every upstream request. Typical uses: tenant-aware gateways (e.g. Azure API Management in front of Bedrock / Anthropic / Vertex), custom auth schemes, request tagging for cost attribution, or correlating upstream provider logs with Prisme.ai audit trails.

**Static values** are sent verbatim:

| Header name | Value | Sent as |
|-------------|-------|---------|
| `X-Tenant-Id` | `acme-corp` | `X-Tenant-Id: acme-corp` |
| `X-Cost-Center` | `R&D-EMEA` | `X-Cost-Center: R&D-EMEA` |

**Runtime placeholders** inject context from the calling Prisme.ai request. The value of the header must be **exactly** one of the patterns below:

| Placeholder value | Replaced with |
|-------------------|---------------|
| `{correlationId}` | The Prisme.ai correlation ID of the current request, which propagates trace context to the LLM provider's logs |
| `{user.<path>}` | Any field of the calling user, at arbitrary depth. `{user.id}` for the Prisme.ai user ID, `{user.email}` for the email, `{user.authData.entraid.firstname}` for a nested provider-specific claim, etc. |
| `{userId}` | Legacy alias of `{user.id}`, kept for backwards compatibility; prefer `{user.id}` in new configurations |
| `{apiKeyId}` | The identifier of the organization API key that authenticated the call. API-key callers carry no user context, so this and `{orgSlug}` are the identity they have |
| `{orgSlug}` | The slug of the calling organization |
| `{sourceWorkspaceId}` | The workspace that issued the call, for workspace-to-workspace traffic |

Resolution rules for `{user.<path>}`:
- If the path doesn't exist on the user object, the header value resolves to an empty string.
- If the resolved value is not a string (object, array, number), it is JSON-stringified before being sent.

<Warning>
Substitution is **full-string only**. The value must match the placeholder pattern exactly; composite values such as `prefix-{user.id}` or `req-{correlationId}-v2` are sent as-is, without substitution. Unknown placeholders that don't match any supported pattern (e.g. `{foo.bar}`) are also sent verbatim — so the provider receives the literal string `{foo.bar}`, which is non-empty and therefore looks like a populated header. `header_policy`, below, catches that — but only for the header names a policy actually requires.
</Warning>

**Examples**

OpenAI-compatible (`openailike`): typical case of routing through a custom gateway:

```yaml
- api_key: '{{secret.myProviderApiKey}}'
  endpoint: https://my-openai-like-provider.example.com/v1/
  models:
    - my-model
  options:
    headers:
      x-correlation-id: '{correlationId}'
      x-user-id: '{user.id}'
      x-user-email: '{user.email}'
      x-user-firstname: '{user.authData.entraid.firstname}'
      x-tenant: 'acme-corp'
```

Anthropic: injecting an Azure API Management gateway's subscription key in front of a Claude-compatible endpoint:

```yaml
anthropic:
  api_key: '{{secret.anthropicApiKey}}'
  anthropic_version: '2023-06-01'
  endpoint: https://my-apim.example.net/ai/anthropic/v1/messages
  models:
    - claude-sonnet-4-5
  options:
    headers:
      x-api-key: '{{secret.anthropicApiKey}}'
      Ocp-Apim-Subscription-Key: '{{secret.apimSubscriptionKey}}'
      x-correlation-id: '{correlationId}'
      x-user-email: '{user.email}'
```

**Notes on headers**:
- Custom headers are **merged on top** of the provider's default headers (auth + content-type + provider-specific headers like `anthropic-version`). Reusing a default header name will override it, useful for `Authorization` on `openailike` when the upstream requires a non-Bearer scheme, or for `x-api-key` on `anthropic` when fronting Anthropic with an API Management gateway whose key differs from the upstream key.
- For multipart endpoints (image edits, `openailike` only), the `Content-Type` is dropped automatically so the runtime can set the multipart boundary.
- On Bedrock and Vertex, the standard provider auth (AWS Signature v4 / Google service account token) is **always added by the gateway**, regardless of `options.headers`; you cannot disable it through this option.

#### Requiring identity headers — `header_policy`

Configuring an identity header is not the same as receiving one. An unresolvable `{user.<path>}`
resolves to an **empty string** rather than dropping the header, so a call whose user context lost
its email reaches the provider with `x-user-email:` empty. A placeholder no version of the gateway
recognises is worse: it is forwarded **literally**, so the provider receives the header with the
value `{apiKeyId}` — non-empty, and therefore indistinguishable from a correct value. In both
cases the call succeeds and nothing anywhere records that the identity was lost.

`header_policy` turns that into a control. Per caller class, it either **refuses the call before
the provider is contacted**, or lets it through and **records the finding**.

**Where it is set.** On the organization, under `settings.llm`, next to `allowed_models`,
`default_completion_model` and `quota_policy`. There is no dedicated panel in Agents Controls yet,
so it is set with `PATCH /v2/orgs/{orgSlug}` on the `settings` object.

<Warning>
That PATCH **replaces `settings` wholesale** — it does not deep-merge. Read the organization first,
merge your change into the `settings` you got back, and send the complete object. Sending only
`{"settings": {"llm": {"header_policy": …}}}` wipes `settings.quotas` along with every other
`settings.llm` key, including `allowed_models` and `quota_policy`.

For the same reason, **importing a governance configuration from the Models tab deletes
`header_policy`**: the import rebuilds `settings.llm` from a fixed list of known fields, and
`header_policy` is not yet one of them. Editing fields in that tab normally is safe — only
import/export drops it. Re-apply the policy after any import.
</Warning>

```yaml
llm:
  allowed_models: [gpt-5-chat-latest, claude-sonnet-5]
  default_completion_model: gpt-5-chat-latest
  header_policy:
    user:
      headers: [x-user-email]
      mode: block
    apikey:
      headers: [x-api-key-issuer]
      mode: report_only
    workspace:
      mode: disabled          # or simply omit the key
```

**Caller classes.** The policy is keyed by *who* is calling, because different callers carry
different identities — requiring `x-user-email` of a machine-to-machine call would refuse every one
of them:

| Class | Who it is | Identity available |
|---|---|---|
| `user` | A real end-user session. Tested first, so it wins whenever a user is present | `{user.<path>}`, `{userId}` |
| `apikey` | An organization API key with **no** user context at all | `{apiKeyId}`, `{orgSlug}` — `{user.*}` resolves to nothing here |
| `workspace` | A trusted workspace-to-workspace call, no user | `{sourceWorkspaceId}` |

<Note>
`workspace` is the one class an **organization** policy may not reach. It is only selected when no
user is in context at all, and on such a call the organization usually is not resolved either — the
gateway then sees no organization settings and falls back to its own default, reporting
`policySource: gateway`. Cover workspace-to-workspace traffic with the gateway-wide default rather
than with a per-organization policy — see **Gateway-wide settings** below.
</Note>

**Modes.** `mode` is mandatory as soon as a class key exists:

| Mode | Behavior |
|---|---|
| `block` | The call is refused with `403 HEADER_POLICY_VIOLATION`; the provider is never contacted |
| `report_only` | The call proceeds normally and the finding is recorded. Use it to discover which provider entries are missing a header before you enforce |
| `disabled` | Nothing is checked. Same as omitting the class entirely |

An enforcing mode (`block`, `report_only`) must declare a non-empty `headers` array; `disabled` does
not need one. A class that is not declared is disabled — so the policy above checks nothing for
`workspace` callers.

The organization value replaces the gateway-wide default **wholesale**, not merged key by key, so an
organization's policy reads in one place — the same way `default_completion_model` overrides the
gateway's `defaults.completions`. An organization opts out of a gateway default entirely with
`header_policy: {}`.

**What counts as a missing header.** Three situations, all of which mean the identity will not
reach the provider:

| | Situation |
|---|---|
| **Declared but empty** | The header **is** declared in `options.headers` on the provider entry serving the model, but its placeholder resolves empty for this call |
| **Not declared** | The required header is absent from the final header set for that provider entry, so it would never be sent |
| **Unresolved placeholder** | The configured value looks like a placeholder the gateway cannot resolve. It would reach the provider as the literal string `{apiKeyId}` — non-empty, and so invisible to any emptiness check |

Header names are matched case-insensitively ([RFC 7230 §3.2](https://datatracker.ietf.org/doc/html/rfc7230#section-3.2)),
and the check runs at the last point common to every provider family — so it behaves identically on
OpenAI, Azure, OpenAI-like, Anthropic, Bedrock and Vertex. It covers chat completions, embeddings,
images, image edits, rerank, and the gateway's own model-routing classifier. The one exception is
`/v1/test`, the connectivity probe behind the Models tab's test button: it reaches the provider
without going through the policy.

In `block`, the caller receives:

```json
{
  "error": "HEADER_POLICY_VIOLATION",
  "message": "Call refused: required identity header(s) would reach the model provider empty.",
  "status": 403,
  "details": { "missing": ["x-user-email"], "model": "gpt-5-chat-latest" }
}
```

`/v1/rerank` is the exception to that shape: it wraps any inner completion failure, so a refusal
arrives as `error: "RERANK_FAILED"` with `code: "HEADER_POLICY_VIOLATION"`, still `403`, and without
the `missing` list. Match on `code` as well as `error` if you handle refusals programmatically.

**What is recorded.** Both modes emit a `governance.headers.missing` event, visible in the activity
feed and available to AI Insights dashboards:

| Field | Meaning |
|---|---|
| `blocked` | `true` when the call was refused, `false` in `report_only`. This is the field that separates the two |
| `mode` | The mode that applied |
| `missing` | The header names that would not have arrived |
| `model`, `provider` | What the call was routed to |
| `authType`, `policySource` | The caller class, and whether the gateway default or the organization policy applied |
| `orgSlug`, `userId`, `sessionId`, `apiKeyId`, `correlationId`, `sourceWorkspaceId` | Call context |

The user's email address is never included — only a `userEmailPresent` boolean, since the missing
identity case is exactly the one where the value is untrusted.

<Note>
**Count requests, not events.** The check runs once per provider call, and one API request is not
one provider call: a failover chain tries each candidate, `/v1/embeddings` splits large inputs into
batches, and `model: auto` runs a routing classifier that can be refused on its own. Counting
distinct `correlationId` gives you requests; a raw event count gives you attempts. `block` is
tighter than `report_only` here — it stops at the first refusal on a batched embedding — but it is
not guaranteed to be one event per request either.

In `report_only` the finding also appears twice in the activity feed, under the app-prefixed name
and under `governance.headers.missing`. Filter on the exact event type rather than a prefix.
</Note>

**A malformed policy is reported, never fatal.** An unknown class key, a missing or unrecognised
`mode`, or an enforcing mode with no headers makes that entry invalid. The gateway then emits an
`error` event with code `HeaderPolicyInvalid` naming each faulty key and its reason, **skips the
faulty keys, applies whatever is still valid, and lets the call through**:

| Reason | What is wrong |
|---|---|
| `UNKNOWN_CALLER_CLASS` | The key is not `user`, `apikey` or `workspace` |
| `MODE_MISSING` | The class has no `mode` (including when the value is a bare string such as `user: block`) |
| `MODE_UNKNOWN` | `mode` is not one of the three |
| `HEADERS_MISSING` / `HEADERS_NOT_ARRAY` / `HEADERS_EMPTY` | An enforcing mode without a usable `headers` list |
| `NOT_AN_OBJECT` | `header_policy` is not an object at all — nothing is salvageable, so the control is disabled entirely |

So a typo in one class does not disable a correct one, and a mistyped policy never costs an
organization its LLM traffic. The condition stays loud — the event repeats on every call until the
policy is fixed — it is simply not fatal.

**Gateway-wide settings.** Two keys live in the LLM Gateway workspace's own configuration, under
`config.value`. They are the platform-level half of the control; the organization settings above are
the per-customer half.

| Key | What it does |
|---|---|
| `header_policy` | The **default policy**, in the same per-class shape as the organization one. It applies to every organization that has not set its own `settings.llm.header_policy`, and it is the only policy that ever reaches `workspace`-class callers |
| `header_policy_enforcement` | The operator **cap**: `enabled` (default), `report_only` — which caps every declared mode at reporting, whatever the organizations configured — or `off`, which neutralises the control platform-wide |

```yaml
# workspaces/llm-gateway/index.yml
config:
  value:
    header_policy:
      user:
        headers: [x-user-email]
        mode: report_only
      workspace:
        headers: [x-source-workspace-id]
        mode: report_only
    header_policy_enforcement: enabled
```

The shape differs from the organization form on one point: on the gateway the policy sits directly
under `config.value`, not under an `llm` key. Everything else is identical — same caller classes,
same modes, same validation, so a malformed entry emits `HeaderPolicyInvalid` with `source: gateway`
and the valid entries still apply. The release ships `header_policy: {}`, so no default is in force
until you set one.

A gateway default is not a safe place to start enforcing: it reaches every organization that has not
overridden it. Set `block` here only once the organizations have been through `report_only`
individually, as in the rollout note below.

`header_policy_enforcement` is an operator control, not an organization one: an organization cannot
re-enable a policy the platform turned off. An unrecognised value falls back to `enabled` and emits
`HeaderPolicyEnforcementInvalid`, so a typo cannot silently switch a compliance control off.

**Deploying them.** Edit `index.yml` in the repository the gateway is pulled from, then run a
platform pull — it rewrites the workspace configuration from `index.yml`. The exception is a
repository that lists `index` in its
[`pull.exclude`](/products/ai-builder/versioning#excluding-files-from-import): there the stored
configuration is deliberately kept and your change never lands, so use the API below instead.

To change either key live, without a release, use `PATCH /v2/workspaces/{workspaceId}/config`. That
endpoint **replaces the whole `value` object**, so send the complete configuration, providers
included, or you wipe the gateway's configuration.

<Note>
Roll it out on one organization first rather than gateway-wide. Start in `report_only`, watch
`governance.headers.missing` to find which provider entries are missing the header, add the missing
`options.headers` lines, then flip that organization to `block` and extend to the others.
</Note>

<Warning>
`report_only` findings reach `governance.headers.missing` through an event listener bound to the
OpenAI app instance by its slug. On a deployment where that instance was renamed from `OpenAI`, the
relay stops silently and `report_only` produces no event at all — while `block` keeps working,
since the gateway emits that one itself. Check the instance slug before trusting an empty
`report_only` dashboard.
</Warning>

<Warning>
The check itself runs inside the OpenAI app that fronts the providers, at the last point that sees
the final header set. On a platform whose apps have not been updated to a version that supports it,
the policy is accepted and stored but **silently not enforced** — no refusal, no
`governance.headers.missing`. Confirm the app version before relying on a `block` policy for
compliance.
</Warning>

### Custom Endpoint (Anthropic)

The native **Anthropic** provider supports an optional `endpoint` field. When set, it is used **verbatim** as the request URL instead of the default `https://api.anthropic.com/v1/messages`. This lets the Anthropic provider target any Anthropic-compatible host: self-hosted Claude deployments, Anthropic-compatible gateways, or **Azure AI Foundry** endpoints whose URL doesn't fit the standard `{resource}.{domain}/anthropic/v1/messages` scheme.

<Note>
Like the [provider options](#provider-options) above, this is configured in the workspace that owns the provider config: **LLM Gateway** (`config.value.providers.anthropic.endpoint`). The OpenAI app instance is a pass-through and is **not** the configuration surface.
</Note>

Example LLM Gateway config (`workspaces/llm-gateway/index.yml`, under `config.value.providers.anthropic`):

```yaml
anthropic:
  api_key: '{{secret.anthropicClientKey}}'
  anthropic_version: '2023-06-01'
  endpoint: https://my-foundry.example.net/custom/path/v1/messages   # used verbatim
  auth_scheme: bearer        # x-api-key (default) | api-key | bearer
  models:
    - claude-opus-4-6
    - claude-sonnet-4-5
```

**Notes**:
- **Additive**: omit `endpoint` and the provider behaves exactly as before, calling `https://api.anthropic.com/v1/messages`.
- **Selectable auth scheme**: set `auth_scheme` to control how the key is sent: `x-api-key` (default, the standard Anthropic header), `api-key`, or `bearer` (sends `Authorization: Bearer <api_key>` and omits `x-api-key`). The key or token always goes in `api_key`. Omit `auth_scheme` to keep the default `x-api-key` behavior. For richer needs (multiple auth headers, gateway subscription keys, request tagging), use [`options.headers`](#headers); it overrides anything set by `auth_scheme`.
- **Include the full path**: the value is taken as-is; append `/v1/messages` (or whatever path the host exposes).
- **vs Azure OpenAI `format: anthropic`**: if the URL fits `https://{resource}.{domain}/anthropic/v1/messages`, configure it as an `azure_openai.resources` entry with `format: anthropic` (you get URL forging and can co-locate GPT + Claude on one resource). Use `anthropic.endpoint` when the URL does **not** fit that scheme.
