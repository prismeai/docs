The Power BI app provides read and write access to the [Microsoft Power BI REST API (v1.0)](https://learn.microsoft.com/en-us/rest/api/power-bi/), rooted at `https://api.powerbi.com/v1.0/myorg`. It can be consumed two ways: as a remote MCP server that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. The MCP surface groups every operation into **eleven entity tools** (`workspaces`, `datasets`, `query`, `refresh`, `reports`, `dashboards`, `dataflows`, `gateways`, `imports`, `capacities`, `admin`), each driven by an `action` argument. It runs in the **tenant app-instance context**: the installing workspace stores its own Microsoft Entra ID application credentials, and each calling agent is gated by a per-workspace authorized-agents allowlist. Authentication is **per-user OAuth2 authorization code with PKCE against Microsoft Entra ID**, so every call runs with the signed-in user's own Power BI permissions.

<Note>
  **Power BI does not support a central OAuth client.** Every workspace that installs this connector registers its own Microsoft Entra ID application and enters its own client id and secret. The connector resolves a single auth mode, `oauth`, from its own app-instance configuration; it has no maintainer view, no core-workspace client, and no `oauthCentral` configuration path. Read [When to use a central client](/apps-store/marketplace/connectors/central-oauth#when-to-use-a-central-client) only to understand the trade-off: for Power BI, the **tenant-owned client** row is the only option, and the rest of that page does not apply.
</Note>

## Prerequisites

On the Microsoft side:

- A **Microsoft Power BI** account. Microsoft gates report export, embed tokens and several admin APIs behind Power BI Pro, Premium Per User, or a Premium or Fabric capacity, so check your [Power BI licence](https://learn.microsoft.com/en-us/power-bi/fundamentals/service-features-license-type) against the operations you plan to run.
- A **Microsoft Entra ID** tenant in which you can register an application, in the [Microsoft Entra admin center](https://entra.microsoft.com) under **App registrations**. You need the **Application (client) ID**, a **client secret**, and the **directory (tenant) ID**.
- The **Dataset Execute Queries REST API** tenant setting enabled in the Power BI admin portal, otherwise the `query` tool and the `executeQueries` instruction are rejected.
- A user holding the **Fabric administrator** or **Power BI administrator** role for anything under the `admin` tool or the `admin*` instructions. Every other call runs with the connected user's ordinary Power BI permissions.

On the Prisme.ai side:

- The `owner`, `editor`, or `admin` role on the target Builder workspace, so you can install the app and read and update that workspace's secrets. The configuration app returns a permission error instead of loading when the signed-in user lacks them. See [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin).
- The connector reads and writes two workspace secrets, both provisioned automatically on install: `powerbiAuth` (the authentication object) and `powerbiAuthorizedAgents` (the agent allowlist).

## How authentication works

The connector supports a single credential model, and it is deliberate: **per-user delegated OAuth2** with the authorization code flow and PKCE against Microsoft Entra ID.

| Property | Value |
|---|---|
| Runtime identity seen by Power BI | The individual Prisme.ai user who signed in with their Microsoft account |
| Permission enforcement point | Power BI, against that user's own workspace and item access |
| Consent | Granted once per user, on first connect |
| Credential scope | Personal to the user; never shared across the workspace |
| Configured by | A workspace administrator, once per workspace, in the configuration app |
| Default requested scopes | `https://analysis.windows.net/powerbi/api/.default offline_access openid profile` |

There is no shared service account and no client-credentials mode, so a user can never see Power BI content they could not open in Power BI themselves, and Power BI audit logs attribute every action to the real person. The trade-off is that every user must connect once, and that **App-mode instructions resolve the token of the Prisme.ai user running the automation**. An unattended run with no connected user resolves no token and fails with `Power BI is not connected for this user`.

Tokens are stored per user. The access token is cached with its expiry and reused while valid, with a 120 second safety margin; when it expires the connector exchanges the stored refresh token for a new one. Microsoft rotates refresh tokens on every exchange, so the connector keeps the rotated value. If Entra ID permanently rejects the refresh token, the connection is dropped and the user is asked to reconnect.

  ## Register the Microsoft Entra ID application

  The install and credential-entry procedure is the standard one, documented in [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace). The steps below add only what Microsoft Entra ID requires.

  <Steps>
    <Step title="Install the connector and open its configuration app">
      Install **Power BI** in the workspace that will own the connection, following [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), then open the **Configuration app** link that install writes into the app instance configuration. The link carries the workspace and app-instance context the app needs:

      ```text
      <studio-url>/apps/powerbi?workspaceId=<workspace-id>&workspaceSlug=<workspace-slug>&appInstance=<app-instance-slug>
      ```

      `workspaceId` is the **raw workspace id**, not the `slug:` form: the configuration app writes the credentials through the workspace `/config` and `/security/secrets` endpoints, which do not resolve a slug. Opening `/apps/powerbi` without those query parameters shows a missing-context message instead of the configuration form.
    </Step>
    <Step title="Copy the callback URL">
      The configuration app displays the connector's **Callback URL** under the authentication section. Copy it verbatim. It has this shape:

      ```text
      <api-url>/workspaces/<workspace-id>/webhooks/<app-instance-slug>.oauthCallback
      ```

      <Warning>
        This URI uses the **raw workspace id**, not the `slug:<workspace-slug>` form shown as the generic tenant-owned shape in [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls) and in [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app). **Microsoft Entra ID rejects a redirect URI containing a colon**, so the `slug:` form is not accepted. Copy the value the configuration app renders rather than assembling it. The raw id never changes, so a workspace rename does not break the Entra exact match.
      </Warning>
    </Step>
    <Step title="Create the app registration in Microsoft Entra ID">
      In the [Microsoft Entra admin center](https://entra.microsoft.com), open **Identity > Applications > App registrations > New registration**. Add a **Web** platform and paste the callback URL you copied as the single redirect URI. Under **API permissions**, add the delegated **Power BI Service** permissions your users need, then under **Certificates & secrets** create a **client secret**. Record the **Application (client) ID**, the secret value and the **Directory (tenant) ID**.
    </Step>
    <Step title="Enter the credentials in the configuration app">
      Back in the configuration app, fill in the **tenant**, **oauthClientId** and **oauthClientSecret** fields, leave **scopes** at the default value unless Microsoft requires a narrower set, and save. The app writes them into the workspace secret `powerbiAuth`. Do not edit that secret by hand in Builder.

      Leaving **tenant** empty falls back to `organizations`, which accepts any work or school account. Set the directory (tenant) ID explicitly to restrict sign-in to your own tenant.
    </Step>
    <Step title="Connect a Microsoft account">
      Select the connect action. The configuration app saves the credentials, then opens the Microsoft sign-in page in a popup. After consent, the popup returns to the configuration app and the connection state switches to connected.
    </Step>
  </Steps>

  <Warning>
    The client secret is stored in the workspace secret `powerbiAuth` and is never sent to an agent or returned by any tool. Never paste it into an agent prompt, an automation body, or a chat message.
  </Warning>

  ## Declare the capability in AI Governance (optional)

  Broad connectors meant to be shared across many agents are best exposed as a named **capability** in AI Governance. Agent builders then enable that capability instead of pasting a raw MCP endpoint.

  The configuration app can do this for you: under the MCP endpoint section, use the catalog action to add or update the Power BI entry. It publishes the endpoint, the Scope and the OAuth block listed below. The generic flow, the role gate, and the manual alternative are documented once in [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability): [publish to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog), or [declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).

  These are the Power BI values to enter, whichever path you take:

  | Capability field | Value for Power BI |
  |---|---|
  | Server URL (**SSE/WebSocket URL**) | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.mcp` |
  | **Scope** | `context_id,agent_id,user_id` |
  | Authorization block type | `oauth2` in the catalog, `oauth` on a per-agent tool |
  | `status_url` | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthStatus` |
  | `connect_url` | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthConnect` |
  | `disconnect_url` | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthDisconnect` |
  | `scopes` | `https://analysis.windows.net/powerbi/api/.default offline_access openid profile` |

  Unlike the OAuth callback URL, these endpoints use the **`slug:` form**, which survives a workspace re-import. The `agent_id` part of the **Scope** is what lets the connector identify and authorize the calling agent; it is unrelated to the Microsoft OAuth scopes. The OAuth block is what makes Agent Creator drive the connect, status and disconnect flow for each user.

  <Warning>
    Declaring the capability makes the connector **available**; it does not authorize a specific agent to call it. This connector follows the **tenant-context model**: the workspace that owns the MCP endpoint gates callers through its **authorized-agents allowlist**. An agent that holds the capability but is missing from that allowlist is refused at the first tool call. See [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization).
  </Warning>

  <Note>
    The per-agent gate is **always on** for Power BI. There is no central-client core endpoint that short-circuits it, so the only way to accept every caller is the `*` sentinel behind **Allow all agents** in the configuration app. See [The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard).
  </Note>
</Accordion>

  <Tab title="Agent builder (Agent Creator)">
    ## Agent builder

    **Goal:** let an agent you build in Agent Creator query and manage Power BI through MCP tools.

    <Note>
      Before an agent can call the connector, the Power BI app must be installed and configured in a workspace (see [Workspace builder](#workspace-builder-dsul)), and a Microsoft Entra ID application must be registered (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    Your agent passes two independent gates on every call. It is identified by the `agent_id` that Agent Creator injects through the capability **Scope**, and that id must appear in the connector's **authorized-agents allowlist**, managed in the configuration app. Only then does the connector resolve the calling user's Power BI token server-side. The agent never receives a token, a client id or a client secret.

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A: enable the shared capability from the catalog

    The fastest path: someone has already published a **Power BI** capability to your organization's catalog, so you just pick it.

    <Steps>
      <Step title="Open your agent in Agent Creator">
        Open the agent you want to extend and go to its capabilities and tools.
      </Step>
      <Step title="Add the Power BI capability">
        Browse the capability catalog, select **Power BI**, and enable it. The MCP endpoint URL, the **Scope** (`context_id,agent_id,user_id`) and the per-user OAuth block are already wired, so there is nothing to paste. See [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability) for the checks to run afterwards.
      </Step>
      <Step title="Ask for your agent to be allowlisted">
        The catalog entry points at a workspace you may not own. Ask whoever owns that workspace to add your agent under **Authorized agents** in its configuration app. Until then, every tool call is refused with an explicit "not authorized" message that carries your agent id.
      </Step>
      <Step title="Connect a Microsoft account">
        On the first tool call, an unconnected user is prompted to sign in and Agent Creator surfaces the connector's connect URL. Subsequent calls reuse the stored token.
      </Step>
    </Steps>

    <Note>
      Convenient, but your agent runs against an instance someone else owns: its Entra ID application, its allowlist and its per-user tokens are outside your control. Prefer Option B for anything beyond quick experiments.
    </Note>

    ## Option B: run it from your own workspace (recommended)

    For production agents, install the connector in **your own workspace** and point the agent at that workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP endpoint runs in your app-instance context, the Entra ID application, the per-user Power BI tokens and the authorized-agents allowlist are all scoped to your workspace. You decide exactly which agents may call it and which Microsoft accounts back them, and a misconfiguration elsewhere cannot expose your data.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder](#workspace-builder-dsul): install **Power BI** in your workspace, open its **Configuration app**, enter the Entra ID credentials and connect a Microsoft account.
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's configuration app, go to **Authorized agents** and tick your agent, or enable **Allow all agents**. The **Install capability** button next to an agent does both jobs at once: it adds the agent to the allowlist and attaches the MCP tool, endpoint, Scope and OAuth block to that agent. See [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Add the MCP capability to your agent">
        If you wired the agent by hand rather than with **Install capability**, add a capability pointing at your workspace's **MCP endpoint** URL and set its **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        Without `agent_id` the connector cannot identify the caller and refuses every call. This scope is unrelated to the Microsoft OAuth scopes.
      </Step>
      <Step title="Connect a Microsoft account">
        Trigger any tool, or use the connect action in the configuration app, and complete the Microsoft sign-in. The connection state switches to connected.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent must know the tools exist and when to use them. Copy-pasteable starter:

    ```text
    You have access to the Power BI MCP server (tools: workspaces, datasets, query, refresh, reports, dashboards, dataflows, gateways, imports, capacities, admin). Each tool takes an `action` argument plus per-action parameters. Use the `query` tool (action executeQuery) to answer data questions with DAX against a dataset; call `datasets` with action getSchema first to discover tables and columns. Power BI's `groupId` is the workspace id and is optional on most tools; leaving it empty targets the user's My workspace. Prefer calling a tool over guessing, and confirm with the user before any destructive action such as deleting a dataset or report, or cancelling a refresh.
    ```

    <Note>
      **Restricting to read-only (least privilege).** The tools cover both reads and writes. The connector requests the `.default` scope, so the issued token inherits exactly the delegated permissions granted to the Microsoft Entra application; it never forces write access. To allow only reads, grant the application read-level **Power BI Service** delegated permissions such as `Dataset.Read.All`, `Report.Read.All`, `Dashboard.Read.All` and `Workspace.Read.All` instead of their `ReadWrite` variants. Connecting still succeeds, and any write call is then rejected by Power BI with `403`, surfaced to the agent as an error. This restriction lives on the Entra application, outside any workspace's reach.
    </Note>

    ## Available tools

    Each tool takes an `action` argument selecting the concrete operation, plus the per-action parameters. `groupId` is the Power BI workspace (group) id; on most tools it is optional and leaving it empty targets the user's My workspace. Omitting `action` returns an error listing the available actions for that tool.

    | Tool | Actions | What it covers |
    |------|---------|----------------|
    | `workspaces` | `list`, `create`, `delete`, `listUsers`, `addUser`, `updateUser`, `deleteUser` | Power BI workspaces (groups) and their user access rights. `groupId` is required for `delete` and for the user actions. |
    | `datasets` | `list`, `get`, `delete`, `getTables`, `getDatasources`, `updateDatasources`, `getParameters`, `updateParameters`, `takeOver`, `bindToGateway`, `getSchema` | Datasets (semantic models): inspection, datasource and parameter management, ownership takeover, gateway binding. |
    | `query` | `executeQuery` | Runs a DAX query against a dataset and returns the result rows. |
    | `refresh` | `trigger`, `history`, `getSchedule`, `updateSchedule`, `cancel` | Dataset refreshes, including enhanced refresh options and the scheduled-refresh configuration. |
    | `reports` | `list`, `get`, `delete`, `clone`, `rebind`, `getPages`, `getPage`, `export`, `getExportStatus`, `getExportFile`, `updateContent`, `generateToken` | Reports, their pages, the asynchronous export-to-file job, and embed tokens. |
    | `dashboards` | `list`, `get`, `create`, `getTiles`, `getTile`, `cloneTile`, `generateToken` | Dashboards, their tiles, and embed tokens. |
    | `dataflows` | `list`, `get`, `delete`, `refresh`, `getTransactions`, `getDatasources` | Dataflows, their `model.json` definition, refreshes and transactions. |
    | `gateways` | `list`, `get`, `getDatasources`, `createDatasource`, `deleteDatasource`, `getDatasourceStatus` | On-premises data gateways and their datasources. |
    | `imports` | `list`, `get`, `createUploadLocation` | Imports, plus the temporary upload location used to publish a PBIX file. |
    | `capacities` | `list`, `getWorkloads`, `getRefreshables` | Premium and Fabric capacities, their workloads and refreshables. |
    | `admin` | `listGroups`, `getGroupUsers`, `listDatasets`, `listReports`, `listDashboards`, `listDataflows`, `getActivityEvents`, `listCapacities`, `getModifiedWorkspaces`, `scanWorkspaces`, `getScanStatus`, `getScanResult` | Tenant-wide admin APIs, including the activity log and the metadata scanner. Requires the connected user to hold the Fabric or Power BI administrator role. |

    ## Output formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - `verbose` (default): a human-readable text block containing the Power BI response as formatted JSON.
    - `structured`: the same payload placed in `structuredContent` as machine-readable JSON, with the JSON also mirrored in the text content.
    - `both`: produces the same response as `structured`.

    ## Tool arguments

    Only `action` is mandatory in every tool schema. The tables below mark the arguments the underlying Power BI operation additionally requires.

    ### workspaces tool

    ```json
    {
      "name": "workspaces",
      "arguments": {
        "action": "listUsers",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of the actions listed above. |
    | `groupId` | For `delete` and all user actions | Workspace (group) id. Empty on `list` means My workspace. |
    | `name` | For `create` | Workspace name. |
    | `identifier` | For `addUser`, `updateUser` | Principal object id, group id or service principal id. |
    | `principalType` | For `addUser`, `updateUser` | `User`, `Group`, `App` or `None`. |
    | `groupUserAccessRight` | For `addUser`, `updateUser` | `Admin`, `Contributor`, `Member` or `Viewer`. |
    | `emailAddress` | No | User email, used by `addUser`. |
    | `user` | For `deleteUser` | Email address or principal object id to remove. |
    | `top`, `filter` | No | `$top` and `$filter` on `list`. |

    ### datasets tool

    ```json
    {
      "name": "datasets",
      "arguments": {
        "action": "getSchema",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8",
        "datasetId": "cfafbeb1-8037-4d0c-896e-a46fb27ff229"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of the actions listed above. |
    | `datasetId` | For every action except `list` | Dataset (semantic model) id. |
    | `groupId` | No | Workspace id; omit for My workspace. |
    | `updateDetails` | For `updateDatasources`, `updateParameters` | Array of update detail objects. |
    | `gatewayObjectId` | For `bindToGateway` | Gateway object id to bind the dataset to. |
    | `datasourceObjectIds` | No | Gateway datasource object ids to bind, used with `bindToGateway`. |

    <Note>
      `getTables` works **only** for Push API datasets; on a regular import or DirectQuery semantic model it fails. To inspect a regular model use `getSchema`, which runs `EVALUATE INFO.VIEW.COLUMNS()`, or the `query` tool with `EVALUATE INFO.VIEW.TABLES()`.
    </Note>

    ### query tool

    ```json
    {
      "name": "query",
      "arguments": {
        "action": "executeQuery",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8",
        "datasetId": "cfafbeb1-8037-4d0c-896e-a46fb27ff229",
        "daxQuery": "EVALUATE TOPN(10, 'Sales', 'Sales'[Amount], DESC)"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `executeQuery`. |
    | `datasetId` | Yes | Target dataset (semantic model) id. |
    | `daxQuery` | Yes, unless `queries` is set | A single DAX query string. |
    | `queries` | No | Array of `{ query }` objects. Overrides `daxQuery`. |
    | `groupId` | No | Workspace id; omit for My workspace. |
    | `impersonatedUserName` | No | UPN to impersonate as the effective identity for row-level security. |

    ### refresh tool

    ```json
    {
      "name": "refresh",
      "arguments": {
        "action": "trigger",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8",
        "datasetId": "cfafbeb1-8037-4d0c-896e-a46fb27ff229",
        "notifyOption": "MailOnFailure"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of the actions listed above. |
    | `datasetId` | Yes | Target dataset id. |
    | `groupId` | No | Workspace id; omit for My workspace. |
    | `notifyOption` | No | `MailOnCompletion`, `MailOnFailure` or `NoNotification`, used by `trigger`. |
    | `type` | No | Enhanced refresh type: `Full`, `Automatic`, `Calculate`, `ClearValues` or `DataOnly`. |
    | `refreshId` | For `cancel` | Id of the in-progress refresh to cancel. |
    | `top` | No | Number of entries returned by `history`. |
    | `value` | For `updateSchedule` | Refresh schedule object. |

    ### reports tool

    ```json
    {
      "name": "reports",
      "arguments": {
        "action": "export",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8",
        "reportId": "5b218778-e7a5-4d73-8187-f10824047715",
        "format": "PDF"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of the actions listed above. |
    | `reportId` | For every action except `list` | Target report id. |
    | `groupId` | No | Workspace id; omit for My workspace. |
    | `format` | For `export` | Export format, for example `PDF`, `PPTX` or `PNG`. |
    | `powerBIReportConfiguration`, `paginatedReportConfiguration` | No | Export configuration objects. |
    | `exportId` | For `getExportStatus`, `getExportFile` | Id of the export job. |
    | `name`, `targetModelId`, `targetWorkspaceId` | For `clone` | New report name and clone destination. |
    | `datasetId` | For `rebind` | Dataset to rebind the report to, and the optional dataset used by `generateToken`. |
    | `pageName` | For `getPage` | Report page name. |
    | `accessLevel`, `identities` | For `generateToken` | `View`, `Edit` or `Create`, and the effective identities used for row-level security. |

    ### dashboards tool

    ```json
    {
      "name": "dashboards",
      "arguments": {
        "action": "generateToken",
        "groupId": "f089354e-8366-4e18-aae3-a5f3c3b0c4d8",
        "dashboardId": "69ffaa6c-b36d-4d01-96f5-1ed67c64d4af",
        "accessLevel": "View"
      }
    }
    ```

    ## Installation

    Power BI follows the standard App + MCP installation flow. Run it once from [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace): [install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), [configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app), [authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector), and [copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint).

    Three things are specific to Power BI:

    - There is no auth mode to select. The connector resolves a single mode, `oauth`, and no central platform client is available, so this workspace must hold its own Microsoft Entra ID application. Register it as described in [Register the Microsoft Entra ID application](#register-the-microsoft-entra-id-application).
    - The **Callback URL** to register at Entra ID uses the **raw workspace id**, not the `slug:` form the shared page shows. Copy it from the configuration app.
    - Each user of the workspace connects their own Microsoft account once. There is no shared service credential to enter.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Read-only, populated on install. Opens the configuration app with the workspace and app-instance context needed to register the Entra ID credentials, connect an account, and manage the allowlist. |

    The configuration app drives everything; the app instance itself has no credential form. Authentication has a single mode:

    | Auth mode | What you provide | Runtime identity |
    |-----------|------------------|------------------|
    | Per-user OAuth2 with PKCE (Microsoft Entra ID) | `tenant`, `oauthClientId`, `oauthClientSecret` and optionally `scopes`, entered once in the configuration app, then each user connects their own Microsoft account | The signed-in Prisme.ai user, acting with their own Power BI permissions |

    <Note>
      Install provisions two workspace secrets, `powerbiAuth` and `powerbiAuthorizedAgents`, and binds them to the app instance configuration, as described in [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions). The configuration app writes to them; do not edit them by hand. The allowlist gates which Agent Creator agents may call the MCP endpoint and has no effect on DSUL instructions.
    </Note>

    <Warning>
      App-mode instructions resolve the Power BI token of the **Prisme.ai user running the automation**. There is no shared service credential, so an automation triggered by a schedule or by a user who has never connected fails with `Power BI is not connected for this user`.
    </Warning>

    ## Available instructions

    The prefix is the app instance slug chosen when you install the app. The examples below assume the default, `Power BI`.

    ```yaml
    - Power BI.listDatasets:
        groupId: '{{workspaceId}}'
      output: datasets
    - Power BI.executeQueries:
        groupId: '{{workspaceId}}'

      output: rows
    - conditions:
        '{{rows.error}}':
          - emit:
              event: powerbi.query.failed
              payload: '{{rows.error}}'
    ```

    ```yaml
    - Power BI.refreshDataset:
        groupId: '{{workspaceId}}'

    - Power BI.getRefreshHistory:
        groupId: '{{workspaceId}}'
        datasetId: '{{datasetId}}'

      output: history
    ```

## Verify the setup

Run these three checks in order. Each one is independent of the previous role's claims. They complete the generic checklist in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation), which also covers proving that a non-allowlisted agent is refused.

1. **Connection.** In the configuration app, confirm the authentication section reports the current user as connected. The state comes from the connector's `oauthStatus` webhook, which does more than read a cached flag: when the access token has expired it attempts a refresh, and reports `connected: false` if Entra ID rejects the stored refresh token.
2. **Builder path.** From an automation, call `listWorkspaces` and check that the response carries a `value` array and that `{{result.error}}` is empty. This is a read-only call and needs no Power BI write permission.
3. **Agent path.** In the agent preview, ask the agent to list your Power BI workspaces. It calls the `workspaces` tool with `action: list` and answers from the result. A refused call returns the allowlist or identity message instead, both listed under [Common issues](#common-issues).

## Rotate, revoke, and remove

The generic rotation and uninstall rules are in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall), including the fact that uninstalling leaves the workspace secrets behind. These are the Power BI specifics:

- **Rotate the client secret**: create a new client secret on the Entra ID app registration, paste it into the configuration app and save, then delete the old secret in Entra ID. Running calls pick up the new value on their next token exchange.
- **Disconnect one user**: use the disconnect action in the configuration app. It deletes that user's stored token and the workspace-scoped copy of their refresh token, then returns to the configuration app. The next call by that user reports `Power BI is not connected for this user`.
- **Revoke access from Microsoft**: an administrator can revoke the user's sessions or remove the application's consent in Entra ID. The next refresh attempt fails permanently, the connector drops the stored connection, and the user is prompted to reconnect.
- **Revoke one agent**: in the configuration app, untick the agent under **Authorized agents** and save. Its next MCP call is refused with the "not authorized" message. If **Allow all agents** is on, turning it off restores per-agent gating for every caller.
- **Remove the connector**: uninstall the Power BI app from the workspace, then delete the `powerbiAuth` and `powerbiAuthorizedAgents` secrets and any `pbiRefresh_<user-id>` secrets left behind. Delete the app registration in Entra ID if no other workspace uses it. If you published a capability to the Capabilities catalog, remove that entry in AI Governance as well, or agent builders keep seeing an endpoint that no longer answers.

## Error handling

Power BI failures are normalized into a single message that names the operation and appends the provider's own error code and detail. For a DAX failure, the detail carries the real Power BI message rather than the generic code.

| HTTP code | Message shape | Meaning |
|-----------|---------------|---------|
| `400` | `Bad request while <operation>` | Invalid parameters, malformed body, or a DAX syntax error. |
| `401` | `Authentication failed while <operation>. The Power BI token is missing, expired or invalid.` | The token was rejected. The user must reconnect. |
| `403` | `Forbidden while <operation>. Check workspace/item access and scope` | Insufficient delegated permission, no access to the item, or an `admin` action by a non-administrator. |
| `404` | `Resource not found while <operation>. Verify the workspace/item id.` | The workspace, dataset, report or other id does not exist or is not visible to the account. |
| `409` | `Conflict while <operation>` | For example a refresh already in progress, or a name collision. |
| `429` | `Rate limit exceeded while <operation>. Wait and retry.` | Power BI throttling. Back off and retry. |
| `500` | `Power BI server error while <operation>` | Transient service error; retry, no reconnection needed. |
| Any other | `Error <status> while <operation>` | Fallback, including `502` and `503`. |

Two failures happen before Power BI is reached:

- `No HTTP response from Power BI while <operation>`: the request never completed at the network level (DNS, connection refused, TLS, timeout, or blocked outbound egress). Verify that the Prisme.ai runtime can reach `api.powerbi.com`.
- `Power BI request build failed for <operation>`: a required argument is missing, for example `Missing required path param: datasetId` or `Missing required argument: groupId` on an operation that has no My workspace variant.

### Common issues

- **"This agent is not authorized to use this connector"**: the calling agent is not in the allowlist. Open the configuration app, go to **Authorized agents**, tick the agent named by the id in the message, and save, or enable **Allow all agents**. The **Install capability** button does this for you. See [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).
- **"The calling agent could not be identified, so it cannot be authorized"**: the MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability, then allow the agent in the configuration app. See [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
- **`Power BI OAuth is not configured. Set Tenant ID + Client ID/Secret in the config app and Save before connecting.`**: the Entra ID client id or client secret is missing from `powerbiAuth`. Enter both in the configuration app and save before connecting.
- **`Power BI is not connected for this user.`**: this user has no stored token. Connect from the configuration app, or use the agent's connect flow. The same message appears when an automation runs without a connected user.
- **`Power BI token refresh failed`**: Entra ID permanently rejected the stored refresh token, usually because it was revoked, the user's password changed, or a conditional access policy now blocks the app. The connection is dropped automatically and the user must reconnect. The connector already retries once against a freshly read token, so this message means a genuine rejection rather than a race between two concurrent calls.
- **`Power BI token endpoint temporarily unavailable`**: Entra ID returned a `5xx`. This is transient, the connection is kept, and no reconnection is needed. Retry shortly.
- **`Unknown tool`**: the MCP client called a tool this connector does not expose. Only the eleven tools listed under [Available tools](#available-tools) exist.
- **`Unknown action`** or **`Missing required argument`**: the agent passed an unsupported `action`, or omitted it. Both messages end with `Available:` followed by the valid actions for that tool.
- **`Direct calls are not allowed`** (HTTP `403`): something called a tool webhook such as `query` or `datasets` directly. Tools are reachable only through the MCP endpoint. From Builder, call the matching App-mode instruction instead, for example `executeQueries` or `listDatasets`.
- **`getTables` fails on a regular dataset**: `getTables` only works on Push API datasets. To inspect an import or DirectQuery semantic model use the `datasets` tool with `action: getSchema`, or run `EVALUATE INFO.VIEW.TABLES()` and `EVALUATE INFO.VIEW.COLUMNS()` through the `query` tool.
- **The OAuth popup returns with an `invalid_state` message**: the callback did not match the pending authorization request, typically after the flow was left open too long or was started in another browser session. Start the connect flow again from the configuration app.
- **Entra ID rejects the redirect URI**: the redirect URI registered on the app registration must match the connector's **Callback URL** byte for byte, including the **raw workspace id** and the `<app-instance-slug>.oauthCallback` suffix. **A `slug:` form is not accepted by Entra ID**, because the colon makes the URI invalid for Microsoft. Copy the value the configuration app renders; see [Register the Microsoft Entra ID application](#register-the-microsoft-entra-id-application).
- **A failed call is a value, not an exception**: after a DSUL call, always branch on `{{result.error}}`. A missing check silently passes the error object downstream.
