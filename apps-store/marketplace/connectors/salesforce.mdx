The Salesforce connector exposes a Salesforce org through the [Salesforce REST API](https://developer.salesforce.com/docs/atlas.en-us.api_rest.meta/api_rest/) to **Agent Creator** agents (through MCP) and to Builder automations (through the `Salesforce.<instruction>:` App instructions). It covers records, SOQL and SOSL queries, composite and collection endpoints, Bulk API 2.0, the Tooling API, process rules and approvals, quick actions, reports and dashboards, and metadata deploys. The MCP surface groups every operation into **13 dispatcher tools**, each driven by an `action` argument; the App surface exposes **76 instructions**, one per REST operation.

The MCP server runs in the **tenant app-instance context**: it resolves the installing workspace's own Salesforce credentials and authorizes the calling agent against that workspace's allowlist. The API version is a workspace setting and defaults to `v62.0`, so every call targets `{instance_url}/services/data/v62.0`.

## Operating model and runtime identity

Salesforce is a **per-workspace** connector: there is no platform-wide credential and no central OAuth client. Each workspace installs the app, opens its configuration app, and stores its own Connected App credentials in the workspace secret `salesforceAuth`. Authentication is resolved server-side on every call; no Salesforce token is ever returned to an agent or to a Builder automation.

Four authentication modes are supported, selected by the `mode` field of `salesforceAuth` through the configuration app's **Method** list.

| Mode | Configuration app label | What you provide | Identity Salesforce sees | Best for |
|------|------------------------|------------------|--------------------------|----------|
| `jwt` (default) | **JWT Bearer (service account) — recommended** | **Login host**, **Username (run-as)**, **Consumer Key**, **JWT Private Key (PEM)** | The run-as user named in **Username (run-as)**, for every caller | Unattended, server-to-server automation with no interactive sign-in |
| `clientCredentials` | **OAuth2 Client Credentials** | **Login host**, **Consumer Key**, **Consumer Secret** | The Connected App's run-as user, for every caller | A Connected App configured with the client credentials flow |
| `oauth` | **OAuth2 per-user (delegated)** | **Login host**, **Consumer Key**, **Consumer Secret**, optional **Scopes**, then each user selects **Connect** | The invoking user's own Salesforce account | Interactive chat, attributable writes, per-user record visibility |
| `accessToken` | **Access token (direct)** | **Instance URL**, **Access Token** | The single account that minted the token, for every caller | Short-lived or externally managed sessions, and testing |

<Note>
  **Which mode should you choose?** Use `oauth` whenever an interactive user is present and Salesforce must enforce that person's own object, field and record access: it is the only mode that attributes writes to the real user in the Salesforce audit trail. Use `jwt` for scheduled or background work that has no user to sign in, because it needs no secret at rest beyond the private key and no interactive consent. Use `clientCredentials` when your Connected App is already configured for that grant. Use `accessToken` only for testing or when an external system already manages the session.
</Note>

<Warning>
  `jwt`, `clientCredentials` and `accessToken` are **shared credentials**. Every agent and every automation in the workspace acts as one Salesforce user, Salesforce audit logs attribute all reads and writes to that one account, and the blast radius is everything that account can reach. Back them with a dedicated Salesforce integration user whose profile and permission sets grant only the objects and fields the connector needs, never a named administrator. For interactive chat use, prefer `oauth`.
</Warning>

<Note>
  **Read-only access is enforced in Salesforce, not in scopes.** Salesforce OAuth uses the broad `api` scope and cannot express read-only at the scope level; object-level and field-level access comes from the connected user's **profile** and **permission sets**. To allow reads only, back the connection (the user who selects **Connect**, or the `jwt` or `clientCredentials` run-as user) with a Salesforce user that has **Read** but not **Create**, **Edit** or **Delete** on the relevant objects. Write calls are then rejected by Salesforce, and the connector surfaces `Forbidden while <operation>. Check user/CRUD permissions in Salesforce.` This restriction lives in Salesforce and cannot be widened from Prisme.ai.
</Note>

## Prerequisites

### Salesforce prerequisites

- A **Salesforce** org (production, Developer Edition or sandbox) and administrator access to **Setup**.
- A **Connected App** created in **Setup > App Manager > New Connected App** with **OAuth Settings** enabled. Its **Consumer Key** and **Consumer Secret** back the `jwt`, `clientCredentials` and `oauth` modes.
- The login host matching the org type: `https://login.salesforce.com` for production and Developer Edition, `https://test.salesforce.com` for a sandbox, or your My Domain host such as `https://<mydomain>.my.salesforce.com`. A pasted `https://<mydomain>.lightning.force.com` URL is rewritten to `https://<mydomain>.my.salesforce.com` automatically, because Salesforce OAuth and API endpoints never live on the Lightning host. Leaving the field empty falls back to `https://login.salesforce.com`.
- For `jwt`: enable **Use digital signatures** on the Connected App and upload the X.509 certificate matching the private key you will paste, select the OAuth scopes `api`, `refresh_token` and `offline_access`, and pre-authorize the run-as user through profiles or permission sets.
- For `clientCredentials`: enable **Enable Client Credentials Flow** on the Connected App, set a run-as user in **Setup > Manage Connected Apps > Client Credentials Flow**, and select the `api` scope.
- For `oauth`: select the OAuth scopes `api refresh_token offline_access` and set the Connected App's callback URL to the value the configuration app shows under **Callback URL — register this in the Connected App**.

### Prisme.ai prerequisites

- Workspace **editor** or **owner** access on the workspace where the connector is installed, to open the configuration app and store the credentials. See [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin) for the full role list.
- For the org-wide **Add to catalog** button, the `org:owner` or `org:admin` role on your active organization. See [Before you begin](/apps-store/marketplace/connectors/declare-capability#before-you-begin).

  ## 1. Configure the connector

  Nothing to configure at the platform level. Each consuming workspace installs the Salesforce app, opens its configuration app and provides its own Connected App credentials and auth mode (see [Workspace builder](#workspace-builder-dsul)). The credentials are scoped to that workspace and are never shared across the organization.

  ## 2. Declare the capability in AI Governance

  Two paths make Salesforce discoverable as a capability, and both are documented once in the shared guide: the one-click button in [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog), and the hand-authored entry in [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance). Both point at a workspace's MCP endpoint and use the same **Scope**; pick whichever fits your governance model, and fill in the Salesforce values below.

  | Catalog field | Salesforce value |
  |---------------|------------------|
  | Where to publish from | The **Capabilities catalog** section of the configuration app, opened in the workspace that owns the credentials. It is visible only to holders of the `org:owner` or `org:admin` role. |
  | Capability type | `mcp` |
  | Entry name | `salesforce` |
  | Category | `crm` |
  | Server URL (**SSE/WebSocket URL**) | That workspace's MCP endpoint, shown in the configuration app under **MCP endpoint**. |
  | **Scope** | `context_id,agent_id,user_id`. The `agent_id` is what lets the connector identify and authorize the calling agent; it is unrelated to the Salesforce OAuth scopes. |
  | Authorization block | Added automatically in `oauth` mode only: an `oauth2` block carrying the connector's connect, status and disconnect URLs. The other three modes need none. |

  If an entry already points at that endpoint, the section shows **Already in the catalog** and the button becomes **Update catalog entry**.

  To smoke-test the published capability, ask an agent that holds it for a read-only tool call: `versions` with `action: "getLimits"`. A successful response lists the org limits, which confirms that the endpoint, the agent allowlist and the Salesforce credentials all resolve. See [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability) for the full check list.

  <Warning>
    Publishing the capability makes the connector **available**; it does not by itself authorize a specific agent ([availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization)). This connector follows the **tenant-context model**: the catalog entry points at a workspace that still owns the credentials and the **Authorized agents** allowlist. An agent that attaches the published capability must still be allowlisted in that workspace's configuration app, or that workspace must have **Allow all agents** enabled. There is no OAuth auth-config JSON to attach by hand in Governance: connect, status and disconnect are wired by the configuration app from the connector's own webhooks.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator read and act on Salesforce through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed and configured the Salesforce app in a workspace (see [Workspace builder](#workspace-builder-dsul)). Your agent is authorized two ways at once: it is identified by the `agent_id` that Agent Creator injects through the capability **Scope**, and that agent id must appear in the connector's **Authorized agents** allowlist, managed in the configuration app. The Salesforce token itself is resolved server-side from the configured auth mode and is never exposed to the agent.

    There are two ways to wire Salesforce into your agent.

    ## Option A: Attach the published capability from the catalog

    If a platform admin used the configuration app's **Add to catalog** button, or declared the capability manually, Salesforce appears in your agent's capability picker pre-wired: the MCP endpoint and the **Scope** `context_id,agent_id,user_id` are already filled in. Select it and enable it.

    <Note>
      The catalog entry points at the **workspace that published it**, and that workspace owns both the Salesforce credentials and the authorized-agents allowlist. Because this is a tenant-context connector, your agent must still be allowlisted in that publishing workspace, or that workspace must have **Allow all agents** enabled, even though the capability is shared across the organization. Ask the workspace owner to allow your agent, or use Option B to run it from your own workspace.
    </Note>

    ## Option B: Run it from your own workspace (recommended)

    <Warning>
      Running the connector from your own workspace is the security-preferred mode: the Connected App credentials, the per-user OAuth tokens and the authorized-agents allowlist are all scoped to *your* workspace. You get least-privilege isolation instead of sharing a broad organization-wide surface whose credentials and allowlist someone else controls.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), then [configure the credentials](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app). For Salesforce that means choosing one of the four auth modes and providing the Connected App credentials it asks for; [Workspace builder](#workspace-builder-dsul) lists the exact fields. In `oauth` mode, also select **Connect** and complete the Salesforce sign-in.
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's configuration app, open **Authorized agents** and tick your agent, or enable **Allow all agents (disables selection + verification)**. Ticking an agent saves the allowlist immediately. See [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).
      </Step>
      <Step title="Add the MCP capability to your agent">

      The configuration app exposes **two distinct publish buttons**. The per-agent **Install capability** button wires the connector into one specific agent and allowlists it.     ## Available tools

    The MCP server advertises itself as `salesforce-mcp`, version `1.0.0`, and negotiates MCP protocol version `2025-06-18`. Each dispatcher tool takes an `action` argument that selects the underlying Salesforce operation; only the arguments relevant to the chosen action need to be passed. Tool names and action names are case-sensitive. Omitting `action` or passing an unknown one returns an error listing the accepted values for that tool.

    ### Records and queries

    | Tool | Description |
    |------|-------------|
    | `records` | CRUD on individual records, one per call. Actions: `create`, `delete`, `get`, `getDeleted`, `getField`, `getUpdated`, `update`, `upsert`. |
    | `query` | SOQL queries, SOSL searches, parameterized search and pagination. Actions: `next`, `parameterizedSearch`, `soql`, `soqlAll`, `sosl`. |
    | `compositeRecords` | Multi-record CRUD via the `composite/sobjects` collection: up to 200 records per write, 2000 per read. Actions: `createMany`, `createManyForType`, `deleteMany`, `getMany`, `updateMany`, `upsertManyForType`. |
    | `composite` | Composite endpoints: up to 25 ordered sub-requests, batch, graph, parent and children tree insert. Actions: `batch`, `graph`, `request`, `tree`. |

    ### Discovery and metadata

    | Tool | Description |
    |------|-------------|
    | `versions` | REST API versions, available resources, org limits and recently viewed items. Actions: `getLimits`, `getRecent`, `listResources`, `listVersions`. |
    | `sobjects` | sObject metadata: global list or per-object describe. Actions: `describe`, `describeBasic`, `describeGlobal`. |

    ### Bulk API 2.0

    | Tool | Description |
    |------|-------------|
    | `bulkIngest` | Bulk API 2.0 ingest jobs (CSV insert, update, upsert, delete). Actions: `create`, `delete`, `get`, `getFailed`, `getSuccessful`, `getUnprocessed`, `list`, `update`, `uploadData`. |
    | `bulkQuery` | Bulk API 2.0 query jobs (asynchronous SOQL, CSV results). Actions: `create`, `delete`, `get`, `getResults`, `list`, `update`. |

    ### Automation and analytics

    | Tool | Description |
    |------|-------------|
    | `tooling` | Tooling API: query and CRUD on metadata objects (`ApexClass`, `CustomField`, `FlexiPage`, and so on), run Apex, code completions. Actions: `completions`, `createRecord`, `deleteRecord`, `describeGlobal`, `describeSObject`, `executeAnonymous`, `getRecord`, `query`, `runTestsAsync`, `runTestsSync`, `updateRecord`. |
    | `process` | Process rules and approval processes. Actions: `listApprovals`, `listRules`, `listRulesForObject`, `submitApproval`, `triggerRule`. |
    | `quickActions` | Global and object quick actions. Actions: `describe`, `invoke`, `list`. |
    | `analytics` | Reports and dashboards. Actions: `describeDashboard`, `describeReport`, `getDashboardStatus`, `getReportInstance`, `listDashboards`, `listReportInstances`, `listReports`, `runDashboard`, `runReport`. |
    | `metadata` | Metadata REST deploy. Actions: `deploy`, `getDeployStatus`. |

    ## How arguments are passed

    Path parameters and query parameters are always top-level arguments. Request bodies follow one of two conventions, depending on the tool:

    - **A `body` object.** `records` (`create`, `update`, `upsert`), `query` (`parameterizedSearch`), `tooling` (`createRecord`, `updateRecord`), `quickActions` (`invoke`) and `analytics` (`runReport`) accept a free-form `body` whose keys are Salesforce field API names. Field API names are case-sensitive.
    - **Named top-level fields.** `compositeRecords`, `composite`, `bulkIngest`, `bulkQuery`, `process`, `metadata` and the Apex test actions of `tooling` declare each body field as its own argument (`records`, `allOrNone`, `graphs`, `operation`, `state`, `requests`, `deployOptions`, and so on) and assemble the body server-side. These tools have no `body` argument.

    `bulkIngest` with `action: "uploadData"` is the one exception: it takes a `rawBody` string sent verbatim as `text/csv`.

    ## Output formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - `verbose` (default): human-readable text optimized for LLM consumption.
    - `structured`: concise machine-readable JSON in `structuredContent`.
    - `both`: both text and structured content.

    ## Tool details

    ### records

    CRUD on individual Salesforce records, one record per call. Pick the operation with `action`; pass record fields nested inside `body`.

    ```json
    {
      "name": "records",
      "arguments": {
        "action": "create",
        "sObjectName": "Lead",
        "body": {
          "FirstName": "Georges",
          "LastName": "Abitbol",
          "Company": "Example Industries",
          "Email": "georges.abitbol@example.com"
        }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `create`, `delete`, `get`, `getDeleted`, `getField`, `getUpdated`, `update`, `upsert`. |
    | `sObjectName` | For every action | API name of the sObject (`Account`, `Contact`, `Lead`, `Opportunity`, `My_Custom_Object__c`, and so on). |
    | `recordId` | For `get`, `getField`, `update`, `delete` | Salesforce 15-character or 18-character record ID. |
    | `body` | For `create`, `update`, `upsert` | Object whose keys are Salesforce field API names. |
    | `externalIdField`, `externalIdValue` | For `upsert` | External ID field API name and value. |
    | `fieldName` | For `getField` | API name of a single field to fetch, including blob and document bodies. |
    | `fields` | Optional, `get` only | Comma-separated list of fields to return. It is never treated as a field to write. |
    | `start`, `end` | For `getDeleted`, `getUpdated` | ISO 8601 time window. |

    ### query

    Read with SOQL (database language), SOSL (cross-object text search) or a structured parameterized search. Use `next` with a `queryLocator` returned by a previous SOQL response to page through large result sets.

    ```json
    {
      "name": "query",
      "arguments": {
        "action": "soql",
        "q": "SELECT Id, Name, AnnualRevenue FROM Account WHERE Industry = 'Technology' ORDER BY AnnualRevenue DESC LIMIT 50"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `next`, `parameterizedSearch`, `soql`, `soqlAll`, `sosl`. |
    | `q` | For `soql`, `soqlAll`, `sosl` | SOQL or SOSL string. |
    | `queryLocator` | For `next` | Locator returned by the previous SOQL call in `nextRecordsUrl`. |
    | `body` | For `parameterizedSearch` | Structured search request. |

    ### compositeRecords

    Multi-record CRUD via the `composite/sobjects` collection: up to 200 records per write call, 2000 per read, with optional `allOrNone` transactional semantics. The body fields are passed at the top level, not nested in a `body` object.

    ```json
    {
      "name": "compositeRecords",
      "arguments": {
        "action": "createManyForType",
        "sObjectName": "Contact",
        "allOrNone": true,
        "records": [
          { "attributes": { "type": "Contact" }, "FirstName": "Jean", "LastName": "Dupont", "Email": "jean.dupont@example.com" },
          { "attributes": { "type": "Contact" }, "FirstName": "Marie", "LastName": "Martin", "Email": "marie.martin@example.com" }
        ]
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `createMany`, `createManyForType`, `deleteMany`, `getMany`, `updateMany`, `upsertManyForType`. |
    | `sObjectName` | For `createManyForType`, `upsertManyForType`, `getMany` | API name of the sObject. |
    | `externalIdField` | For `upsertManyForType` | External ID field API name. |
    | `records` | For `createMany`, `createManyForType`, `updateMany`, `upsertManyForType` | Array of record objects, each carrying `attributes.type`. |
    | `allOrNone` | Optional | Transactional semantics for the write. |
    | `ids` | For `deleteMany`, `getMany` | Comma-separated record IDs. |
    | `fields` | For `getMany` | Comma-separated list of fields. |

    ### bulkIngest

    Asynchronous high-volume writes via Bulk API 2.0. The lifecycle is `create`, then `uploadData` with the CSV, then `update` with `state: "UploadComplete"`, then poll `get` until the state is `JobComplete`, then `getSuccessful` or `getFailed`. The job creation fields are passed at the top level.

    ```json
    {
      "name": "bulkIngest",
      "arguments": {
        "action": "create",
        "object": "Contact",
        "operation": "insert",
        "contentType": "CSV",
        "lineEnding": "LF"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `create`, `delete`, `get`, `getFailed`, `getSuccessful`, `getUnprocessed`, `list`, `update`, `uploadData`. |
    | `jobId` | For every action except `create` and `list` | Job ID returned by `create`. |
    | `object`, `operation` | For `create` | Target sObject API name and one of the Bulk API operations. |
    | `contentType`, `lineEnding`, `columnDelimiter`, `externalIdFieldName`, `assignmentRuleId` | Optional, `create` only | Job options. |
    | `state` | For `update` | `UploadComplete` starts processing, `Aborted` stops the job. |
    | `rawBody` | For `uploadData` | Raw CSV payload, sent as `text/csv`. |
    | `isPkChunkingEnabled`, `jobType`, `queryLocator` | Optional, `list` only | Filters. `jobType` is one of `BigObjectIngest`, `Classic`, `V2Ingest`. |

    ### analytics

    Run reports and dashboards asynchronously, then fetch the resulting instance. Reports return both the metadata and the row-level facts when `includeDetails` is `true`.

    ```json
    {
      "name": "analytics",
      "arguments": {
        "action": "runReport",
        "reportId": "00O5g00000F1234EAA",
        "includeDetails": true
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `describeDashboard`, `describeReport`, `getDashboardStatus`, `getReportInstance`, `listDashboards`, `listReportInstances`, `listReports`, `runDashboard`, `runReport`. |
    | `reportId` | For the report actions | Salesforce report ID. |
    | `dashboardId` | For the dashboard actions | Salesforce dashboard ID. |
    | `instanceId` | For `getReportInstance` | Asynchronous report instance ID. |
    | `includeDetails` | Optional | Include row-level details in the response. |
    | `body` | Optional, `runReport` only | Report metadata overrides. |

    ### tooling

    Tooling API for metadata-as-data: query and CRUD on `ApexClass`, `CustomField`, `FlexiPage`, `ValidationRule` and similar objects, plus running Apex and fetching code completions.

    ```json
    {
      "name": "tooling",
      "arguments": {
    ```

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call Salesforce operations from your automations.

    ## Installation

    Salesforce follows the standard App + MCP installation flow. Run it end to end from [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace): [install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app) by searching for **Salesforce** in **Apps**, then [configure the credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app), and finally [authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).

    Three points are specific to Salesforce:

    - Choose the auth mode from the configuration app's **Method** list and provide the Connected App credentials that mode requires, as listed in [Operating model and runtime identity](#operating-model-and-runtime-identity).
    - In `oauth` mode, register the callback URL verbatim in the Connected App before anyone selects **Connect**. The configuration app shows it under **Callback URL — register this in the Connected App**.
    - The **REST API Version** field on the app instance selects the `/services/data/` path segment. It defaults to `v62.0`.

    ## Configuration

    Installing the app provisions two workspace secrets and writes read-only values on the app instance, as described in [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions). The Salesforce-specific names and values are below. In the tables, `<api-url>` is your environment's API URL, `<studio>` its studio URL, `<workspace-slug>` and `<workspace-id>` identify the workspace, and `<app-instance>` is the slug the app was installed under.

    | Instance field | Description |
    |-------|-------------|
    | **Configuration app** (`configAppUrl`) | Read-only, auto-populated on install. Open this link to configure authentication, connect a Salesforce account, manage the authorized-agents allowlist and publish to the Capabilities catalog. Its form is `<studio>/apps/salesforce?workspaceId=<workspace-id>&workspaceSlug=<workspace-slug>&appInstance=<app-instance>`. |
    | **REST API Version** (`apiVersion`) | Salesforce REST API version, the path segment after `/services/data/`. Defaults to `v62.0`. Override it per workspace if you need a different version. |
    | `oauthCallbackUrl` | Auto-populated on install: `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance>.oauthCallback`. In `oauth` mode, register it verbatim as the Connected App's callback URL. The configuration app displays it under **Callback URL — register this in the Connected App**. |
    | MCP endpoint | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance>.mcp`. This is the URL an Agent Creator capability points at. The configuration app shows it under **MCP endpoint** with a copy button. |

    | Workspace secret | Description |
    |-------|-------------|
    | `salesforceAuth` | Object holding the auth mode and its credentials: `mode`, `loginHost`, `jwtUsername`, `oauthClientId`, `oauthClientSecret`, `jwtPrivateKey`, `scopes`, `accessToken`, `instanceUrl`. Written by the configuration app, which keeps only the fields relevant to the selected mode. |
    | `salesforceAuthorizedAgents` | Comma-separated agent IDs allowed to call the MCP endpoint, or `*` for all. Written by the configuration app. |
    | `sfnRefresh_<user-id>` | Per-user Salesforce refresh token, stored in `oauth` mode so background runs can resolve a user without an interactive session. Written only when the person who connects is a workspace editor or owner; for anyone else the write is denied and only the interactive path works. Deleted when that user selects **Disconnect**. |

    The configuration app drives authentication and the allowlist; the app instance itself exposes only the API version field. Do not edit the secrets by hand.

    <Note>
      Credentials are resolved server-side on every call and no Salesforce token is ever returned to an agent or to a Builder automation. In `jwt` mode the exchanged token is cached for 30 minutes per Connected App, run-as user and login host. In `oauth` mode the access token is cached per user and refreshed proactively 120 seconds before it expires; Salesforce does not reissue the refresh token on refresh, so the stored one is kept.
    </Note>

    <Note>
      The **Authorized agents** allowlist gates which Agent Creator agents may call the MCP endpoint; see [Agent builder](#agent-builder-agent-creator) and [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector). It does not gate Builder automations: any automation in the workspace that calls `Salesforce.<instruction>:` resolves the same workspace credentials.
    </Note>

## Verify the connection

Run these Salesforce-specific checks after configuring the connector, before wiring any write operation. They complement the generic sequences in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation) and [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability).

<Steps>
  <Step title="Validate the stored credentials">
    In the configuration app, in the `jwt`, `clientCredentials` or `accessToken` mode, select **Test connection**. The app saves the credentials, resolves the auth mode and performs a read-only call to the org limits. Success shows `Connection OK — credentials valid.` A failure shows the resolver's own message, which names the mode that failed.
  </Step>
  <Step title="Confirm the per-user connection (oauth mode)">
    In `oauth` mode, select **Connect**, complete the Salesforce sign-in in the popup, and return to the configuration app. The button becomes **Disconnect** and a confirmation line reports the connected instance URL. Selecting **Connect** again for a different user stores a separate token; connections are personal, never shared.
  </Step>
  <Step title="Run a read-only tool call from the agent">
    From an agent that has the capability, ask for the org limits. The agent calls `versions` with `action: "getLimits"` and the response lists `DailyApiRequests` and the other limits. This proves the endpoint, the agent allowlist and the Salesforce credentials all resolve together.
  </Step>
  <Step title="Check the runtime identity">
    In `oauth` mode, run `query` with `action: "soql"` and `q` set to `SELECT Id, Name, Username FROM User WHERE Id = ...`, or open the Salesforce setup audit trail, and confirm that the acting user is the person who connected, not a shared account. In the other three modes the acting user is the configured run-as or token-owning account for every caller.
  </Step>
  <Step title="Test a negative case">
    Ask an agent that is not in the **Authorized agents** allowlist to call any tool. The call must be refused with the message stating that the agent is not authorized. If it succeeds, **Allow all agents** is enabled on that workspace.
  </Step>
</Steps>

## Error handling

The connector normalizes Salesforce REST errors into these messages, where `<operation>` names the operation that failed and `<detail>` carries the Salesforce `errorCode` and message when the response provides one.

| HTTP status | Connector message | Resolution |
|-------------|-------------------|------------|
| 400 | `Bad request while <operation>: <detail>` | Malformed SOQL, invalid field API name, or a missing required field. Inspect the `errorCode` in the detail. |
| 401 | `Authentication failed while <operation>. Check Salesforce credentials.` | The access token expired or was revoked. Reconnect in `oauth` mode, or recheck the JWT or client credentials configuration. |
| 403 | `Forbidden while <operation>. Check user/CRUD permissions in Salesforce.` | The connected user's profile lacks API access or object-level and field-level permissions. |
| 404 | `Resource not found while <operation>.` | The sObject name or record ID does not exist. sObject API names are case-sensitive. |
| 429 | `Rate limit / org limit exceeded while <operation>. Wait and retry.` | The org API allocation is exhausted. Inspect usage with `versions` and `action: "getLimits"`, then back off. |
| 500 | `Salesforce server error while <operation>.` | Transient Salesforce error. Retry with exponential backoff. |
| Any other | `Error <status> while <operation>: <detail>` | Includes validation-rule failures, which Salesforce reports outside the statuses above. |

When the response carries no recognized error field, the detail is reported as `(no further detail)` rather than echoing the raw body, so credentials and provider metadata are never leaked into a tool result.

### Common issues

The agent-authorization and installation failures shared by every App + MCP connector are documented in [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting) and [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability#troubleshooting). Two of them have a Salesforce-specific twist:

**"This agent is not authorized to use this connector"**: the calling agent is not in the allowlist. Open the configuration app, go to **Authorized agents**, tick this agent (its id is shown in the error) and the allowlist saves immediately, or enable **Allow all agents (disables selection + verification)**. This applies even when the agent attached the capability from the Capabilities catalog, because the catalog entry points at a workspace that still owns the allowlist. The **Install capability** button does this for you.

**"The calling agent could not be identified, so it cannot be authorized"**: the MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the scope to `context_id,agent_id,user_id` on the capability, then allow the agent in the configuration app.

The remaining messages below are raised by the Salesforce connector itself.

**`Salesforce not authenticated. Configure the auth mode and its credentials in the connector config app.`**: no usable credentials resolved for the selected mode. In `jwt` mode this message also covers every JWT failure, including a private key that does not match the uploaded certificate, a run-as user that is not pre-authorized, and **Use digital signatures** left disabled: the underlying exchange error is not surfaced. Recheck the Connected App configuration, then use **Test connection**.

**`Salesforce is not connected for this user.`**: in `oauth` mode, no token is stored for the caller. Open the configuration app and select **Connect**, or use the agent's connect flow.

**`Salesforce token refresh failed (<status>). The user must reconnect from the config app (OAuth mode).`**: the stored refresh token was revoked or expired. The user must reconnect from the configuration app.

**`Salesforce client_credentials exchange failed (<status>). Check the Consumer Key/Secret and that the Connected App has a run-as user.`**: the client credentials grant was rejected. Confirm that **Enable Client Credentials Flow** is on and that a run-as user is set in **Setup > Manage Connected Apps**.

**`Salesforce OAuth is not configured. Set OAuth mode + Consumer Key/Secret in the config app and Save before connecting.`**: **Connect** was selected before the Consumer Key and Consumer Secret were saved. Fill both fields, select **Save authentication**, then **Connect**.

**`Forbidden — you need catalog write rights in this org.`**: the catalog write was refused. The **Capabilities catalog** section is shown only to `org:owner` and `org:admin`. Ask an organization owner or admin to publish the capability, or wire your agent from your own workspace (Option B in [Agent builder](#agent-builder-agent-creator)).

**`Forbidden — you must be a workspace admin.`**: saving a secret from the configuration app requires workspace editor or owner access on the workspace being configured.

**`invalid_state` on the OAuth callback**: the authorization response did not match the pending request, usually because the flow was restarted in another tab or the popup was reused. Close the popup and select **Connect** again.

**`redirect_uri_mismatch` at callback time**: the callback URL shown in the configuration app must be pasted verbatim into the Connected App's callback URL field, including the path. The login host must also match the org type: use `https://test.salesforce.com` for a sandbox.

**Every call fails right after configuration**: check the login host. Salesforce OAuth and API endpoints live on `login.salesforce.com`, `test.salesforce.com` or `*.my.salesforce.com`, never on the Lightning UI host. A `*.lightning.force.com` value is rewritten automatically, but any other custom host is used as-is.

  <Step title="Rotate the Connected App secret or key">
    Generate a new Consumer Secret, or a new certificate and private key pair, in Salesforce. Open the configuration app, paste the new values into the fields for the selected mode, and select **Save authentication**. In the `jwt` and `clientCredentials` modes the next call exchanges a fresh token; the previous `jwt` token stays cached for at most 30 minutes.
  </Step>
  <Step title="Disconnect one user (oauth mode)">
    The user opens the configuration app and selects **Disconnect**. The connector revokes the access token at the org's `/services/oauth2/revoke` endpoint on a best-effort basis, deletes the stored per-user token, and deletes that user's `sfnRefresh_<user-id>` workspace secret. The popup confirms **Salesforce disconnected** and closes.
  </Step>
  <Step title="Offboard a user">
    Disconnect them as above, or deactivate their Salesforce user. In the shared-credential modes, an individual offboarding has no effect: rotate the run-as account's credentials instead.
  </Step>
  <Step title="Revoke agent access">
    In the configuration app, untick the agent under **Authorized agents**, or turn off **Allow all agents**. The change applies to the next tool call. To withdraw the connector from the whole organization, delete the `salesforce` entry from the Capabilities catalog in AI Governance.
  </Step>
  <Step title="Remove the connector">
    Uninstall the Salesforce app from the workspace, then delete the `salesforceAuth`, `salesforceAuthorizedAgents` and any remaining `sfnRefresh_<user-id>` workspace secrets. Finally, delete or disable the Connected App in Salesforce, which invalidates every token the connector still holds.
  </Step>
</Steps>
