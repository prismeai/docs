The Snowflake app exposes the Snowflake SQL API and selected Snowflake REST APIs to **Agent Creator** agents through MCP and to Builder workflows through DSUL instructions. It runs in the installing workspace's tenant context: credentials are stored as workspace secrets and resolved server-side, and the MCP capability carries no API key. The connector covers SQL execution, asynchronous results, databases, schemas and virtual warehouses.

## Choose an authentication mode

Every call reaches Snowflake with one resolved credential. The mode you select decides which Snowflake identity the account sees, and therefore which privileges apply and who appears in the Snowflake query history. Pick the mode before installing anything.

| Mode | Identity Snowflake sees | Scope of the credential | Choose it when |
|------|-------------------------|-------------------------|----------------|
| `oauthCentral` | The signed-in Prisme.ai user, after they authorize Snowflake themselves | Per user, on the single Snowflake account configured by the connector maintainer | Interactive chat use on the platform-managed Snowflake account. This is the default when no mode is set. |
| `oauth` | The signed-in Prisme.ai user, after they authorize Snowflake themselves | Per user, on the workspace's own Snowflake account and OAuth client | Interactive chat use on a Snowflake account the workspace owns |
| `keyPair` | The Snowflake service user backing the key pair | Shared by every caller in the workspace | Unattended automations that must run without an interactive sign-in |
| `programmaticAccessToken` | The Snowflake user the token was issued for | Shared by every caller in the workspace | Unattended automations that need a rotatable token with a Snowflake role restriction |
| `accessToken` | The Snowflake identity encoded in the supplied token | Shared by every caller in the workspace | An OAuth or External OAuth access token minted and rotated outside Prisme.ai |

<Warning>
  `keyPair`, `programmaticAccessToken` and `accessToken` are shared service credentials. Every agent and automation allowed to reach the app instance acts as that single Snowflake user, Snowflake attributes all queries to it, and per-user attribution is lost. Restrict the backing Snowflake role to the exact objects and privileges the workspace needs, and prefer an OAuth mode whenever an agent reads or writes data on behalf of a person.
</Warning>

In both OAuth modes the connector performs an authorization-code flow with PKCE, stores the resulting access and refresh tokens per user, and refreshes the access token about two minutes before it expires. It requests the `refresh_token` scope plus a `session:role:<ROLE>` scope when a default role is configured; a role that is not made only of letters, digits, `_` or `$` is requested as `session:role-encoded:<url-encoded role>` instead.

## Prerequisites (Snowflake side)

- A **Snowflake account** and its public HTTPS account origin, for example `https://myorg-myaccount.snowflakecomputing.com`. The connector accepts only an `https://` URL whose host ends with `.snowflakecomputing.com` or `.snowflakecomputing.cn` and carries no embedded credentials. A Snowsight page URL is rejected.
- A Snowflake user or OAuth integration whose role has the privileges required by the operations you intend to expose. Use a dedicated least-privilege role rather than an account-admin role.
- One supported credential:
  - A [Snowflake OAuth custom-client integration](https://docs.snowflake.com/en/user-guide/oauth-custom) that issues refresh tokens and enforces PKCE.
  - A [key pair](https://docs.snowflake.com/en/user-guide/key-pair-auth) assigned to the Snowflake user, together with the account identifier, the user name and the public-key fingerprint.
  - A [programmatic access token](https://docs.snowflake.com/en/user-guide/programmatic-access-tokens). Snowflake requires the token owner to be covered by a network policy, and `ROLE_RESTRICTION` pins the token to one role.
  - A valid pre-minted OAuth or External OAuth access token.
- A virtual warehouse for SQL that needs compute. Database, schema and warehouse metadata operations go through the Snowflake REST resource endpoints and do not need a running warehouse.

### OAuth endpoints and redirect URIs

The connector derives the Snowflake OAuth endpoints from the account origin: `<account-url>/oauth/authorize` for authorization and `<account-url>/oauth/token-request` for token exchange and refresh. The redirect URI depends on the mode. Throughout, `<api-url>` is your environment's API URL (`https://api.studio.prisme.ai/v2` on production) and `<studio>` is your Studio URL.

| Mode | Redirect URI to register in Snowflake |
|------|----------------------------------------|
| `oauthCentral` | `<api-url>/workspaces/slug:snowflake/webhooks/oauthCallback` |
| `oauth` | `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthCallback` |

With `oauthCentral`, this is the only redirect URI to register: the core `snowflake` workspace receives the authorization code and proxies it back to the workspace that started the flow. With `oauth`, the exact value is written into the app instance configuration on install and shown by the configuration app. The two shapes are not interchangeable, and registering the wrong one is the most common failure in this flow; see [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls).

  **Goal:** configure a shared OAuth client for one Snowflake account, then expose the connector as a reusable capability in AI Governance.

  ## 1. Configure the central OAuth client

  <Steps>
    <Step title="Create a dedicated Snowflake role">
      Create a role containing only the database, schema, warehouse and SQL privileges that agents need, and grant it to the users who will authorize the connector. Snowflake OAuth cannot grant a session more privileges than the consented role holds.
    </Step>
    <Step title="Create a Snowflake OAuth security integration">
      In the target Snowflake account, create a confidential custom-client integration whose redirect URI is the core workspace callback:

      ```text
      <api-url>/workspaces/slug:snowflake/webhooks/oauthCallback
      ```

      The statement below uses the parameter names documented in the Snowflake reference for [CREATE SECURITY INTEGRATION (Snowflake OAuth)](https://docs.snowflake.com/en/sql-reference/sql/create-security-integration-oauth-snowflake). The connector always sends PKCE and authenticates the client with HTTP Basic, so a confidential client that issues refresh tokens is required.

      ```sql
      CREATE SECURITY INTEGRATION PRISME_SNOWFLAKE_OAUTH
        TYPE = OAUTH
        ENABLED = TRUE
        OAUTH_CLIENT = CUSTOM
        OAUTH_CLIENT_TYPE = CONFIDENTIAL
        OAUTH_REDIRECT_URI = '<api-url>/workspaces/slug:snowflake/webhooks/oauthCallback'
        OAUTH_ISSUE_REFRESH_TOKENS = TRUE
        OAUTH_ENFORCE_PKCE = TRUE
        ALLOWED_ROLES_LIST = ('PRISME_AGENT_ROLE');
      ```
    </Step>
    <Step title="Retrieve the OAuth client credentials">
      Run the following command with a role allowed to inspect the integration, then keep the returned secret in a secrets manager.

      ```sql
      SELECT SYSTEM$SHOW_OAUTH_CLIENT_SECRETS('PRISME_SNOWFLAKE_OAUTH');
      ```

      The result contains the client id and two rotatable client secrets.
    </Step>
    <Step title="Store the client in the core workspace">
      Open the core `snowflake` workspace configuration app at `<studio>/apps/snowflake` and enter the **Snowflake account URL**, **client id**, **client secret**, **default role** and optional **warehouse**, then save. Snowflake has no free-form scope field here: the connector derives its OAuth scopes from the default role, as described in [Choose an authentication mode](#choose-an-authentication-mode).

      The maintainer view is served only to a user holding `owner`, `editor` or `admin` on the core workspace, or the platform `superadmin` role; anyone else gets `Core workspace editor access is required.` The saved profile is written to the core workspace secret `snowflakeCentralOAuth`. Do not edit the workspace secrets by hand. See [Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client) for the full maintainer-view procedure and its role checks.
    </Step>
    <Step title="Tell workspaces to use the central client">
      Each consuming workspace selects `oauthCentral` in its connector configuration, as described in [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace). Installed workspaces receive only the account URL, client id, default role and warehouse; the client secret never leaves the core workspace, and every authorization-code and refresh exchange is proxied through the core token-service endpoint (see [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace)). The central client is tied to the Snowflake account configured above, so another account must use `oauth`, `keyPair`, `programmaticAccessToken` or `accessToken`.
    </Step>
  </Steps>

  ## 2. Declare the capability in AI Governance

  Follow [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability) for the publishing and manual paths. Snowflake needs these values:

  | Capability field | Value for Snowflake |
  |------------------|---------------------|
  | Name | **Snowflake** |
  | Server URL | The connector's **MCP Endpoint** |
  | **Scope** | `context_id,agent_id,user_id` |
  | Authorization block | None to attach by hand. There is no OAuth auth-config JSON for Snowflake in Governance. |

  `agent_id` lets the connector identify and authorize the calling agent. `user_id` keeps delegated OAuth sessions user-specific. This scope is unrelated to the Snowflake OAuth scopes; see [What the scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).

  To smoke-test, enable the capability on an agent, authorize that agent in the connector configuration app, connect a Snowflake user and run a read-only query such as `SELECT CURRENT_USER(), CURRENT_ROLE()`. Then work through [Verify the connection](#verify-the-connection).

  <Warning>
    Declaring the capability makes Snowflake available; it does not authorize an agent. A workspace-owned app instance always applies its **Authorized agents** allowlist. The core workspace endpoint behaves differently: once the central OAuth client is configured there, that endpoint accepts every calling agent and the per-user Snowflake authorization is the only gate. There is no OAuth auth-config JSON to attach in Governance. Read [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint) before publishing the core endpoint to the catalog.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an Agent Creator agent query and manage Snowflake through five MCP tools.

    <Note>

    ## Option A, Enable the shared capability from the catalog

    <Steps>
      <Step title="Open your agent">
        Open the agent in Agent Creator and go to its capabilities.
      </Step>
      <Step title="Enable Snowflake">
        Select **Snowflake** from the capability catalog. The endpoint and `context_id,agent_id,user_id` scope are already configured.
      </Step>
      <Step title="Connect to Snowflake">
        With an OAuth mode, connect on the first tool call or from the connector configuration app. Key-pair, programmatic-token and access-token modes do not need an interactive sign-in.
      </Step>
    </Steps>

    <Note>
      The shared capability runs on the platform account and OAuth client. That endpoint accepts any agent, so access is controlled entirely by each user's own Snowflake authorization; see [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint). Use a workspace-owned instance when the agent needs an isolated Snowflake account, role or credential boundary, or when you need a per-agent allowlist.
    </Note>

    ## Option B, Run it from your own workspace (recommended)

    <Warning>
      Prefer a workspace-owned instance for production. Its credentials, OAuth tokens and authorized-agent list are isolated to your workspace, and its Snowflake role can be restricted to the agent's exact duties.
    </Warning>

    <Steps>
      <Step title="Install and configure Snowflake">
        Follow [Workspace builder](#workspace-builder-dsul). Select an authentication mode and test the credential.
      </Step>
      <Step title="Allowlist the agent and attach the tool">
        In the configuration app, open **Authorized agents** and select **Install capability** on the agent's row. That single action allowlists the agent and attaches the MCP tool with the endpoint and **Scope** already set. See [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Or wire the capability by hand">
        Point the capability at this app instance's **MCP Endpoint** and set **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance). Ticking the agent in **Authorized agents** is still required.
      </Step>
      <Step title="Connect the user when using OAuth">
        Select **Connect** in the configuration app, or follow the connection prompt surfaced by Agent Creator.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    ```text
    You have access to the Snowflake MCP tools: sql, results, databases, schemas and warehouses.
    Each tool requires an `action`. Prefer read operations unless the user explicitly requests a mutation.
    Before executing DML, DDL, database/schema deletion, or warehouse resume/suspend, restate the target
    and obtain confirmation. Narrow SQL results with SELECT columns, WHERE, aggregation and deterministic
    keyset pagination; never assume an omitted result row can be recovered from MCP output.
    ```

    <Note>
      **Legacy AI Knowledge agents** without the native capability picker can add an MCP tool under **Advanced > Tools > MCP** and paste the **MCP Endpoint**. The agent must still be allowlisted and its identity propagated to the connector. See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).
    </Note>

    <Note>
      **Restricting to read-only (least privilege).** Snowflake permissions are role-based, and the connector cannot widen them. For OAuth, list only a read-only role in `ALLOWED_ROLES_LIST` on the security integration and configure that role in the connector. For a programmatic access token, set `ROLE_RESTRICTION`; for key-pair or access-token modes, restrict the backing user's grants. Reads keep working while Snowflake rejects writes, which the connector surfaces as `Forbidden while <operation>.`
    </Note>

    ## Available tools

    Each tool takes an `action` argument that selects the concrete operation.

    | Tool | Description |
    |------|-------------|
    | `sql` | Execute one SQL statement, inspect its status or cancel it. |
    | `results` | Fetch a page from an asynchronous Snowflake resource API result by opaque `result_handler`. |
    | `databases` | List, get, create, create-or-alter, undrop and delete databases. |
    | `schemas` | List, get, create, create-or-alter, undrop and delete schemas within a database. |
    | `warehouses` | List, get, create, create-or-alter, resume, suspend and delete virtual warehouses. |

    ## Response limits and truncation

    Snowflake tool calls return one bounded JSON payload in MCP text content. Over MCP the connector:

    - forces `multi_statement_count=1`, `rows_per_resultset=100` and `client_result_chunk_size=16` on SQL execution, so a single statement runs and Snowflake returns at most 100 rows;
    - clamps `showLimit` to the range 1 to 100 on every list action, whatever the schema maximum suggests;
    - caps the serialized MCP response at 80 KB, shortening long strings, then dropping trailing columns, then trailing rows until the payload fits;
    - replaces values in `BINARY` columns with `[binary value omitted by connector]`;
    - adds `_mcpLimits` and, when anything was cut, `_truncation` metadata carrying `omittedDataRecoverable: false` and a refinement suggestion.

    Statement handles, result handles and error codes are never truncated, so a follow-up `status` or `results` call always works. A provider `partition` addresses Snowflake-side partitions only; it cannot recover rows the connector omitted locally.

    The schema accepts `outputFormat` (`verbose`, `structured` or `both`) for compatibility. The Snowflake implementation returns the same bounded JSON text envelope for all three values.

    ## Tool details

    ### sql

    ```json
    {
      "name": "sql",
      "arguments": {
        "action": "execute",
        "statement": "SELECT REGION, SUM(REVENUE) AS TOTAL FROM ANALYTICS.SALES GROUP BY REGION ORDER BY TOTAL DESC",
        "warehouse": "ANALYTICS_WH",
        "role": "PRISME_AGENT_ROLE",
        "async": false
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `execute`, `status` or `cancel`. |
    | `statement` | For `execute` | One SQL statement. It may be read-only or mutating. |
    | `statementHandle` | For `status` and `cancel` | Handle returned by this connector's `execute` action. |
    | `database`, `schema`, `warehouse`, `role` | No | Case-sensitive execution context. `role` and `warehouse` fall back to the values configured on the connector. |
    | `bindings` | No | Snowflake SQL bind values. |
    | `parameters` | No | Session parameters. The MCP limits above always win. |
    | `timeout` | No | Execution timeout in seconds. |
    | `async` | No | Return a statement handle without waiting. When omitted or `false`, Snowflake returns the first result if execution completes within 45 seconds, and a statement handle otherwise. |
    | `nullable` | No | When `false`, Snowflake returns the string `null` instead of a null value. |
    | `requestId` | No | UUID that makes submission idempotent. |
    | `partition` | For additional SQL partitions | Zero-based provider partition requested by `status`. |

    ### results

    ```json
    {
      "name": "results",
      "arguments": {
        "action": "get",
        "result_handler": "opaque-result-handler",
        "page": 0
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Only `get`. |
    | `result_handler` | Yes | Opaque handle returned by an asynchronous Snowflake resource API operation. |
    | `page` | No | Zero-based result page; defaults to `0`. |

    ### databases

    ```json
    {
      "name": "databases",
      "arguments": {
        "action": "list",
        "like": "ANALYTICS_%",
        "showLimit": 25
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list`, `get`, `create`, `createOrAlter`, `undrop` or `delete`. |
    | `name` | For `get`, `createOrAlter`, `undrop` and `delete` | Case-sensitive database identifier. |
    | `body` | For `create` and `createOrAlter` | Complete Snowflake database resource definition. `createOrAlter` replaces the whole definition. |
    | `createMode` | No | `errorIfExists` (default), `orReplace` or `ifNotExists`. |
    | `kind` | No | `transient`, or the empty string for a permanent database. |
    | `like`, `startsWith`, `fromName`, `showLimit`, `history` | For `list` | Server-side filters and pagination controls. |
    | `ifExists` | For `delete` | Return success instead of an error when the database is absent. |
    | `restrict` | For `delete` | Defaults to `true` in the connector, which refuses to drop a database still referenced by foreign keys. Set it to `false` only on explicit cascading-removal intent. |

    ### schemas

    ```json
    {
      "name": "schemas",
      "arguments": {
        "action": "create",
        "database": "ANALYTICS",
        "createMode": "ifNotExists",
        "body": {
          "name": "REPORTING",
          "comment": "Curated reporting layer"
        }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list`, `get`, `create`, `createOrAlter`, `undrop` or `delete`. |
    | `database` | Yes | Parent database identifier. |
    | `name` | For `get`, `createOrAlter`, `undrop` and `delete` | Schema identifier. |
    | `body` | For `create` and `createOrAlter` | Complete Snowflake schema resource definition. |
    | `createMode` | No | `errorIfExists` (default), `orReplace` or `ifNotExists`. |
    | `kind` | No | `transient`, or the empty string for a permanent schema. |
    | `like`, `startsWith`, `fromName`, `showLimit`, `history` | For `list` | Server-side filters and pagination controls. |
    | `ifExists` | For `delete` | Return success instead of an error when the schema is absent. |
    | `restrict` | For `delete` | Defaults to `true` in the connector. Set it to `false` only on explicit cascading-removal intent. |

    ### warehouses

    ```json
    {
      "name": "warehouses",
      "arguments": {
        "action": "suspend",
        "name": "ANALYTICS_WH",
        "ifExists": true
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list`, `get`, `create`, `createOrAlter`, `resume`, `suspend` or `delete`. |
    | `name` | For every action except `list` and `create` | Warehouse identifier. |
    | `body` | For `create` and `createOrAlter` | Complete Snowflake warehouse resource definition. |
    | `createMode` | No | `errorIfExists` (default), `orReplace` or `ifNotExists`. |
    | `like` | For `list` | Case-insensitive name filter. |
    | `ifExists` | For `resume`, `suspend` and `delete` | Return success instead of an error when the warehouse is absent. |

    <Warning>
      Resuming a warehouse starts compute billing. Suspending it can interrupt workloads. Call either action only after explicit user confirmation.
    </Warning>

    ## Workspace builder

    **Goal:** install Snowflake in a workspace, configure credentials and call its operations from automations.

    ## Installation

    Snowflake follows the standard App + MCP installation flow: [install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app) by searching for **Snowflake** in **Apps**, then [configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app) and [authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector). Choose the authentication mode from [Choose an authentication mode](#choose-an-authentication-mode) before you start, and satisfy the [Snowflake-side prerequisites](#prerequisites-snowflake-side) first.

    Snowflake-specific values for that flow:

    | Item | Value for Snowflake |
    |------|---------------------|
    | Workspace secrets provisioned | `snowflakeAuth` for the mode and its credentials, `snowflakeAuthorizedAgents` for the allowlist |
    | Per-user OAuth token secret | `snfRefresh_<userId>` |
    | Capability **Scope** | `context_id,agent_id,user_id` |
    | Test connection call | `GET /api/v2/databases?showLimit=1` with the resolved credential |

    Installing writes the app instance bindings that resolve those secrets. Reinstalling or reconfiguring the app is idempotent and preserves existing values; see [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions).

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Auto-populated on install. Opens authentication, connection testing and the authorized-agent allowlist. |

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | `oauthCentral` | Connect a user; optional role and warehouse | A platform-managed OAuth client tied to the configured Snowflake account. Applied when no mode is set. |
    | `oauth` | Account URL, OAuth client id and secret, optional role and warehouse; then connect | A workspace-owned Snowflake OAuth integration |
    | `keyPair` | Account URL, account identifier, username, public-key fingerprint, PEM private key, optional passphrase, role and warehouse | Non-interactive service users with key-pair authentication |
    | `programmaticAccessToken` | Account URL, programmatic access token, optional role and warehouse | Rotatable non-interactive access with a Snowflake role restriction |
    | `accessToken` | Account URL, pre-minted token, optional role and warehouse | Caller-managed OAuth or External OAuth tokens |

    <Note>
      Credentials and the allowlist are stored as workspace secrets and resolved server-side. Each request carries the resolved bearer token plus the `X-Snowflake-Authorization-Token-Type` header set to `OAUTH`, `KEYPAIR_JWT` or `PROGRAMMATIC_ACCESS_TOKEN`. In `keyPair` mode the connector signs a fresh RS256 JWT valid for 59 minutes on every call, so no key material is sent to Snowflake.
    </Note>

    ## Available instructions

    Every instruction resolves credentials from the workspace configuration and returns the raw Snowflake API payload. `role` and `warehouse` default to the values configured on the connector when the call does not set them.

    ### SQL and asynchronous results

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `submitStatement` | Submit a statement; `statement` is required and the execution context is optional. `multi_statement_count` defaults to `1` and can be overridden through `parameters` in App mode. | A SQL API ResultSet (`data`, `resultSetMetaData`, `statementHandle`) or QueryStatus for asynchronous work. |
    | `getStatementStatus` | Check execution and fetch a result partition by `statementHandle`; optional `partition` is zero-based. | A ResultSet when complete or QueryStatus while running. |
    | `cancelStatement` | Cancel a running statement by `statementHandle`; optional `requestId` identifies the request. | Snowflake cancellation status. |
    | `fetchResult` | Fetch page `page` from a resource API asynchronous `result_handler`. | The raw result page and its provider pagination metadata. |

## Verify the connection

Run these checks after configuring the connector and before letting an agent write to Snowflake. Each one is independent of the setup screens. They are the Snowflake instances of the generic checks in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation); run that page's non-allowlisted-agent check as well, and [Verify the central client](/apps-store/marketplace/connectors/central-oauth#verify-the-central-client) when using `oauthCentral`.

<Steps>
  <Step title="Test the stored credential">
    In the configuration app, run the connection test. It performs `GET /api/v2/databases?showLimit=1` with the resolved credential and returns the normalized account origin on success. A failure reports the HTTP status without echoing the credential.
  </Step>
  <Step title="Confirm the runtime identity">
    Call the `sql` tool with `action: execute` and the statement `SELECT CURRENT_USER(), CURRENT_ROLE(), CURRENT_ACCOUNT()`, or run the same statement through `Snowflake.submitStatement`. In an OAuth mode the result must name the signed-in user; in `keyPair`, `programmaticAccessToken` and `accessToken` modes it names the shared service user that every query in the workspace will be attributed to.
  </Step>
  <Step title="Run a read-only listing">
    Call `databases` with `action: list` and `showLimit: 5`. Only databases visible to the resolved role are returned.
  </Step>
  <Step title="Check that unauthorized access is blocked">
    Call `databases` with `action: get` on a database the role must not see. The call fails with `Resource not found while fetchDatabase.` or `Forbidden while fetchDatabase.` instead of returning data.
  </Step>
  <Step title="Check the write path last">
    Only once the reads behave as expected, create a throwaway schema with `schemas` `create` and `createMode: ifNotExists`, confirm it appears in Snowflake, then remove it with `schemas` `delete`. If the connector is scoped read-only, Snowflake rejects the write and the tool returns `Forbidden while createSchema.`
  </Step>
</Steps>

## Revoke, rotate and remove

The generic lifecycle is documented in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall) and, for the platform client, in [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client). Snowflake differs on these points:

- **Disconnect one user.** From the configuration app, disconnect. The connector deletes that user's stored access and refresh tokens and the workspace-scoped copy of the refresh token. Snowflake exposes no generic token-revocation endpoint to the connector, so provider-side revocation must be done in Snowflake, for example by removing the user's role grants or by disabling the security integration.
- **Offboard a user.** Disconnect them before their Prisme.ai account is removed. Their refresh token is stored under a workspace secret named `snfRefresh_<userId>`, which the disconnect flow deletes.
- **Force a reconnection.** Changing the account URL, the OAuth client id or the default role invalidates every cached delegated token. The next call fails with `Snowflake OAuth settings changed. Reconnect to authorize the new account, client, or role.` and each user reconnects once.
- **Plan for refresh-token expiry.** Snowflake refresh tokens live for `OAUTH_REFRESH_TOKEN_VALIDITY` seconds, which the [Snowflake security integration reference](https://docs.snowflake.com/en/sql-reference/sql/create-security-integration-oauth-snowflake) documents as 90 days by default and at most. Users must reconnect at least that often.
- **Rotate the central client secret.** Generate a new secret in Snowflake, then re-enter the client id and secret in the maintainer view of the configuration app. Every token exchange uses the stored secret, so refreshes fail until the stored value matches the one Snowflake expects.
- **Rotate a key pair, programmatic access token or access token.** Replace the value in the configuration app. No user re-consent is required because these modes have no per-user connection.
- **Revoke an agent's access.** Untick the agent in **Authorized agents**, or clear **Allow all agents**. The next call is rejected with `This agent is not authorized to use this connector.`
- **Uninstall.** Remove the app instance from the workspace. Uninstalling does not delete the workspace secrets the install flow provisioned (`snowflakeAuth`, `snowflakeAuthorizedAgents`) or the per-user `snfRefresh_<userId>` secrets; delete them from the workspace secrets to purge the stored credentials.

## Error Handling

Snowflake responses are normalized into one message per status, carrying the failing operation name and a compact detail extracted from the provider body (`code`, `message` and `request_id`, or `error` and `error_description` on the token endpoints). An unrecognized body is reported as `(no further detail)` rather than dumped, so credentials are never echoed back.

| HTTP code | Returned message |
|-----------|------------------|
| `400` | `Bad request while <operation>: <detail>` Invalid SQL, identifier, request body or OAuth request. |
| `401` | `Authentication failed while <operation>. Check Snowflake credentials.` The connector first retries once with a freshly refreshed token. |
| `403` | `Forbidden while <operation>. Check the active Snowflake role and object privileges.` Also returned when a network policy rejects the request. |
| `404` | `Resource not found while <operation>.` The statement, database, schema, warehouse or result handle does not exist or is not visible to the role. |
| `429` | `Rate limit / org limit exceeded while <operation>. Wait and retry.` Marked transient. |
| `500`, `503`, `504` | `Snowflake server error while <operation>.` `503` and `504` are marked transient. |
| Other | `Error <status> while <operation>: <detail>` |

### Common Issues

Install, allowlist and capability failures that are not specific to Snowflake are covered in [Install troubleshooting](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting), [Central OAuth troubleshooting](/apps-store/marketplace/connectors/central-oauth#troubleshooting) and [Capability troubleshooting](/apps-store/marketplace/connectors/declare-capability#troubleshooting).

**"This agent is not authorized to use this connector."**: The calling agent is not in the allowlist. Open the configuration app, go to **Authorized agents**, tick this agent and save, or enable **Allow all agents**. The **Install capability** button does this for you.

**"The calling agent could not be identified, so it cannot be authorized."**: The MCP capability *Scope* does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability, then allow the agent in the configuration app.

**"Snowflake OAuth is not connected for this user."**: No per-user token is stored. Open the connector configuration and select **Connect**, or follow the connection prompt surfaced by Agent Creator.

**"Snowflake rejected the OAuth refresh token. Reconnect from the connector configuration."**: The refresh token expired or was revoked. The stored connection is dropped automatically and the user must reconnect.

**"Snowflake OAuth settings changed. Reconnect to authorize the new account, client, or role."**: The configured account URL, OAuth client id or role no longer matches the cached token. Reconnect once to authorize the new combination.

**"Snowflake OAuth token endpoint is temporarily unavailable (status …). Retry shortly."**: The Snowflake token endpoint returned a `5xx`. This is transient and requires no reconnection.

**"Snowflake platform OAuth is not configured for an account."**: No central client is available. Ask the connector maintainer to configure it in the core workspace, or select `oauth`, `keyPair`, `programmaticAccessToken` or `accessToken`.

**"Snowflake authentication is incomplete. Configure all required fields in the connector configuration app."**: The selected mode is missing a required credential field, for example a programmatic access token or an access token that was never stored.

**"Invalid Snowflake account URL. Use https://organization-account.snowflakecomputing.com."**: The account URL is not an `https://` origin on `snowflakecomputing.com` or `snowflakecomputing.cn`, or it carries embedded credentials. Enter the bare account origin, not a Snowsight page URL.

**"Snowflake key-pair JWT generation failed: …"**: The account identifier, username, public-key fingerprint or PEM private key is missing or unusable. The connector uppercases the account identifier and username, replaces dots in the account identifier with dashes, and prefixes the fingerprint with `SHA256:` when absent; supply the passphrase when the key is encrypted.

**"Core workspace editor access is required."**: The maintainer view of the configuration app was opened without `owner`, `editor` or `admin` on the core workspace or the platform `superadmin` role.

**SQL output is truncated**: MCP responses are limited to 100 rows and 80 KB. Narrow the query with selected columns, `WHERE`, aggregation and deterministic keyset pagination. A provider `partition` cannot recover rows omitted locally by the connector.
