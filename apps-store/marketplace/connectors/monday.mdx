The monday.com connector exposes the [monday.com API v2](https://developer.monday.com/api-reference) (a single GraphQL endpoint) to **Agent Creator** agents through MCP, and to Builder automations through `Monday.<operation>` App instructions. It covers boards, items and subitems, columns, groups, workspaces, updates, docs, folders, tags, assets, webhooks, notifications, users, teams and account diagnostics. The 78 monday.com operations are grouped into **15 entity tools**, each driven by an `action` argument. The MCP server runs in the **tenant app-instance context**: it resolves the installing workspace's own credentials and authorizes the calling agent against that workspace's allowlist. Authentication supports three modes:

- **Per-user OAuth2, central client** (`oauthCentral`, recommended): one monday.com OAuth application is registered once by the platform maintainer; every end user signs in with their own monday.com account. Nothing to register per workspace: each one just installs the app and selects **Connect**.
- **Per-user OAuth2, tenant client** (`oauth`): you store your own monday.com OAuth client ID and secret in the connector configuration app. Each user signs in with their own account against your client (authorization code plus PKCE flow).
- **API token** (`accessToken`): a caller-managed monday.com API token (v2), used as-is with no exchange. One identity acts for the whole workspace.

## Which identity does monday.com see?

Pick the authentication mode from the runtime identity you need, not from setup convenience.

| Mode | monday.com sees | Permissions come from | Best for | Blast radius |
|------|-----------------|-----------------------|----------|--------------|
| `oauthCentral` | The individual end user who connected | That user's own monday.com account | Chat agents acting on behalf of a person, on a platform where the maintainer registered the central client | One user at a time; each user consents and can disconnect |
| `oauth` | The individual end user who connected | That user's own monday.com account | The same, when you want to own the monday.com OAuth application yourself | One user at a time, against your own client |
| `accessToken` | The owner of the stored API token | That single account's monday.com permissions | Builder automations and unattended jobs where one service identity is intentional | Every caller in the workspace acts as that one account |

<Warning>
  In `accessToken` mode every agent and every automation in the workspace acts as the same monday.com account, and monday.com attributes every board change, update and notification to that account. Use a dedicated monday.com service account with the minimum board and workspace access it needs, never a personal admin account.
</Warning>

If no mode is stored, the connector behaves as `oauth`: it uses the tenant OAuth client when a client ID and secret are stored, and otherwise falls back to the central platform client. Selecting `oauthCentral` explicitly ignores any tenant client fields and always resolves the central client.

## Prerequisites

- A **monday.com** account.
- For the **OAuth modes**: a **monday.com OAuth application** created at [monday.com/developers/apps](https://monday.com/developers/apps); copy its **Client ID** and **Client Secret**. The platform maintainer registers one application for the central mode; a workspace can also register its own for the tenant mode.
- For the **`accessToken` mode**: a **monday.com API token (v2)**, generated from the monday.com [authentication settings](https://developer.monday.com/api-reference/docs/authentication). monday.com expects the raw token as the `Authorization` header value, with **no `Bearer` prefix**, so paste the token exactly as monday.com issued it and do not prepend anything.
- To install the connector in a workspace: the `owner`, `editor` or `admin` role on that Builder workspace, as described in [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin).
- To configure the central client: the **owner**, **editor** or **admin** role on the core `monday` workspace, or the platform `superadmin` role.
- The default OAuth scopes requested by the connector are:

  ```text
  boards:read boards:write docs:read docs:write updates:read updates:write users:read users:write workspaces:read workspaces:write webhooks:read webhooks:write assets:read notifications:write me:read account:read teams:read tags:read
  ```

- Endpoints used by the connector: `https://api.monday.com/v2` for the GraphQL API (sent with the `API-Version: 2024-10` header), `https://auth.monday.com/oauth2/authorize` and `https://auth.monday.com/oauth2/token` for OAuth. monday.com is single-host, so there is no per-tenant base URL to configure.

## Platform admin setup

**Goal:** two one-time tasks: (1) configure the shared **central OAuth client** so every workspace lets its users sign in with their own monday.com account, and (2) optionally expose monday.com as a reusable **capability** in AI Governance so agent builders can pick it without pasting endpoint URLs. Throughout, `<api-url>` is your environment's API URL (`https://api.studio.prisme.ai/v2` on production) and `<studio-url>` is your Studio URL (`https://studio.prisme.ai` on production).

### Configure the central OAuth client

The procedure is the standard one: [Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client). These are the monday.com values it asks for.

| Value | For monday.com |
|-------|----------------|
| Provider console | [monday.com/developers/apps](https://monday.com/developers/apps), create an OAuth application. The **Client Secret** is shown only once |
| Connector slug (core workspace) | `monday` |
| Core redirect URI to register | `<api-url>/workspaces/slug:monday/webhooks/oauthCallback`, for example `https://api.studio.prisme.ai/v2/workspaces/slug:monday/webhooks/oauthCallback` on production |
| Scopes to grant | The default list in [Prerequisites](#prerequisites) |
| Maintainer view URL | `<studio-url>/apps/monday`, opened from the core `monday` workspace |
| Core workspace secret written | `mondayCentralOAuth` |
| Auth mode workspaces then select | `oauthCentral`, with no client ID or secret on their side |

Register only the core redirect URI above for the central client; the per-instance URI has a different shape and is not interchangeable. See [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls).

The monday.com client secret never leaves the core `monday` workspace: tenant instances resolve only the public client ID and scopes through the core `getOAuthClientPublic` webhook, and every token exchange is proxied through the core `centralTokenExchange` webhook. See [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace).

From the same maintainer view, **Add to catalog** publishes monday.com to the organization-wide **Capabilities catalog**, as described in [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog). Agent builders then pick it up through [Option A](#agent-builder-agent-creator).

### Declare the capability in AI Governance

As an alternative to (or in addition to) the catalog button, declare monday.com as a named **capability** in AI Governance, following [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance). Two values are monday.com-specific:

- **MCP server URL**: the app instance's own `mcp` webhook.

  ```text
  <api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.mcp
  ```

- **Scope**: `context_id,agent_id,user_id`. This connector does not consume chat attachments, so it needs no `attachment_urls`. The `agent_id` part is what lets the connector identify and authorize the calling agent, and it is unrelated to the monday.com OAuth scopes. See [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).

To smoke-test the result: from an agent that has the capability, in a workspace configured for `oauthCentral`, call the `users` tool with `action: "me"`. The user is prompted to connect once through monday.com sign-in; subsequent calls reuse the stored token and refresh it automatically. A successful response contains the connected user's monday.com id, name and account.

<Warning>
  Declaring the capability makes the connector **available**; it does not by itself authorize a specific agent. This connector follows the **tenant-context model**: which agents may actually call a tenant instance is gated per workspace by the **authorized agents** allowlist in the configuration app (see [Workspace builder](#workspace-builder-dsul)). There is no OAuth auth-config JSON to attach in Governance: connect, status and disconnect are handled by the connector's own webhooks, wired automatically on install. See [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization).
</Warning>

<Note>
  The core `monday` workspace behaves differently from tenant instances. When the central OAuth client is configured there, its own MCP endpoint accepts **every** calling agent, because per-user OAuth consent is the access gate on that shared endpoint. The per-agent allowlist only applies to instances installed in a tenant workspace. See [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint).
</Note>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator use monday.com through MCP tools.

    <Note>
      Before an agent can call a tenant instance of the connector, a workspace builder must have installed and configured the monday.com app in a workspace (see [Workspace builder](#workspace-builder-dsul)), and, for the central OAuth mode, a platform admin must have provisioned the shared OAuth client (see [Platform admin setup](#platform-admin-setup)).
    </Note>

    On a tenant instance, your agent is authorized two ways at once: it is identified by the `agent_id` that Agent Creator injects through the capability **Scope**, and that agent must appear in the connector's **authorized agents** allowlist (managed in the configuration app). The monday.com access token itself is resolved server-side from the configured auth mode, so the agent never handles credentials.

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A: enable the shared capability from the catalog

    The fastest path: a platform admin has already published a **monday.com** capability to the Capabilities catalog (see [Platform admin setup](#platform-admin-setup)), so you pick it from the catalog. Open your agent in Agent Creator, go to its capabilities, and select **monday.com**. The MCP endpoint URL and the **Scope** (`context_id,agent_id,user_id`) are already wired by the admin, and the shared core instance accepts every agent, so there is no allowlist step on your side.

    On the first tool call, an unconnected user is prompted to sign in: Agent Creator surfaces a `connect_url` pointing at the connector's `oauthConnect` webhook, which redirects to monday.com's authorization page. After sign-in the per-user token is stored and reused on subsequent calls.

    <Note>
      This is convenient, but your agent runs against a **shared, platform-managed instance** whose monday.com OAuth client is owned by someone else and which accepts every agent granted the capability. Prefer Option B for anything beyond quick experiments. The reason that shared endpoint accepts every agent is explained in [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint).
    </Note>

    ## Option B: run it from your own workspace (recommended)

    For production agents, install the connector in **your own workspace** and point the agent at that workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP server runs in your app-instance context, the monday.com credentials, the per-user OAuth tokens and the authorized agents allowlist are all scoped to your workspace, not shared platform-wide. You decide exactly which agents may call it and which monday.com account or auth mode backs them. The shared catalog capability (Option A) is a broad surface many agents can reach; your own workspace is an isolated, least-privilege boundary.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder](#workspace-builder-dsul): install **monday.com** in your workspace, open its configuration app, choose the auth mode and connect a monday.com account (or store an API token).
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's configuration app, open **Authorized agents** and select your agent, or enable **Allow all agents**. The **Install capability** button allowlists the agent and attaches the tool in one action: [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Add the MCP capability to your agent">
        If you wired it by hand instead, add a capability on your agent pointing at your workspace's MCP endpoint:

        ```text
        <api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.mcp
        ```

        Set its **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        The `agent_id` is what lets the connector identify and authorize your agent. Without it, every call is rejected with an explicit "could not be identified" message. This **Scope** is separate from the monday.com OAuth scopes.
      </Step>
      <Step title="Connect a monday.com account">
        On the first tool call, the user is prompted to sign in, or uses **Connect** in the configuration app. The per-user token is stored in user scope and refreshed automatically.
      </Step>
      <Step title="Verify the wiring">
        Ask the agent to list your monday.com boards. The `boards` tool with `action: "list"` returns board ids and names, which confirms agent authorization, credential resolution and API access in one call. Run the rest of [Verify the setup](#verify-the-setup) before letting the agent write anything.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent also needs to know the tools exist and when to reach for them. Copy this starter and adapt it:

    ```text
    You have access to the monday.com MCP server. Use it whenever the user asks about monday.com content: boards, groups, items, subitems, columns (status, person, date, and so on), updates, docs or users. Every tool takes a required `action` argument, for example the `items` tool with action "page" to list items, or action "create" to add one. monday.com ids are numeric strings, so list the parent (boards, then columns, groups or items) before acting on it rather than guessing ids. Confirm with the user before any destructive action such as deleting an item, archiving a board, or changing workspace membership.
    ```

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced**, **Tools**, **MCP** and paste the MCP endpoint URL. The agent still has to be allowlisted in the configuration app, and its identity must be propagated so the connector can read its `agent_id`.
    </Note>

    <Note>
      **Restricting to read-only access.** monday.com tools cover both reads and writes. The granted OAuth scopes are the enforcement point. To allow only read access, set the scopes in the configuration app to the read-only set, dropping every `:write` scope:

      ```text
      boards:read docs:read updates:read users:read workspaces:read webhooks:read assets:read me:read account:read teams:read tags:read
      ```

      With `oauthCentral` you do not create your own monday.com application; keep `oauthCentral` and enter the read scopes. The tenant scope string overrides the central default, and the central application must itself list those read scopes. GraphQL mutations are then rejected by monday.com with a permission error. Scopes are set at the workspace level, so a workspace editor can widen them again. Users must reconnect for a scope change to take effect.
    </Note>

    ## Available tools

    The MCP server exposes 15 entity-level tools. Every tool requires an `action` argument selecting the operation, and accepts an `outputFormat` argument (see [Output formats](#output-formats)). monday.com ids are numeric strings, so list the parent resource first to obtain them. List actions accept `limit` (default `25`) and `page` (default `1`) unless stated otherwise.

    ### `boards`

    | Action | Description |
    |--------|-------------|
    | `list` | List boards, optionally filtered by `ids`, `workspace_ids`, `state`, `order_by`, `board_kind` |
    | `get` | Get a single board by `id`, with its groups, columns and first page of items |
    | `create` | Create a board (`board_name` and `board_kind` required) |
    | `update` | Change one `board_attribute` (`name`, `description`, `communication`) to `new_value` |
    | `duplicate` | Duplicate a board by `duplicate_type` |
    | `archive` | Archive a board by `board_id` |
    | `delete` | Delete a board by `board_id` |
    | `views` | List the views configured on `board_id` |
    | `tags` | List the tags of a private or shareable `board_id` |

    ### `items`

    | Action | Description |
    |--------|-------------|
    | `page` | Cursor-paginated items of `board_ids`, with optional `query_params` rules |
    | `pageByColumnValues` | Cursor-paginated items of `board_id` filtered by `columns` |
    | `get` | Fetch items by `ids` (up to 100) |
    | `create` | Create an item (`board_id` and `item_name` required) |
    | `createSubitem` | Create a subitem under `parent_item_id` |
    | `duplicate` | Duplicate `item_id` on `board_id`, optionally `with_updates` |
    | `moveToGroup` | Move `item_id` to `group_id` on the same board |
    | `moveToBoard` | Move `item_id` to another `board_id` and `group_id`, mapping columns |
    | `archive` | Archive `item_id` |
    | `delete` | Delete `item_id` |
    | `clearUpdates` | Remove every update posted on `item_id` |

    ### `columns`

    | Action | Description |
    |--------|-------------|
    | `list` | List the columns of `board_id` with their types and JSON settings |
    | `create` | Create a column (`board_id`, `title` and `column_type` required; 37 column types) |
    | `changeTitle` | Rename a column (`board_id`, `column_id`, `title`) |
    | `changeMetadata` | Change a `column_property` (`title` or `description`) to `value` |
    | `delete` | Delete `column_id` from `board_id` |
    | `changeValue` | Set one column value from a typed JSON `value` |
    | `changeSimpleValue` | Set one column value from a plain string `value` |
    | `changeMultipleValues` | Set several columns at once from a `column_values` map |

    ### `groups`

    | Action | Description |
    |--------|-------------|
    | `list` | List the groups of `board_ids` |
    | `create` | Create a group (`board_id`, `group_name`) |
    | `update` | Change one `group_attribute` (`title`, `color`, `position`, `relative_position_after`, `relative_position_before`) to `new_value` |
    | `duplicate` | Duplicate `group_id`, optionally `add_to_top` with a new `group_title` |
    | `archive` | Archive `group_id` |
    | `delete` | Delete `group_id` |

    ### `users`

    | Action | Description |
    |--------|-------------|
    | `list` | List account users, filtered by `ids`, `emails`, `name`, `kind` (`all`, `non_guests`, `guests`, `non_pending`) |
    | `me` | Return the user whose token backs the call |
    | `invite` | Invite users by `emails`, with an optional `user_role` and `product` |
    | `deactivate` | Deactivate `user_ids` |

    ### `teams`

    | Action | Description |
    |--------|-------------|
    | `list` | List teams, optionally filtered by `ids` |
    | `addUsers` | Add `user_ids` to `team_id` |
    | `removeUsers` | Remove `user_ids` from `team_id` |

    ### `workspaces`

    | Action | Description |
    |--------|-------------|
    | `list` | List workspaces, optionally filtered by `ids`, `kind` (`open`, `closed`), `state` |
    | `create` | Create a workspace (`name` and `kind` required) |
    | `update` | Update workspace `attributes` (`name`, `kind`, `description`) of `id` |
    | `delete` | Delete `workspace_id` |
    | `addUsers` | Add `user_ids` to `workspace_id` |
    | `removeUsers` | Remove `user_ids` from `workspace_id` |

    ### `updates`

    | Action | Description |
    |--------|-------------|
    | `list` | List updates across the account, paginated |
    | `forItem` | List the updates attached to `item_id` |
    | `create` | Post an update on `item_id` (`body` required, optional `parent_id` to reply) |
    | `edit` | Change the `body` of the update `id` |
    | `delete` | Delete the update `id` |
    | `pin` | Pin the update `id` to the top |
    | `unpin` | Unpin the update `id` |
    | `like` | Like `update_id` |
    | `unlike` | Remove your like from `update_id` |

    ### `docs`

    | Action | Description |
    |--------|-------------|
    | `list` | List docs, filtered by `ids`, `object_ids`, `workspace_ids` |
    | `blocks` | List the ordered blocks of `doc_id` |
    | `create` | Create a doc through `location` (workspace-level or attached to an item column) |
    | `createBlock` | Add a block to `doc_id` (`type` and `content` required; 16 block types) |
    | `updateBlock` | Replace the `content` of `block_id` |
    | `deleteBlock` | Delete `block_id` |

    ### `folders`

    | Action | Description |
    |--------|-------------|
    | `list` | List folders, filtered by `ids` and `workspace_ids` |
    | `create` | Create a folder in `workspace_id` (`name` required, optional `color` and `parent_folder_id`) |
    | `update` | Rename, recolor or reparent `folder_id` |
    | `delete` | Delete `folder_id`; its contents move to the workspace root |

    ### `webhooks`

    | Action | Description |
    |--------|-------------|
    | `list` | List the webhooks registered on `board_id`, optionally `app_webhooks_only` |
    | `create` | Subscribe `url` to an `event` on `board_id`, with `config` for column-specific or group-specific events |
    | `delete` | Delete the webhook `id` |

    ### `tags`

    | Action | Description |
    |--------|-------------|
    | `list` | List the public tags of the account, optionally filtered by `ids` |
    | `createOrGet` | Create the public tag `tag_name`, or return the existing one; pass `board_id` for a private or shareable board |

    ### `assets`

    | Action | Description |
    |--------|-------------|
    | `get` | Fetch file assets by `ids`, returning name, URL, public URL, extension, size and uploader |

    ### `notifications`

    | Action | Description |
    |--------|-------------|
    | `create` | Send an in-app notification to `user_id` about `target_id`, with `text` and a `target_type` of `Project` or `Post` |

    ### `account`

    | Action | Description |
    |--------|-------------|
    | `get` | Account metadata: name, slug, country code, active member count, tier and plan |
    | `products` | Products enabled on the account |
    | `activityLogs` | Activity log of `board_ids`, filtered by `from`, `to`, `user_ids`, `column_ids`, `group_ids`, `item_ids` (`limit` defaults to `100`) |
    | `complexity` | Remaining monday.com complexity budget and `reset_in_x_seconds` |
    | `version` | The monday.com API version served for these calls |

    ## Output formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - `verbose` (default): human-readable text optimized for LLM consumption.
    - `structured`: machine-readable JSON in `structuredContent`.
    - `both`: both text and structured content.

    ## Tool details

    ### `items` with action `create`

    ```json
    {
      "name": "items",
      "arguments": {
        "action": "create",
        "board_id": "1234567890",
        "item_name": "Ship onboarding revamp",
        "group_id": "topics",
        "column_values": {
          "status": { "label": "Working on it" },
          "date": { "date": "2026-05-15" }
        },
        "create_labels_if_missing": true
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `create` |
    | `board_id` | Yes | Existing board id (numeric string). Call the `boards` tool first |
    | `item_name` | Yes | Name of the new item |
    | `group_id` | No | Target group id (call the `groups` tool first) |
    | `column_values` | No | Map of `column_id` to value; the payload shape depends on the column type |
    | `create_labels_if_missing` | No | Auto-create missing `status` and `dropdown` labels. Defaults to `false` |
    | `position_relative_method` | No | `before_at` or `after_at`, used with `relative_to` |

    ### `items` with action `pageByColumnValues`

    Filter board items by column values server-side.

    ```json
    {
      "name": "items",
      "arguments": {
        "action": "pageByColumnValues",
        "board_id": "1234567890",
        "columns": [
          { "column_id": "status", "column_values": ["Done"] },
          { "column_id": "person", "column_values": ["alice@example.com"] }
        ],
        "limit": 50
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `pageByColumnValues` |
    | `board_id` | Yes | Board to query |
    | `columns` | Yes | Array of `{ column_id, column_values }` filters |
    | `cursor` | No | Pagination cursor returned by a previous page |
    | `limit` | No | Page size. Defaults to `25` |

    ### `columns` with action `changeValue` or `changeSimpleValue`

    - `changeValue` takes a **typed JSON payload** in `value`, for example `{"label": "Done"}` for a `status` column or `{"date": "2026-05-15"}` for a `date` column.
    - `changeSimpleValue` takes a **plain string** in `value` and lets monday.com infer the format, for example `Done` or `2026-05-15`.

    Use the typed variant when you need precise control, for example a people column with `{"personsAndTeams":[{"id":123,"kind":"person"}]}`.

    ```json
    {
      "name": "columns",
      "arguments": {
        "action": "changeSimpleValue",
        "board_id": "1234567890",
        "item_id": "9876543210",
        "column_id": "status",
        "value": "Done"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `changeValue` or `changeSimpleValue` |
    | `board_id` | Yes | Board the item belongs to |
    | `column_id` | Yes | Column to update |
    | `value` | Yes | Plain string for `changeSimpleValue`, typed JSON for `changeValue` |
    | `item_id` | No | Target item id |
    | `create_labels_if_missing` | No | Auto-create missing labels. Defaults to `false` |

    ### `notifications` with action `create`

    ```json
    {
      "name": "notifications",
      "arguments": {
        "action": "create",
        "user_id": "987",
        "target_id": "1234567890",
        "text": "Staging is ready for review",
        "target_type": "Project"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `create` |
    | `user_id` | Yes | Recipient user id (call the `users` tool first) |
    | `target_id` | Yes | Item or board id the notification points to |
    | `text` | Yes | Notification text |
    | `target_type` | Yes | `Project` for boards and items, `Post` for updates |

    ### `docs` with action `create`

    ```json
    {
      "name": "docs",
      "arguments": {
        "action": "create",
        "location": {
          "workspace": {
            "workspace_id": "42",
            "name": "Release notes",
            "kind": "private",
            "folder_id": "99"
          }
        }
      }
    }
    ```

    To attach a doc to a doc-type column of an existing item, use `location.board` instead:

    ```json
    { "location": { "board": { "item_id": "1234567890", "column_id": "doc_column" } } }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `create` |
    | `location` | Yes | Exactly one of `workspace` (requires `workspace_id`, `name`, `kind`) or `board` (requires `item_id`, `column_id`) |

    <Note>
      The connector keeps only the branch of `location` that carries its required id, so passing both `workspace` and `board` is not a supported way to create two docs.
    </Note>

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call monday.com operations from your automations.

    ## Installation

    monday.com follows the standard App + MCP installation flow. Run it once, then come back here for the monday.com-specific values:

    1. [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app): search for **monday.com** in **Apps** and install it.
    2. [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app): choose one of the three monday.com auth modes below, enter its credentials, and connect a monday.com account in the OAuth modes.
    3. [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector): select the agents in **Authorized agents**, or enable **Allow all agents**.
    4. [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint) and hand it to the agent builder with the **Scope** value `context_id,agent_id,user_id`.
    5. [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation), then run the monday.com checks in [Verify the setup](#verify-the-setup).

    <Warning>
      Enter monday.com credentials only through the configuration app. Writing `mondayAuth` or `mondayAuthorizedAgents` by hand in Studio **Secrets** leaves the connector reading an unresolved binding, which fails closed. An allowlist value that still contains `{{` is treated as empty and every call is denied.
    </Warning>

    ## Configuration

    The app instance exposes a single configuration field; everything else is driven from the configuration app.

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Read-only, populated on install. Open this link to configure authentication (mode and credentials), connect a monday.com account for the OAuth modes, and manage the authorized agents allowlist. Its URL has the form `<studio-url>/apps/monday?workspaceId=<workspace-id>&workspaceSlug=<workspace-slug>&appInstance=<app-instance-slug>` |

    From the configuration app you pick one of:

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | `oauthCentral` | Nothing; select **Connect**, as described in [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace) | Workspaces on a platform where the maintainer set up the central monday.com client |
    | `oauth` | Your own monday.com **Client ID** and **Client Secret**. The redirect URI to register at monday.com is `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthCallback` | You manage your own monday.com OAuth application |
    | `accessToken` | A monday.com **API token (v2)** | Builder automations and shared service accounts where one identity acts for the whole workspace |

    <Note>
      Install runs the connector's `onInstall` automation, described in [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions). For monday.com it provisions two workspace secrets: `mondayAuth` holds the auth mode and its credentials, and `mondayAuthorizedAgents` holds the comma-separated agent ids allowed to call the MCP endpoint (or `*` for all agents). The central client lives in the core workspace secret `mondayCentralOAuth` and is never copied into tenant workspaces. Per-user OAuth refresh tokens are additionally stored, best effort, as a workspace secret named `monRefresh_<userId>`, which is what lets scheduled automations resolve a specific user's token. That write only succeeds when the connecting user is a workspace editor or owner; interactive use works for everyone regardless.
    </Note>

    <Note>
      The authorized agents allowlist gates which Agent Creator agents may call the MCP endpoint; see [Agent builder](#agent-builder-agent-creator) and [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector). Builder automations calling `Monday.<operation>` instructions resolve the same workspace credentials, and are not affected by the allowlist.
    </Note>

## Verify the setup

Run these checks in order after installing and configuring the connector. Each one isolates a different failure point. They are the monday.com form of the generic sequence in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation).

| Check | How to run it | Expected result |
|-------|---------------|-----------------|
| Credentials resolve | In the configuration app, run the connection test | The test reports success. It resolves the configured mode and calls `{ me { id name } }` against monday.com |
| Runtime identity | Call the `users` tool with `action: "me"` | The returned id and name are the connected end user in the OAuth modes, or the token owner in `accessToken` mode |
| Read access | Call the `boards` tool with `action: "list"` | Board ids and names are returned |
| Agent authorization | Call any tool from an agent that is not allowlisted | The call is refused with `This agent is not authorized to use this connector` instead of executing |
| Write control | Ask the agent to create an item on a test board | The item appears in monday.com and its creation is attributed to the identity checked above |
| Least privilege | With read-only scopes configured, ask the agent to create an item | monday.com rejects the mutation with a permission error |

## Disconnect, rotate and remove

The generic lifecycle is documented in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall) and, for the central client, [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client). The table below is the monday.com-specific form, including the secret names to delete.

| Task | Who does it | Procedure |
|------|-------------|-----------|
| Disconnect one user | The user, or a workspace editor on their behalf | Use **Disconnect** in the configuration app, or the capability's disconnect action. This deletes the stored per-user token and the `monRefresh_<userId>` workspace secret. monday.com exposes no token revocation endpoint, so also remove the application's authorization from the monday.com account to invalidate the grant on monday.com's side |
| Force re-consent after a scope change | Workspace builder | Update the scopes in the configuration app, then have each user disconnect and connect again. The authorize request always sends `prompt=consent`, so a fresh refresh token is issued |
| Rotate the tenant OAuth client secret | Workspace builder | Create a new client secret at monday.com, enter it in the configuration app and save, then remove the old secret at monday.com. Existing per-user refresh tokens stop working, so users reconnect |
| Rotate the central OAuth client secret | Platform admin | Enter the new secret in the maintainer view of the core `monday` configuration app. It is written to the core workspace secret `mondayCentralOAuth` and never leaves that workspace |
| Rotate the API token | Workspace builder | Generate a new monday.com API token, enter it in the configuration app and save, then revoke the previous token at monday.com |
| Offboard a user | Workspace builder | Delete the `monRefresh_<userId>` workspace secret so scheduled automations stop resolving that user, and revoke their monday.com account access |
| Revoke an agent | Workspace builder | In the configuration app, clear the agent from **Authorized agents** and save. The next tool call from that agent is refused |
| Remove the connector | Workspace builder | Uninstall the monday.com app from the workspace, then delete the `mondayAuth`, `mondayAuthorizedAgents` and remaining `monRefresh_*` workspace secrets |

## Error handling

The connector normalizes monday.com responses into MCP errors. A GraphQL failure returned with HTTP 200 and a non-empty `errors` array surfaces as `GraphQL error while <operation>: <message>`.

| HTTP status | Message | Resolution |
|-------------|---------|------------|
| 400 | `Bad request while <operation>` | An argument or column-value shape is invalid. Check the column type reference |
| 401 | `Authentication failed while <operation>. Your monday.com token may be invalid or revoked.` | The connector retries once with a freshly resolved token. If it still fails, reconnect in the configuration app, or replace the API token |
| 403 | `Forbidden while <operation>. The token lacks permissions for this operation.` | Check the board or workspace permissions of the connected user, and the granted OAuth scopes |
| 404 | `Resource not found while <operation>` | Verify the board, item, group, column or doc id by listing the parent first |
| 429 | `Rate limit / complexity exceeded while <operation>. Wait before retrying.` | monday.com meters query complexity, not request count. Call the `account` tool with `action: "complexity"` to read `reset_in_x_seconds`, then back off |
| 500 | `monday.com server error while <operation>` | A transient monday.com failure. Retry shortly |

### Common issues

**`This agent is not authorized to use this connector`**: the calling agent is not in the tenant allowlist. Open the configuration app, select **Authorized agents**, add the agent id shown in the error message, and save; or enable **Allow all agents**. The **Install capability** button does this for you. If the agent is ticked and calls are still denied, see [Troubleshooting](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting) for the unresolved-binding case.

**`The calling agent could not be identified, so it cannot be authorized`**: the MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the scope to `context_id,agent_id,user_id` on the capability, which is separate from the monday.com OAuth scopes, then allowlist the agent in the configuration app.

**`Monday is not connected for this user`**: no per-user OAuth token is stored for the caller. Open the configuration app in an OAuth mode and select **Connect**, or use the agent's connect action. In `accessToken` mode, store a monday.com API token in the configuration app instead.

**`Monday token refresh failed`**: monday.com rejected the stored refresh token, typically because it was revoked or expired. The connector deletes the stored connection so the status endpoint reports `connected: false`, and the user must reconnect from the configuration app.

**`Monday token endpoint temporarily unavailable`**: monday.com's token endpoint returned a 5xx. This is transient and the connection is preserved, so retry shortly. No reconnection is needed.

**`No stored Monday token for this user`**: a non-interactive run, such as a scheduled automation, tried to act on behalf of a user with no `monRefresh_<userId>` secret. That secret is written only when the connecting user is a workspace editor or owner, so have such a user connect once from the configuration app.

**`Monday OAuth is not configured`**: neither a tenant OAuth client nor the central platform client is available. Enter the client ID and secret in the configuration app for the tenant mode, or ask the platform maintainer to provision the central OAuth client from the core `monday` workspace. For central-client failures such as `central_client_not_configured` or a rejected redirect URI, see [Troubleshooting](/apps-store/marketplace/connectors/central-oauth#troubleshooting).

**`Monday is not authenticated`**: no auth mode resolved any credentials. Open the configuration app and select an auth mode, then provide its credentials.

**`Missing required argument 'action'`**: every entity tool requires `action`. The error message lists the available actions for that tool. `Unknown entity` and `Unknown action` errors list the valid values the same way.

**Invalid column value**: the payload shape depends on the column type. Prefer `changeSimpleValue` for simple types such as text, numbers and status, and `changeValue` for complex ones such as people, dropdown and timeline. `create_labels_if_missing` applies only to `status` and `dropdown` columns.
