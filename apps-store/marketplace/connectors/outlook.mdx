The Outlook app (`outlook-next`) gives read and write access to a Microsoft 365 mailbox (mail, calendar and contacts) through the [Microsoft Graph](https://learn.microsoft.com/en-us/graph/overview) REST API. It can be consumed two ways: as a remote MCP server that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. The MCP surface groups every operation into **six entity tools** (`mail`, `mailFolders`, `calendars`, `events`, `contacts`, `contactFolders`), each driven by an `action` argument, and runs in the **tenant app-instance context**: it resolves the installing workspace's own credentials, never a platform-wide identity.

Pick the authentication mode from the runtime identity you want Microsoft to see:

| Auth mode | Runtime identity at Microsoft | Consent and rotation | Best for |
|-----------|-------------------------------|----------------------|----------|
| `oauthCentral` (default) | The invoking Prisme.ai user's own Microsoft account | A platform maintainer registers one Microsoft Entra OAuth application; each user consents once | Interactive agents and Chat, with per-user least privilege |
| `oauth` | The invoking Prisme.ai user's own Microsoft account, through your own Entra application | Your Entra admin owns the client and its secret; each user consents once | Workspaces that must use their own Entra client and their own consent policy |
| `clientCredentials` | A single Entra **application** identity, shared by every caller | An Entra Global Administrator grants admin consent once; you rotate the client secret | Unattended and scheduled automations with no interactive user |
| `accessToken` | Whatever account minted the token, shared by every caller | You paste and rotate the token yourself | Short-lived or caller-managed tokens, and testing |

When `config.auth.mode` is not set, the connector resolves `oauthCentral`.

<Warning>
  `clientCredentials` and `accessToken` are **shared credentials**: every agent and every automation in the workspace acts as the same Microsoft identity, and Microsoft audit logs attribute all reads, sends and deletions to that single identity instead of the real user. Application Graph permissions granted with admin consent can reach every mailbox in the tenant. Use a delegated per-user mode (`oauthCentral` or `oauth`) whenever a real user is driving the action, and restrict the application permissions with an [application access policy](https://learn.microsoft.com/en-us/graph/auth-limit-mailbox-access) when you do need `clientCredentials`.
</Warning>

## Prerequisites (Microsoft side)

- A **Microsoft 365** account, and an **Azure / Microsoft Entra ID** tenant where you can register an application (or a maintainer who already did).
- An **app registration** in [Microsoft Entra ID](https://entra.microsoft.com) (**App registrations**), with a **client secret** created under **Certificates & secrets**.
- **Microsoft Graph delegated permissions** granted on the app (for the per-user OAuth modes), covering the resources you intend to use:
  - Mail: `Mail.ReadWrite`, `Mail.Send`
  - Calendar: `Calendars.ReadWrite`
  - Contacts: `Contacts.ReadWrite`
  - Sign-in and identity: `User.Read`, `openid`, `profile`, `offline_access`
- For the **application (client credentials)** mode instead, grant the equivalent **application** permissions and have a Global Administrator grant admin consent. The connector then requests the fixed scope `https://graph.microsoft.com/.default`, so the **Scopes** field of the configuration app is ignored in that mode.

`offline_access` is required in the per-user modes: without it Microsoft Entra issues no refresh token and every user is disconnected as soon as the first access token expires.

The connector requests these scopes when the **Scopes** field is left empty:

```text
offline_access openid profile
https://graph.microsoft.com/Mail.ReadWrite
https://graph.microsoft.com/Mail.Send
https://graph.microsoft.com/Calendars.ReadWrite
https://graph.microsoft.com/Contacts.ReadWrite
https://graph.microsoft.com/User.Read
```

  ## 1. Configure the central OAuth client

  The generic maintainer flow is documented once in [Central OAuth client](/apps-store/marketplace/connectors/central-oauth): [when to prefer a central client over a tenant-owned one](/apps-store/marketplace/connectors/central-oauth#when-to-use-a-central-client), [how to open the maintainer view and save the client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client), and [how the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace). The steps below cover only what is specific to Microsoft Entra ID and to the `outlook-next` core workspace.

  <Steps>
    <Step title="Register the OAuth application in Microsoft Entra ID">
      In [Microsoft Entra ID](https://entra.microsoft.com), select **App registrations > New registration** and register a **Web** application. Add a **Redirect URI** pointing at the core workspace callback:

      ```text
      <api-url>/workspaces/<core-workspace-id>/webhooks/oauthCallback
      ```

      For example, `https://api.studio.prisme.ai/v2/workspaces/<core-workspace-id>/webhooks/oauthCallback` on production. The connector resolves this value in the core workspace context and never hardcodes the id, so read the exact URI from the configuration app.

      <Warning>
        Microsoft Entra rejects redirect URIs that contain a colon in the path, so use the **raw workspace id** of the core Outlook workspace, **not** the `slug:outlook-next` form shown as the central shape in [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls). Copy the exact URI from the connector's configuration app, which renders the value resolved in the core workspace context.
      </Warning>

      Add the Microsoft Graph **delegated** permissions listed in [Prerequisites (Microsoft side)](#prerequisites-microsoft-side), create a **client secret** under **Certificates & secrets**, and note the **Application (client) ID**, the **secret value**, and the **Directory (tenant) ID**. Use `common` or `organizations` for a multi-tenant client; the connector falls back to `common` when the tenant is left empty.
    </Step>
    <Step title="Enter the credentials through the configuration app">
      Open the core `outlook-next` workspace and launch its **Configuration app** at `<studio-url>/apps/outlook-next`, also linked as **Configuration app** on the installed instance. Switch to the maintainer view and enter the **Client ID**, **Client Secret**, **Tenant** and, optionally, the **Scopes**. Save. The app stores the whole client object in the core workspace secret `outlookNextCentralOAuth`; do not edit Studio's raw secrets by hand.

      Tenant instances read only the public part (client id, scopes, tenant, redirect URI) and proxy every token exchange through the core `centralTokenExchange` webhook, as described in [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace). Re-saving the form with the secret field empty keeps the stored secret, so you can change only the tenant or the scopes.
    </Step>
    <Step title="Tell workspaces to use the central client">
      Each consuming workspace selects auth mode `oauthCentral` in the connector configuration app; there is no client id or secret to enter on their side. Their users then connect individually. Hand them [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace).
    </Step>
  </Steps>

  ## 2. Declare the capability in AI Governance

  Generic connectors (broad tool surfaces meant to be shared across many agents, like Outlook) are best exposed as a named **capability** in AI Governance. Agent builders then enable that capability on their agents instead of pasting a raw MCP endpoint.

  The three ways to declare one are documented in [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability): the config app's [Install capability button](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent), its one-click [Add to catalog publishing](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog), and the [manual AI Governance path](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance). For Outlook, name the capability **Outlook**, point it at the connector's **MCP Endpoint**, and set its **Scope** to:

  ```text
  context_id,agent_id,user_id
  ```

  The `agent_id` in the scope is what lets the connector identify and authorize the calling agent. Add `attachment_urls` to the scope if agents must send files that users upload in Chat; see [Sending files uploaded in Chat](#sending-files-uploaded-in-chat) for the limits the connector then enforces, and [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means) for what each identifier does.

  Smoke-test it as described in [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability): from an agent that has the capability, in a workspace configured for `oauthCentral`, call the `mailFolders` tool with `action: "list"`. The user is prompted to connect once with Microsoft; subsequent calls reuse the stored token and refresh it automatically. The tool returns the mailbox folders, including `inbox` and `drafts`.

  <Note>
    The connector's configuration app also offers a one-click **Add to catalog** button (organization owner or admin only) that publishes the Outlook capability to the organization-wide Capabilities catalog for you, the easiest way to expose it to agent builders without hand-editing Governance.
  </Note>

  <Warning>
    Declaring the capability makes the connector **available**; it does not by itself authorize a specific agent ([Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization)). This connector follows the **tenant-context model**: which agents may call a tenant instance is gated by the **Authorized agents** allowlist in that workspace's configuration app (see [Workspace builder](#workspace-builder-dsul)). The core workspace behaves differently: because the central OAuth client resolves there, its own MCP endpoint accepts every agent and relies entirely on per-user Microsoft consent as the gate ([Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint)). There is also **no OAuth auth-config JSON** to attach in Governance: connect, status and disconnect are handled by the connector's own webhooks, wired automatically.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator read and act on Outlook mail, calendar and contacts through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed and configured the Outlook app in a workspace (see [Workspace builder](#workspace-builder-dsul) and [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace)), and, for the central OAuth mode, a platform admin must have provisioned the shared Microsoft Entra OAuth client (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    This connector runs in the **tenant app-instance context**: your agent is identified by the `agent_id` that Agent Creator injects through the capability *Scope*, and on a tenant instance that agent must also appear in the **Authorized agents** allowlist managed in the configuration app. The Microsoft Graph access token is resolved server-side from the configured auth mode; in the per-user modes it is the token of the human running the conversation, so Microsoft enforces that person's own mailbox permissions.

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A: Enable the shared capability from the catalog

    The fastest path: a platform admin has already published an **Outlook** capability (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup), section 2), so you just pick it from the catalog. An organization owner or admin can publish it in one click with the config app's **Add to catalog** button, as described in [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog).

    <Steps>
      <Step title="Open your agent in Agent Creator">
        Open the agent you want to extend and go to its capabilities and tools.
      </Step>
      <Step title="Add the Outlook capability">
        Browse the capability catalog, select **Outlook**, and enable it. Save the agent. The MCP endpoint URL and the *Scope* (`context_id,agent_id,user_id`) are already wired by the admin, and the shared instance accepts every agent, so there is no allowlist step on your side.
      </Step>
      <Step title="Connect a Microsoft account (per-user OAuth modes)">
        On the first tool call, an unconnected user is prompted to sign in; Agent Creator surfaces a `connect_url` returned by the connector. The `clientCredentials` and `accessToken` modes report themselves as always connected and need no per-user sign-in.
      </Step>
    </Steps>

    <Note>
      Convenient, but your agent runs against a **shared, platform-managed instance**: its Microsoft OAuth client is owned by someone else and the instance accepts every agent that is granted the capability. Prefer Option B for anything beyond quick experiments.
    </Note>

    ## Option B: Run it from your own workspace (recommended)

    For production agents, install the connector in **your own workspace** and point the agent at *that* workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP runs in *your* app-instance context, the Microsoft credentials, the per-user OAuth tokens and the authorized-agents allowlist are all **scoped to your workspace**, not shared platform-wide. You decide exactly which agents may call it and which Microsoft account or auth mode backs them, and a misconfiguration elsewhere can never expose your mailbox. The shared catalog capability (Option A) is a broad surface many agents can reach; your own workspace is an isolated, least-privilege boundary.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder](#workspace-builder-dsul): install **Outlook** in your workspace, open its **Configuration app**, choose the auth mode and connect a Microsoft account.
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's config app, open **Authorized agents**, tick your agent and save, as described in [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector). The [Install capability](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent) button does this for you. Enabling **Allow all agents** stores the `*` wildcard and disables the per-agent gate entirely; read [The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard) before you do.
      </Step>
      <Step title="Add the MCP capability to your agent">
        In your agent, add a capability pointing at **your workspace's MCP Endpoint** URL, set its **Scope** to the value below, and save:

        ```text
        context_id,agent_id,user_id
        ```

        The `agent_id` is what lets the connector identify and authorize your agent; without it, every call is rejected with an explicit message saying the calling agent could not be identified. This *Scope* is separate from the Microsoft Graph OAuth scopes; see [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
      </Step>
      <Step title="Connect a Microsoft account (per-user OAuth modes)">
        On the first tool call, the user is prompted to sign in, or connects from the configuration app.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent must know the MCP server exists and when to use it. Copy-pasteable starter:

    ```text
    You have access to the Outlook MCP server (tools: mail, mailFolders, calendars, events, contacts, contactFolders). Each tool takes an `action` argument. Use it whenever the user asks about their Outlook email, calendar events or contacts: listing, searching, reading, sending, replying, scheduling or updating. Prefer calling a tool over guessing, and confirm with the user before any destructive or outbound action (send, reply, forward, delete, decline a meeting).
    ```

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the **MCP Endpoint** URL. The agent still has to be allowlisted in the config app and its identity propagated so the connector can read its `agent_id`.
    </Note>

    <Note>
      **Restricting to read-only (least privilege).** Outlook tools cover both reads and writes (send mail, create and update events and contacts). In the per-user modes the requested OAuth scopes **are** the grant, so the connector only ever obtains what the **Scopes** field in the configuration app asks for. To allow only read access, set a read-only scope list there, for example:

      ```text
      offline_access openid profile https://graph.microsoft.com/Mail.Read https://graph.microsoft.com/Calendars.Read https://graph.microsoft.com/Contacts.Read https://graph.microsoft.com/User.Read
      ```

      With central OAuth (`oauthCentral`) you do **not** create your own Entra client; keep `oauthCentral` and enter the read-only scopes, which override the platform default for your workspace (the central app must expose these read permissions). Write calls such as sending mail are then rejected by Microsoft Graph with `403`. This is a workspace-level setting that a workspace editor can widen again; for a hard guarantee, use an Entra app limited to read permissions. In `clientCredentials` mode the field has no effect, because the connector always requests `.default`.
    </Note>

    ## Sending files uploaded in Chat

    When the capability *Scope* includes `attachment_urls`, Agent Creator injects the tokenized URLs of the files the user just uploaded in the conversation. The `mail` tool's `send` action downloads them and folds them into the Microsoft Graph message as inline `fileAttachment` entries, appending to any recipients, subject and attachments the agent already set.

    Limits enforced by the connector, derived from the roughly 4 MB ceiling of the simple Graph `sendMail` call:

    - At most **10** files per message.
    - At most **3 MB** per file.
    - At most **3 MB** for all attachments combined.

    Files above those limits are skipped rather than truncated, and the message is still sent with the remaining attachments.

    ## Available tools

    Each tool takes an `action` argument selecting the concrete operation, plus the per-action parameters. Omit `userId` to target the signed-in user (`me`).

    | Tool | Description |
    |------|-------------|
    | `mail` | Outlook mail messages. Actions: `list`, `get`, `create`, `update`, `delete`, `send`, `sendDraft`, `reply`, `replyAll`, `forward`, `move`, `listAttachments`, `getAttachment`, `checkAccess`. |
    | `mailFolders` | Mail folders (well-known ids: `inbox`, `drafts`, `sentitems`, `deleteditems`). Actions: `list`, `get`, `create`, `delete`, `listMessages`, `listChildFolders`. |
    | `calendars` | Outlook calendars (the default calendar plus secondary ones). Actions: `list`, `get`, `create`, `delete`. |
    | `events` | Calendar events. Actions: `list`, `view`, `get`, `create`, `update`, `delete`, `accept`, `decline`, `tentativelyAccept`, `listForCalendar`. |
    | `contacts` | Personal contacts. Actions: `list`, `get`, `create`, `update`, `delete`. |
    | `contactFolders` | Contact folders. Actions: `list`, `get`, `create`, `listContacts`. There is no delete action. |

    <Note>
      `checkAccess` is advertised in the `mail` action enum, but it is **not** an operation for your agent. The MCP endpoint intercepts it before the agent allowlist and answers it only for the trusted Knowledge Sync caller; every other caller is refused with JSON-RPC `-32003` and `The delegated Resource access action is restricted to the trusted Knowledge Sync caller.` It exists for the per-reader access check of the sync surface, described in [Knowledge base (sync)](#knowledge-base-sync).
    </Note>

    The MCP server advertises itself as `outlook-next-mcp` version `1.0.0`, declares the `tools` and `resources` capabilities, and derives its `tools/list` manifest from the six tool automations. Each tool automation compares the calling workspace (`run.sourceWorkspaceId`) against its own and refuses anything else with HTTP `403` and `Direct calls are not allowed — use the MCP endpoint.`, so every invocation must go through the MCP endpoint.

    ## Response limits

    The connector bounds every response before it reaches the agent context:

    - `top` maps to Graph `$top`. It defaults to `20` and is clamped to the range `1` to `100`.
    - Collections are capped at **100** items.
    - Message and attachment listings get a default `$select` when you do not pass one: `id,subject,from,toRecipients,receivedDateTime,isRead,hasAttachments,bodyPreview,webLink` for message lists, and `id,name,contentType,size,isInline,lastModifiedDateTime` for attachment lists.
    - Binary fields such as `contentBytes` are **omitted**, never truncated, so `listAttachments` and `getAttachment` return metadata only.
    - Oversized text is shortened field by field; identifiers, `@odata.*` keys and link fields are preserved intact.
    - When anything is dropped, the payload carries a `_truncation` object describing what was removed and suggesting a narrower query.
    - The final MCP envelope is capped by the `maxToolResponseCharacters` configuration field (default `80000`, clamped to the range `8000` to `100000` at runtime).

    ## Output formats

    Each tool also accepts an `outputFormat` argument that controls the MCP response shape. It defaults to `verbose` and is not advertised in the tool schema, so agents use the default unless you set it explicitly:

    - `verbose` (default): a human-readable text view, optimized for LLM consumption.
    - `structured`: the payload in `structuredContent`, with its JSON also rendered as text.
    - `both`: identical to `structured`.

    When the text part would be an exact JSON copy of `structuredContent`, the connector replaces it with a short pointer sentence to avoid sending the same payload twice.

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call Outlook operations from your automations.

    ## Installation

    Outlook follows the standard App + MCP installation flow: [install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app) from **Apps** in your workspace, then [configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app), [authorize the agents that may call it](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector), and [copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint). Search the catalog for **Outlook**.

    For Outlook specifically, installing the app provisions two workspace secrets, `outlookNextAuth` (the auth mode and its credentials) and `outlookNextAuthorizedAgents` (the agent allowlist), and wires them to the app instance configuration. Never edit these secrets by hand; the configuration app owns their shape. The install also seeds `knowledgeSync.trustedCallers` with the `knowledge-sync` slug when the instance has none, so a scheduled synchronization is recognized without any configuration; a list you edited yourself is left alone on every reinstall.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Auto-populated on install; open this link to configure authentication (mode and credentials), connect a Microsoft account (per-user OAuth modes), test the connection, and manage the authorized-agents allowlist. The URL has the form `<studio-url>/apps/outlook-next?workspaceId=<workspace-id>&workspaceSlug=<workspace-slug>&appInstance=<app-instance>`. |
    | **Microsoft Graph API version** | `v1.0` (default) or `beta`. It selects the Graph base URL `https://graph.microsoft.com/<version>`. |
    | **Maximum MCP response characters** | Upper bound on the serialized MCP response before fair truncation. Defaults to `80000` and is clamped to the range `8000` to `100000` at runtime. The field's own help text quotes a wider range; the runtime clamp above is the one that applies. |
    | **Knowledge-sync** (`knowledgeSync`) | Delegated MCP Resource access settings, used only by the sync surface. `trustedCallers` lists the workspace **slugs** allowed to browse and to run the delegated access check on a named user's behalf; each slug is resolved to this environment's workspace id through the platform registry at call time, so the same value works in sandbox and in production, and a slug that resolves to nothing fails closed. A raw workspace id written by an older install is still accepted. `mailbox` names the mailbox a scheduled sync reads when the instance ingests with an application identity; leave it empty for the ordinary per-user case. Non-secret: stored directly in the configuration value. |

    ## Authentication modes

    The configuration app drives everything; the app instance itself has no per-field credential form. From it you pick one of:

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | `oauthCentral` (default) | Nothing; each user connects their own Microsoft account | Workspaces on a platform where a maintainer set up the central client |
    | `oauth` | Your own Entra **Application (client) ID + Secret**, plus the **Tenant** (defaults to `common` when empty) and the redirect URI below | You manage your own Microsoft Entra OAuth app |
    | `clientCredentials` | Entra **client ID + secret + tenant**, all three required, with admin-consented **application** Graph permissions | Unattended, scheduled or server-to-server automations |
    | `accessToken` | A pre-minted Microsoft Graph **access token** | Short-lived or caller-managed tokens |

    In `oauth` mode, register this redirect URI at Microsoft Entra:

    ```text
    <api-url>/workspaces/<your-workspace-id>/webhooks/<app-instance>.oauthCallback
    ```

    <Warning>
      Microsoft Entra rejects a colon in the redirect URI path, so this URI uses your workspace's **raw id**, not the `slug:` form shown as the tenant shape in [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls). It keeps the `<app-instance>.` prefix, which is what distinguishes it from the core workspace URI used by the central client. It must match byte for byte what you register at Entra; copy the exact value from the configuration app.
    </Warning>

    <Note>
      **Unattended automations.** In the per-user modes the token belongs to the human running the automation, so a cron or event-triggered run that has no user session fails with `Microsoft Graph is not connected for this user`. Use `clientCredentials` or `accessToken` for scheduled automations, and accept that every such run is attributed to the shared identity.
    </Note>

    <Note>
      The agent allowlist (**Authorized agents**) gates which Agent Creator agents may call this workspace's MCP endpoint; it has no effect on the App-mode instructions below, which are governed by your workspace's own roles. See [Agent builder](#agent-builder-agent-creator) and [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).
    </Note>

    ## Knowledge base

    **Goal:** index the messages of a mail folder into a knowledge base so an agent can search their **content**, and keep that base up to date.

    <Note>
      Before a base can be attached, a workspace builder must have installed and configured the Outlook app in a workspace and connected a mailbox (see [Workspace builder](#workspace-builder-dsul)). Nothing else is needed: the same app instance serves both the agent tools and the sync surface.

      The **Authorized agents** allowlist does **not** apply here. `resources/list`, `resources/read` and the delegated `mail` / `checkAccess` action are authorized on a different axis, because nobody in those flows is an agent: a caller that is signed in must be able to **read the workspace that holds the connector's configuration**, and a synchronization run — scheduled or triggered by hand — carries no identity at all, so it is authorized as a workspace, by being listed in `knowledgeSync.trustedCallers`. The allowlist stays reserved for `tools/call` ([Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector)), so you never have to open the connector to every agent to make a knowledge base work.
    </Note>

    <Warning>
      **A mailbox is personal data.** Everything under the folder you select becomes searchable by everyone the knowledge base is shared with, subject to the access check below. Sync a **shared or functional mailbox** — support@, invoices@, a project archive — or one clearly delimited folder, rather than someone's inbox. Calendar events and contacts are not synced at all.
    </Warning>

    The connector publishes those two templates, plus `outlook://profile/knowledge`, through `resources/templates/list`. Both that method and a read of the profile URI answer **anonymously**, because catalog discovery probes them with no credentials; everything that touches the mailbox is behind the authorization described below.

    ## Who may sync, and who may read

    | Moment | Acts as | Authorized by |
    |--------|---------|---------------|
    | Attaching the connection, browsing the tree | You | Your **role on the workspace** holding the connector's configuration — the right to read that workspace is the right to read this mailbox through it |
    | A scheduled sync run | No user at all | The calling workspace must be listed by **slug** in `knowledgeSync.trustedCallers`; installing the app seeds `knowledge-sync` there, and the connector resolves that slug to the workspace id of the current environment |
    | Answering a reader's question | The reader | A live per-reader access check (`mail` / `checkAccess`, batches of up to 100 distinct URIs), itself restricted to the same `knowledgeSync.trustedCallers` list, probing each message against Microsoft Graph |

    <Note>
      **Per-user access control is supported — keep it on for a mailbox.** Each reader's own rights are re-checked in Outlook at query time, so a message they could not open in Outlook is not served to them either. Turning it off hands every synced message to anyone who can query the agent.

      The check always resolves the **reader's own Microsoft account** through the central OAuth client, even on an instance that ingests with `clientCredentials` or a stored access token — a check run on a shared identity would answer for that identity and clear correspondence the reader has no business seeing. A reader who has never connected Outlook therefore receives no documents: the check answers `requires_oauth` with a connect URL instead. On a shared mailbox fed by an application identity, be explicit about who is meant to read the base: the check can only reflect what Outlook itself grants each reader.

      The check fails closed throughout. A malformed URI, a denial, an expired token and a Microsoft Graph outage all end with the document withheld, and a batch of more than 100 distinct URIs is refused rather than silently shortened.
    </Note>

    ## What gets indexed

    | Aspect | Behavior |
    |--------|----------|
    | Document unit | One **message** = one document, published as `text/plain` (subject, correspondents and body text). Folders are containers, never indexed themselves. |
    | Attachments | **Not ingested.** A message is a leaf, so the sync never descends into it; `hasAttachments` travels as metadata and the citation link opens the message. This matches the agent-tool surface, where binary fields such as `contentBytes` are stripped from every response (see [Response limits](#response-limits)). |
    | Size ceiling | 200 000 characters of text per message; beyond it the text is cut and the resource is flagged `truncated` in its metadata. |
    | Empty messages | A message with no extractable text — an empty body and no preview — is reported as unfetchable rather than indexed as a blank document. |
    | Revision marker | `changeKey`, falling back to `lastModifiedDateTime`. Unchanged messages are never re-read and never re-indexed. |
    | Deletions | Each run is a **full traversal**: a message absent from a complete listing is removed from the base — which also covers a message moved out of the synced folder. A listing that failed halfway deletes nothing. |

    <Note>
      **The Knowledge profile this connector declares** — the descriptor Knowledges probes at `outlook://profile/knowledge`:

      | Field | Value |
      |-------|-------|
      | `provider` | `outlook-next` |
      | `tools` | `mail` |
      | `hierarchy` | `folder` › `message` |
      | `canonical_uri` | `outlook://message/{messageId}` |
      | `revision` | `changeKey`, fallback `lastModifiedDateTime` |
      | `read` | Inline text only, 200 000 characters max; binary `not_applicable` |
      | `list` | 50 resources per page by default, 100 max; `delta_on_drive: false` |
      | `access` | Tool `mail`, action `checkAccess`, up to 100 distinct URIs per call |
      | `authentication` | `oauthCentral`, `oauth`, `clientCredentials`, `accessToken` |
      | `resource_access` | Workspace role, or the trusted Knowledge Sync caller |
    </Note>

    ## Troubleshooting the sync

    **The URL check says "You are not allowed to read it"**, and the connector answers `You do not have the rights to read this connector on the workspace that holds its configuration.`: you have no role on the workspace holding the connector's configuration. Ask its administrator for one — this is not about your mailbox rights.

    **`This connector answers Resource calls to its workspace members, or to the trusted Knowledge Sync workspace.`**: the call carries no identity and its workspace is not trusted. On a sync run, add the `knowledge-sync` slug to `knowledgeSync.trustedCallers` in the connector's **Knowledge-sync** configuration — installing the app normally seeds it.

    **`Delegated Resource access is restricted to the trusted Knowledge Sync caller.`**: the run named a `targetUserId` from a workspace that is not in `knowledgeSync.trustedCallers`. Add that workspace's **slug** to the connector's **Knowledge-sync** configuration.

    **`This connector could not authenticate the call, so membership of the workspace holding its configuration could not be established.`**: the platform declined to authenticate the call itself — a run carrying a user id but no session, or an organization enforcing MFA. This is not a missing role; sign in again rather than hunting for a permission.

    **The URL check says "It answered, but could not serve its content"**: the connector itself is not fully configured. Open its configuration app and connect a mailbox.

    **A message is in the folder but not in the base**: it may have no extractable text (an empty body with no preview), in which case it is listed in the connection's synchronization errors rather than indexed.

    **An attachment's content is not searchable**: by design — attachments are not ingested. Index the documents themselves from where they live (SharePoint, Drive, WebDAV) if their content must be searchable.

    **Messages disappear from the base after being filed**: moving a message out of the synced folder removes it on the next complete traversal. Sync the folder the mail actually lands in, or a parent of it.

    **A reader gets no documents at all, and the workspace activity feed shows `knowledge.access.delegation_unavailable`**: the access check was asked to act for another user from a run that already carries a signed-in user. The delegated token lives in a workspace-scoped secret that only a user-less run may read, so the check returns nothing rather than guessing. This is the sync path's own concern; it does not affect a reader querying the base normally.

    **A scheduled sync keeps running after a right was revoked**: the role check runs on the interactive paths only. A scheduled run is authorized as the platform's synchronization workspace — delete the connection to stop it for certain.

## Verify the setup

Run these checks in order; each one is observable without inspecting logs. They are the Outlook instance of the generic sequence in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation).

1. In the configuration app, select **Test connexion**. The connector resolves the configured credentials and calls Microsoft Graph `GET /me`. A success response confirms both the auth mode and the granted permissions.
2. In the same app, confirm that the connection status reports the current user as connected in the per-user modes. The `clientCredentials` and `accessToken` modes always report connected, because they have no per-user session.
3. From an agent that has the capability, ask for a read-only operation, for example listing mail folders. The response must contain the well-known folders of the connected mailbox, such as `inbox` and `drafts`.
4. From a Builder automation, run `OutlookNext.listMailFolders` and check that `{{result.value}}` is populated and `{{result.error}}` is empty.
5. Negative check: temporarily remove your agent from **Authorized agents** on a tenant instance and call any tool again. The call must fail with the message stating that the agent is not authorized. Restore the entry afterwards.
6. Write check: send a message to yourself with the `mail` tool and `action: "send"`, then confirm it in the mailbox. Skip this step if the workspace is configured with read-only scopes.

<Note>
  Message subjects, body content, body previews, comments and inline attachment bytes are registered as redaction secrets before the connector emits its execution events, so mailbox content does not appear in the workspace activity feed.
</Note>

## Error handling

Microsoft Graph failures are normalized into a single text message that names the operation and appends the Graph error code and message.

| HTTP code | Normalized message | Meaning |
|-----------|--------------------|---------|
| `400` | `Bad request while <operation>` | Invalid parameters or malformed body, for example a bad OData filter or an invalid event resource. |
| `401` | `Authentication failed while <operation>` | The Microsoft Graph access token is missing, expired or revoked. The user must reconnect in the per-user modes. |
| `403` | `Forbidden while <operation>` | Insufficient Graph scope or permission, missing admin consent in `clientCredentials` mode, or the account lacks access to the resource. |
| `404` | `Resource not found while <operation>` | The message, folder, event, contact or calendar id does not exist or is not visible to the account. |
| `429` | `Throttled by Microsoft Graph while <operation>` | Microsoft Graph [throttling limit](https://learn.microsoft.com/en-us/graph/throttling) reached. Wait and retry. |
| `500` | `Microsoft Graph server error while <operation>` | Transient service error; retry shortly, no reconnection needed. |
| Any other | `Error <status> while <operation>` | Fallback for statuses without a dedicated message, including `503`. |

### Common issues

Errors that every App + MCP connector shares are covered in [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting), [Central OAuth client](/apps-store/marketplace/connectors/central-oauth#troubleshooting) and [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability#troubleshooting). The entries below are the Outlook and Microsoft Graph strings.

**`This agent is not authorized to use this connector`**: the calling agent is not in the allowlist of a tenant instance. Open the configuration app, go to **Authorized agents**, tick the agent named by the id in the message, and save, or enable **Allow all agents**. The **Install capability** button does this for you.

**`The calling agent could not be identified`**: the MCP capability *Scope* does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability, then allow the agent in the config app.

**`Unknown tool`**: the tool name in the MCP request does not match one of the six entity tools. Check the spelling against [Available tools](#available-tools).

**`Unknown action`** or **`Missing required argument`**: the `action` value is absent or not in the tool's enum. The error message lists the valid actions for that tool.

**`Direct calls are not allowed — use the MCP endpoint.`**: a tool automation was called over HTTP instead of through the MCP endpoint, and answered `403`. The tool checks the provenance of the call — the workspace it came from must be the workspace that owns the automation — so no header or key can stand in for the endpoint. Point the capability at the connector's **MCP Endpoint**.

**`The delegated Resource access action is restricted to the trusted Knowledge Sync caller.`** (JSON-RPC `-32003`): something called the `mail` tool with `action: "checkAccess"` from a workspace that is not in `knowledgeSync.trustedCallers`. This action belongs to the sync surface, not to agents; remove it from the agent's instructions, or add the calling workspace's slug to the connector's **Knowledge-sync** configuration if it really is a synchronization caller.

**`Microsoft Graph is not connected for this user`**: no per-user OAuth token exists. Open the configuration app in a per-user OAuth mode and select **Connexion**, or use the agent's connect flow. In a scheduled automation with no user session, switch the workspace to `clientCredentials` or `accessToken`.

**`Microsoft Graph token refresh failed`**: the stored refresh token was revoked or expired, for example because Microsoft Entra invalidated it or it aged past its limit. The connector retries once, then drops the stored connection so the status endpoint reports the user as disconnected; the user must reconnect from the config app.

**`Microsoft Graph token endpoint temporarily unavailable`**: Microsoft returned a `5xx` on the token exchange. This is flagged as transient, the connection is preserved, and the call succeeds on retry.

**`No stored Microsoft Graph token for this user`**: a non-interactive resolution — a scheduled run, or the sync surface's delegated access check — found no workspace-scoped refresh token for the target user. That copy is deposited when the user connects once from the configuration app, and the connector grants every workspace **member** the right to write their own `olnRefresh_<user-id>` secret, so no editor role is needed despite what the message says. Ask the target user to connect; on the sync surface the same condition surfaces as `requires_oauth` with a connect URL rather than as an error.

**`Microsoft Graph OAuth is not configured`**: neither a tenant OAuth client nor the central platform client is available. Set the client ID, secret and tenant in the config app, or ask the platform maintainer to provision the central Entra OAuth client from the core workspace.

**`Microsoft Graph not authenticated`**: `config.auth` carries no usable mode or credentials, usually because the configuration app was never completed. Choose an auth mode and save its credentials.

**`client_credentials mode requires clientId, clientSecret and tenant`**: one of the three values is missing. Unlike the per-user modes, `clientCredentials` has no `common` fallback for the tenant.

**`Microsoft Graph client_credentials exchange failed`**: check the Application (client) ID, the secret, the tenant id, and that a Global Administrator granted admin consent for the application Graph permissions.

**`you must be an editor of the core workspace`**: the maintainer form rejected the save because your role on the core `outlook-next` workspace is not owner, editor or admin. Ask a core workspace owner to grant the role or to enter the central client for you.

**Microsoft Entra redirect URI rejected**: Entra rejects a colon in the redirect URI path. Register the redirect URI with the workspace's **raw id**, not the `slug:` form, and copy the exact value from the config app.

**A tool returns `_truncation` instead of the full payload**: the response exceeded the size budget. Retry with a smaller `top`, a `select` limited to the fields you need, a narrower `filter` or `search`, or a shorter `startDateTime` to `endDateTime` window, then fetch full detail with a `get` action on a returned id.

## Revoke, rotate and remove

The generic lifecycle is documented in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall), [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client) and [Remove or update a capability](/apps-store/marketplace/connectors/declare-capability#remove-or-update-a-capability). What differs for Outlook:

- **Disconnect one user.** In the configuration app, use the disconnect action, or open the connector's `oauthDisconnect` webhook from the agent. It deletes the stored user token and the workspace-scoped refresh secret. Microsoft Entra offers no simple per-token revocation endpoint, so an Entra administrator must also [revoke the user's sign-in sessions](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-mfa-userdevicesettings) to invalidate tokens already issued.
- **Block an agent.** Remove it from **Authorized agents** in the tenant configuration app, and turn off **Allow all agents** if it was enabled. The next tool call from that agent is rejected. On the core workspace endpoint this has no effect, because the central client short-circuits the per-agent check.
- **Rotate the central client secret.** Create a new secret in the Microsoft Entra app registration, enter it in the maintainer view of the configuration app and save, then delete the old secret at Entra. Existing user connections keep working, because refresh exchanges use the newly stored secret.
- **Rotate a tenant client secret or access token.** Update the value in the workspace's configuration app. In `accessToken` mode the new token takes effect on the next call; in `oauth` mode existing users stay connected.
- **Remove the connector.** Uninstall the Outlook app from the workspace, then delete the `outlookNextAuth` and `outlookNextAuthorizedAgents` secrets and any remaining per-user refresh-token secrets from the workspace secrets. Finally, delete the Outlook capability in AI Governance so it stops appearing in the catalog.
