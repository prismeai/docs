The SonarQube app exposes the [SonarQube](https://www.sonarsource.com/products/sonarqube/) and [SonarQube Cloud](https://sonarcloud.io) Web API. It can be consumed two ways: as a remote MCP server that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. It covers projects, components, issues, security hotspots, measures, metrics, quality gates, quality profiles, rules, organizations, user tokens, analyses, branches, webhooks and SVG badges, through 46 operations that are identical in both surfaces.

Authentication is a single **SonarQube user token**, stored as a secret in the installing workspace and sent server-side as an HTTP `Authorization: Bearer` header. The token is never exposed to the agent, and there is no per-user sign-in flow.

## Operating model

SonarQube ships a single authentication mode, so there is no credential decision to make: the connector authenticates with one **static SonarQube user token** per installing workspace, stored as a workspace secret and sent server-side. Read this section before configuring anything, because it determines whose SonarQube permissions every agent and automation inherits.

| Property | Value |
|----------|-------|
| Credential model | Static user token, one per installing workspace |
| Runtime identity at SonarQube | The **owner of the user token**, never the invoking end user or agent builder |
| Where the credential lives | The `sonarqubeToken` workspace secret, provisioned empty on install and bound to the app instance's **API Token** field |
| How SonarQube receives it | `Authorization: Bearer <token>` on every request |
| Delegated per-user OAuth | Not supported by this connector |
| Deployment variants | SonarQube Cloud (`https://sonarcloud.io/api`, the default) and self-hosted SonarQube (`https://<your-sonarqube-host>/api`) |
| Transport | Prisme.ai calls the SonarQube Web API with all arguments in the query string, including for `POST` operations |

<Warning>
  **Shared-credential blast radius.** Every call uses the same user token, so SonarQube attributes all reads and writes to its owner, and every agent and automation that can reach the connector inherits that account's permissions. The connector exposes destructive operations (`deleteProject`, `deleteProjectBranch`, `deleteWebhook`, `revokeUserToken`, `transitionIssue`), so a read-only deployment requires a SonarQube account that lacks the corresponding administer permissions. Grant the token owner the narrowest SonarQube role that covers your use case.
</Warning>

### How the MCP endpoint identifies your workspace

The MCP server is hosted once, by the central SonarQube connector workspace, and shared by every workspace that installs the app. Installations are told apart by an auto-generated key rather than by separate URLs.

<Steps>
  <Step title="Install provisions a signed key">
    On install (and on every reconfiguration), the app requests a key from the central workspace. The key is an HMAC-SHA256 signed token that encodes your workspace ID and the URL of your instance's `getConfig` webhook. It is written back into the app instance as the read-only **MCP API Key** field.
  </Step>
  <Step title="Tool calls present the key">
    Each MCP `tools/call` request must carry that key in a dedicated request header:

    ```text
    mcp-api-key: <the MCP API Key value from the app instance>
    ```

    Missing or tampered keys are rejected with JSON-RPC error code `-32001` before any SonarQube call is made.
  </Step>
  <Step title="The endpoint fetches your credential">
    Once the signature is verified, the central endpoint calls your workspace's `getConfig` webhook to read your SonarQube token and base URL, then caches them for that workspace for **10 minutes**.
  </Step>
</Steps>

<Note>
  The MCP handshake methods (`initialize`, `notifications/initialized`, `tools/list`) are answered without a key: they disclose the tool manifest, never SonarQube content. The server announces itself as `sonarqube-mcp` version `1.0.0` and speaks MCP protocol version `2025-06-18`.
</Note>

<Warning>
  Because credentials are cached for 10 minutes per workspace, changing the SonarQube token or base URL can take up to 10 minutes to take effect on MCP tool calls. Builder instructions read the configuration directly and are not affected.
</Warning>

## Prerequisites

- The `owner`, `editor`, or `admin` role on the Prisme.ai workspace that will install the connector, because installing writes a workspace secret. See [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin).
- A **SonarQube** server (self-hosted) or a **SonarQube Cloud** account.
- A **user token** generated in SonarQube under **My Account > Security > Generate Tokens**.
- The token owner must hold the SonarQube permissions required by the operations you intend to use. Administer-scoped operations (`searchProjects`, `searchUserTokens` for another login, project and webhook management) fail with `403` when the account lacks them.
- The **API base URL** of your instance. The connector defaults to `https://sonarcloud.io/api`; for a self-hosted instance use `https://<your-sonarqube-host>/api`.
- For SonarQube Cloud only: the **organization key** that owns your projects. Several search and create operations require it; discover the keys your token can see with `searchOrganizations`.

<Accordion title="Platform admin (Governance): one-time platform setup" icon="shield-halved">
  **Goal:** SonarQube is a **per-workspace** connector: each workspace supplies its own SonarQube user token (see [Workspace builder (DSUL)](#workspace-builder-dsul)), so there is **no platform-wide credential to provision**. The only optional platform task is to publish SonarQube as a reusable **capability** in AI Governance so agent builders can enable it from the catalog instead of wiring the MCP endpoint by hand.

  <Note>
    There is no shared SonarQube credential and no central OAuth client for this connector, so [Central OAuth client](/apps-store/marketplace/connectors/central-oauth) does not apply: nothing here registers a provider application or holds a client secret. The SonarQube user token always lives in the consuming workspace and is resolved server-side. A Governance capability you publish here points at the shared MCP endpoint; the installing workspace still owns the credential, and the key that identifies it.
  </Note>

  ## Declare the capability in AI Governance (optional)

  SonarQube ships no configuration app, so the two one-click paths on [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability) are unavailable: there is no **Install capability** button ([Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent)) and no **Add to catalog** button ([Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog)). Only the manual path applies: follow [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance) and enter the SonarQube values below.

  | Field in AI Governance | Value for SonarQube |
  |---|---|
  | Capability type | `mcp` |
  | Server URL (**SSE/WebSocket URL**) | The **MCP Endpoint** value shown on an installed SonarQube app instance |
  | Request header | That same instance's **MCP API Key**, sent under the header name given in [How the MCP endpoint identifies your workspace](#how-the-mcp-endpoint-identifies-your-workspace) |
  | **Scope** | Not used. This connector never reads the calling agent's identity, so adding `agent_id` changes nothing |
  | Authorization block | None. Authentication is a server-side user token, not a per-user OAuth flow |
  | Agent authorization | Not available. This connector has no **Authorized agents** allowlist; the key alone decides which workspace's token is used |

  Once saved, the capability appears in the capability picker for agent builders in your organization, who enable it on their agents. Access to the catalog follows your organization's existing roles; there is no per-capability role grant for this connector.

  <Warning>
    Declaring the capability makes the connector **available**; the SonarQube credential is still owned by the workspace that installed the app, and the key pinned in the capability decides which workspace's token is used. There is **no OAuth auth-config JSON** to attach in Governance: authentication is a server-side user token, not a per-user OAuth flow. The connector performs no agent-level authorization of its own, so anyone who can attach the capability can act as the token owner. The usual second gate described in [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization) does not exist here: for SonarQube, availability **is** authorization.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator read and act on SonarQube code-quality data through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed the SonarQube app in a workspace and filled its SonarQube token, as described in [Workspace builder (DSUL)](#workspace-builder-dsul). Optionally, a platform admin may have published a SonarQube capability in AI Governance, as described in [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup).
    </Note>

    The SonarQube credential is resolved server-side from the installed app's configuration and never reaches the agent. The agent's own identity is not propagated: every agent pointed at the same app instance acts as the same SonarQube account.

    <Steps>
      <Step title="Install and configure the connector in a workspace">
        Follow [Workspace builder (DSUL)](#workspace-builder-dsul): install **SonarQube** in your workspace, set the **SonarQube API Base URL**, and fill the `sonarqubeToken` secret with your SonarQube user token.
      </Step>
      <Step title="Add the MCP capability to your agent">
        In your agent, add a capability pointing at the app instance's **MCP Endpoint** URL, configure it to send that instance's **MCP API Key** header, and save the agent. Without the key, tool discovery still works but every tool call is rejected.

        There is no **Install capability** button for SonarQube, because the connector ships no configuration app, and no allowlist to tick afterwards. Wiring the capability by hand is the only path; the field values are listed in [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup).
      </Step>
      <Step title="Brief the agent in its system prompt">
        Wiring the capability is not enough: the agent also needs to know the MCP server exists and when to reach for it. Add a short paragraph to the agent's system prompt, then publish the agent. Copy-pasteable starter:

        ```text
        You have access to the SonarQube MCP server. Use it whenever the user asks about code-quality data: projects, issues, security hotspots, measures, quality gates, rules or badges. Examples: "List the blocker issues in project X", "What's the coverage of auth-service?", "Show the security hotspots still to review", "Why is the quality gate failing on main?". On SonarQube Cloud, several search and create operations need an organization key; call searchOrganizations first if you don't know it. Prefer calling MCP tools directly over guessing, and confirm with the user before any destructive action (mark issues as false positive, change severity, delete a project or branch, revoke a token).
        ```

        Refine the trigger keywords (project keys, branch names, rule families) so the agent reliably picks up the right intent in your context.
      </Step>
    </Steps>

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the **MCP Endpoint** URL. Newer Agent Creator agents use the native capability picker described above.
    </Note>

    ## Output formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - **`verbose`** (default): a human-readable text summary built for LLM consumption, with the SonarQube payload embedded as a JSON block.
    - **`structured`**: the raw SonarQube payload as JSON, both in the text `content` and in `structuredContent`.
    - **`both`**: identical to `structured` in this connector.

    ## Tool details

    Argument names and required flags below come from the connector's tool manifest. For the semantics of individual SonarQube filter values, see the [SonarQube Web API reference](https://next.sonarqube.com/sonarqube/web_api).

    ### searchIssues

    Search and filter issues. With no arguments it returns every issue the token can see, so combine filters to scope it down.

    ```json
    {
      "name": "searchIssues",
      "arguments": {
        "componentKeys": "my_org_my-project",
        "types": "BUG,VULNERABILITY",
        "severities": "CRITICAL,BLOCKER",
        "statuses": "OPEN,CONFIRMED,REOPENED",
        "branch": "main",
        "ps": 100
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `componentKeys` | No | Comma-separated component or project keys |
    | `projects` | No | Project keys |
    | `assignees` / `author` | No | Assignee logins, or the login that reported the issue |
    | `severities` | No | `INFO`, `MINOR`, `MAJOR`, `CRITICAL`, `BLOCKER` |
    | `types` | No | `BUG`, `VULNERABILITY`, `CODE_SMELL` |
    | `statuses` / `resolutions` / `resolved` | No | Issue lifecycle filters passed through to SonarQube |
    | `tags` / `languages` / `rules` | No | Comma-separated filter values |
    | `createdAfter` / `createdBefore` | No | Creation-date window |
    | `branch` / `pullRequest` | No | Restrict to a branch or pull request |
    | `s` / `asc` | No | Sort field and direction |
    | `p` / `ps` | No | Page index and page size |

    ### searchOrganizations

    Discover the SonarQube Cloud organization keys your token can see; call this first when you do not know the `organization` value other tools require.

    ```json
    {
      "name": "searchOrganizations",
      "arguments": {
        "member": true
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `member` | No* | When `true`, return only organizations the token owner belongs to |
    | `organizations` | No* | Comma-separated organization keys to check |
    | `p` / `ps` | No | Page index (default `1`) and page size (default `100`) |

    <Note>
      Pass at least one of `member` or `organizations`. SonarQube Cloud rejects the call when both are omitted.
    </Note>

    ### transitionIssue

    Move an issue through SonarQube's workflow.

    ```json
    {
      "name": "transitionIssue",
      "arguments": {
        "issue": "<issue-key>",
        "transition": "falsepositive"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `issue` | Yes | Issue key |
    | `transition` | Yes | `confirm`, `unconfirm`, `reopen`, `resolve`, `falsepositive`, `wontfix`, `close` |

    ### getComponentMeasures

    Read one or several metric values for a component (project, file or directory).

    ```json
    {
      "name": "getComponentMeasures",
      "arguments": {
        "component": "my_org_my-project",
        "metricKeys": "ncloc,bugs,vulnerabilities,coverage,duplicated_lines_density",
        "branch": "main"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `component` | Yes | Component key (project, file or directory) |
    | `metricKeys` | Yes | Comma-separated metric keys; list the available ones with `searchMetrics` |
    | `branch` | No | Branch name |
    | `pullRequest` | No | Pull request identifier |
    | `additionalFields` | No | Extra response fields |

    ### getProjectQualityGateStatus

    Useful as a one-shot pass/fail check for CI gates.

    ```json
    {
      "name": "getProjectQualityGateStatus",
      "arguments": {
        "projectKey": "my_org_my-project",
        "branch": "main"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `projectKey` | No* | Project key |
    | `projectId` | No* | Project identifier, an alternative to `projectKey` |
    | `branch` | No | Restrict to a branch |
    | `pullRequest` | No | Restrict to a pull request |

    <Note>
      Pass either `projectKey` or `projectId`. With neither, SonarQube answers with a `400` and the connector returns `Bad request while get the quality gate status of a project`.
    </Note>

    ### createProject

    Provision a new project. On SonarQube Cloud, `organization` is required.

    ```json
    {
      "name": "createProject",
      "arguments": {
        "name": "Website Revamp",
        "project": "my_org_website-revamp",
        "organization": "my_org",
        "visibility": "private"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `name` | Yes | Display name |
    | `project` | Yes | Project key |
    | `organization` | No* | Required on SonarQube Cloud |
    | `visibility` | No | `public` or `private` |

    ## Workspace builder

    **Goal:** install the connector in a workspace, store the SonarQube credential, and call SonarQube operations from your automations.

    ## Installation

    <Note>
      SonarQube does not follow [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace). Four differences matter, so use the steps below rather than the shared flow:

      - **No configuration app.** The app instance has no **Configuration app** link, so [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app) does not apply. You enter the SonarQube token in the workspace **Secrets** section instead.
      - **No authorized-agents allowlist.** There is nothing to tick, so [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector) does not apply. Access is controlled by the **MCP API Key** alone.
      - **One shared MCP endpoint, not a per-instance URL.** [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint) does not apply; the endpoint is identical for every installation and the key tells them apart.
      - **Install provisions one string secret**, not the usual auth-object plus allowlist pair described in [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions).
    </Note>

    <Steps>
      <Step title="Install the app">
        Open **Apps** in your workspace, search for **SonarQube** and install it. The install handler provisions two things for you: an empty `sonarqubeToken` secret in the workspace, and the app instance's read-only **MCP Endpoint** and **MCP API Key** values.
      </Step>
      <Step title="Fill the SonarQube token">
        Open the workspace's **Secrets** section, set `sonarqubeToken` to the user token you generated in SonarQube under **My Account > Security > Generate Tokens**, and save. The app instance's **API Token** field is already bound to this secret, so you never paste the token into the app configuration itself.
      </Step>
      <Step title="Set the base URL if you are self-hosted">
        In the app instance configuration, replace the default **SonarQube API Base URL** with `https://<your-sonarqube-host>/api`, and save.
      </Step>
    </Steps>

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **SonarQube API Base URL** | Base URL of the SonarQube API. The connector falls back to `https://sonarcloud.io/api` when it is empty |
    | **API Token** | SonarQube API token. Bound on install to the `sonarqubeToken` workspace secret and sent as `Authorization: Bearer <token>` |
    | **MCP Endpoint** | Read-only. The URL of the shared MCP endpoint, filled automatically on install |
    | **MCP API Key** | Read-only. The signed key that identifies this workspace on the shared MCP endpoint. Generated on install; do not modify it |

    | Secret | Description |
    |--------|-------------|
    | `sonarqubeToken` | The SonarQube user token used for every call from this workspace. Provisioned empty on install, for you to fill |
    | `appSecret` | The HMAC secret used to sign MCP API keys. Present only on the central SonarQube connector workspace, never on an installing workspace |

    <Warning>
      Until `sonarqubeToken` holds a value, every MCP tool call fails with `SonarQube token not configured on this app instance.` and every Builder instruction returns `SonarQube not configured. Set token in the workspace config.`
    </Warning>

    <Note>
      SonarQube identifiers are project keys, component keys, issue keys, rule keys and login names. Most list and search operations accept `p` (page index) and `ps` (page size); `searchOrganizations`, `searchProjects` and `searchPublicProjects` default to `p: 1` and `ps: 100`. On SonarQube Cloud, several search and create operations also require an `organization` key.
    </Note>

    ## Return shape

    Every instruction returns the same envelope rather than the bare SonarQube response. On success:

    ```yaml
    operation: list          # list, read, create, update, delete or action
    itemType: Issues         # the entity family the instruction touched
    structuredData: {...}    # the raw SonarQube Web API response
    items: [...]             # list operations only
    jsonData: {...}          # read operations only
    location: SonarQube      # list operations only
    hint: '...'              # list operations only
    ```

    On failure the envelope holds a single `error` key containing the message shown in [Error handling](#error-handling).

    <Warning>
      Always read the SonarQube payload from `structuredData`, never from the top level of the output. `{{result.projectStatus.status}}` resolves to nothing; `{{result.structuredData.projectStatus.status}}` is the value you want.
    </Warning>

    For the field-level shape of `structuredData`, see the [SonarQube Web API reference](https://next.sonarqube.com/sonarqube/web_api), which documents each endpoint's response.

## Verify the connection

Run these read-only checks in order. Each one isolates a different layer, so the first failure tells you where to look.

<Steps>
  <Step title="Check the credential from Builder">
    Call `SonarQube.validateAuthentication` from an automation. A working setup returns an envelope whose `structuredData` reports the token as valid. An `error` key means the token or base URL is wrong; see [Error handling](#error-handling).
  </Step>
  <Step title="Check the tool manifest from the MCP endpoint">
    Send a `tools/list` JSON-RPC request to the **MCP Endpoint**. It must return the 46 tools listed in [Agent builder (Agent Creator)](#agent-builder-agent-creator). This method needs no key, so a failure here points at the endpoint URL, not at your configuration.
  </Step>
  <Step title="Check an end-to-end tool call from the agent">
    Ask the agent a read-only question such as "What SonarQube version are we on?" or "List my SonarQube organizations". A correct answer proves the key, the credential lookup and the SonarQube call all work.
  </Step>
</Steps>

The connector-agnostic checks that surround these three are in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation): confirm the runtime identity, run a narrow read, confirm that a resource the account must not see is refused, and leave the write path for last. Skip its non-allowlisted-agent check, which has no equivalent here: SonarQube has no allowlist, so any caller holding a valid key is accepted.

## Rotate, revoke and remove

| Task | Procedure |
|------|-----------|
| Rotate the SonarQube token | Generate a new user token in SonarQube, update the `sonarqubeToken` secret in the workspace, and save. Revoke the old token in SonarQube, or with `revokeUserToken`. MCP tool calls pick up the new value within 10 minutes; Builder instructions pick it up immediately |
| Cut off agent access without uninstalling | Clear the `sonarqubeToken` secret. Tool calls then fail with `SonarQube token not configured on this app instance.` while the app stays installed |
| Offboard the token owner | The token dies with the SonarQube account. Create a replacement token owned by a service account before disabling the person's account, and update the secret |
| Remove one agent's access | Remove the SonarQube capability from that agent and republish it. The connector performs no agent-level authorization, so the capability is the only gate |
| Uninstall the connector | Uninstall the SonarQube app from the workspace, then delete the `sonarqubeToken` secret and revoke that token in SonarQube. Removing the app instance invalidates its MCP API Key for credential lookups |

Uninstalling leaves the provisioned secret in place, as described in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall); this connector ships no uninstall handler, so deleting `sonarqubeToken` is a manual step. If you published a SonarQube capability in AI Governance, remove that entry too, or agent builders keep seeing a connector whose credential is gone. See [Remove or update a capability](/apps-store/marketplace/connectors/declare-capability#remove-or-update-a-capability).

## Error handling

Failed calls return a single message built from the HTTP status, the operation description, and SonarQube's own error body.

| Status | Message returned |
|--------|------------------|
| 400 | `Bad request while <operation>: <detail>` |
| 401 | `Authentication failed while <operation>. Check credentials. Detail: <detail>` |
| 403 | `Forbidden while <operation>. Check permissions. Detail: <detail>` |
| 404 | `Resource not found while <operation>. Detail: <detail>` |
| 429 | `Rate limit exceeded while <operation>. Wait and retry. Detail: <detail>` |
| 500 | `SonarQube server error while <operation>. Detail: <detail>` |
| Any other non-2xx, including 409 | `Error <status> while <operation>: <detail>` |

`<operation>` is the operation description of the instruction that failed, for example `search for issues` or `create a project`. `<detail>` is SonarQube's error body; SonarQube usually returns `{"errors":[{"msg":"..."}]}`, which the connector includes as raw JSON.

### Common issues

#### SonarQube token not configured on this app instance.

**Symptom:** every MCP tool call fails with this message, while `tools/list` still works.

**Cause:** the `sonarqubeToken` secret is empty in the workspace that installed the app.

**Owner:** workspace builder.

**Fix:** generate a user token in SonarQube under **My Account > Security > Generate Tokens**, set it as the `sonarqubeToken` secret, and save.

**Verify:** run the first step of [Verify the connection](#verify-the-connection), *Check the credential from Builder*.

#### SonarQube not configured. Set token in the workspace config.

**Symptom:** a Builder instruction returns this message instead of data.

**Cause:** same as above, seen from the Builder surface: neither the instruction arguments nor the app configuration supplied a token.

**Owner:** workspace builder.

**Fix:** fill the `sonarqubeToken` secret, or pass `token` and `baseUrl` explicitly to the instruction.

**Verify:** re-run the instruction and confirm the output has a `structuredData` key rather than an `error` key.

#### Missing required header

**Symptom:** `tools/call` fails with JSON-RPC error code `-32001` and this message:

```text
Missing required header: mcp-api-key
```

**Cause:** the capability wired into the agent does not send the workspace's **MCP API Key** header.

**Owner:** agent builder, with the workspace builder who holds the app instance.

**Fix:** copy the **MCP API Key** value from the SonarQube app instance, add it to the capability's header configuration, and save the agent.

**Verify:** re-run a read-only tool call from the agent.

#### Invalid API key

**Symptom:** `tools/call` fails with error code `-32001` and a message beginning `Invalid API key:`, followed by `Invalid key format`, `Invalid signature` or `Invalid payload`.

**Cause:** the key sent by the capability was truncated, edited, or belongs to a workspace whose signature no longer verifies.

**Owner:** workspace builder.

**Fix:** re-copy the **MCP API Key** from the app instance without altering it. If it still fails, reconfigure the app instance to have a fresh key issued, then update the capability.

**Verify:** re-run a read-only tool call from the agent.

#### Credentials lookup failed

**Symptom:** `tools/call` fails with error code `-32001` and a message of the form `Credentials lookup failed (<status>): <error>`.

**Cause:** the MCP endpoint reached your workspace's `getConfig` webhook but it did not return credentials. A `400` here means the token is not configured.

**Owner:** workspace builder.

**Fix:** confirm the SonarQube app is still installed in the workspace and that `sonarqubeToken` holds a value.

**Verify:** re-run a read-only tool call from the agent.

#### Authentication failed while ... Check credentials.

**Symptom:** SonarQube answers `401` on every operation.

**Cause:** the token is revoked or expired, or it belongs to a different SonarQube instance than the configured base URL.

**Owner:** workspace builder.

**Fix:** generate a fresh user token on the instance the base URL points at, update the `sonarqubeToken` secret, and confirm the base URL matches (`https://sonarcloud.io/api` for SonarQube Cloud, `https://<your-sonarqube-host>/api` for self-hosted).

**Verify:** call `SonarQube.validateAuthentication`.

#### Forbidden while ... Check permissions.

**Symptom:** SonarQube answers `403` on some operations while reads succeed.

**Cause:** the token owner lacks the SonarQube permission the operation needs. Administer-scoped operations, and `searchUserTokens` for another login, require elevated rights.

**Owner:** a SonarQube administrator, together with the workspace builder.

**Fix:** grant the token owner the missing SonarQube permission, or use a token owned by an account that already has it.

**Verify:** re-run the failing operation.

#### searchProjects returns nothing on a public organization

**Symptom:** `searchProjects` returns an empty list even though the organization has projects.

**Cause:** `searchProjects` is admin-scoped and lists only projects in organizations the token administers.

**Owner:** agent builder or workspace builder.

**Fix:** use `searchPublicProjects` with the `organization` key instead. It browses any organization, including public ones the token owner is not a member of.

**Verify:** re-run with `searchPublicProjects` and confirm the expected projects appear.

#### Badge tools return a JSON-encoded string

**Symptom:** `getProjectMeasureBadge` and `getProjectQualityGateBadge` return SVG markup wrapped in a JSON string rather than a renderable image.

**Cause:** SonarQube returns raw SVG, and the MCP layer serializes every payload as JSON.

**Owner:** workspace builder.

**Fix:** call the badge instructions from Builder instead, and write `structuredData` straight to a file or an HTTP response.

**Verify:** confirm the written file opens as an SVG image.
