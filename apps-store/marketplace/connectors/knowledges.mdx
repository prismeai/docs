The Knowledges app exposes the **Prisme.ai Knowledges API** (`/v1/knowledge_bases*`, served by the platform's `storage` workspace) — the RAG layer where documents and crawled web pages are chunked, embedded and searched. It can be consumed two ways: as a remote MCP server (`knowledges-mcp`) that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. Unlike third-party connectors, **there is no credential to paste**: the connector runs in the installing workspace's app-instance context and forwards the caller's own Prisme.ai identity to the Knowledges backend, which applies that caller's permissions. An agent therefore sees exactly the knowledge bases its user is allowed to see. Three entity tools cover 20 operations: knowledge bases, their documents and their web crawl sources.

## Prerequisites

- A Prisme.ai account on the same instance as the workspace running the connector. **No API key, OAuth client or third-party account is required** — the connector calls the platform's own Knowledges backend.
- The `owner`, `editor` or `admin` role on the workspace that will host the connector, if you are the one installing it. See [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin).
- Permission on the knowledge bases you intend to reach. Every call inherits the caller's own permissions: a user sees the knowledge bases they own or that were shared with them, and nothing else.
- (Optional) A **credential override**, if you want the connector to act under a fixed identity instead of the caller's — for example an unattended automation that must always reach the same knowledge base. Accepted credentials are an organization API key (`iak_…`), a user access token (`at:…`) or a session JWT.
- (Optional) A **base URL override**, if the Knowledges backend of your instance is not reachable at the default `{apiUrl}/workspaces/slug:storage/webhooks`.

<Note>
  Knowledge bases created through this connector are the same objects you see in the **Knowledges** product UI. The connector adds automation and agent access on top of them; it does not create a separate store.
</Note>

<Note>
  Knowledges replaces the deprecated [Storage connector](/apps-store/marketplace/connectors/storage-client), which exposed the same knowledge bases under the older `vectorStores` naming. Two things live only on that older connector: per-knowledge-base **API keys** and **RBAC access bindings**, and **agent skills** plus admin diagnostics. Keep it installed if you need those; use Knowledges for everything else.
</Note>

  ## Declare the capability in AI Governance (optional)

  The procedure is the standard one: publish from the configuration app with **Add to catalog**, described in [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog), or author the entry yourself as described in [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).

  Two values are specific to Knowledges:

  | Field | Value for Knowledges |
  |---|---|
  | Server URL | The MCP endpoint of the workspace running the connector, rendered by its configuration app: `https://api.<your-instance>/v2/workspaces/slug:<workspace>/webhooks/<app-instance>.mcp` |

  ```text

  ```

  `agent_id` is what lets Agent Creator identify the calling agent, and `attachment_urls` passes the URLs of files the user uploaded in the chat so the document tools can reach them. There is **no OAuth authorization block** to attach for this connector: authentication forwards the caller's own identity rather than a per-user OAuth token.

  <Warning>
    Declaring the capability makes the connector **available**; it does not authorize a specific agent. Per-agent gating is the **Authorized agents** allowlist in the connector's configuration app (see [Agent builder (Agent Creator)](#agent-builder-agent-creator)).   </Warning>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator create knowledge bases, ingest documents and search them through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed the Knowledges app in a workspace (see [Workspace builder (DSUL)](#workspace-builder-dsul)). Optionally, a platform administrator may have published a Knowledges capability in AI Governance (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    No credential is pasted into the agent. The connector forwards the calling user's Prisme.ai identity to the Knowledges backend, which applies that user's permissions — so an agent can only reach knowledge bases its user is allowed to reach.

    Wiring the capability follows the standard flow: the fastest path is **Install capability** on the agent's row in the configuration app, which allowlists the agent and attaches the tool in one action ([Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent)). If an organization owner or admin has published Knowledges to the catalog, pick it there instead, with the endpoint and Scope already wired ([Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog)). Either way the connector still enforces this workspace's allowlist.

    <Steps>
      <Step title="Install the connector in your workspace">
        Follow [Workspace builder (DSUL)](#workspace-builder-dsul): install **Knowledges** in your workspace. The default authentication mode needs no configuration.
      </Step>
      <Step title="Allowlist your agent and attach the tool">
        In that workspace's configuration app, open **Authorized agents** and select **Install capability** on your agent's row. To wire it by hand instead, tick the agent, save, then add a capability on the agent pointing at your workspace's MCP endpoint URL. Enabling **Allow all agents** stores the wildcard `*` and disables the per-agent gate entirely ([The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard)).
      </Step>
      <Step title="Set the capability Scope">
        Knowledges needs one identifier more than most connectors. Set the capability **Scope** to:

        ```text
        context_id,agent_id,user_id,attachment_urls
        ```

        `agent_id` lets Agent Creator identify the calling agent — without it the connector cannot tell which agent is calling and rejects the call. `attachment_urls` carries the URLs of files the user uploaded in the conversation, which you can pass to the document tools as `source_url`. See [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
      </Step>
      <Step title="Brief the agent in its system prompt">
        Wiring the capability is not enough: the agent also needs to know the MCP exists and when to reach for it. Add a short paragraph to the agent's system prompt, then save the agent. Copy-pasteable starter:

        ```text
        You have access to the Knowledges MCP server through three tools — `knowledges` (knowledge bases), `documents` (their sources) and `webSources` (web crawl seeds) — each taking an `action` argument. Use `knowledges` with action `search` to answer questions from an existing knowledge base, `documents` with action `add` to ingest a file the user uploaded (pass its native_file_id) or a URL (source_url), and `documents` with action `get` to report indexing status. Always confirm with the user before `delete` on a knowledge base or a document.
        ```

        Refine the trigger keywords (knowledge base names, business domains, typical user phrasings) so the agent reliably picks up the right intent in your context.
      </Step>
    </Steps>

    <Note>
      **Restricting to read-only (least privilege).** The connector never forces write permissions: it acts as the caller, so what an agent may do is exactly what its user may do on each knowledge base. To make an agent read-only, share the target knowledge bases with the calling users in a **read** role rather than as owners — write calls then fail with `403` while search keeps working (the connection itself stays healthy, since every check is a read). When the workspace uses the **credential override** mode instead, back the credential with an account that only holds read bindings. This is enforced by the Knowledges backend on every call, not by the connector, so it is a hard boundary rather than a declarative hint.
    </Note>

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the MCP endpoint URL. Identity is still resolved server-side, and the agent still has to be allowlisted in the configuration app. See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).
    </Note>

    ## Available Tools

    The MCP server exposes three entity-level tools, each dispatching across its actions through an `action` argument.

    ### `knowledges`

    | Action | Description |
    |--------|-------------|
    | `list` | List knowledge bases. `scope` accepts `owned`, `shared`, `all`, `agents` (comma-separated, default `owned,shared`); filter by `name` substring or `status`. |
    | `create` | Create a knowledge base. Only `name` is required; `embedding`, `dimensions`, `chunking_strategy`, `parser`, `file_parsing`, `provider` and `expires_after` default to the platform settings. |
    | `get` | Get a knowledge base by `knowledge_id`. Pass `include: "processing"` to probe live crawler status and metrics; otherwise those fields are `null` and only the persisted `processing.health` is returned. |
    | `update` | Update metadata (`name`, `description`, `chunking_strategy`, `parser`, `file_parsing`) and `crawl_settings`. |
    | `delete` | Delete a knowledge base. Cascades to its documents and vectors; native platform files are preserved. |
    | `search` | Semantic search. Hits carry `document_id`, which `documents` action `download` resolves into a link. |

    ### `documents`

    | Action | Description |
    |--------|-------------|
    | `list` | List a knowledge base's documents; filter by `status`, `source_type`, `origin`, `web_source_id`, `scope`, `conversation_id` or a `search` substring. |
    | `add` | Attach a source: `source_url` (a URL to ingest) and/or `native_file_id` (an already-uploaded platform file). Idempotent — re-adding the same source refreshes it. |
    | `get` | Get a document, including its indexing state (`status`, `last_error`, `indexed_at`). |
    | `update` | Edit `tags`, `metadata`, `expires_at` or `filename`. Source fields are immutable. |
    | `delete` | Detach the source and delete its vectors. The native file is never deleted. |
    | `getChunks` | List the chunks produced for a document (paginated). |
    | `reindex` | Re-run indexing on an existing document, optionally overriding `parser` or `chunking_strategy`. Returns `404` if the document does not exist — it never upserts. |
    | `download` | Resolve a browser-usable URL: a short-lived link for uploads, the original `source_url` otherwise. |

    ### `webSources`

    | Action | Description |
    |--------|-------------|
    | `list` | List the knowledge base's crawl seeds, each with its metrics, plus a knowledge-base-wide `summary`. |
    | `add` | Register a crawl start URL. URL-idempotent: re-adding a known URL returns the existing seed. |
    | `get` | Get a seed's configuration and metrics by `seed_id` (`seed_<uuid>`). |
    | `update` | Update a seed's `crawler_options`. The URL is immutable. |
    | `delete` | Delete a seed. Only pages attributed solely to it are removed. |
    | `recrawl` | Trigger an immediate crawl of the seed. Returns `409` if a crawl is already running for the knowledge base. |

    <Warning>
      Direct binary upload is not available over MCP. Upload the file to the platform first, then pass its `native_file_id` to `documents` action `add`. When the capability declares `attachment_urls`, files the user drops in the conversation are reachable as URLs and can be passed as `source_url`.
    </Warning>

    <Note>
      The tool automations only accept traffic coming from the MCP endpoint. A direct HTTP call to a tool's own webhook is rejected with `403` and the message `Direct calls are not allowed — use the MCP endpoint.`
    </Note>

    <Note>
      **Response size.** `limit` is clamped to `100` on every paginated action, and list or search payloads are trimmed to the first 100 items before reaching the agent, with a trailing `__truncated` marker telling it to narrow the query with filters or pagination (`page`, `limit`). Use `page` to walk the rest.
    </Note>

    <Note>
      Tool arguments accept an `agent_id` field, but on the MCP path it is only a transport-identity fallback for capabilities that do not inject the `agent-id` header. It is consumed for authorization and then stripped before the call reaches the Knowledges backend, so an agent cannot use it to bind a knowledge base or a document to another agent.
    </Note>

    ## Output Formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - **`verbose`** (default): human-readable text for LLM consumption.
    - **`structured`**: machine-readable JSON in `structuredContent`.
    - **`both`**: both text and structured content.

    ## Tool Details

    ### `knowledges` (action: `create`)

    ```json
    {
      "name": "knowledges",
      "arguments": {
        "action": "create",
        "name": "Product documentation",
        "description": "Public docs and release notes",
        "embedding": { "model": "text-embedding-3-small", "dimensions": 1536 }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `create`. |
    | `name` | Yes | Display name of the knowledge base. |
    | `description` | No | Free-text description. |
    | `embedding` | No | Object `{ model, dimensions }`. Defaults to the platform's embedding settings. |
    | `dimensions` | No | Shorthand for `embedding.dimensions`. |
    | `chunking_strategy` | No | Chunking configuration, passed through to the Knowledges API. |
    | `parser` | No | Parsing backend override: `tika`, `tika-ocr`, `unstructured`, `unstructured-ocr`, `llm`. |
    | `file_parsing` | No | Per-modality model overrides: `{ image, audio, document }`. |
    | `provider` | No | Vector index backend. Defaults to the platform setting. |
    | `expires_after` | No | TTL configuration for the knowledge base. |

    Returns the created knowledge base with HTTP `201` and `status: active` — provisioning is synchronous.

    ### `knowledges` (action: `search`)

    ```json
    {
      "name": "knowledges",
      "arguments": {
        "action": "search",
        "knowledge_id": "vs_81c2e3ae9d3c4d9989e3c06b95f01a3f",
        "query": "What is the retention policy for exports?",
        "limit": 8,
        "min_score": 0.35,
        "filter": { "op": "eq", "field": "tags.department", "value": "legal" }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `search`. |
    | `knowledge_id` | Yes | The knowledge base to search. |
    | `query` | Yes | Natural-language query. |
    | `limit` | No | Maximum number of hits. |
    | `min_score` | No | Score threshold below which hits are dropped. |
    | `filter` | No | Structured filter AST over `tags.*` fields: a leaf `{ op, field, value }` (`op` = `eq`, `ne`, `in`, `nin`, `gt`, `gte`, `lt`, `lte`, `exists`, `matches`) composed with `{ and: [...] }`, `{ or: [...] }`, `{ not: {...} }`. |
    | `scope` | No | `knowledge` or `conversation`. |
    | `conversation_id` | No | Required when `scope` is `conversation`. |

    ### `documents` (action: `add`)

    ```json
    {
      "name": "documents",
      "arguments": {
        "action": "add",
        "knowledge_id": "vs_81c2e3ae9d3c4d9989e3c06b95f01a3f",
        "source_url": "https://docs.example.com/handbook.pdf",
        "filename": "handbook.pdf",
        "tags": { "department": "hr", "year": "2026" }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `add`. |
    | `knowledge_id` | Yes | Target knowledge base. |
    | `source_url` | No* | Stable provenance URL to ingest. Also the dedup key for non-native sources. |
    | `native_file_id` | No* | Id of a file already uploaded to the platform. A missing file returns `404 FILE_NOT_FOUND`. |
    | `source_type` | No | `uploaded_file`, `remote_file`, `web_page` or `connector_document`. Inferred when omitted. |
    | `fetch_url` | No | Ephemeral bytes-retrieval URL for connector or remote sources. Never returned in responses. |
    | `filename` | No | Display name of the document. |
    | `mime_type` | No | Content type hint for the ingested source. |
    | `bytes` | No | Declared size of the source. |
    | `chunking_strategy` | No | Per-document chunking override. |
    | `tags` | No | Key/value **object** (not an array), used later as search filters. |
    | `metadata` | No | Free-form key/value object. |
    | `expires_at` | No | Unix seconds or ISO date after which the document is dropped. |

    <Note>
      \* At least one of `source_url` / `native_file_id` is required. Adding a source that already exists returns `200` with the same document id and reschedules indexing, so re-running an ingestion never creates duplicates. A brand-new source returns `201`.
    </Note>

    ### `documents` (action: `get`)

    ```json
    {
      "name": "documents",
      "arguments": {
        "action": "get",
        "knowledge_id": "vs_81c2e3ae9d3c4d9989e3c06b95f01a3f",
        "document_id": "<document id returned by add or list>"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `get`. |
    | `knowledge_id` | Yes | Knowledge base the document belongs to. |
    | `document_id` | Yes | The document id returned by `add` / `list`. |

    Returns the document with its indexing state: `status` (`queued`, `in_progress`, `completed`, `failed`, `fetch_expired`, `rejected`), `last_error` and `indexed_at`. This is the call to make when a user asks "is my file ready?".

    ### `webSources` (action: `add`)

    ```json
    {
      "name": "webSources",
      "arguments": {
        "action": "add",
        "knowledge_id": "vs_81c2e3ae9d3c4d9989e3c06b95f01a3f",
        "url": "https://docs.example.com/"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | Must be `add`. |
    | `knowledge_id` | Yes | Knowledge base that owns the crawl. |
    | `url` | Yes | Crawl start URL. Immutable once created, and SSRF-validated. |
    | `crawler_options` | No | Advanced crawler tuning for this seed. |

    <Warning>
      Crawl volume and scheduling are **not** per-seed: there is one crawler per knowledge base, configured through `knowledges` action `update` with a `crawl_settings` object accepting `webpages_limit` (integer or `null` to re-inherit the governance default, and capped by governance), `periodicity` (**seconds** between crawls, or `null` for manual) and `paused` (boolean, pauses or resumes the whole crawler). Adding a seed to a paused knowledge base does not resume the crawler.
    </Warning>

    ## Workspace builder

    **Goal:** install the connector in a workspace, pick an authentication mode, and call knowledge-base operations from your automations.

    ## Installation

    Installation follows the standard connector flow — [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), then [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app) and [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector) — with one shortcut: search for **Knowledges** in **Apps**, install it, and stop there. The default authentication mode needs no credential at all, so the only reason to open the **Configuration app** is to allowlist agents, override the credential, or install the capability.

    Installing the app provisions two workspace secrets, `knowledgesAuth` and `knowledgesAuthorizedAgents`, and writes the bindings that let the connector read them at call time ([What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions)). Re-running the install is idempotent: existing secrets are left untouched.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Auto-populated on install; open this link to set the authentication mode, manage the authorized-agents allowlist and install the capability. |

    The configuration app drives everything; the app instance itself has no per-field credential form. Authentication is stored in the `knowledgesAuth` secret shaped as `{ accessToken?, baseUrl? }`, and the allowlist in `knowledgesAuthorizedAgents` (comma-separated agent ids, or `*` for all). Both are resolved server-side at call time and never reach the agent.

    The MCP endpoint of the instance follows the standard app-instance webhook form, and the configuration app renders the exact value for your instance ([Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint)):

    ```text
    https://api.<your-instance>/v2/workspaces/slug:<workspace>/webhooks/<app-instance>.mcp
    ```

    Pick one of the two authentication modes:

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | **Caller identity** (default) | Nothing — leave `accessToken` empty | Agents and automations that should see exactly what their user sees. Permissions are enforced per call by the Knowledges backend. |
    | **Credential override** | An organization API key (`iak_…`), a user access token (`at:…`) or a session JWT | Unattended flows (crons, webhooks triggered by anonymous callers) that must always act under one fixed identity, regardless of who triggered them. |

    <Note>
      In caller-identity mode the connector sends no credential of its own: the platform forwards the caller's user and workspace identity on cross-workspace calls (`forwardWorkspaceAuth`), and the Knowledges backend authorizes from there. A cron or an anonymous webhook has no user to forward — that is when the credential override is needed. The connector routes the credential by kind: an `iak_…` organization key travels on the `x-prismeai-api-key` header, everything else on `Authorization: Bearer`.
    </Note>

    <Warning>
      A credential override is a **shared identity**: every caller of this workspace's connector acts as that account, and the Knowledges audit trail attributes their reads and writes to it rather than to the individual user. Scope the backing account to the minimum set of knowledge bases, and prefer caller identity whenever a real user is present.
    </Warning>

    <Note>
      `knowledgesAuth` also accepts a `baseUrl` field, which overrides the Knowledges backend base URL. Leave it empty to use the environment default, `{apiUrl}/workspaces/slug:storage/webhooks`.
    </Note>

    ## Available Instructions

    Every instruction resolves authentication from the workspace configuration and targets the Knowledges API of the current environment.

    ### Knowledge bases

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `listKnowledges` | List knowledge bases; `scope` = `owned,shared,all,agents` (default `owned,shared`), plus `name`, `status`, `agent_id`, `limit`, `page`. | `{ data: [KnowledgeBase], total, page, limit }` |
    | `createKnowledge` | Create a knowledge base by `name`; optional `description`, `provider`, `embedding`, `dimensions`, `chunking_strategy`, `parser`, `file_parsing`, `expires_after`, `agent_id`. | `KnowledgeBase` (HTTP 201, `status: active`) |
    | `getKnowledge` | Get one by `knowledge_id`; `include: "processing"` probes live crawler status and metrics. | `KnowledgeBase` |
    | `updateKnowledge` | Update `name`, `description`, `chunking_strategy`, `parser`, `file_parsing` and `crawl_settings`. | `KnowledgeBase` |
    | `deleteKnowledge` | Delete by `knowledge_id`; cascades documents, vectors and bindings (native files preserved). | `{ status: "deleting" }` (HTTP 202, completes synchronously) |
    | `searchKnowledge` | Semantic search by `query`; optional `limit`, `min_score`, `filter` AST, `scope`, `conversation_id`, `agent_id`. | Search results; every hit carries a `document_id` |

    ### Documents

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `listDocuments` | List a knowledge base's documents; filters `status`, `source_type`, `origin`, `web_source_id`, `search`, `scope`, `conversation_id`. | `{ data: [Document], total, page, limit }` |
    | `addDocument` | Attach `source_url` and/or `native_file_id`; optional `source_type`, `fetch_url`, `filename`, `mime_type`, `bytes`, `tags`, `metadata`, `expires_at`, `chunking_strategy`, `agent_id`. | `Document` (201 new, 200 refreshed) |
    | `getDocument` | Get a document by `document_id`, with `status`, `last_error`, `indexed_at`. | `Document` |
    | `updateDocument` | Edit `tags`, `metadata`, `expires_at`, `filename`. | `Document` |
    | `deleteDocument` | Detach the source and delete its vectors; the native file survives. | Empty (HTTP 204) |
    | `getDocumentChunks` | List the document's chunks; `limit` defaults to 50, capped at 100. | Paginated chunks |
    | `reindexDocument` | Re-index an existing document; optional `parser` (or `"default"` to clear the override), `chunking_strategy`, `reason`. Existing documents only — `404` otherwise. | `Document` (HTTP 202, `status: in_progress`) |
    | `getDocumentSourceUrl` | Resolve a download URL: short-lived share link for uploads (unix `expires_at`), `source_url` as-is otherwise (`expires_at: null`). | `{ url, expires_at }` |

    ### Web sources

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `listWebSources` | List crawl seeds with per-seed metrics, plus a knowledge-base-wide `summary` (web-page total and unattributed residual). | `{ data: [WebSource], summary, total, page, limit }` |
    | `addWebSource` | Register a crawl start `url` (SSRF-validated, idempotent); optional `crawler_options`. | `WebSource` (200 when the URL is already registered) |
    | `getWebSource` | Get a seed by `seed_id`, with its configuration and metrics. | `WebSource` |
    | `updateWebSource` | Update `crawler_options`. The `url` is immutable. | `WebSource` |
    | `deleteWebSource` | Delete a seed; only pages attributed solely to it are removed. | Empty (HTTP 204) |
    | `recrawlWebSource` | Trigger an immediate crawl of the seed. | `WebSource` (HTTP 202, `metrics.last_run_status: running`) |

    <Note>
      App-mode instructions never throw on an API failure: they return `{ error: { isError: true, content: [{ type: "text", text: "…" }] } }`. Test `{{result.error}}` in your automation before consuming the payload.
    </Note>

    <Note>
      `getDocumentSourceUrl` is a lazy resolver. Call it on demand, for example when a user clicks a citation, rather than eagerly for every search hit.
    </Note>

    ## DSUL Examples

    ### Search a knowledge base and keep the best hits

    ```yaml
    - Knowledges.searchKnowledge:
        knowledge_id: '{{config.knowledgeId}}'
        query: '{{body.question}}'
        limit: 8
        min_score: 0.3
        output: hits
    ```

    ### Ingest a document and tag it

    ```yaml
    - Knowledges.addDocument:
        knowledge_id: '{{config.knowledgeId}}'
        source_url: '{{document.url}}'
        filename: '{{document.name}}'
        tags:
          department: '{{document.department}}'
          year: '{{run.year}}'
        output: created
    ```

    ### Poll a document until indexing completes

    ```yaml
    - repeat:
        until: 10
        do:
          - Knowledges.getDocument:
              knowledge_id: '{{config.knowledgeId}}'
              document_id: '{{created.id}}'
              output: doc
          - conditions:
              '{{doc.status}} == "completed"':
                - break:
                    scope: all
          - wait:
              timeout: 5
    ```

    ### Register a crawl seed and cap the crawl

    `periodicity` is expressed in **seconds** (`604800` is one week); set it to `null` to crawl only on demand.

    ```yaml
    - Knowledges.addWebSource:
        knowledge_id: '{{config.knowledgeId}}'
        url: 'https://docs.example.com/'
        output: seed
    - Knowledges.updateKnowledge:
        knowledge_id: '{{config.knowledgeId}}'
        crawl_settings:
          webpages_limit: 500
          periodicity: 604800
          paused: false
    ```

    ### Rebuild a document with a different parser

    ```yaml
    - Knowledges.reindexDocument:
        knowledge_id: '{{config.knowledgeId}}'
        document_id: '{{doc.id}}'
        parser: 'unstructured-ocr'
        reason: 'scanned PDF, OCR required'
    ```

## Verify the connection

Run these checks after installing or after changing the authentication mode. They replace the generic identity and allowlist checks in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation), because Knowledges resolves identity per call rather than from a stored provider account.

<Steps>
  <Step title="Test the backend connection from the configuration app">
    Open the configuration app and run its connection test. It calls `GET /v1/knowledge_bases?limit=1` with the resolved authentication and returns `{ ok: true, baseUrl }` on success. A failure returns `{ ok: false, error }` with the HTTP status of the probe. The probe deliberately uses a plain read that any authenticated user can perform, so a valid configuration never reports a false failure.
  </Step>
  <Step title="Confirm App mode from a Builder automation">
    Call `Knowledges.listKnowledges` with `limit: 1` and inspect the output. A `{ data, total, page, limit }` envelope confirms the instruction path; an `error` object means authentication or permissions failed.
  </Step>
  <Step title="Confirm MCP mode from the agent">
    Ask the published agent to list your knowledge bases. It should return only the bases the signed-in user owns or that were shared with them. If it returns an authorization message instead, the agent is missing from the allowlist or the capability **Scope** does not inject `agent_id`.
  </Step>
  <Step title="Check the negative case">
    Ask the agent about a knowledge base the signed-in user has no access to. The call must fail with `403`, not return content. This confirms the backend, not the connector, is enforcing permissions.
  </Step>
</Steps>

## Rotation, revocation and removal

These are the Knowledges-specific cases of the standard flow described in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall).

| Task | How |
|------|-----|
| Rotate the credential override | Mint a new organization API key or access token, paste it in the configuration app, save, then revoke the old one at its source. Existing calls pick up the new value on the next request. |
| Return to caller identity | Clear the `accessToken` field in the configuration app and save. The connector falls back to forwarding the caller's identity. |
| Revoke one agent's access | Untick the agent in **Authorized agents** and save, or replace `*` with an explicit list. The next `tools/call` from that agent is refused. |
| Offboard a user | Nothing to do on the connector in caller-identity mode: disabling the user's platform account removes their access on the next call. In credential-override mode, check whether the shared credential belongs to the departing user and rotate it if so. |
| Remove the connector | Uninstall the app instance from **Apps**. The workspace secrets `knowledgesAuth` and `knowledgesAuthorizedAgents` are not removed by the uninstall — delete them from the workspace security settings if the credential must not survive. Knowledge bases and documents live in the Knowledges backend and are unaffected. |

<Warning>
  Uninstalling the connector does **not** delete any knowledge base. To remove the data, delete the knowledge bases themselves (`deleteKnowledge`, or the Knowledges product UI) before uninstalling.
</Warning>

## Error Handling

The Knowledges API uses standard HTTP status codes. The connector normalizes them into a single text message and never echoes the raw response body, which may carry sensitive metadata.

| HTTP Status | Meaning | Typical Cause |
|-------------|---------|----------------|
| `400` | Bad Request | Missing `action`, unknown action for the entity, malformed `filter` AST, `tags` sent as an array instead of an object. |
| `401` | Unauthorized | The backend rejected the forwarded identity, or the credential override. Anonymous and cron callers have no identity to forward. |
| `403` | Forbidden | The caller has no access to this knowledge base or document, or only a read binding on a write call. |
| `404` | Not Found | Unknown `knowledge_id`, `document_id` or `seed_id` — or a `native_file_id` that does not exist. |
| `409` | Conflict | `webSources` action `recrawl` while a crawl is already running for this knowledge base. |
| `413` | Payload Too Large | The ingested source exceeds the platform's document size limit. |
| `429` | Rate Limited | Too many indexing or search calls in a short window. Wait and retry. |
| `500` | Server Error | Transient Knowledges backend error. Retry with exponential backoff. |
| `502` | Upstream Unavailable | The crawler or the vector backend is unreachable. |

Over MCP, a failing tool call comes back as an `isError` result reading `Tool <name> failed (<status>): <message>`, so the agent can report the failure instead of retrying blindly.

### Common Issues

**"This agent is not authorized to use this connector"**: the calling agent is not in the connector's allowlist. Open the configuration app → **Authorized agents**, tick the agent and save, or enable **Allow all agents**. The **Install capability** button does this for you ([Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent)).

**"The calling agent could not be identified"**: the MCP capability does not inject the agent id. Set its **Scope** to `context_id,agent_id,user_id,attachment_urls` and retry, then allow the agent in the configuration app. This Scope is unrelated to any OAuth scope ([What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means)).

**"Direct calls are not allowed — use the MCP endpoint"**: something called a tool automation's webhook directly. Agents must go through the `.mcp` endpoint; Builder automations must call the App instructions (`Knowledges.listKnowledges:` and friends) instead.

**"Unknown tool `<name>`"**: the tool name in the `tools/call` request does not match any tool the server exposes. The three valid names are `knowledges`, `documents` and `webSources`.

**`401` from a cron or a webhook**: scheduled runs and anonymous webhooks carry no user identity to forward. Set a credential override in the configuration app so the connector acts under a fixed identity.

**A search returns nothing while the UI shows documents**: check the documents' `status` with `documents` action `get`. Sources still `queued` or `in_progress` are not searchable yet, and a `failed` document reports why in `last_error`.

**A filter matches nothing**: only `tags.*` fields are filterable, and tags must have been set as a key/value **object** at ingestion time (`{"department": "hr"}`, not `["hr"]`).

**A list stops at 100 items**: `limit` is clamped to `100` and longer payloads are trimmed before reaching the agent. Narrow the query with filters, or page through the results with `page`.

**Re-adding a file creates no new document**: this is intended. `documents` action `add` is an idempotent upsert on the source key — the same `source_url` or native file returns the existing document id and reschedules indexing.

**Deleting a document leaves the file in place**: also intended. `documents` action `delete` detaches the source and drops its vectors; the native platform file is never deleted by the connector.
