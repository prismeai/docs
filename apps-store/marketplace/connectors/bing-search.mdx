The Bing Search connector (workspace slug `tools-search-bing`, published as **Bing Web Search (Microsoft Foundry)**) exposes web search as a remote MCP server with a single tool, `bing_search`. Each call sends one synchronous request to the Foundry project **Responses** API (`POST /openai/v1/responses`) carrying the `bing_grounding` tool with `tool_choice: required`, and returns the grounded answer together with its Microsoft URL citation annotations in the standard MCP `content` shape. The connector creates no assistants, threads, or runs, and it does not poll.

Authentication to Azure is a **shared service credential**: one Microsoft Entra ID application (service principal) configured once on the connector workspace, using the OAuth 2.0 client credentials flow. There is no per-user sign-in and no App mode credential form.

## Operating model and runtime identity

This connector supports exactly one authentication method, so there is no credential choice to make. Understand what it implies before you configure it.

| Property | Value |
|---|---|
| Authentication method | OAuth 2.0 client credentials against Microsoft Entra ID (`config.auth.type` is `oauth_client_credentials`) |
| Runtime identity seen by Azure | The Entra application (service principal) configured on the connector workspace, never the end user |
| Permission enforcement point | Azure role assignments on the Foundry resource or project, plus the Bing Grounding connection referenced by `bing_connection_id` |
| Credential scope | Shared across every agent and every user that can reach the MCP endpoint |
| Caller authentication | The MCP endpoint requires an authenticated Prisme.ai principal: a user JWT, a workspace JWT, or an organization API key |
| Audit attribution in Azure | All searches appear as the shared service principal, not as the invoking user |

<Warning>
  Because the Azure credential is a shared service principal, every caller that can reach the MCP endpoint searches with the same identity and consumes the same Azure quota. Azure-side logs cannot tell one Prisme.ai user from another. Keep the workspace `editor` role restricted to the people who are allowed to change the [Foundry configuration fields](#foundry-configuration-fields) and the [workspace secrets](#workspace-secrets), and give the service principal the least-privileged role that lets it call the project Responses endpoint.
</Warning>

The connector performs read-only web search. It creates nothing in your Foundry project and writes nothing to your business systems.

## Prerequisites

### Azure prerequisites

- An **Azure subscription** with an **Azure AI Foundry** resource and a project inside it.
- A **model deployment** in that project for the model named in `foundry_model`. It must be a GPT-5.x deployment that supports the Foundry Responses API and the `bing_grounding` tool. The connector ships no default model, so this value is always yours to supply.
- A **Grounding with Bing Search** resource connected to the project. Note the full Azure resource ID of the project connection; it is the value of `bing_connection_id`. It must belong to the Foundry project you configure, otherwise the Responses call fails.
- Permission in **Microsoft Entra ID** to create an app registration and a client secret, or an existing service principal you can reuse.
- Permission to create **role assignments** on the Foundry resource or project.

### Prisme.ai prerequisites

- Access to the `tools-search-bing` workspace with the `editor` role, which is what grants `update` on the workspace and `manage` on its automations.
- The platform API URL for your environment, used to build the MCP endpoint.
- For the agent builder: an agent in Agent Creator that you can edit and publish.

<Note>
  This connector needs no Microsoft Graph permissions and no Graph admin consent, unlike the Outlook, SharePoint, Excel, and Word connectors. Access is governed entirely by Azure role assignments on the Foundry project and by the Bing Grounding connection.
</Note>

## Register the Azure application

Perform these steps in the Azure portal as the Azure administrator, then hand the values listed in step 5 to the workspace builder, who uses them in [Configure the connector workspace](#configure-the-connector-workspace).

<Steps>
  <Step title="Create the app registration">
    In **Microsoft Entra ID**, open **App registrations** and select **New registration**. Give it a name that identifies this connector, leave the redirect URI empty (the client credentials flow does not use one), and select **Register**.
  </Step>
  <Step title="Copy the identifiers">
    On the application **Overview** page, copy the **Directory (tenant) ID** and the **Application (client) ID**.
  </Step>
  <Step title="Create a client secret">
    Open **Certificates & secrets**, select **New client secret**, set an expiry that matches your rotation policy, and select **Add**. Copy the secret **Value** immediately; Azure shows it only once.
  </Step>
  <Step title="Grant the service principal a role on Foundry">
    On the Azure AI Foundry resource or project, open **Access control (IAM)**, select **Add role assignment**, choose the **Azure AI User** role, and assign it to the application you registered. This is the built-in Azure AI Foundry role that grants data-plane access to the project, which is what the Responses endpoint requires. See the [Azure AI Foundry role-based access control reference](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/rbac-azure-ai-foundry) for the full role list.
  </Step>
  <Step title="Hand off the configuration values">
    Send the workspace builder, through your approved secret-sharing channel and never in a chat prompt or a ticket comment: the tenant ID, the client ID, the client secret, the token scope (`https://ai.azure.com/.default`, the `.default` scope of the Azure AI Foundry data plane), the Foundry base URL, the project name, the model deployment name, and the Bing Grounding project connection resource ID. All eight values are stored as workspace secrets, so treat the whole set as confidential.
  </Step>
</Steps>

## Configure the connector workspace

Perform these steps in Builder, on the `tools-search-bing` workspace, as the workspace builder, using the values handed over in [Register the Azure application](#register-the-azure-application).

### Workspace secrets

Store the Azure credential **and the Foundry coordinates** in workspace secrets first. The connector configuration references these secrets by name, so no tenant, subscription, project, or credential value ever appears in a visible configuration field.

| Secret | Description |
|--------|-------------|
| `AZURE_TENANT_ID` | Microsoft Entra ID directory (tenant) ID |
| `AZURE_CLIENT_ID` | Application (client) ID of the registered app |
| `AZURE_CLIENT_SECRET` | Client secret value of the registered app |
| `AZURE_TOKEN_SCOPE` | OAuth scope requested in the client credentials flow, for the Azure AI Foundry data plane: `https://ai.azure.com/.default` |
| `FOUNDRY_BASE_URL` | Foundry resource URL, or the full project endpoint |
| `FOUNDRY_PROJECT` | Foundry project name |
| `FOUNDRY_MODEL` | Name of the GPT-5.x model deployment used for the Responses call |
| `BING_CONNECTION_ID` | Full Azure resource ID of the Grounding with Bing Search project connection |

The connector reads each one through the matching configuration field. `azure_tenant_id`, `azure_client_id`, `azure_client_secret`, `azure_token_scope`, `foundry_base_url`, `foundry_project`, `foundry_model`, and `bing_connection_id` are pre-bound to `{{secret.AZURE_TENANT_ID}}`, `{{secret.AZURE_CLIENT_ID}}`, `{{secret.AZURE_CLIENT_SECRET}}`, `{{secret.AZURE_TOKEN_SCOPE}}`, `{{secret.FOUNDRY_BASE_URL}}`, `{{secret.FOUNDRY_PROJECT}}`, `{{secret.FOUNDRY_MODEL}}`, and `{{secret.BING_CONNECTION_ID}}`.

<Warning>
  Never paste the client secret into a visible configuration field, an agent system prompt, an automation, or a commit. Only `AZURE_CLIENT_SECRET` in workspace secrets is a supported location for it.
</Warning>

### Foundry configuration fields

These fields point the connector at your Azure AI Foundry project and Bing Grounding connection. The connector's authentication form declares eight of them, with the labels shown below; `provider` is a fixed configuration value and has no form field.

| Field | Form label | Description | Example |
|-------|------------|-------------|---------|
| `provider` | — | Search provider identifier | `bing` |
| `foundry_base_url` | **Foundry base URL** | Foundry resource URL, or a full project endpoint. The connector appends `/api/projects/<project>` only when that path is absent, and it tolerates a trailing slash or a trailing `/openai/v1/responses`. | `https://<resource-name>.services.ai.azure.com` |
| `foundry_project` | **Foundry project** | Project name used to build the Foundry project endpoint | `<project-name>` |
| `foundry_model` | **Foundry model deployment** | GPT-5.x deployment compatible with Foundry Responses and `bing_grounding` | `<model-deployment-name>` |
| `bing_connection_id` | **Bing project connection ID** | Full Azure resource ID of the Grounding with Bing project connection. It must belong to the configured Foundry project. | `/subscriptions/<subscription-id>/resourceGroups/<resource-group>/providers/Microsoft.CognitiveServices/accounts/<resource-name>/projects/<project-name>/connections/<connection-name>` |
| `azure_tenant_id` | **Azure Tenant ID** | Microsoft Entra ID directory (tenant) ID | `<tenant-id>` |
| `azure_client_id` | **Azure Client ID** | Application (client) ID of the registered app | `<client-id>` |
| `azure_client_secret` | **Azure Client Secret** | Client secret of the registered app, declared as a secret field | `<client-secret>` |
| `azure_token_scope` | **Microsoft Foundry OAuth scope** | Scope requested in the client credentials flow | `https://ai.azure.com/.default` |

All eight form fields are required. A call made while any of `foundry_base_url`, `foundry_project`, `foundry_model`, or `bing_connection_id` is empty fails before Azure is contacted; see [Troubleshooting](#troubleshooting).

<Note>
  `foundry_api_version` is gone. The project Responses endpoint is `/openai/v1/responses`, which takes no `api-version` query parameter. Remove any leftover `foundry_api_version` override from an instance configured before the Responses migration.
</Note>

### Default search options

These values apply when the agent omits the matching `bing_search` argument.

| Field | Default | Description |
|-------|---------|-------------|
| `default_count` | `5` | Number of results requested when `num_results` is omitted. The effective count is clamped to the range 1 to 10. |
| `default_market` | `en-US` | Market code sent to Bing Grounding when `market` is omitted. Its language part also becomes the `set_lang` search parameter, so `fr-FR` sends `set_lang: fr`. |
| `default_freshness` | `Week` | Recency filter applied when `freshness` is omitted |
| `token_cache_ttl` | `3300` | Maximum lifetime in seconds of the cached Azure access token. The connector falls back to `3300` when the field is empty. |

<Warning>
  `default_freshness` is `Week`, so a call that omits `freshness` returns only results from the past week. Raise it to `Month` in the configuration, or have the agent pass `freshness` explicitly, when you need older sources.
</Warning>

<Note>
  `token_cache_ttl` is a ceiling, not the actual lifetime. The connector caches the token for `min(expires_in - 300, token_cache_ttl)` seconds, where `expires_in` is what Microsoft Entra ID granted, so a tenant that issues short-lived tokens never gets an already-expired token served from the cache. The cache entry is also keyed on the tenant, client, scope, and normalized project endpoint, so changing any of those four values bypasses the previous entry immediately.
</Note>

Select **Save** to persist the configuration. The change takes effect on the next MCP call; no republish is required.

## Connect an agent to the MCP endpoint

Perform these steps in Agent Creator as the agent builder, after the workspace builder confirms that [the connector workspace configuration](#configure-the-connector-workspace) is saved.

The MCP endpoint of the connector workspace is:

```text
<api-url>/workspaces/slug:tools-search-bing/webhooks/bing-search/mcp
```

Replace `<api-url>` with the platform API URL of your environment, for example `https://api.studio.prisme.ai/v2` on production.

<Steps>
  <Step title="Open the agent">
    In Agent Creator, open the agent you want to extend and go to its capabilities.
  </Step>
  <Step title="Add the MCP capability">
    Add a capability of type MCP and set its server URL to the endpoint above. The endpoint authenticates the caller's Prisme.ai principal, so no extra header or API key is needed. The Azure credential is resolved server-side and is never sent to the agent.
  </Step>
  <Step title="Save the agent">
    Select **Save**. The agent now discovers the `bing_search` tool through `tools/list`.
  </Step>
  <Step title="Brief the agent">
    Add the tool guidance below to the agent's system instructions, then select **Save** again. Publish the agent when you are ready to expose it to end users.
  </Step>
</Steps>

### Brief the agent in its system prompt

Attaching the capability is not enough; the agent also needs to know when to reach for the tool. Use this starter and adapt the trigger topics to your context.

```text
You have access to the Bing Search MCP server (tool: bing_search). Use it whenever the answer depends on fresh, public web information: news, regulatory updates, market data, product specifications, factual lookups. Pass the user's intent as `query`. Set `market` to match the user's language (for example fr-FR for French). Set `freshness` explicitly: the default is Week, so pass Month when the user asks about older material and Day for breaking news. Keep `num_results` between 1 and 10. Always cite the source URLs returned by the tool.
```

<Note>
  For AI Knowledge agents that have no native MCP capability picker, add the connector under **Advanced > Tools** on the **MCP** tab and paste the same endpoint URL. Prefer the Agent Creator capability path for new agents.
</Note>

## Tool reference

The connector exposes one tool. The MCP endpoint delegates every `bing_search` call to the workspace's `web-search` automation, which is where the Foundry Responses call happens.

| Tool | Description |
|------|-------------|
| `bing_search` | Web search powered by Bing Grounding via Microsoft Foundry Responses. Returns grounded text with Microsoft URL citation annotations. |

### bing_search arguments

Every optional argument falls back to the matching value in [Default search options](#default-search-options).

| Argument | Type | Required | Description |
|----------|------|----------|-------------|
| `query` | string | Yes | Search query. An empty or missing value returns an error result. |
| `num_results` | number | No | Number of results. Falls back to `default_count`. The value is rounded down and clamped to the range 1 to 10 rather than rejected, so `99` becomes `10` and `0` becomes `1`. |
| `market` | string | No | Market code, for example `en-US` or `fr-FR`. Falls back to `default_market`, then to `en-US`. Its language part is sent as `set_lang`. |
| `freshness` | string | No | Recency filter: `Day`, `Week`, or `Month`, forwarded to Bing Grounding unchanged. Falls back to `default_freshness`. Any other value is dropped and the search runs with no recency filter at all. |

Any tool name other than `bing_search` returns the JSON-RPC error `-32601` with the message `Tool not found: <name>`.

## MCP protocol surface

The endpoint speaks JSON-RPC 2.0 over HTTP POST and answers four methods.

| Method | Result |
|--------|--------|
| `initialize` | `protocolVersion` `2025-06-18`, `capabilities.tools`, and `serverInfo` `{ "name": "bing-search", "version": "1.0.0" }` |
| `notifications/initialized` | HTTP `202` with an empty body |
| `tools/list` | The `bing_search` tool definition and its input schema |
| `tools/call` | The tool result for `bing_search`, or error `-32601` for any other tool |

Any other method returns the JSON-RPC error `-32601` with the message `Method not found: <method>`. A request that carries no authenticated Prisme.ai principal returns HTTP `401` and the JSON-RPC error `-32000` with the message `Authentication required`.

### Call examples

Search with the configured defaults:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "bing_search",
    "arguments": {
      "query": "Azure AI Foundry Bing Grounding documentation"
    }
  }
}
```

Search a French market, restricted to the past day:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "bing_search",
    "arguments": {
      "query": "actualites intelligence artificielle entreprise",
      "num_results": 5,
      "market": "fr-FR",
      "freshness": "Day"
    }
  }
}
```

### Response format

Each `output_text` block that Foundry returns becomes one entry in `content`. Its text and its Microsoft URL citation annotations are forwarded verbatim, with no citation rewriting, so a single call can return more than one text block:

```json
{
  "content": [
    {
      "type": "text",
      "text": "Grounded answer text with inline citation markers",
      "annotations": [
        {
          "type": "url_citation",
          "url": "https://example.com/source",
          "title": "Source title"
        }
      ]
    }
  ],
  "isError": false
}
```

Failures inside the tool are returned as a tool result with `isError` set to `true` and a single text block carrying the message, rather than as a JSON-RPC error. Every such failure also emits a Prisme.ai `error` event on the workspace, so you can trace a call in the activity feed by its `correlationId`. The event names are `AzureFoundryConfigurationError`, `AzureFoundryAuthenticationFailed`, `AzureFoundryResponsesFailed`, `AzureFoundryResponseIncomplete`, and `AzureFoundryResponseEmpty`, and each payload carries the stage, the provider code and message, the model, and the project.

## Verify the connector

Run these checks in order. Stop at the first failure and use the matching entry in [Troubleshooting](#troubleshooting).

1. In Builder, open the `tools-search-bing` workspace and run the `tests-run-all` automation. It chains the `tests-mcp` and `tests-web-search` suites and returns a consolidated report. Expected result: `report.status` is `✅ ALL TESTS PASSED` and `report.total_failed` is `0`.
2. To check the protocol surface on its own, run `tests-mcp`. It exercises `initialize`, `notifications/initialized` (expecting `202`), `tools/list`, the `bing_search` input schema, a live `bing_search` call, an unknown method, an unknown tool, and a call with no `query`. Expected result: `passed` equals `total`.
3. To check the search path without going through HTTP, run `tests-web-search`. It covers project-endpoint normalization, parameter mapping and clamping, multi-block parsing with citations, the empty and incomplete response cases, a missing `query`, and one live Responses request. Expected result: `passed` equals `total`, and the live case returns `isError: false` with a non-empty first text block.
4. From the agent, ask a question that requires a fresh web source. Expected result: the agent calls `bing_search` and answers with the URLs returned by the tool.

## Troubleshooting

**`Authentication required`** (HTTP `401`, JSON-RPC error `-32000`): the request reached the endpoint without an authenticated Prisme.ai principal. Call it with a user JWT, a workspace JWT, or an organization API key. Agent Creator capabilities and Builder cross-workspace calls supply one automatically.

**`Method not found: <method>`** (JSON-RPC error `-32601`): the client sent a method outside `initialize`, `notifications/initialized`, `tools/list`, and `tools/call`. Check the client's MCP protocol version against the `2025-06-18` version returned by `initialize`.

**`Tool not found: <name>`** (JSON-RPC error `-32601`): the call used a tool name that this server does not expose. The only tool is `bing_search`.

**`Error: query parameter is required`**: the call carried no `params.arguments.query`, or the value was empty. Have the agent always pass a non-empty `query`.

**`Configuration error: missing <fields>`**: one or more of `foundry_base_url`, `foundry_project`, `foundry_model`, and `bing_connection_id` is empty, so the connector stopped before contacting Azure. The message lists every missing field. Set the matching secrets from [Workspace secrets](#workspace-secrets) and save.

**`Authentication error [AzureFoundryConfigurationError]: Missing required configuration: <fields>`**: the Foundry fields are set but one or more of `azure_tenant_id`, `azure_client_id`, `azure_client_secret`, and `azure_token_scope` is empty. Set the matching secrets from [Workspace secrets](#workspace-secrets).

**`Authentication error [AzureFoundryAuthenticationFailed]: <code> - <description>`**: Microsoft Entra ID rejected the client credentials request, or returned no access token. Check `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and `AZURE_CLIENT_SECRET` in [Workspace secrets](#workspace-secrets), and confirm the client secret has not expired. The `<code>` and `<description>` are the `error` and `error_description` returned by Entra ID and name the exact cause.

**`Authentication error [AzureFoundryAuthenticationFailed]: Microsoft Entra ID could not be reached.`**: the token request to `https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token` returned no HTTP response at all. Check that `AZURE_TENANT_ID` is a valid directory ID and that the platform can reach the Microsoft identity endpoint.

**`Foundry Responses error [network_error]: Microsoft Foundry could not be reached.`**: the `POST` to `<project-endpoint>/openai/v1/responses` returned no HTTP response. Check `foundry_base_url` and `foundry_project` in [Foundry configuration fields](#foundry-configuration-fields) and the platform's outbound network access to the Foundry resource.

**`Foundry Responses error [<code>]: <message>`**: Foundry answered the Responses call with a non-2xx status. The `<code>` and `<message>` come from the provider's `error` object. Verify `foundry_base_url`, `foundry_project`, and that `foundry_model` names a GPT-5.x deployment that exists in the project and supports Responses with `bing_grounding`, in [Foundry configuration fields](#foundry-configuration-fields). A `403` here usually means the role assignment from step 4 of [Register the Azure application](#register-the-azure-application) is missing or was made on the wrong scope. A Bing-related code usually means `bing_connection_id` does not point at a Grounding with Bing Search connection that belongs to this project.

**`Foundry Responses error [response_incomplete]: Microsoft Foundry returned an incomplete response.`**: the Responses call returned HTTP `2xx` but its `status` is not `completed`. When Foundry names a reason, it replaces `response_incomplete` in the message, for example a token-limit reason. Retry with a narrower query or a lower `num_results`, and check the deployment's token limits.

**`Foundry Responses error [response_empty]: no output text was returned.`**: the Responses call completed but carried no `output_text` block. Retry with a broader query. A repeated occurrence usually means the model deployment is not returning grounded text for this search configuration.

**Results are systematically too old or too narrow**: `default_freshness` is `Week` and `default_count` is `5`. Either raise them in [Default search options](#default-search-options) or instruct the agent to pass `freshness` and `num_results` on every call.

**The recency filter seems to be ignored**: `freshness` accepts only `Day`, `Week`, and `Month`. Any other value, including a lowercase spelling, is dropped and the search runs with no recency filter. Check what the agent actually passes, and pin the wording in its system prompt.

**A rotated client secret is not picked up**: the connector caches the Azure access token in the run session for `min(expires_in - 300, token_cache_ttl)` seconds, with `token_cache_ttl` defaulting to `3300`. Wait for the cached token to expire, or start a new session, after changing `AZURE_CLIENT_SECRET`. See [Rotate secrets and remove access](#rotate-secrets-and-remove-access) for the full rotation order.

## Rotate secrets and remove access

- **Rotate the client secret**: create a second client secret on the app registration in Azure, update `AZURE_CLIENT_SECRET` in [Workspace secrets](#workspace-secrets), wait for the cached token to expire (`min(expires_in - 300, token_cache_ttl)` seconds, with `token_cache_ttl` defaulting to `3300`), verify with the `tests-web-search` automation as described in [Verify the connector](#verify-the-connector), then delete the old secret in Azure.
- **Revoke the connector's access to Azure**: remove the role assignment of the service principal on the Foundry resource or project, or delete the client secret. Both make every subsequent search fail with an authentication or Responses error rather than returning stale data.
- **Disconnect a single agent**: in Agent Creator, remove the MCP capability you added in [Connect an agent to the MCP endpoint](#connect-an-agent-to-the-mcp-endpoint) and save. The agent stops discovering `bing_search`; no Azure change is needed.
- **Disable the connector for everyone**: clear the four `AZURE_*` secrets listed in [Workspace secrets](#workspace-secrets) on the `tools-search-bing` workspace. Every call then returns `Authentication error` until the secrets are restored.
- **Uninstall completely**: remove the MCP capability from every agent that references the endpoint, delete the eight workspace secrets, then delete the Entra app registration and the Grounding with Bing Search connection in Azure if no other system uses them.
