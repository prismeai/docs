The DataGalaxy app exposes the [DataGalaxy](https://www.datagalaxy.com) data catalog API. It can be consumed two ways: as a remote MCP server that **Agent Creator** agents call through twelve entity tools, or as a Builder app whose instructions you call directly from DSUL. It covers the dictionary (sources, containers, structures, fields), the glossary (properties), usages, data processings, links, comments and tasks, plus a global search across the catalog.

It runs in the **tenant app-instance context**: each workspace stores its own DataGalaxy **integration token**, resolved server-side and never exposed to the agent. Agents are identified by the capability **Scope** `context_id,agent_id,user_id` and gated by a per-workspace authorized-agents allowlist.

## Operating model and runtime identity

This connector supports **one credential mode**: a DataGalaxy **integration token** stored in the consuming workspace. There is no OAuth flow, no per-user delegated identity and no platform-wide credential.

| Property | Value |
|---|---|
| Credential | One DataGalaxy integration token per installed app instance, stored in the workspace secret `dataGalaxyAuth` as `{ mode, token, baseUrl }` with `mode` set to `apiKey`. |
| Identity seen by DataGalaxy | The DataGalaxy account that owns the integration token. Every agent, every end user and every automation acts as that single account. |
| Permission enforcement | DataGalaxy, based on the space rights granted to the integration token. |
| Prisme.ai authorization gate | The `dataGalaxyAuthorizedAgents` allowlist, checked on every MCP `tools/call`. |
| Audit attribution | DataGalaxy records the integration-token account, not the individual Prisme.ai user. |

<Warning>
  The integration token is a **shared service credential**. Anything the token can read or write in DataGalaxy, every allowlisted agent can read or write, and DataGalaxy audit entries name the token's account rather than the person who prompted the agent. Grant the token the narrowest space rights that cover your use case, and keep the **Authorized agents** allowlist explicit instead of enabling **Allow all agents** in production.
</Warning>

## Prerequisites

- A **DataGalaxy account** with access to the workspaces (client spaces) you intend to manage.
- A DataGalaxy **integration token**. A **Client Admin** creates it in the DataGalaxy web application under **Administration > Integration**. A newly created token has no metamodel access: a workspace admin must then grant it **Admin** or **Access** rights per workspace under **Settings > Access**. Read rights cover the `list` and `get` actions; write rights are required for `create`, `update` and `delete`.
- Your **DataGalaxy API base URL**. The connector defaults to `https://api.datagalaxy.com`; copy the exact base URL of your tenant from the DataGalaxy web application if it differs.
- A Prisme.ai workspace where you can install apps and where the connector's configuration app can write workspace secrets. That requires the `owner`, `editor` or `admin` role on the workspace, as listed in [Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin).

<Accordion title="Platform admin (Governance): one-time platform setup" icon="shield-halved">
  **Goal:** DataGalaxy is a **per-workspace** connector: each workspace stores its own DataGalaxy integration token through the connector's configuration app (see [Workspace builder](#workspace-builder-dsul)), so there is **no platform-wide credential to provision** and **no central OAuth client**.

  <Note>
    There is no shared DataGalaxy credential. The integration token always lives in the consuming workspace's secrets, written by the connector's configuration app. The platform operator has nothing to register centrally.

  ## Declare the capability (optional)

  If you want agent builders to pick DataGalaxy from the capability catalog instead of pasting an MCP endpoint URL by hand, publish it as a reusable **capability**. The generic procedure is documented once in [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability); the DataGalaxy configuration app exposes both paths:

  - **Organization-wide.** The configuration app's **Capabilities catalog** section, visible only to `org:owner` and `org:admin`, publishes the connector with **Add to catalog** (or **Update catalog entry** when one already exists). See [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog).
  - **By hand.** Author the **DataGalaxy** entry yourself in **Governance > Org > Capabilities**. See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).

  Either way, the entry points at the MCP endpoint of the app instance running the connector — the configuration app renders the exact URL under **MCP endpoint** — and carries the **Scope**:

  ```text
  context_id,agent_id,user_id
  ```

  The `agent_id` in the scope is what lets the connector identify and authorize the calling agent; see [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means). Catalog visibility then follows your organization's existing roles; there is **no per-capability role grant** for this tenant-context connector. DataGalaxy authenticates with a server-side integration token, so the catalog entry carries **no** `oauth2` authorization block.

  To smoke-test the wiring, enable the capability on a test agent, allowlist that agent in the connector's configuration app, then ask the agent to run the `catalog` tool's `listWorkspaces` action. A successful read confirms the capability, the allowlist and the integration token at once.

  <Warning>
    Declaring the capability makes the connector **available** to agent builders; it does not authorize a specific agent and does not provision any DataGalaxy credential. Per-agent gating remains the configuration app's **Authorized agents** allowlist, and the integration token still lives in the workspace running the connector. There is **no OAuth auth-config JSON** to attach here.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator read and write the DataGalaxy catalog through twelve MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed and configured the DataGalaxy app in a workspace (see [Workspace builder](#workspace-builder-dsul)). Optionally, a platform administrator may have published a DataGalaxy capability to the Capabilities catalog (see [Platform admin setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    Your agent is authorized two ways at once: it is identified by the `agent_id` that Agent Creator injects through the capability **Scope**, and that agent must appear in the connector's **Authorized agents** allowlist. The DataGalaxy integration token itself is resolved server-side from the workspace configuration and never reaches the agent.

    <Steps>
      <Step title="Install and configure the connector in a workspace">
        Install **DataGalaxy** in a workspace and enter the integration token (and the base URL if it differs from the default) in its configuration app, as described under [Workspace builder](#workspace-builder-dsul) and in [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app).
      </Step>
      <Step title="Allowlist your agent">
        In the same configuration app, open **Authorized agents**, tick your agent and save. Enabling **Allow all agents** disables the per-agent gate entirely; avoid it in production. See [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).
      </Step>
      <Step title="Add the MCP capability to your agent">
        Selecting **Install capability** on your agent's row in **Authorized agents** allowlists the agent and wires the tool in one action; see [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent). To wire it by hand instead, add a capability pointing at that app instance's MCP endpoint URL and set its **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        Without `agent_id` in the scope, every call is rejected with an explicit "calling agent could not be identified" message.
      </Step>
      <Step title="Verify with a read-only call">
        Ask the agent to list the DataGalaxy workspaces, then the versions of one of them. Two successful reads confirm the allowlist, the token exchange and the base URL before you attempt any write.
      </Step>
    </Steps>

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the MCP endpoint URL. The agent must still be allowlisted, and its identity must still be propagated so the connector can read its `agent_id`.
    </Note>

    ## Brief the agent in its system prompt

    Every tool takes an `action` argument, and almost every action is scoped to a DataGalaxy workspace version. A short brief avoids the agent guessing:

    ```text
    You have access to the DataGalaxy MCP server (tools: catalog, sources, containers, structures,
    fields, properties, usages, dataProcessings, links, comments, tasks, objects). Each tool takes an
    `action` argument selecting the concrete operation.
    Almost every action needs a `versionId`. Discover it first: catalog/listWorkspaces, then
    catalog/listVersions with that workspaceId. Never invent a versionId or an entity id.
    Use catalog/search for open-ended lookups, then the entity tool to read or edit the object.
    Prefer list and get actions. Before any create, update or delete, restate the target entity and
    the exact change, and wait for explicit user confirmation.
    ```

    Refine the trigger keywords (source names, glossary domains, project tags) so the agent reliably picks up the right intent in your context.

    <Note>
      **Restricting to read-only (least privilege).** The connector exposes write actions on every tool and has no read-only switch. The boundary is enforced by DataGalaxy: grant the integration token **Access** rather than **Admin** rights on the target workspaces, so write attempts fail at the provider. Reinforce it in the agent prompt, but treat the DataGalaxy space rights as the real control.
    </Note>

    ## Available tools

    Tools are **entity-grouped**: each tool takes an `action` argument selecting the concrete operation, plus the per-action parameters. Most actions require a `versionId` (a DataGalaxy workspace version); discover it with the `catalog` tool.

    | Tool | Actions |
    |------|---------|
    | `catalog` | `listWorkspaces`, `listVersions`, `listAttributes`, `search` |
    | `sources` | `list`, `get`, `create`, `update`, `delete` |
    | `containers` | `list`, `get`, `create`, `update`, `delete` |
    | `structures` | `list`, `get`, `create`, `update`, `delete` |
    | `fields` | `list`, `get`, `create`, `update`, `delete` |
    | `properties` | `list`, `get`, `create`, `update`, `delete` |
    | `usages` | `list`, `get`, `create`, `update`, `delete` |
    | `dataProcessings` | `list`, `get`, `create`, `update`, `delete` |
    | `links` | `get`, `create`, `delete` |
    | `comments` | `list`, `create` |
    | `tasks` | `list`, `create`, `update` |
    | `objects` | `get`, `update` |

    <Note>
      `type`, `status`, `columnDataType` and link type codes are free-form strings passed straight to DataGalaxy. The accepted values depend on your client space metamodel; use the `catalog` tool's `listAttributes` action, or the [DataGalaxy API reference](https://developers.datagalaxy.com/docs/api/overview), to discover them instead of guessing.
    </Note>

    ## Output formats

    Every tool accepts an `outputFormat` argument:

    | Value | Response |
    |-------|----------|
    | `verbose` | Default. A formatted text summary of the operation in the MCP text content. |
    | `structured` | The DataGalaxy payload serialized as JSON in the text content, and the same payload in `structuredContent`. |
    | `both` | Identical to `structured` in this connector. |

    Set `outputFormat` to `structured` whenever the agent needs to reason over the raw DataGalaxy payload.

    ## Tool details

    ### catalog

    ```json
    {
      "name": "catalog",
      "arguments": {
        "action": "search",
        "query": "customer",
        "versionId": "00000000-0000-0000-0000-000000000000",
        "limit": 50
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `listWorkspaces`, `listVersions`, `listAttributes` or `search`. |
    | `workspaceId` | For `listVersions` | DataGalaxy workspace (client space) id. |
    | `query` | For `search` | Full-text search query. |
    | `versionId` | No | Scopes a `search` to one workspace version. |
    | `limit` | No | Maximum number of search results. |
    | `filters` | No | Attribute filter object forwarded to the DataGalaxy [advanced search](https://developers.datagalaxy.com/docs/api/guides/basics/advanced-search). |

    `listWorkspaces` and `listAttributes` take no parameters.

    ### sources, containers, structures and fields

    The four dictionary tools share the same action set and the same attribute parameters. They differ in their id parameter and in what a `create` attaches to.

    | Tool | Id parameter | `create` attaches to | Extra parameters |
    |------|--------------|----------------------|------------------|
    | `sources` | `sourceId` | `versionId` only | none |
    | `containers` | `containerId` | `parentId` | `parentId` also filters `list` |
    | `structures` | `structureId` | `parentId` | `parentId` also filters `list` |
    | `fields` | `fieldId` | `structureId` | `columnDataType`, `size`; `parentId` filters `list` |

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list`, `get`, `create`, `update` or `delete`. |
    | `versionId` | Yes | Workspace version id, required by every action. |
    | *id parameter* | For `get`, `update`, `delete` | The entity id, as listed above. |
    | `parentId` / `structureId` | For `create` | Parent entity the new object is created under. |
    | `limit`, `page` | No | Pagination for `list`. |
    | `includeAttributes` | No | Comma-separated attribute names to include in `list` results. |
    | `name`, `type` | For `create` | Display name and entity type code. `type` is not accepted by `update`. |
    | `technicalName`, `description`, `summary`, `status`, `owners`, `stewards`, `tags` | No | Catalog attributes accepted by `create` and `update`. `owners`, `stewards` and `tags` are arrays of strings. |

    ```json
    {
      "name": "fields",
      "arguments": {
        "action": "create",
        "versionId": "00000000-0000-0000-0000-000000000000",
        "structureId": "11111111-1111-1111-1111-111111111111",
        "name": "email",
        "type": "Column",
        "columnDataType": "varchar",
        "size": 255
      }
    }
    ```

    ### properties, usages and data processings

    `properties` (glossary entries), `usages` and `dataProcessings` share the dictionary action set with one difference: `list` accepts `versionId`, `limit`, `page` and `includeAttributes` but no `parentId`. Their id parameters are `propertyId`, `usageId` and `dataProcessingId`; `create` attaches the new object to a `parentId`.

    ### links

    ```json
    {
      "name": "links",
      "arguments": {
        "action": "create",
        "versionId": "00000000-0000-0000-0000-000000000000",
        "fromId": "22222222-2222-2222-2222-222222222222",
        "toId": "33333333-3333-3333-3333-333333333333",
        "type": "IsImplementedBy"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `get`, `create` or `delete`. |
    | `versionId` | Yes | Workspace version id. |
    | `fromId` | Yes | Origin entity id. `get` returns every link starting from it. |
    | `toId` | For `create`, `delete` | Target entity id. |
    | `type` | For `create` | Link type code. |
    | `linkType` | For `delete` | Link type code of the link to remove. |

    ### comments

    ```json
    {
      "name": "comments",
      "arguments": {
        "action": "create",
        "versionId": "00000000-0000-0000-0000-000000000000",
        "entityId": "44444444-4444-4444-4444-444444444444",
        "content": "Reviewed and validated."
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list` or `create`. |
    | `versionId` | Yes | Workspace version id. |
    | `entityId` | Yes | Entity the comment is attached to. |
    | `content` | For `create` | Comment body. |

    ### tasks

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `list`, `create` or `update`. |
    | `versionId` | For `create`, `update` | Workspace version id. |
    | `entityId` | For `create`, `update` | Entity the task is attached to. |
    | `taskId` | For `update` | Task id. |
    | `title`, `description`, `status`, `assignee` | No | Task fields accepted by `create` and `update`. |
    | `type` | No | Task type code, accepted by `create` only. |

    The `list` action takes no parameters and returns the tasks the integration token can see.

    ### objects

    Use `objects` when you hold an entity id but not its type.

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `get` or `update`. |
    | `versionId` | Yes | Workspace version id. |
    | `objectId` | Yes | Id of any catalog object. |
    | `name`, `technicalName`, `description`, `summary`, `status`, `owners`, `stewards`, `tags` | No | Attributes accepted by `update`. |

    ## Workspace builder

    **Goal:** install the connector in a workspace, store your DataGalaxy integration token and the agent allowlist through its configuration app, and call catalog operations from your automations.

    ## Installation

    DataGalaxy follows the standard App + MCP installation flow: [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace) documents it end to end, from [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app) through [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint) and [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation). The DataGalaxy-specific values to use at each point:

    | Step in the shared flow | DataGalaxy value |
    |---|---|
    | [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app) | Search for **DataGalaxy** in **Apps**. |
    | [Configure credentials](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app) | One mode only. Paste the **Integration token**, and fill **Base URL (optional)** only if your tenant is not on `https://api.datagalaxy.com`. Then select **Save authentication**. |
    | Test the credential | **Test connection**. The connector exchanges the integration token for an access token and lists your DataGalaxy workspaces, so a success confirms both the token and the base URL. It reports `Connection OK — API key valid.` |
    | [Authorize the agents](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector) | Open **Authorized agents**, tick each Agent Creator agent allowed to call this instance, then select **Save allowlist**. Leave the list empty if only DSUL automations call the connector. |
    | [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint) | Rendered under **MCP endpoint**. Hand it to the agent builder with the Scope `context_id,agent_id,user_id`. |

    There is **no OAuth callback URL** to register for DataGalaxy, and no per-user connection to complete: the integration token is the only credential.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Auto-populated on install (`configAppUrl`, read-only). Opens the credential form, the connection test, the **Authorized agents** allowlist, and the MCP endpoint URL for this app instance. |

    The configuration app drives everything; the app instance itself has no per-field credential form. It writes two workspace secrets, both resolved server-side at call time:

    | Secret | Shape | Purpose |
    |--------|-------|---------|
    | `dataGalaxyAuth` | `{ mode: "apiKey", token, baseUrl }` | The DataGalaxy integration token and API base URL. |
    | `dataGalaxyAuthorizedAgents` | Comma-separated agent ids, or `*` | Agents allowed to call the MCP endpoint. `*` allows every agent. |

    This connector uses a single auth mode:

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | **Integration token** (`apiKey`) | A DataGalaxy integration token and, optionally, a tenant-specific base URL | Every workspace; each stores its own token, and no platform-level setup is required |

    <Note>
      The base URL is normalized before use: a trailing `/v2` and any trailing slashes are stripped, so `https://api.datagalaxy.com`, `https://api.datagalaxy.com/` and `https://api.datagalaxy.com/v2` are equivalent.
    </Note>

    ### How the token is exchanged and cached

    The connector never sends the integration token to a catalog endpoint. On the first call of a session it performs `GET {baseUrl}/v2/credentials` with the integration token as the bearer, and uses the returned access token for the actual request. DataGalaxy access tokens expire after two hours; the connector caches one for 110 minutes, keyed on a fingerprint of the integration token, so replacing the token immediately invalidates the cached access token. If a request still returns `401`, the connector re-exchanges once and retries the request.

    ## DSUL examples

    ### Discover a version, then search the catalog

    ```yaml
    - DataGalaxy.listWorkspaces:
        output: workspaces
    - DataGalaxy.listVersions:
        workspaceId: '{{workspaces[0].id}}'
    ```

## Error handling

DataGalaxy HTTP failures are mapped to these messages, where `<operation>` names the failing operation:

| Status | Message | What to check |
|--------|---------|---------------|
| `400` | `Bad request while <operation>: ...` | A malformed body, an unknown attribute or an invalid type code. |
| `401` | `Authentication failed while <operation>. Your token may be expired or invalid.` | The integration token. The connector already retried once with a fresh access token. |
| `404` | `Resource not found while <operation>.` | `versionId`, the entity id and any parent id. |
| `429` | `Rate limit exceeded while <operation>. Please wait before retrying.` | DataGalaxy rate limiting; back off before retrying. |
| `500` | `DataGalaxy server error while <operation>.` | A transient DataGalaxy failure; retry shortly. |
| Any other status | `Error <status> while <operation>: ...` | Statuses such as `403` and `422` fall here and carry the DataGalaxy message verbatim. |

### Common issues

Authorization and installation failures that every App + MCP connector shares — an empty **Configuration app** field, an allowlist secret left holding an unresolved binding, calls denied for a ticked agent — are covered in [Troubleshooting](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting). The entries below are the DataGalaxy-specific ones.

- **"This agent is not authorized to use this connector"**: the calling agent is not in the allowlist. Open the configuration app, tick the agent under **Authorized agents** (or enable **Allow all agents**) and save. The message includes the agent id that was rejected.
- **"The calling agent could not be identified"**: the MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability, then allowlist the agent. See [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
- **"DataGalaxy is not configured for this workspace"**: no integration token could be resolved. Open the connector's configuration app and enter the token. There is no session credential, no request header and no platform-level fallback: the workspace secret is the only source.
- **"DataGalaxy credentials exchange failed"**: DataGalaxy rejected the integration token when exchanging it for an access token. The message carries the HTTP status. Confirm the token is still valid in **Administration > Integration**, and that the base URL points at your tenant.
- **"Authenticated call failed"** in the connection test: the token exchange succeeded but listing DataGalaxy workspaces did not. The token most likely has no space rights yet; grant it **Admin** or **Access** on the target workspaces under **Settings > Access**.
- **"DataGalaxy request build failed for ... Missing required path param"**: a path parameter was omitted, most often `versionId` or an entity id. Resolve the id first with `catalog` → `listWorkspaces` → `listVersions`, or with a `list` action.
- **"Direct calls are not allowed"** with HTTP `403`: an entity tool endpoint was called directly instead of through the connector's MCP endpoint. Use the MCP endpoint, or use the App-mode instructions from DSUL.
- **"Unknown tool"** or **"Unknown action"**: the tool or `action` name does not exist. The error message lists the accepted values for that tool.
- **Empty results from `search`**: the search is scoped to `versionId` when you pass one. Drop it to search every version, or confirm the version id with `catalog` → `listVersions`.

## Rotate, revoke and remove

The mechanics are the shared ones, in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall). What is specific to DataGalaxy:

- **Rotate the integration token**: create a new token in DataGalaxy under **Administration > Integration**, grant it the same space rights, paste it in the connector's configuration app and save, then delete the old token in DataGalaxy. The connector keys its access-token cache on a fingerprint of the integration token, so the new token takes effect on the next call with no restart. There is no per-user consent to renew.
- **Revoke an agent's access**: remove the agent from **Authorized agents** in the configuration app and save. Subsequent `tools/call` requests from that agent are rejected. If **Allow all agents** is enabled, disable it first, otherwise the per-agent gate stays off.
- **Revoke all access immediately**: delete the integration token in DataGalaxy. Every subsequent call fails the credentials exchange. Cached access tokens are session-scoped and expire within 110 minutes.
- **Uninstall the connector**: uninstall the DataGalaxy app from **Apps**. Uninstalling does not delete the workspace secrets it provisioned; clear `dataGalaxyAuth` and `dataGalaxyAuthorizedAgents` in the workspace secrets afterwards, delete the corresponding integration token in DataGalaxy, and remove the DataGalaxy entry from the Capabilities catalog if you published one.
