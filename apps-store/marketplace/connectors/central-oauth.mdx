---
title: 'Central OAuth client'
description: 'Standard platform administrator flow: register one platform-wide OAuth client in a connector core workspace so tenant workspaces do not register their own, and understand what it changes about agent authorization'
---

Connectors that authenticate users individually need an OAuth application registered at the provider. Registering one per workspace does not scale: every workspace builder would need provider administrator access, and every redirect URI would need approving. The **central OAuth client** solves that. A platform administrator registers one application at the provider, stores its credentials once in the connector's **core workspace**, and every tenant workspace then signs its users in through that application without ever seeing the client secret.

This page documents the flow those connectors share. The actor is the **platform administrator** or the **connector maintainer**; the outcome is that a workspace builder can select the central mode and connect users with nothing to register on their side.

<Note>
  Not every connector supports a central client. A connector supports it when its configuration app exposes a maintainer view. Connector-specific values, including the connector slug, the default scope list, and the provider console path, are on the connector's own page.
</Note>

## When to use a central client

Choose deliberately rather than defaulting to whichever is easier to reach.

| Choose | When |
|---|---|
| **Central platform client** | The platform serves many workspaces against the same provider tenant or the same public provider, and you want one application to approve, one redirect URI to register, and one place to rotate the secret. Recommended for per-user OAuth on a shared platform. |
| **Tenant-owned client** | A workspace must keep its OAuth application under its own control: a separate provider tenant, a distinct consent screen, an audit or compliance requirement to own the client, or a scope set that must not be shared. The workspace builder registers the application and enters the client id and secret in that workspace's configuration app. |

The two coexist. A workspace that enters its own client id and secret uses it. A workspace that does not falls back to the central client, which is why the central client is the platform default rather than an exclusive choice.

<Warning>
  A central client is an **OAuth2** client. Where a connector also supports a legacy, non-OAuth2 per-user mechanism, that mechanism cannot be stored centrally: a workspace needing it configures it in its own configuration app. A connector in that situation reports `unsupported_central_auth_mode` when a workspace tries to resolve an incompatible central profile.
</Warning>

## Before you begin

- The `owner`, `editor`, or `admin` role **on the connector's core workspace**, or the platform `superadmin` role. The workspace role is checked on that core workspace itself, so holding it elsewhere does not grant it. A caller who holds neither is refused.
- Provider administrator access to register an OAuth application in the provider's developer or administration console, and authority to approve the scopes the connector requests.
- The connector slug, so you can build and check the core callback URL. It is the slug of the connector's core workspace, for example `jira-next` for the Jira connector.

## Callback URLs

There are two callback URL shapes and they are not interchangeable. Registering the wrong one at the provider is the most common failure in this flow.

<Tabs>
  <Tab title="Central client (core workspace)">
    Register **this single URI** at the provider when you configure the central client:

    ```text
    <api-url>/workspaces/slug:<connector-slug>/webhooks/oauthCallback
    ```

    One URI serves every workspace on the platform. When a workspace instance starts a central sign-in, the provider redirects to the core workspace, and the core workspace forwards the authorization code back to the instance that started the flow. There is no per-workspace URI to add, and no provider change when a new workspace installs the connector.

    The maintainer view renders the exact value with a copy action. Copy it from there: it must match byte for byte what the connector sends, and the `slug:` form is part of the URI.
  </Tab>
  <Tab title="Tenant-owned client (app instance)">
    A workspace that registers its own OAuth application registers **its instance's own** callback instead:

    ```text
    <api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.oauthCallback
    ```

    This value is generated by the connector's install flow and stored on the app instance. The workspace builder copies it from the configuration app. See [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app).
  </Tab>
</Tabs>

<Warning>
  The core URI has **no app-instance prefix** and the tenant URI **does**. Registering a tenant URI as the central redirect URI breaks central sign-in for every other workspace; registering the core URI for a tenant-owned client breaks that workspace's sign-in. Always copy the value the configuration app renders for the view you are in.
</Warning>

## Configure the central client

<Steps>
  <Step title="Register the OAuth application at the provider">
    In the provider's console, create an OAuth 2.0 application, set its redirect URI to the core callback URL above, and grant the scopes listed on the connector's page. Note the **Client ID** and **Client secret**.
  </Step>
  <Step title="Open the maintainer view">
    In Builder, open the connector's **core workspace** and open its configuration app. Hosted on that workspace, and without a tenant workspace in the link, the app renders the maintainer view instead of the per-workspace configuration form.

    If you see **Access restricted** instead of the form, you hold none of `owner`, `editor`, or `admin` on the core workspace and are not a platform superadmin. The view asks the connector's `maintainerStatus` endpoint before rendering anything, so a non-maintainer never reaches the form.
  </Step>
  <Step title="Enter the client id, secret and scopes">
    Paste the **Client ID** and **Client secret**, and set the **Scopes** field. The connector requests exactly the scopes stored here, so this field is the effective grant: it can narrow what the provider application exposes, never widen it. Leaving it empty stores the connector's own default scope list, documented on the connector page.
  </Step>
  <Step title="Save the client">
    Select the save action. On success the app confirms that the central profile is stored, and reopening the view reports that a client is set. A save is refused with HTTP `403` and `Forbidden — you must be an editor of the core workspace.` when the role check fails, and with HTTP `401` and `Authentication required (workspace editor).` when the request carries no session.

    The profile is written to the core workspace secret `<connector>CentralOAuth`. Do not write that secret by hand in Studio **Secrets**: the maintainer view stores the object in the exact shape the connector reads.
  </Step>
  <Step title="Optional: publish the connector to the Capabilities catalog">
    The maintainer view can publish a catalog entry pointing at the **core** MCP endpoint. The action stays disabled until the central client is saved. Read [Agent authorization on the core endpoint](#agent-authorization-on-the-core-endpoint) before you publish, then see [Declare a connector capability](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog).
  </Step>
</Steps>

## How the client secret stays in the core workspace

The central client secret never leaves the core workspace, and no tenant workspace can read it. Two core endpoints make that possible.

| Core endpoint | Returns | Used by |
|---|---|---|
| `getOAuthClientPublic` | Only non-secret fields: whether a client is configured, the mode, the deployment, the base URL, the client id, and the scopes | A tenant instance, to build the provider sign-in URL |
| `centralTokenExchange` | The provider's token response, obtained by the core workspace using the stored client secret | A tenant instance, in place of calling the provider token endpoint directly |

A tenant instance that resolves the central client therefore holds the client id and the scopes, and never the secret. When it needs to exchange an authorization code or refresh a token, it posts to `centralTokenExchange`, which attaches the secret inside the core workspace and returns the provider response. The exchange endpoint accepts only the `authorization_code` and `refresh_token` grants; anything else is refused with `unsupported_grant_type`, and a request made before a client is stored is refused with `central_client_not_configured`.

<Note>
  Per-user tokens obtained this way are still stored per workspace and per user, and resolved server-side at call time. The central client governs **who the provider trusts to ask for tokens**, not whose data a workspace can reach.
</Note>

## Agent authorization on the core endpoint

This is a real security property of the central model and it is easy to get wrong.

A connector authorizes an incoming MCP call by reading the calling agent's id and checking it against the workspace's authorized-agents allowlist. Before that check, it tests whether a central client resolves in the current context. When one does, the check short-circuits: the call is authorized with the reason `global_endpoint`, and the per-agent allowlist is not consulted at all.

That branch resolves only in the **core workspace**, because the central profile lives in the core workspace's own secret store. A tenant app instance inherits the binding but not the value, so the central client never resolves there.

| Endpoint | Central client resolves | Per-agent allowlist | Effective gate |
|---|---|---|---|
| Core workspace endpoint, `<api-url>/workspaces/slug:<connector-slug>/webhooks/mcp` | Yes, once a central client is stored | **Not applied** | The end user's own OAuth connection and the provider's permissions |
| Tenant app-instance endpoint, `<api-url>/workspaces/slug:<workspace-slug>/webhooks/<app-instance-slug>.mcp` | No | Applied | The workspace allowlist, plus the user's connection and the provider's permissions |

<Warning>
  Storing a central client makes the **core** MCP endpoint accept every calling agent. Any agent granted a capability that points at the core endpoint can call it; the allowlist offers no protection there, because the per-user OAuth connection is the gate by design. A tenant instance is unaffected and keeps enforcing its own allowlist. Publish the core endpoint to the Capabilities catalog only when accepting every agent in the organization is the behavior you intend; otherwise point agents at a workspace-installed instance, as described in [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).
</Warning>

## Select the central client in a workspace

Hand this to each workspace builder once the central client is stored.

<Steps>
  <Step title="Open the connector's configuration app in the workspace">
    Use the **Configuration app** link on the installed app instance.
  </Step>
  <Step title="Select the central authentication mode">
    Select the mode the connector names for the central client, `oauthCentral`. No client id and no client secret are entered on the workspace side.
  </Step>
  <Step title="Optional: narrow the scopes">
    Set the **Scopes** field to a subset of what the central application exposes, for example a read-only list. A workspace can narrow the platform default, never widen it beyond what the provider application allows.
  </Step>
  <Step title="Connect an account and save">
    Save the configuration, then start the connection. Each user of the workspace signs in once with their own provider account against the central application.
  </Step>
</Steps>

<Note>
  A workspace that leaves the client id and secret empty falls back to the central client even when it selected the tenant-owned OAuth mode. Entering a client id and secret always takes precedence over the central client for that workspace.
</Note>

## Verify the central client

<Steps>
  <Step title="Confirm the maintainer view reports a stored client">
    Reopen the maintainer view. It reports that a central client is set, and prefills the non-secret fields.
  </Step>
  <Step title="Connect one user from a tenant workspace">
    In a workspace configured for the central mode, start the connection from the configuration app and complete the provider sign-in. The provider consent screen names the central application. If the provider rejects the redirect, the registered URI does not match the core callback URL.
  </Step>
  <Step title="Confirm the runtime identity">
    Call the connector's "who am I" operation from that workspace. It must return the account of the user who just connected, not a service account.
  </Step>
  <Step title="Confirm the secret never leaves the core">
    From a tenant workspace, inspect the connector's resolved configuration. The client id and scopes are present; no client secret is. Token exchanges appear as calls to the core `centralTokenExchange` endpoint.
  </Step>
  <Step title="Test the core endpoint authorization deliberately">
    If you published the core endpoint to the catalog, call it from an agent that is in no workspace allowlist. It succeeds, which confirms the `global_endpoint` short-circuit is active and is exactly why that endpoint must only be published when every agent in the organization may use it.
  </Step>
</Steps>

## Rotate and revoke the central client

- **Rotate the client secret.** Generate a new secret at the provider, then re-enter the client id and the new secret in the maintainer view and save. The connector sends the stored secret on every token exchange, so refreshes fail from the moment the provider invalidates the old secret until the stored value matches. Rotate during a low-traffic window and expect users to reconnect once if the provider also invalidated their grants.
- **Change the scopes.** Update the **Scopes** field in the maintainer view. The connector requests exactly the stored list, so widening it takes effect only after each user re-consents; the provider issues the added scopes on the next authorization, not on a refresh. Narrowing takes effect for new authorizations and leaves existing tokens carrying the older grant until they are replaced.
- **Triggers for user re-consent.** Replacing the central application, adding scopes, or a provider-side revocation of the application's access all require the user to sign in again. Users see the connector's "not connected" message on the next call and reconnect from the configuration app.
- **Disconnect one user.** The user disconnects from the configuration app of the workspace they use, which deletes their stored tokens. To also revoke the grant at the provider, the user removes the application's access from their own provider account settings.
- **Withdraw the central client.** Delete the `<connector>CentralOAuth` secret from the core workspace **Secrets**. The maintainer view has no withdraw action, so this is the removal path. Afterwards `getOAuthClientPublic` reports that no client is configured, workspaces relying on the central client can no longer start or refresh connections, and the core MCP endpoint stops short-circuiting agent authorization and falls back to its own allowlist. Give workspaces a tenant-owned client, or a shared-credential mode, before withdrawing.
- **Remove the catalog entry.** If you published the core endpoint to the Capabilities catalog, remove that entry as well, or agent builders keep attaching a capability that no longer authenticates.

## Troubleshooting

**`Access restricted` in place of the maintainer form**: the account holds none of `owner`, `editor`, or `admin` on the connector's core workspace and is not a platform superadmin. Grant the role on that core workspace, and note that a role on a tenant workspace does not count. Owner: platform administrator.

**`Forbidden — you must be an editor of the core workspace.` on save (HTTP `403`)**: the same role check, applied on write. The read-side view and the write-side endpoint enforce it independently, so a form that renders does not guarantee a save will pass if the role changed in between. Owner: platform administrator.

**`Authentication required (workspace editor).` on save (HTTP `401`)**: the request carried no authenticated session. Reopen the configuration app from Builder rather than from a stale tab. Owner: platform administrator.

**`central_client_not_configured` during a token exchange**: no central client is stored in the core workspace, or it was withdrawn while workspaces still relied on it. Store the client in the maintainer view. Owner: platform administrator.

**`unsupported_central_auth_mode` in a workspace connection status**: the stored central profile uses a mechanism that cannot be served centrally, so tenant workspaces cannot resolve it. Configure that mechanism directly in the workspace's own configuration app instead of selecting the central mode. Owner: platform administrator plus workspace builder.

**`unsupported_grant_type` from the exchange endpoint**: the exchange endpoint serves only the `authorization_code` and `refresh_token` grants. Any other grant belongs in a different auth mode. Owner: connector maintainer.

**The provider rejects the redirect URI during a central sign-in**: the registered URI is not the core one, or does not match byte for byte. Copy it from the maintainer view. A tenant-shaped URI carrying an app-instance prefix is the usual mistake. Owner: provider administrator.

**Users are asked to sign in again after a change**: expected after replacing the application, rotating the secret in a way the provider treats as a new client, or adding scopes. Announce it, then let users reconnect from the configuration app.

**An agent that was never allowlisted can call the connector**: it is calling the core endpoint, where a resolved central client short-circuits the per-agent check. Point the agent at a workspace-installed instance instead, or accept that the core endpoint is open to every agent granted the capability.
