The SharePoint app provides read/write access to Microsoft SharePoint Online and OneDrive through the [Microsoft Graph](https://learn.microsoft.com/en-us/graph/overview) REST API: sites, document libraries (drives), files and folders, SharePoint lists, sharing permissions, and the Microsoft Entra ID directory. It also reads file **content** without an external extraction service: Excel `.xlsx` cells through the Graph Excel API, Word `.docx` text by parsing the OOXML in-process, text files inline, and large CSV files through a server-side dataset that agents query with filters instead of loading into context.

It is consumed two ways: as a remote MCP server that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. The MCP surface groups every operation into **ten entity tools** (`sites`, `drives`, `items`, `search`, `permissions`, `lists`, `directory`, `workbook`, `documents`, `dataset`), each driven by an `action` argument, and runs in the **tenant app-instance context**: the endpoint resolves the installing workspace's own credentials and its own agent allowlist.

## Choose an authentication mode

Pick the mode before you configure anything: it decides whose identity Microsoft Graph sees, and therefore what the connector can reach. For the trade-off between the platform-wide client and an Entra app you own, see [When to use a central client](/apps-store/marketplace/connectors/central-oauth#when-to-use-a-central-client).

| Mode | Runtime identity at Microsoft | Best for | What you provide |
|------|-------------------------------|----------|------------------|
| `oauthCentral` (default, recommended) | The **end user** who signed in | Interactive Chat agents on a platform where a maintainer registered the shared Entra app | Nothing — each user clicks **Connect** |
| `oauth` | The **end user** who signed in, against **your** Entra app | You want to own the Entra app registration, its consent and its audit trail | Your Entra tenant, **Application (client) ID** and **Client secret value** |
| `clientCredentials` | The **Entra application** itself (no user) | Unattended back-office automation and content indexing | Tenant, client ID, client secret, plus admin-consented **application** Graph permissions |
| `accessToken` | Whoever minted the token | Short-lived tests and externally managed sessions | A Microsoft Graph access token, used as-is with no refresh |

<Warning>
  `clientCredentials` grants the connector the Entra application's own tenant-wide permissions, so every agent call reaches every site those permissions cover, and Microsoft's audit log attributes the action to the application rather than to a person. Use it only for unattended workloads, and keep the application permissions as narrow as the workload allows. For anything a user triggers in Chat, prefer `oauthCentral` or `oauth`.
</Warning>

## Prerequisites (Microsoft side)

- A **Microsoft 365 / SharePoint Online** tenant, and a **Microsoft Entra ID** tenant where you can register an application (or a platform maintainer who already did, for `oauthCentral`).
- An **app registration** in the [Microsoft Entra admin center](https://entra.microsoft.com) (**App registrations → New registration**), with a **client secret** created under **Certificates & secrets**. Copy the secret **Value**, not the **Secret ID**.
- **Microsoft Graph delegated permissions** on the app, for the per-user OAuth modes:
  - Sites & files: `Sites.Read.All` and `Files.Read.All`, or `Sites.ReadWrite.All` and `Files.ReadWrite.All` for create/update/move/delete.
  - Directory (access-aware RAG): `User.Read`, and `GroupMember.Read.All` if agents resolve group membership.
  - Refresh tokens: `offline_access`.
- For `clientCredentials`, grant the equivalent **application** permissions instead and have a Global Administrator grant admin consent; the connector requests `https://graph.microsoft.com/.default`.
- The app registration's **supported account types** must match the sign-in authority you configure (`common`, `organizations`, `consumers`, or a specific tenant id/domain). Microsoft rejects a mismatch at sign-in.

The **Scopes** field of the configuration app offers two presets:

```text
Read-only preset
offline_access https://graph.microsoft.com/Sites.Read.All https://graph.microsoft.com/Files.Read.All https://graph.microsoft.com/User.Read

Read + write preset
offline_access https://graph.microsoft.com/Sites.ReadWrite.All https://graph.microsoft.com/Files.ReadWrite.All https://graph.microsoft.com/User.Read
```

<Warning>
  **The central platform client defaults to read + write.** Leaving **Scopes** empty falls back to a connector default that differs by mode: an `oauth` instance with its own Entra client falls back to the **read-only** set, while the central platform client is stored with `Sites.ReadWrite.All` and `Files.ReadWrite.All` unless the maintainer narrows it. Every workspace on `oauthCentral` therefore inherits write access to every site the connected user can edit. Set the field explicitly — on the maintainer view for the platform default, or per workspace to narrow it — whenever the distinction matters to you.
</Warning>

  ## 1. Configure the central OAuth client

  The procedure is the standard one documented in [Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client). The Microsoft-specific values are below.

  <Steps>
    <Step title="Register the OAuth application in Microsoft Entra ID">
      In the [Microsoft Entra admin center](https://entra.microsoft.com) → **App registrations → New registration**, register an application, then under **Authentication** add this **Web** redirect URI:

      ```text
      <api-url>/workspaces/<core-workspace-id>/webhooks/oauthCallback
      ```

      Only this single URI is needed for the whole platform: tenant callbacks are proxied through it, with the tenant's own callback packed into the OAuth `state`. It is **not** the per-instance URI a tenant-owned client registers; see [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls) for the difference.

      <Warning>
        Microsoft Entra rejects a redirect URI containing a colon, so this URI uses the **raw workspace id** of the core `sharepoint-next` workspace, never the `slug:sharepoint-next` form used elsewhere and shown on the shared page. Copy the exact value from the maintainer view, which renders it under **Redirect URI to register in Microsoft Entra**.
      </Warning>

      Add the Microsoft Graph **delegated** permissions listed in [Prerequisites (Microsoft side)](#prerequisites-microsoft-side), create a **client secret** under **Certificates & secrets**, and note the **Application (client) ID**, the secret **Value**, and the **Directory (tenant) ID**.
    </Step>
    <Step title="Store the credentials through the configuration app">
      Open the core `sharepoint-next` workspace and launch its configuration app at `<studio-url>/apps/sharepoint-next`. In the maintainer section, fill **Application (client) ID**, **Client secret value**, **Sign-in authority** and, optionally, **Scopes**, then click **Save central OAuth client**. The confirmation reads `Central OAuth client stored.`

      For **Sign-in authority**, pick the option matching the app registration: **Common — work/school + personal accounts**, **Organizations — any work/school account**, **Consumers — personal Microsoft accounts**, or **Specific tenant (single-tenant app)** with the tenant id or domain.

      The credentials are written to the core workspace secret `sharepointNextCentralOAuth` and never leave it: tenant instances call the core token-exchange webhook, so the client secret is never exposed to a workspace or an end user. Do not edit Studio's raw Secrets by hand. See [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace) for the two core endpoints involved and the role checks applied on save.
    </Step>
    <Step title="Set the default dataset retention (optional)">
      In the same maintainer section, **Dataset retention → Default retention (days)** sets the sliding lifetime applied to CSV datasets ingested by the `dataset` tool when the caller does not pass `ttlDays`. Accepted range is 1–90; leaving it empty falls back to 7 days. Click **Save default retention**.
    </Step>
    <Step title="Tell workspaces to use the central client">
      Each consuming workspace selects **OAuth2 connection (platform client)** (`oauthCentral`) in its own configuration app — no client id or secret on their side. Their users then click **Connect**. Hand them [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace).
    </Step>
  </Steps>

  Verify the result with [Verify the central client](/apps-store/marketplace/connectors/central-oauth#verify-the-central-client), and handle secret rotation, scope changes and withdrawal with [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client).

  ## 2. Publish the capability

  Generic connectors with a broad tool surface, like SharePoint, are best exposed as a named **capability** so agent builders enable it instead of pasting a raw MCP endpoint. The publishing flow, the organization role it needs and the manual alternative are documented in [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog) and [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).

  For SharePoint, the configuration app publishes the entry for you: click **Add to catalog** (or **Update catalog entry**). From the maintainer view it publishes the shared core MCP endpoint, and the button stays disabled until the central OAuth client is saved. From a tenant workspace's view it publishes that workspace's own endpoint. Either way the entry carries the MCP server URL, the **Scope** `context_id,agent_id,user_id`, and — in the OAuth modes — the connect, status and disconnect URLs that drive the per-user sign-in flow.

  Publishing needs catalog write rights in your organization; without them the app answers `Forbidden — you need catalog write rights in this org.`

  To wire a capability by hand instead, create it in Governance, set its MCP server URL to the connector's **MCP endpoint**, and set its **Scope** field to:

  ```text
  context_id,agent_id,user_id
  ```

  The `agent_id` in that scope is what lets the connector identify and authorize the calling agent, as explained in [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means). It is unrelated to the Microsoft Graph OAuth scopes.

  <Warning>
    Publishing the capability makes the connector **available**; it does not by itself authorize a specific agent, as explained in [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization). This connector follows the **tenant-context model**: which agents may call a workspace's endpoint is gated by that workspace's **Authorized agents** allowlist (see [Workspace builder (DSUL)](#workspace-builder-dsul)). The shared core endpoint is the exception — when the central OAuth client is configured, it accepts every agent and per-user OAuth is the only gate, as described in [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint).
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator browse SharePoint sites, read and manage files, query lists, and check permissions through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed and configured the SharePoint app in a workspace (see [Workspace builder (DSUL)](#workspace-builder-dsul)), and, for the central OAuth mode, a platform admin must have provisioned the shared Microsoft Entra OAuth client (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    Your agent is authorized twice over: it is identified by the `agent_id` that Agent Creator injects through the capability **Scope**, and that agent id must appear in the target workspace's **Authorized agents** allowlist. The Microsoft Graph token itself is resolved server-side from the configured auth mode — in the OAuth modes, from the token of the user talking to the agent. The general rule is on [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization).

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A: Enable the shared capability from the catalog

    The fastest path: a platform admin has already published a **SharePoint** capability from the [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup) section, so you pick it from the catalog.

    <Steps>
      <Step title="Open your agent in Agent Creator">
        Open the agent you want to extend and go to its capabilities / tools.
      </Step>
      <Step title="Add the SharePoint capability">
        Browse the capability catalog, select the SharePoint entry, and enable it. The MCP endpoint URL and the **Scope** (`context_id,agent_id,user_id`) come with the entry, and the shared core endpoint accepts every agent, so there is no allowlist step on your side.
      </Step>
      <Step title="Connect a Microsoft account (OAuth modes)">
        On the first tool call, an unconnected user is prompted to sign in; Agent Creator surfaces the connector's connect URL. The `clientCredentials` and `accessToken` modes need no per-user sign-in.
      </Step>
    </Steps>

    <Note>
      Convenient, but your agent runs against a **shared, platform-managed instance**: its Microsoft credentials are owned by someone else and the instance accepts every agent that is granted the capability, because a resolved central client short-circuits the per-agent check ([Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint)). Prefer Option B for anything beyond quick experiments.
    </Note>

    ## Option B: Run it from your own workspace (recommended)

    For production agents, install the connector in **your own workspace** and point the agent at *that* workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP runs in *your* app-instance context, the Microsoft credentials, the per-user OAuth tokens and the authorized-agents allowlist are all **scoped to your workspace**, not shared platform-wide. You decide exactly which agents may call it and which Microsoft account or auth mode backs them, and a misconfiguration elsewhere can never expose your SharePoint content.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder (DSUL)](#workspace-builder-dsul) for the Microsoft-specific settings, and [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace) for the generic flow: install **SharePoint** in your workspace, open its configuration app, choose the auth mode and connect a Microsoft account.
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's configuration app, open **Authorized agents** and tick your agent. The **Install capability** button next to the agent allowlists it and attaches the tool in one action; see [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Add the MCP capability to your agent">
        If you did not use **Install capability**, add a capability pointing at **your workspace's MCP endpoint**, and set its **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        The `agent_id` is what lets the connector identify and authorize your agent; without it every call is rejected with an explicit "calling agent could not be identified" message. This **Scope** is separate from the Microsoft Graph OAuth scopes — see [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
      </Step>
      <Step title="Connect a Microsoft account (OAuth modes)">
        On the first tool call, the user is prompted to sign in, or they use **Connect** in the configuration app.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent must know the MCP exists and when to use it. Copy-pasteable starter:

    ```text
    You have access to the SharePoint MCP server (tools: sites, drives, items, search, permissions, lists, directory, workbook, documents, dataset). Each tool takes an `action` argument. Use it whenever the user asks about SharePoint sites, document libraries, files and folders, SharePoint lists, sharing permissions, or who can access a document.
    For the user's OWN files ("my files", "my OneDrive"), call items with action listMyRootChildren or listMyChildrenByPath — these need no driveId, do not call sites first. For a shared team site, call sites to get a siteId, then drives to get a driveId, then items.
    To read content: items getContent for text files, workbook for an Excel .xlsx file, documents for a Word .docx file, and dataset ingest + query/aggregate for a large CSV. items get and listChildren return @microsoft.graph.downloadUrl for out-of-band download; file bytes are never returned inline.
    Prefer calling a tool over guessing, and confirm with the user before any write or destructive action (createFolder, update, delete, copy, invite, createLink, updateRange, addTableRow, addWorksheet, createTable, createItem, updateItemFields, deleteItem, drop).
    ```

    <Note>
      **Restricting to read-only (least privilege).** SharePoint tools cover both reads and writes. The scope set is what draws the line: select the **Read-only preset** in the configuration app's **Scopes** field to keep the connector from writing, and Microsoft Graph then rejects every write with `403 Forbidden`. This matters on `oauthCentral`, where the platform default is the **read + write** preset ([Prerequisites (Microsoft side)](#prerequisites-microsoft-side)). The field is workspace-level, so a workspace editor can widen it again; for a hard guarantee, register an Entra app that only holds read permissions.
    </Note>

    ## Available tools

    Each tool takes an `action` argument selecting the concrete operation, plus the per-action parameters.

    | Tool | Description |
    |------|-------------|
    | `sites` | SharePoint sites discovery. Actions: `search`, `get`, `getRoot`, `listSubsites`. |
    | `drives` | Document libraries (drives) of sites and OneDrive. Actions: `listForSite`, `getSiteDefault`, `get`, `getMine`, `listMine`. |
    | `items` | Files & folders (driveItems), including the signed-in user's OneDrive, the drive delta feed and file content. Actions: `listMyRootChildren`, `listMyChildrenByPath`, `listChildren`, `listRootChildren`, `changes`, `get`, `createFolder`, `update`, `delete`, `copy`, `thumbnails`, `versions`, `getContent`, `checkAccess`. |
    | `search` | Microsoft Search across SharePoint / OneDrive. Action: `query`. |
    | `permissions` | Sharing & permissions on driveItems (access-aware RAG). Actions: `list`, `get`, `invite`, `createLink`, `delete`. |
    | `lists` | SharePoint lists and list items. Actions: `listForSite`, `get`, `listItems`, `getItem`, `createItem`, `updateItemFields`, `deleteItem`. |
    | `directory` | Microsoft Entra ID users & groups: resolve identities and group membership. Actions: `getUser`, `userMemberOf`, `checkUserMemberGroups`, `getGroup`, `groupMembers`. |
    | `workbook` | Read & write Excel `.xlsx` workbooks **natively** via the Microsoft Graph Excel API: no download, no OCR; cells are returned as structured values. Target a file by `driveId` + `itemId`. Actions: `listWorksheets`, `usedRange`, `getRange`, `listTables`, `listTableRows`, `updateRange`, `addTableRow`, `addWorksheet`, `createTable`, `executeFunction`. |
    | `documents` | Read the content of Word `.docx` documents **natively**: no external extraction service, no OCR; parses the OOXML in-process. Target a file by `driveId` + `itemId`. Actions: `getText`, `getStructure`. |
    | `dataset` | Ingest a large CSV file into a private, per-user, TTL-bound collection and query it server-side, so the file never enters the agent's context. Actions: `ingest`, `query`, `aggregate`, `list`, `drop`. |

    ## Output formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - **`verbose`** (default): a human-readable text view, optimized for LLM consumption.
    - **`structured`**: concise machine-readable JSON in `structuredContent`.
    - **`both`**: the structured payload, with its JSON also rendered as text.

    ## Tool details

    ### sites

    ```json
    {
      "name": "sites",
      "arguments": {
        "action": "search",
        "search": "marketing",
        "top": 10
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `search`, `get`, `getRoot`, `listSubsites`. |
    | `siteId` | For `get` / `listSubsites` | SharePoint site id (`hostname,siteCollectionId,siteId`). |
    | `search` | For `search` | Keyword to match sites; use `*` to list all. |
    | `top` / `select` | No | OData `$top` / `$select`. |

    ### drives

    ```json
    {
      "name": "drives",
      "arguments": {
        "action": "listForSite",
        "siteId": "contoso.sharepoint.com,<site-collection-id>,<site-id>"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `listForSite`, `getSiteDefault`, `get`, `getMine`, `listMine`. |
    | `siteId` | For `listForSite` / `getSiteDefault` | SharePoint site id. |
    | `driveId` | For `get` | Drive (document library) id. |
    | `select` | No | OData `$select`. |

    `getMine` and `listMine` target the signed-in user's OneDrive and therefore work only in the OAuth modes.

    ### items

    ```json
    {
      "name": "items",
      "arguments": {
        "action": "listChildren",
        "driveId": "<drive-id>",
        "itemId": "<item-id>",
        "top": 50
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `listMyRootChildren`, `listMyChildrenByPath`, `listChildren`, `listRootChildren`, `changes`, `get`, `createFolder`, `update`, `delete`, `copy`, `thumbnails`, `versions`, `getContent`, `checkAccess`. |
    | `driveId` | Yes, except `listMyRootChildren` / `listMyChildrenByPath` | Drive id. The two `listMy*` actions target the signed-in user's OneDrive (OAuth modes only). |
    | `itemId` | For `listChildren`, `get`, `update`, `delete`, `copy`, `thumbnails`, `versions`, `getContent` | DriveItem id. |
    | `parentItemId` | For `createFolder` | Parent folder item id. |
    | `path` | For `listMyChildrenByPath` | OneDrive folder path relative to the drive root, no leading slash, for example `Documents/Reports`. |
    | `token` | No (`changes`) | Opaque Microsoft Graph delta token. |
    | `top` / `select` / `orderby` / `expand` / `skiptoken` | No | OData query options and pagination. |
    | `body` | For `createFolder` / `update` / `copy` | JSON body passed through to Microsoft Graph, e.g. `createFolder` → `{ name, folder: {}, "@microsoft.graph.conflictBehavior" }`; `copy` → `{ parentReference, name }`. |

    **Routing.** For "my files" or "my OneDrive", start with `listMyRootChildren` or `listMyChildrenByPath` — they need no `driveId`. For a shared team site, resolve a `siteId` with `sites`, then a `driveId` with `drives`, then browse with `listRootChildren` / `listChildren`. `sites` `getRoot` returns the root **site** object, not files.

    **Reading a file.** `get` and `listChildren` return each file's `@microsoft.graph.downloadUrl`, a pre-signed link you fetch out-of-band; the MCP response never embeds file bytes. `getContent` returns the decoded text of a text-based file (`.txt`, `.csv`, `.md`, `.json`, `.html`, `.xml`, …), capped at 200,000 characters; other file types come back as base64 with a hint. Prefer `workbook` for `.xlsx`, `documents` for `.docx`, and `dataset` for a large CSV.

    **Change tracking.** `changes` follows the drive-root delta feed. Page through `@odata.nextLink`, then persist the final `@odata.deltaLink` token and pass it back as `token` on the next run.

    **`checkAccess`** is an infrastructure action reserved for the trusted knowledge-sync caller; ordinary agents do not call it. See [Knowledge-base sync and MCP Resources](#knowledge-base-sync-and-mcp-resources).

    ### lists

    ```json
    {
      "name": "lists",
      "arguments": {
        "action": "listItems",
        "siteId": "contoso.sharepoint.com,<site-collection-id>,<site-id>",
        "listId": "<list-id>",
        "expand": "fields"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `listForSite`, `get`, `listItems`, `getItem`, `createItem`, `updateItemFields`, `deleteItem`. |
    | `siteId` | Yes | SharePoint site id. |
    | `listId` | For every action except `listForSite` | SharePoint list id. |
    | `itemId` | For `getItem` / `updateItemFields` / `deleteItem` | List item id. |
    | `expand` | No | OData `$expand`; use `fields` to get column values. |
    | `select` / `top` / `filter` | No | OData query options. |
    | `body` | For `createItem` / `updateItemFields` | `createItem` → `{ fields: { <Column>: <value> } }`; `updateItemFields` → `{ <Column>: <value> }`. |

    ### permissions

    ```json
    {
      "name": "permissions",
      "arguments": {
        "action": "list",
        "driveId": "<drive-id>",
        "itemId": "<item-id>"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `list`, `get`, `invite`, `createLink`, `delete`. |
    | `driveId` | Yes | Drive id. |
    | `itemId` | Yes | DriveItem id. |
    | `permId` | For `get` / `delete` | Permission id. |
    | `body` | For `invite` / `createLink` | `invite` → `{ recipients, roles, requireSignIn, sendInvitation }`; `createLink` → `{ type, scope }`. |

    ### directory

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `getUser`, `userMemberOf`, `checkUserMemberGroups`, `getGroup`, `groupMembers`. |
    | `userId` | For `getUser` / `userMemberOf` / `checkUserMemberGroups` | Entra user id or UPN (email). |
    | `groupId` | For `getGroup` / `groupMembers` | Entra group id. |
    | `select` / `top` | No | OData query options. |
    | `body` | For `checkUserMemberGroups` | `{ groupIds: [<id>] }`. |

    ### workbook

    Read and write the cells of an Excel `.xlsx` file natively via the Microsoft Graph Excel API: no download, no OCR.

    ```json
    {
      "name": "workbook",
      "arguments": {
        "action": "usedRange",
        "driveId": "<drive-id>",
        "itemId": "<item-id>",
        "worksheetId": "Sheet1"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `listWorksheets`, `usedRange`, `getRange`, `listTables`, `listTableRows`, `updateRange`, `addTableRow`, `addWorksheet`, `createTable`, `executeFunction`. |
    | `driveId` | Yes | Drive id containing the `.xlsx` file. |
    | `itemId` | Yes | DriveItem id of the `.xlsx` file. |
    | `worksheetId` | For `usedRange` / `getRange` / `updateRange` | Worksheet id or name. |
    | `address` | For `getRange` / `updateRange` | A1 range address, e.g. `A1:D50` or `Sheet1!A1:D50`. |
    | `tableId` | For `listTableRows` / `addTableRow` | Table id or name. |
    | `functionName` | For `executeFunction` | Excel function name, e.g. `vlookup`, `sum`, `today`. |
    | `top` / `select` | No | Max rows (`listTableRows`) and OData `$select`. |
    | `body` | For write actions | `{ values: [[...], [...]] }` (`updateRange` / `addTableRow`), `{ name }` (`addWorksheet`), `{ address, hasHeaders }` (`createTable`), or the function's named arguments (`executeFunction`). |

    `usedRange` reads every populated cell of a sheet and is the action to reach for when an agent should "read the spreadsheet". `addWorksheet`, `createTable` and `updateRange` mutate the workbook; `executeFunction` evaluates an Excel function server-side and returns `{ value }`.

    ### documents

    Read the content of a Word `.docx` file natively: the file is downloaded and its OOXML parsed in-process, with no external extraction service and no OCR.

    ```json
    {
      "name": "documents",
      "arguments": {
        "action": "getText",
        "driveId": "<drive-id>",
        "itemId": "<item-id>"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `getText` returns the full plain text (paragraphs and table cells), capped at about 200,000 characters, and is the right choice for RAG and reading. `getStructure` returns the element tree — paragraphs with style, runs and formatting, tables with rows, columns, headers and cells — plus metadata and the full text. |
    | `driveId` | Yes | Drive id containing the `.docx` file. |
    | `itemId` | Yes | DriveItem id of the `.docx` file. |
    | `includeContent` | No (`getStructure` only) | Include per-element text and runs. Default `true`. Ignored by `getText`. |
    | `maxContentLength` | No (`getStructure` only) | Max characters of text per element; `0` removes the per-element cap. |

    ### dataset

    Ingest a large CSV file once, then query it server-side as many times as needed. The rows live in a private, per-user collection, so the file never enters the agent's context.

    ```json
    {
      "name": "dataset",
      "arguments": {
        "action": "query",
        "datasetId": "<dataset-id>",
        "filter": { "category": "Audio", "price_eur": { "$gt": 100 } },
        "sort": { "price_eur": -1 },
        "limit": 50
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `ingest`, `query`, `aggregate`, `list`, `drop`. |
    | `driveId` / `itemId` | For `ingest` | The CSV DriveItem to stream in. |
    | `ttlDays` | No (`ingest`) | Sliding lifetime, 1–90 days. Defaults to the maintainer-configured retention, otherwise 7 days. |
    | `datasetId` | For `query` / `aggregate` / `drop` | Identifier returned by `ingest`. |
    | `filter` | No | Portable Mongo-style object on the CSV columns: equality, `$gt`, `$lt`, `$gte`, `$lte`, `$in` (non-empty), `$ne`. |
    | `sort` | No (`query`) | `{ <column>: 1 \| -1 }`. |
    | `fields` | No (`query`) | Subset of columns to return. |
    | `limit` / `page` | No (`query`) | Max rows, 1200 maximum, default 50; `page` is 1-based. |
    | `groupBy` / `metric` / `metricField` | For `aggregate` | Column to group on; `count` (default), `sum`, `avg`, `min` or `max`; the numeric column to aggregate for anything other than `count`. |

    `ingest` returns immediately with a `datasetId` and `status: ingesting`, and a background worker streams the rows until `status: ready`; poll with `list`. Files above 50 MB are rejected. Datasets are isolated per user — only their owner can query or drop them — and each read slides the expiry forward. Use `aggregate` for totals or top-N over the whole file: `query` is capped at 1200 rows.

    ## Knowledge-base sync and MCP Resources

    Beyond tools, the endpoint exposes SharePoint content as **MCP Resources** with stable, id-based URIs, so a knowledge base can enumerate, read and re-check them:

    | URI template | What it addresses |
    |---|---|
    | `sharepoint://site/{siteId}` | A site |
    | `sharepoint://site/{siteId}/drive/{driveId}` | A document library |
    | `sharepoint://site/{siteId}/drive/{driveId}/item/{itemId}` | A file or folder |
    | `sharepoint://profile/knowledge` | A machine-readable descriptor of the hierarchy, limits, revision fields and auth modes |

    Listings page at 50 resources by default and 200 at most. Reads return inline text up to 200,000 characters, download binaries up to 1,000,000 bytes, and otherwise return metadata only. Item revisions are tracked by `cTag`, falling back to `eTag`, and drives support a delta feed.

    Resource requests are authorized by the same agent allowlist as tool calls. A scheduled sync that runs without a user session may name the connection owner through `targetUserId`, but only from a workspace listed in the connector's `knowledgeSync.trustedCallers` configuration; any other caller is refused with `Delegated Resource access is restricted to the trusted Knowledge Sync caller.`

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call SharePoint operations from your automations.

    ## Installation

    The installation flow is the standard one: [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), then [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app). Search for **SharePoint** in **Apps**, install it, then open the **Configuration app** link that installation writes into the instance configuration, choose the auth mode, provide credentials, connect, and allow the agents that may call the connector. You need the `owner`, `editor` or `admin` role on the workspace ([Before you begin](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin)).

    For SharePoint, installation provisions two workspace secrets, `sharepointNextAuth` (auth mode and credentials) and `sharepointNextAuthorizedAgents` (the agent allowlist), and binds them so the connector resolves them at runtime ([What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions)). Manage both through the configuration app rather than by editing Secrets directly.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Auto-populated on install; open this link to configure authentication, connect a Microsoft account (OAuth modes), publish the capability, and manage the authorized-agents allowlist. |
    | **Microsoft Graph API version** | `v1.0` (default) or `beta`. |
    | **Knowledge-sync** | Delegated MCP Resource access settings. `trustedCallers` lists the workspace ids allowed to pass a server-verified `targetUserId`. |

    The configuration app drives everything else; the app instance itself has no per-field credential form. From it you pick one of:

    | Auth mode | Label in the app | What you provide |
    |-----------|------------------|------------------|
    | `oauthCentral` | **OAuth2 connection (platform client)** | Nothing; click **Connect** |
    | `oauth` | **OAuth2 per-user — your own Entra app** | **Directory (tenant) ID or domain**, **Application (client) ID**, **Client secret value**, optional **Scopes** |
    | `clientCredentials` | **Client credentials (app-only) — server-to-server** | Tenant, client ID and secret with admin-consented **application** Graph permissions; scopes default to `https://graph.microsoft.com/.default` |
    | `accessToken` | **Access token (direct)** | A Microsoft Graph access token, used as-is with no refresh |

    In the `oauth` mode, register this callback as a **Web** redirect URI on your Entra app registration:

    ```text
    <api-url>/workspaces/<your-workspace-id>/webhooks/<app-instance-slug>.oauthCallback
    ```

    <Warning>
      Microsoft Entra rejects a colon in a redirect URI, so this URI uses your workspace's **raw id**, not the `slug:` form shown on [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls), and it includes the app-instance prefix. Copy the exact value from the configuration app, which renders it under **Callback URL — add this as an Authorized redirect URI on the OAuth client**; it must match byte for byte.
    </Warning>

    <Note>
      **Authorized agents** gates which Agent Creator agents may call this workspace's MCP endpoint; the flow is described in [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector). Tick each agent, or turn on **Allow all agents (disables selection + verification)** — which, as the app warns, lets any agent call the connector ([The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard)). The allowlist does not apply to the shared core endpoint when a central OAuth client is configured.
    </Note>

    Copy the endpoint agents will call from the configuration app, as described in [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint), and hand it to the agent builder together with the **Scope** `context_id,agent_id,user_id`.

## Verify the setup

Run these checks in order after configuring a workspace. Each has an observable result, so a failure tells you which step to revisit. They are the SharePoint form of the generic checks in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation) and [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability).

<Steps>
  <Step title="Verify the credentials reach Microsoft Graph">
    In the configuration app, click **Test connection**. The expected result is `Connection OK — credentials valid.` In the OAuth modes, connect an account first; the app then shows a green **✅ Connected** line naming the account.

    A failure reading `Authenticated, but the Microsoft Graph test call failed (status 403)` means the credentials are valid but the app registration lacks the granted permission or admin consent for `Sites.Read.All`.
  </Step>
  <Step title="Verify the agent is authorized">
    From an agent that has the capability, ask a read-only question such as "list the SharePoint sites you can see". A successful call returns sites. A response containing "This agent is not authorized to use this connector" means the allowlist step was skipped; "The calling agent could not be identified" means the capability **Scope** is missing `agent_id`.
  </Step>
  <Step title="Verify the runtime identity is the end user">
    In the OAuth modes, have a second user with different SharePoint access ask the same question. They must be prompted to connect their own Microsoft account, and their answer must reflect *their* permissions, not the first user's. If both users see identical content, the instance is on `clientCredentials` or `accessToken`, where every call uses one shared identity.
  </Step>
  <Step title="Verify a negative case">
    Ask the agent for a site the connected user cannot open. Microsoft Graph must answer `403 Forbidden` or `404 Not found`; the connector never widens access beyond the connected account's own permissions.
  </Step>
  <Step title="Verify write control">
    If you configured the read-only scope preset, ask the agent to create a folder. The expected result is a `403 Forbidden` from Microsoft Graph, surfaced as a tool error.
  </Step>
</Steps>

## Revoke, rotate and remove

The generic procedures are on [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall), [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client) and [Remove or update a capability](/apps-store/marketplace/connectors/declare-capability#remove-or-update-a-capability). What is specific to Microsoft:

- **Disconnect one account.** A user clicks **Disconnect** in the configuration app, or uses the agent's disconnect action in Chat. The stored token and its refresh token are dropped. A user who connected for both a knowledge base and an agent holds two separate credentials, and disconnecting one leaves the other running. Microsoft Entra has no per-token revocation endpoint, so an Entra administrator revokes sessions from Entra when a hard revocation is required.
- **Rotate the client secret.** Create a new secret in Entra (**App registrations → Certificates & secrets**), paste its **Value** into the configuration app, and save. Entra client secrets expire; an expired one surfaces as `AADSTS7000215: Invalid client secret provided`.
- **Rotate the central client.** A maintainer re-saves the central OAuth client from the maintainer view. Tenants that use `oauthCentral` pick it up with no change on their side; users reconnect only if the scopes changed. Withdrawing it entirely means deleting the `sharepointNextCentralOAuth` secret from the core workspace, which also stops the core MCP endpoint accepting every agent.
- **Remove an agent's access.** Untick the agent under **Authorized agents** and save, or remove the capability from the agent in Agent Creator.
- **Uninstall.** Remove the app instance from the workspace, then delete the `sharepointNextAuth` and `sharepointNextAuthorizedAgents` secrets — uninstalling does not delete them. Ingested CSV datasets expire on their own sliding TTL, and a daily job drops the expired ones; use `dataset` `drop` to free one immediately.

## Error handling

| HTTP code | Meaning |
|-----------|---------|
| `400` | Bad request: invalid parameters or malformed body, for example a bad OData filter or an invalid driveItem or list resource. |
| `401` | Unauthorized: the Microsoft Graph access token is missing, expired or revoked. The user must reconnect (OAuth modes). |
| `403` | Forbidden: insufficient Graph scope or permission, missing admin consent (application mode), or the account lacks access to the site, drive or item. |
| `404` | Not found: the site, drive, item, list or permission id does not exist or is not visible to the account. |
| `429` | Throttled: Microsoft Graph rate limit; back off and retry, honoring `Retry-After`. |
| `500` / `503` | Microsoft Graph service error: transient; retry shortly, no reconnection needed. |

### Common issues

The messages below are the ones SharePoint emits. Failures every App + MCP connector shares are documented once: an empty **Configuration app** field or an allowlist secret left as an unresolved binding in [installation troubleshooting](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting), and a maintainer view showing **Access restricted** in [central-client troubleshooting](/apps-store/marketplace/connectors/central-oauth#troubleshooting).

**"This agent is not authorized to use this connector"**: the calling agent is not in the allowlist. Open the configuration app → **Authorized agents** → tick this agent (the message quotes its id) and save, or turn on **Allow all agents**. The **Install capability** button does both steps for you.

**"The calling agent could not be identified, so it cannot be authorized"**: the MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability, then allow the agent in the configuration app.

**"Microsoft Graph is not connected for this user"**: no per-user OAuth token. The user opens the configuration app and clicks **Connect**, or uses the agent's connect action in Chat.

**"Microsoft Graph token refresh failed … They must reconnect from the config app."**: the stored refresh token was revoked or expired. The connection is dropped automatically and the user must reconnect.

**"Microsoft Graph token endpoint temporarily unavailable … Retry shortly — no reconnection needed."**: a transient Microsoft outage. Do not reconnect; retry.

**"Microsoft Graph OAuth is not configured."**: neither a tenant OAuth client nor the central platform client is available. Set the client ID, secret and tenant in the configuration app, or ask the platform maintainer to provision the central client from the core workspace.

**"Microsoft Graph client_credentials exchange failed …"**: in application mode, check the **Application (client) ID**, the secret **Value**, the tenant id, and that a Global Administrator granted admin consent for the application permissions.

**"No access token configured."**: the instance is in `accessToken` mode with an empty token. Paste a valid Microsoft Graph access token in the configuration app.

**`AADSTS7000215: Invalid client secret provided`**: the **Secret ID** (a GUID) was pasted instead of the secret **Value** (the long string shown only once, right after creation) — or the secret has expired. Create a fresh secret in Entra and paste its Value.

**OAuth popup returns `invalid_state`**: the authorization response no longer matches the pending request, usually because the flow was resumed in another browser session or a stale popup was reused. Close the popup and click **Connect** again.

**OAuth popup returns `oauth_client_not_configured`**: the connect flow ran before any OAuth client was available. Configure the tenant client, or ask the maintainer to store the central one.

**Microsoft Entra rejects the redirect URI**: Entra rejects a colon in a redirect URI. Register the callback with the workspace's **raw id** and the app-instance prefix, exactly as the configuration app renders it, never the `slug:` form.

**Microsoft rejects the sign-in for a single-tenant app**: the **Sign-in authority** must match the app registration's supported account types. A single-tenant app requires **Specific tenant** with its id or domain.

**"Direct calls are not allowed — use the MCP endpoint."**: an entity tool automation was invoked directly instead of through the connector's MCP endpoint. Call the MCP endpoint, or use the public Builder instructions from DSUL.

**"File too large for ingestion"**: `dataset` `ingest` rejects CSV files above 50 MB. Split the file, or filter it in SharePoint before ingesting.
