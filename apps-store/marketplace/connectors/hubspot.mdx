The HubSpot connector exposes a HubSpot portal through the [HubSpot REST API](https://developers.hubspot.com/docs/api/overview) to **Agent Creator** agents (through MCP) and to Builder automations (through the `Hubspot.<instruction>` App instructions), covering the CRM (contacts, companies, deals, tickets, engagements, associations, pipelines, properties, owners, lists) and the Marketing layer (forms, marketing emails, workflows, files). The same 124 HubSpot operations are published twice: as **124 App instructions** for Builder automations, and as **18 entity tools** for MCP, each driven by an `action` argument. The MCP server (`hubspot-mcp`) runs in the **tenant app-instance context**: it resolves the installing workspace's own credentials and authorizes the calling agent against that workspace's allowlist. HubSpot is a single-host API: every call goes to `https://api.hubapi.com` with an `Authorization: Bearer <token>` header.

Three authentication modes are supported. Pick one before configuring anything:

| Mode | Runtime identity at HubSpot | Choose it when |
|------|-----------------------------|----------------|
| `oauthCentral` (recommended) | The end user who signed in, on the platform-wide HubSpot OAuth application | A platform maintainer has registered the central HubSpot application and you want each user to act as themselves with nothing to register per workspace |
| `oauth` | The end user who signed in, on your own HubSpot OAuth application | You must own the HubSpot application (portal allowlist, scope set, secret rotation) for your workspace |
| `accessToken` | The HubSpot Private App itself, one shared identity for every caller | Unattended automations with no interactive user, where a single service identity is acceptable |

`oauthCentral` and `oauth` are the same per-user authorization-code flow with Proof Key for Code Exchange (PKCE); they differ only in which OAuth client is used. `oauthCentral` explicitly ignores any client ID and secret left in the workspace configuration and always resolves the central client.

<Warning>
  **`accessToken` is a shared credential.** Every agent and every automation that reaches the connector acts as the same HubSpot Private App, so HubSpot audit records show one identity for all callers and per-user permissions are not enforced. Use it only for unattended workloads, grant the Private App the narrowest scope set that covers the operations you call, and prefer a per-user OAuth mode for anything a person triggers.
</Warning>

## Prerequisites

- The Prisme.ai roles listed in [what a workspace install requires](/apps-store/marketplace/connectors/install-in-workspace#before-you-begin), or, for the central client, in [what the central OAuth setup requires](/apps-store/marketplace/connectors/central-oauth#before-you-begin).
- A **HubSpot account** with access to the portal you want to expose.
- For the **OAuth modes**: a HubSpot OAuth application. HubSpot Developer Platform `2025.2` declares the OAuth app as code in a HubSpot project deployed with the HubSpot CLI, from a free **HubSpot developer account** at [developers.hubspot.com](https://developers.hubspot.com/), which is separate from any CRM account. The platform maintainer registers one app for `oauthCentral`; a workspace can register its own for `oauth`. Copy the **Client ID** and **Client Secret** from the deployed app's **Auth** tab.
- For **`accessToken`**: a **Private App access token** created in the HubSpot portal under **Settings > Integrations > Private Apps**, granted the scopes that cover the operations you intend to call.
- **OAuth scopes**: the connector sends every requested scope in the `scope=` parameter of the authorization URL, so each one must already be declared in the HubSpot application as a required or an optional scope. The shipped application declares the sets below.
- Base URL: `https://api.hubapi.com` (single host). Authorization endpoint: `https://app.hubspot.com/oauth/authorize`. Token endpoint: `https://api.hubapi.com/oauth/v1/token`.

The shipped HubSpot application declares these scopes.

| Tier | Scopes | Covers |
|------|--------|--------|
| Required | `oauth`, `crm.objects.contacts.read`, `crm.objects.contacts.write`, `crm.objects.companies.read`, `crm.objects.companies.write`, `crm.objects.deals.read`, `crm.objects.deals.write`, `crm.objects.owners.read`, `tickets` | The `contacts`, `companies`, `deals`, `tickets` and `owners` tools, plus refresh-token issuance (`oauth`) |
| Optional | `crm.schemas.contacts.read`, `crm.schemas.companies.read`, `crm.schemas.deals.read`, `crm.lists.read`, `crm.lists.write`, `files`, `forms`, `automation`, `content`, `e-commerce` | `properties` schema reads, `lists`, `files`, `forms`, `workflows` (`automation`) and `marketingEmails` (`content`) |

When no scope string is configured for a workspace, the connector requests the required tier only:

```text
oauth crm.objects.contacts.read crm.objects.contacts.write crm.objects.companies.read crm.objects.companies.write crm.objects.deals.read crm.objects.deals.write crm.objects.owners.read tickets
```

Optional-tier scopes depend on the portal's HubSpot subscription. Requesting one the portal does not carry makes HubSpot reject the authorization request, so add optional scopes to the workspace **Scopes** field only for portals that have the matching feature.

  ## 1. Configure the connector

  <Steps>
    <Step title="Register the OAuth application at HubSpot">
      Create a free **HubSpot developer account**, install the CLI (`npm install -g @hubspot/cli@latest`), then deploy the OAuth app project. The `hubspot` workspace ships ready-to-deploy projects under `workspaces/hubspot/project/` (one per environment); each `app-hsmeta.json` declares the redirect URI, required and optional scopes. Set the single Authorized redirect URI to the **core workspace** callback:

      ```text
      <api-url>/workspaces/slug:hubspot/webhooks/oauthCallback
      ```

      (e.g. `https://api.studio.prisme.ai/v2/workspaces/slug:hubspot/webhooks/oauthCallback` on production). This is the **only** redirect URI to register: tenant workspaces reuse it, and the core workspace proxies the authorization code back to the workspace that started the flow. Do not register a tenant-shaped URI here; see [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls) for the two shapes and why they are not interchangeable. The shipped app declares `"distribution": "private"`, so list the HubSpot portals allowed to install it. Deploy with `hs project upload && hs project deploy`, then copy the **Client ID** and **Client Secret** from the app's **Auth** tab (the secret is shown only once).
    </Step>
    <Step title="Enter the credentials through the configuration app">
      Open the central `hubspot` workspace and launch its **Configuration app**: `<studio>/apps/hubspot` (e.g. `https://studio.prisme.ai/apps/hubspot`). Loaded from the core workspace, the app shows the **maintainer view** (org owner / editor / admin only); paste the **Client ID** and **Client Secret** there and Save. Follow [Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client) for the form itself. The app writes them to the core workspace secret `hubspotCentralOAuth`; do not edit Studio's raw Secrets by hand. These credentials stay in the `hubspot` workspace and are never exposed to tenants or end users: tenants read the public client id and scopes from the core `getOAuthClientPublic` webhook, and token exchange is proxied through the core `centralTokenExchange` webhook, so the client secret never leaves the core workspace ([how this works](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace)).
    </Step>
    <Step title="Tell workspaces to use the central client">
      Each consuming workspace selects auth mode **`oauthCentral`** in the connector configuration app (no client id/secret to enter on their side). Their users then just click **Connect**. Hand them [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace).
    </Step>
    <Step title="(Optional) Publish to the Capabilities catalog">
      From that same maintainer view, the **Add to catalog** button publishes HubSpot to the org-wide **Capabilities catalog** in one click (org owner / admin only; it stays disabled until the central client is saved). Once published, every agent builder in the org can enable HubSpot from the catalog without pasting an endpoint; see [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog) and [Option A, the shared catalog capability](#option-a-shared-catalog-capability).
    </Step>
  </Steps>

  ## 2. Declare the capability in AI Governance

  As an alternative to (or in addition to) the catalog button, you can declare HubSpot as a named **capability** in AI Governance. Agent builders then enable that capability on their agents instead of pasting a raw MCP endpoint. Follow [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance), with these HubSpot values:

  | Field | Value for HubSpot |
  |-------|-------------------|
  | Capability name | `HubSpot` |
  | Server URL (**SSE/WebSocket URL**) | The connector's **MCP Endpoint**: the core `<api-url>/workspaces/slug:hubspot/webhooks/mcp`, or a tenant workspace's `<api-url>/workspaces/slug:<workspace>/webhooks/<app-instance>.mcp` |
  | **Scope** | `context_id,agent_id,user_id` — the `agent_id` is what lets the connector identify and authorize the calling agent |
  | Authorization block | Nothing to author. Connect, status and disconnect are served by the connector's own `oauthConnect`, `oauthStatus` and `oauthDisconnect` webhooks, wired automatically |

  <Steps>
    <Step title="Verify the central client end to end">
      From an agent that has the capability, in a workspace configured for `oauthCentral`, run a read-only call: `owners` with `action: "list"`. The user is prompted to connect once (HubSpot sign-in, then portal selection). The call must return the owners of **that user's own portal**, which confirms that the runtime identity is the end user and not a shared account. Subsequent calls reuse the stored token and refresh it automatically. The remaining checks are in [Verify the central client](/apps-store/marketplace/connectors/central-oauth#verify-the-central-client).
    </Step>
  </Steps>

  <Warning>
    Declaring the capability makes the connector **available**; it does not by itself authorize a specific agent. This connector follows the **tenant-context model**: which agents may actually call it is gated per-workspace by the **authorized-agents allowlist** in the configuration app (see [Workspace builder](#workspace-builder-dsul)). Read [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization).
  </Warning>

  <Warning>
    **The core `hubspot` workspace's own MCP endpoint bypasses the allowlist.** As soon as the central OAuth client is stored there, that endpoint accepts every calling agent, on the assumption that per-user OAuth is the real access gate. Publish the core endpoint as a capability only if you accept that any agent in the organization may call it; otherwise publish a capability that points at a dedicated tenant workspace, which does enforce its allowlist. See [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint).
  </Warning>

  <Note>
    **Every requested scope must be declared in the HubSpot application.** The connector puts all configured scopes into the `scope=` parameter of the authorization URL, so a scope missing from the application's `requiredScopes` or `optionalScopes` makes HubSpot reject the authorization request. To add a scope, edit `app-hsmeta.json` for each environment, then re-run `hs project upload && hs project deploy` from that project folder. Existing user sessions stay valid; the next user to connect sees the updated consent screen.
  </Note>

  ## 3. Rotate or revoke the central client

  The generic rotation, scope-change and withdrawal rules are in [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client). What is specific to HubSpot:

  - **Rotate the client secret.** Generate a new secret on the HubSpot application, reopen the maintainer view of the configuration app, paste the new **Client ID** and **Client Secret**, and select **Save**. Access tokens already issued keep working until they expire; refreshes then run against the new secret through the core `centralTokenExchange` webhook.
  - **Revoke the client.** Delete the HubSpot application from the developer account. Every stored per-user token stops refreshing, `oauthStatus` reports `connected: false`, and agents re-propose the connect flow. Workspaces that must keep working should first switch to auth mode `oauth` with their own HubSpot application, or to `accessToken`.
  - **Withdraw the central client without deleting the HubSpot application.** Delete the `hubspotCentralOAuth` secret from the core `hubspot` workspace **Secrets**. The maintainer view has no withdraw action.
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator use HubSpot through MCP tools.

    <Note>
      Before an agent can call the connector, a workspace builder must have installed and configured the HubSpot app in a workspace (see [Workspace builder](#workspace-builder-dsul)), and, for the central OAuth mode, a platform admin must have provisioned the shared OAuth client (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    This connector runs in the **tenant app-instance context**, and your agent is authorized in two steps. First it is identified by the `agent_id` that Agent Creator injects through the capability **Scope**. Then that agent id must appear in the connector's **authorized-agents allowlist**, managed in the configuration app. The HubSpot access token itself is resolved server-side from the configured auth mode, so no credential ever reaches the agent. The full model is in [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization).

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A (shared catalog capability)

    The fastest path: a platform admin has already published a **HubSpot** capability to the Capabilities catalog (see [Publish to the Capabilities catalog](#platform-admin-governance-one-time-platform-setup)), so you just pick it from the catalog. Open your agent in Agent Creator, browse the capability catalog, select **HubSpot**, and enable it. The MCP endpoint URL and the **Scope** (`context_id,agent_id,user_id`) are already wired by the admin, so there is nothing to paste. When the capability points at the core `hubspot` workspace, that endpoint accepts every calling agent once the central OAuth client is stored there, so there is no allowlist step on your side.

    On the first tool call, an unconnected user is prompted to sign in: Agent Creator surfaces a `connect_url` to HubSpot's authorization page, where the user picks the portal to authorize (from the allowlisted set) and reviews the requested scopes. After sign-in the per-user token is stored and reused on subsequent calls.

    <Note>
      Convenient, but your agent runs against a **shared, platform-managed instance**: its HubSpot credentials are owned by someone else and the instance accepts every agent that is granted the capability. Prefer [Option B, your own workspace](#option-b-your-own-workspace) for anything beyond quick experiments.
    </Note>

    ## Option B (your own workspace)

    Recommended for production agents: install the connector in **your own workspace** and point the agent at *that* workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP runs in *your* app-instance context, the HubSpot credentials, the per-user OAuth tokens and the authorized-agents allowlist are all **scoped to your workspace**, not shared platform-wide. You decide exactly which agents may call it and which HubSpot account / auth mode backs them, and a misconfiguration elsewhere can never expose your data. The shared catalog capability ([Option A](#option-a-shared-catalog-capability)) is a broad surface many agents can reach; your own workspace is an isolated, least-privilege boundary.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder](#workspace-builder-dsul): install **HubSpot** in your workspace, open its **Configuration app**, choose the auth mode and connect a HubSpot account (or paste a Private App token).
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's config app, open **Authorized agents** and tick your agent, or enable **Allow all agents**. The **Install capability** button allowlists the agent and attaches the tool in one action; see [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Add the MCP capability to your agent">
        In your agent, add a capability pointing at **your workspace's MCP Endpoint**, which has the form `<api-url>/workspaces/slug:<your-workspace>/webhooks/<app-instance>.mcp`, and set its **Scope** to:

        ```text
        context_id,agent_id,user_id
        ```

        The `agent_id` is what lets the connector identify and authorize your agent; without it, every call is rejected with an explicit "calling agent could not be identified" message. This *Scope* is separate from the HubSpot OAuth scopes; see [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
      </Step>
      <Step title="Connect a HubSpot account">
        On the first tool call, the user is prompted to sign in (or uses **Connect** in the config app). The per-user token is stored and reused; refresh is automatic.
      </Step>
      <Step title="Verify with a read-only call">
        Ask the agent to list HubSpot owners. The `owners` tool with `action: "list"` must return the owners of the connected portal. If it returns an authorization message instead, work through [Common Issues](#common-issues). The rest of the capability checks are in [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability).
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent must know the connector exists and when to reach for it. Add a short paragraph to the agent's system prompt. Copy-pasteable starter:

    ```text
    You have access to the HubSpot MCP server. Use it whenever the user asks about CRM data: contacts, companies, deals, tickets, engagements, pipelines or marketing assets (forms, emails, workflows). Each tool is an entity that takes an `action` argument. Always prefer `action: search` over `action: list` for filtered lookups. For batch work, use the `batch*` actions instead of looping individual calls. Always confirm with the user before destructive actions (archive, delete, batchArchive, unenrollContact, removeMembers).
    ```

    Refine the trigger keywords (resource names, business domains, typical user phrasings) so the agent reliably picks up the right intent in your context.

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the **MCP Endpoint** URL. The agent still has to be allowlisted in the config app and its identity propagated so the connector can read its `agent_id`. See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).
    </Note>

    <Note>
      **Restricting to read-only (least privilege).** HubSpot tools cover both reads and writes (create, update and archive contacts, companies, deals and tickets). The granted OAuth scopes **are** the enforcement point. To allow reads only, set the **Scopes** field in the configuration app to the read set, dropping every `*.write` scope:

      ```text
      oauth crm.objects.contacts.read crm.objects.companies.read crm.objects.deals.read crm.objects.owners.read
      ```

      HubSpot's `tickets` scope grants read **and** write in one scope, so leaving it in keeps ticket writes open; drop it to close them, at the cost of losing the `tickets` tool entirely. With `oauthCentral` you do not create your own HubSpot application: keep `oauthCentral` and enter the read scopes, and the workspace scope string overrides the platform default (the central application must declare those read scopes). Write calls are then rejected by HubSpot with `403`. The scope string is a workspace-level setting that a workspace editor can widen again, and existing connections keep the scopes they were granted until their owner disconnects and reconnects.
    </Note>

    ## Available Tools

    The MCP server exposes 18 entity-level tools, each with an `action` argument to select the operation. `action` is the only argument the tool schemas mark as required; every other parameter is optional in the schema and validated by HubSpot at call time. Every tool also accepts an `outputFormat` parameter (see [Output Formats](#output-formats)).

    ### `contacts` / `companies` / `deals`

    These three CRM tools share the same set of actions.

    | Action | Description |
    |--------|-------------|
    | `list` | List records with pagination and property selection |
    | `get` | Retrieve a single record by id (or by `idProperty`) |
    | `create` | Create a record with properties and optional associations |
    | `update` | Update a record by id |
    | `archive` | Archive (soft-delete) a record |
    | `search` | Full-text and structured search with filter groups, sorts and a `query` shortcut |
    | `merge` | Merge two records into one (`primaryObjectId` keeps, `objectIdToMerge` is absorbed) |
    | `batchRead` | Read several records in one call, from `inputs` |
    | `batchCreate` | Create several records in one call, from `inputs` |
    | `batchUpdate` | Update several records in one call, from `inputs` |
    | `batchArchive` | Archive several records in one call, from `inputs` |

    ### `tickets`

    Same actions as the CRM trio above, minus `merge`.

    ### `associations`

    | Action | Description |
    |--------|-------------|
    | `list` | List associations from a record to a target object type |
    | `create` | Create an association between two records |
    | `archive` | Remove an association between two records |

    `fromObjectType` and `toObjectType` accept `contacts`, `companies`, `deals`, `tickets`, `notes`, `tasks`, `meetings`, `calls` and `emails`.

    ### `notes` / `tasks` / `calls` / `engagementEmails` / `meetings`

    All five engagement tools share the same actions.

    | Action | Description |
    |--------|-------------|
    | `list` | List engagements |
    | `get` | Retrieve a single engagement |
    | `create` | Create an engagement, optionally with associations to CRM records |
    | `update` | Update an engagement |
    | `archive` | Archive an engagement |

    ### `pipelines`

    | Action | Description |
    |--------|-------------|
    | `list` | List pipelines for an object type |
    | `get` | Retrieve a pipeline |
    | `create` | Create a pipeline |
    | `update` | Update a pipeline |
    | `archive` | Archive a pipeline |
    | `listStages` | List the stages of a pipeline |
    | `getStage` | Retrieve a stage |
    | `createStage` | Add a stage to a pipeline |
    | `updateStage` | Update a stage |
    | `archiveStage` | Archive a stage |

    Every `pipelines` action takes an `objectType` of `deals` or `tickets`.

    ### `properties`

    | Action | Description |
    |--------|-------------|
    | `list` | List properties for an object type |
    | `get` | Retrieve a property |
    | `create` | Create a property |
    | `update` | Update a property |
    | `archive` | Archive a property |
    | `listGroups` | List property groups for an object type |
    | `createGroup` | Create a property group |
    | `updateGroup` | Update a property group |
    | `archiveGroup` | Archive a property group |

    Every `properties` action takes an `objectType` such as `contacts`, `companies`, `deals`, `tickets`, `notes`, `tasks`, `calls`, `emails` or `meetings`. Property definitions read through this tool need the matching `crm.schemas.*.read` scope.

    ### `owners`

    | Action | Description |
    |--------|-------------|
    | `list` | List owners (optionally filter by email) |
    | `get` | Retrieve an owner by id |

    ### `lists`

    | Action | Description |
    |--------|-------------|
    | `create` | Create a list |
    | `get` | Retrieve a list (optionally with filters) |
    | `update` | Rename a list |
    | `delete` | Delete a list |
    | `search` | Search lists by name and processing type |
    | `addMembers` | Add records to a `MANUAL` list |
    | `removeMembers` | Remove records from a `MANUAL` list |
    | `getMemberships` | List the members of a list |

    `processingType` is one of `MANUAL`, `SNAPSHOT` or `DYNAMIC`, and `objectTypeId` identifies the record type (for example `0-1` for contacts). Membership of a `DYNAMIC` list is computed from its filter tree, so only `MANUAL` lists accept `addMembers` and `removeMembers`. The `lists` tool schema declares `listId` as the only parameter of those two actions; the record ids travel as extra top-level arguments passed through to the HubSpot endpoint.

    ### `forms`

    | Action | Description |
    |--------|-------------|
    | `list` | List marketing forms |
    | `get` | Retrieve a form |
    | `create` | Create a form |
    | `update` | Update a form |
    | `archive` | Archive a form |
    | `submit` | Submit values to a form on behalf of a visitor |

    ### `marketingEmails`

    | Action | Description |
    |--------|-------------|

    | `get` | Retrieve a marketing email |
    | `create` | Create a marketing email |
    | `update` | Update a marketing email |
    | `archive` | Archive a marketing email |
    | `sendTransactional` | Send a transactional single-send email to a recipient |

    ### `workflows`

    | Action | Description |
    |--------|-------------|
    | `list` | List workflows |
    | `get` | Retrieve a workflow |
    | `enrollContact` | Enroll a contact in a workflow by email |
    | `unenrollContact` | Unenroll a contact from a workflow by email |

    ### `files`

    | Action | Description |
    |--------|-------------|
    | `list` | List files |
    | `get` | Retrieve file metadata |

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call HubSpot operations from your automations.

    ## Installation

    HubSpot follows the standard App + MCP install flow: [Install a connector in your workspace](/apps-store/marketplace/connectors/install-in-workspace). Search for **HubSpot** in **Apps** and install it ([Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app)), then open the **Configuration app** link that the install populates ([Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app)) to choose the auth mode, provide credentials, connect a HubSpot account, and allow the agents that may call the connector ([Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector)). The MCP endpoint you hand to an agent builder is the one described in [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint).

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** (`configAppUrl`) | Read-only, auto-populated on install: open this link to configure authentication (mode plus credentials), connect a HubSpot account (OAuth modes), and manage the authorized-agents allowlist. |

    The configuration app drives everything; the app instance itself has no per-field credential form. From it you pick one of:

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | `oauthCentral` | Nothing beyond selecting **Connect**. An optional **Scopes** string narrows the platform default. See [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace) | Platforms where the maintainer configured the central HubSpot client, and human-facing agents where each user acts as themselves |
    | `oauth` | Your own HubSpot **Client ID** and **Client Secret**, plus an optional **Scopes** string. Register the redirect URI shown in the config app, of the form `<api-url>/workspaces/slug:<your-workspace>/webhooks/<app-instance>.oauthCallback` | You manage your own HubSpot OAuth application |
    | `accessToken` | A HubSpot **Private App access token** | Unattended automations where one shared identity is acceptable |

    <Warning>
      The tenant redirect URI carries an app-instance prefix and the central one does not. Copy the value the configuration app renders rather than assembling it; see [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls).
    </Warning>

    Installing the app provisions two workspace secrets and wires them to the app instance ([what installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions)):

    | Secret | Holds |
    |--------|-------|
    | `hubspotAuth` | The auth object `{ mode, oauthClientId, oauthClientSecret, accessToken, scopes }`, resolved server-side as `config.auth`. |
    | `hubspotAuthorizedAgents` | Comma-separated agent ids allowed to call this instance's MCP endpoint, or `*` for all. Resolved as `config.authorizedAgents`. |

    A third secret, `hubspotCentralOAuth`, exists only in the core `hubspot` workspace and holds the central OAuth client. Tenant workspaces cannot read it: they obtain the public client id and scopes from the core `getOAuthClientPublic` webhook, and token exchanges are proxied through the core `centralTokenExchange` webhook. See [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace).

    <Note>
      Secrets are resolved server-side and never returned to a caller, so no credential value is echoed by the connector. The agent allowlist (**Authorized agents**) gates which Agent Creator agents may call the MCP endpoint; see [Agent builder](#agent-builder-agent-creator) and, for the `*` wildcard and its blast radius, [The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard). Builder automations calling `Hubspot.<instruction>` resolve the same workspace credentials without going through the allowlist.
    </Note>

    ### Per-user tokens and unattended runs

    In the OAuth modes, each connected user's access token and refresh token are stored in that user's own scope. The access token is reused until it is within 120 seconds of expiry, then refreshed automatically; when HubSpot returns no expiry the connector assumes 3300 seconds. A refresh rejected with a `4xx` status invalidates the stored connection so the user is prompted to reconnect instead of hitting repeated failures, while a `5xx` is reported as transient and left connected.

    For unattended runs such as scheduled automations, there is no signed-in user. The connector then resolves a token from a workspace secret named `hubRefresh_<userId>`, which is written during the OAuth callback. That write only succeeds when the connecting user is a workspace editor or owner, so to enable unattended runs have an editor connect once from the configuration app. Ordinary end users still get a working interactive connection either way.

    <Warning>
      The `targetUserId` that selects whose stored refresh token to use must come from trusted server-side configuration. Never wire it to an inbound request parameter or to an argument supplied by an agent, since that would let a caller act as another user.
    </Warning>

    ## Verify the workspace setup

    Run the full check list in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation). The HubSpot-specific checks are:

    1. In the configuration app, confirm that the auth mode is set and, in the OAuth modes, that the connection status shows as connected for your user.
    2. In a Builder automation, run `Hubspot.listOwners` with no arguments. It must return the owners of the connected HubSpot portal. This is the connector's "who am I" check: in an OAuth mode the owners must belong to the signed-in user's own portal, and in `accessToken` mode they belong to the Private App's portal.
    3. If the step returns an `error` field instead, match its message against [Common Issues](#common-issues).

## Error Handling

The connector normalizes every non-`2xx` HubSpot response into a single message that names the failing operation and appends HubSpot's own detail. It never echoes an unrecognized response body, so credentials and provider metadata cannot leak into a tool result.

| HTTP status | Message the connector returns | Typical cause |
|-------------|-------------------------------|----------------|
| `400` | `Bad request while <operation>: <detail>` | Invalid property value, malformed `filterGroups`, missing required field |
| `401` | `Authentication failed while <operation>. Check HubSpot credentials / OAuth connection.` | Missing or invalid Private App token or OAuth token, revoked refresh token |
| `403` | `Forbidden while <operation>. Check the user's HubSpot permissions / OAuth scopes.` | The token lacks the scope, or the portal does not carry the feature the endpoint needs |
| `404` | `Resource not found while <operation>.` | The record, list, workflow or form does not exist, or was archived |
| `429` | `Rate limit / org limit exceeded while <operation>. Wait and retry.` | Portal quota exceeded |
| `500` | `HubSpot server error while <operation>.` | Transient HubSpot failure; retry with backoff |
| Any other | `Error <status> while <operation>: <detail>` | Includes `409` conflicts such as a unique-property collision on contact creation |

### Common Issues

Failures that are not HubSpot-specific — an empty **Configuration app** field, a rejected redirect URI, an allowlist secret left as an unresolved binding — are covered in [Install a connector in your workspace: Troubleshooting](/apps-store/marketplace/connectors/install-in-workspace#troubleshooting), [Central OAuth client: Troubleshooting](/apps-store/marketplace/connectors/central-oauth#troubleshooting) and [Declare a connector capability: Troubleshooting](/apps-store/marketplace/connectors/declare-capability#troubleshooting).

**"This agent is not authorized to use this connector"**: The calling agent is not in the allowlist. Open the configuration app, select **Authorized agents**, tick this agent (its id is quoted in the error) or enable **Allow all agents**, then select **Save**. The **Install capability** button does this for you.

**"The calling agent could not be identified, so it cannot be authorized"**: The MCP capability **Scope** does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id` on the capability (this is separate from the HubSpot OAuth scopes), then allow the agent in the config app.

**"Unknown tool `<name>`"**: The MCP client asked for a tool this server does not publish. Re-read the tool list; the server exposes the 18 entity tools listed under [Available Tools](#available-tools).

**"Direct calls are not allowed, use the MCP endpoint"**: A tool automation was invoked directly rather than through the MCP endpoint. Point the capability at the `.mcp` webhook, not at an individual tool webhook.

**"Missing required argument `action`"**: The tool was called without an `action`. The message lists the actions that tool accepts; pick one.

**"HubSpot is not connected for this user"**: No per-user OAuth token is stored for the caller. Open the configuration app in an OAuth mode and select **Connect**, or use the agent's connect flow.

**"HubSpot is not authenticated"**: No auth mode resolved at all. Set the auth mode and its credentials in the configuration app.

**"HubSpot token refresh failed"**: HubSpot rejected the stored refresh token, usually because the user revoked access or the grant expired. The connector deletes the stale connection automatically; the user reconnects from the config app.

**"HubSpot token endpoint temporarily unavailable"**: HubSpot returned a `5xx` on the token endpoint. This is transient and marked as such, so the connection stays valid. Retry shortly; no reconnection is needed.

**"No stored HubSpot token for this user"**: An unattended run tried to resolve a user who has no `hubRefresh_<userId>` workspace secret. Have that user connect once from the configuration app while holding the workspace editor or owner role.

**"HubSpot OAuth is not configured"**: Neither a workspace OAuth client nor the central platform client is available. Set the OAuth client id and secret in the config app for mode `oauth`, or ask the platform maintainer to provision the central OAuth client from the core workspace.

**OAuth callback reports `invalid_state`**: The authorization response did not match a pending connect request, typically after the connect page was left open too long or reused. Restart the flow from **Connect**.

**OAuth callback reports `oauth_client_not_configured`**: The callback ran before any OAuth client was resolvable. Configure the client, then reconnect.

**Authorization is rejected for a scope**: The authorization URL requested a scope the deployed HubSpot application does not declare, or one the portal's subscription does not carry. Every requested scope must appear in `requiredScopes` or `optionalScopes` of `app-hsmeta.json`; re-run `hs project upload && hs project deploy` after editing, and remove scopes the portal cannot grant.

**No token revocation at HubSpot**: The connector's disconnect flow deletes the stored access token, the stored refresh token and the `hubRefresh_<userId>` workspace secret; it does not revoke anything at HubSpot. To cut access at the provider, uninstall the connected application from the HubSpot portal.

## Disconnect, revoke and uninstall

The generic lifecycle, including what survives an uninstall, is in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall). Applied to HubSpot:

| Goal | Who | How |
|------|-----|-----|
| Disconnect one user | The user | Select **Disconnect** in the configuration app, or use the agent's disconnect action. The stored tokens and that user's `hubRefresh_<userId>` secret are deleted, and the status view reports `disconnected`. |
| Cut a user's access at HubSpot | HubSpot portal admin | Uninstall the connected application from the HubSpot portal. Refreshes then fail with a `4xx`, and the connector drops the stale connection on the next call. |
| Rotate a workspace OAuth client secret | Workspace builder | Generate a new secret at HubSpot, paste the new **Client ID** and **Client Secret** in the configuration app, and select **Save**. |
| Rotate a Private App token | Workspace builder | Rotate the token in the HubSpot portal, paste the new value in the configuration app, and select **Save**. |
| Revoke one agent | Workspace builder | Untick it in **Authorized agents** in the configuration app, or clear **Allow all agents**. Its next call is denied with `This agent is not authorized to use this connector`. |
| Rotate or revoke the central client | Platform maintainer | See [Rotate or revoke the central client](#3-rotate-or-revoke-the-central-client). |
| Remove the connector from a workspace | Workspace builder | Uninstall the app, then delete the `hubspotAuth`, `hubspotAuthorizedAgents` and any `hubRefresh_<userId>` workspace secrets it provisioned. |
