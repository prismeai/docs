<Note>
  This is the **legacy** Outlook connector. It is built from two workspaces, **Outlook App** (`outlook-app`) and **Outlook MCP** (`outlook-mcp`), and it authenticates either with Azure application credentials passed as request headers or with a per-user delegated OAuth connection stored in the Outlook MCP workspace.

  It is superseded by the **[Outlook](/apps-store/marketplace/connectors/outlook)** connector (App+MCP, tenant-context, central Microsoft Entra OAuth, with `mail`, `mailFolders`, `calendars`, `events`, `contacts` and `contactFolders` entity tools). Use the Outlook connector for any new work. This page is kept for existing installations and for planning the move.
</Note>

The legacy Outlook connector exposes a Microsoft 365 mailbox through the [Microsoft Graph](https://learn.microsoft.com/en-us/graph/overview) REST API (v1.0). It can be consumed two ways: as a Builder app whose instructions you call directly from DSUL, or as a remote MCP server that **Agent Creator** agents call as tools. Mail operations are available on both surfaces; calendar operations are available on the Builder surface only.

<CardGroup cols={3}>

  </Card>
  <Card title="Send and reply" icon="paper-plane">
    Send mail, send an existing draft, reply, reply all and forward, with HTML or text bodies.
  </Card>
  <Card title="Manage messages and calendar" icon="folder-open">

  </Card>

## Who is this for?

This connector involves three roles. Each section below is self-contained; start with the one that matches yours.

<CardGroup cols={3}>
  <Card title="Workspace builder" icon="puzzle-piece" href="#configure-the-connector">
    You install **Outlook App** in a workspace, fill in its configuration, and call its instructions from DSUL.
  </Card>
  <Card title="Agent builder" icon="robot" href="#usage-as-mcp">
    You build agents in **Agent Creator** and attach the Outlook MCP endpoint as a tool.
  </Card>
  <Card title="Microsoft Entra admin" icon="shield-halved" href="#prerequisites">
    You register the Azure application, grant Graph permissions, add the redirect URI, and apply mailbox access policies.
  </Card>

Workspace builders continue in [Usage as App](#usage-as-app) for the instruction catalog and the DSUL examples. Microsoft Entra admins read [Restrict application mode to one mailbox](#restrict-application-mode-to-one-mailbox) before granting application permissions.

<Note>
  This legacy connector predates the App + MCP tenant-context model, so the three shared connector flows do not apply to it: there is no configuration app to enter credentials in, no central OAuth client, and no authorized-agents allowlist. Everything you need is on this page. The current [Outlook](/apps-store/marketplace/connectors/outlook) connector does follow those flows.
</Note>

## How the connector is built

Two workspaces cooperate. Knowing which one holds which setting saves most of the configuration guesswork.

| Workspace | Slug | Responsibility |
|---|---|---|
| Outlook App | `outlook-app` | Business logic: authentication resolution, Graph calls, data shaping, scope gating. Published as the **Outlook App** app and installed into consuming workspaces. |
| Outlook MCP | `outlook-mcp` | Protocol wrapper: the JSON-RPC MCP endpoint, the tool catalog, the delegated OAuth flow (authorize, callback, refresh, disconnect) and the `connect-outlook` page. It imports **Outlook App** and delegates every tool call to it. |

Outlook App itself imports the shared **Microsoft Graph Auth** app, which performs the Azure client-credentials token exchange, builds Graph base URLs, and maps Graph HTTP errors to messages.

## Choose an authentication mode

The connector supports two operating models. Decide before you configure anything, because they differ in runtime identity, in what an administrator must approve, and in which mailboxes are reachable.

<CardGroup cols={2}>
  <Card title="Application mode (client credentials)" icon="building">
    One Azure application acts for the whole workspace. Its runtime identity is the application itself, not a person. It can reach any mailbox in the tenant unless you restrict it. Best for back-office automations, scheduled jobs and shared service mailboxes.
  </Card>
  <Card title="Delegated mode (per-user OAuth)" icon="user-check">
    Each end user signs in to Microsoft once. The runtime identity is that user, and Graph enforces exactly what the user is allowed to see. Best for agents that act on behalf of the signed-in person.
  </Card>
</CardGroup>

| Aspect | Application mode | Delegated mode |
|---|---|---|
| Graph permission type | Application | Delegated |
| Runtime identity seen by Microsoft | The Azure application (service principal) | The signed-in end user |
| Admin consent | Required | Required only if the tenant blocks user consent |
| Mailbox reach | Every mailbox in the tenant, unless an application access policy restricts it | The connected user's own mailbox only |
| Who signs in | Nobody, the token is machine-to-machine | Each user, once, then silent refresh |
| `userId` argument | Selects the target mailbox, falls back to `defaultUserId` | Ignored, calls always target `/me` |
| Graph URL used | `https://graph.microsoft.com/v1.0/users/{userId}` | `https://graph.microsoft.com/v1.0/me` |
| Token acquisition | Client credentials, cached as a platform secret with a 300 second safety margin | Authorization code with PKCE (S256), refresh token stored for 90 days |
| Audit attribution | All actions attributed to the application | Actions attributed to the individual user |
| Calendar operations | Supported (Builder surface) | Not covered by the delegated scope string requested at connect time |

<Warning>
  Application mode is a **shared credential**. Every caller that can reach the connector acts with the same Azure application, and Microsoft's audit logs cannot tell one Prisme.ai user from another. Application Graph permissions such as `Mail.ReadWrite` grant access to **all** mailboxes in the tenant by default. Restrict the blast radius with an application access policy, as described in [Restrict application mode to one mailbox](#restrict-application-mode-to-one-mailbox), and keep the workspace `editor` role limited to the people allowed to change the Azure secrets.
</Warning>

## Prerequisites

<Tabs>
  <Tab title="Application mode">
    - A **Microsoft 365** tenant with Exchange Online, and an application registered in [Microsoft Entra ID](https://entra.microsoft.com) under **App registrations**.
    - A **client secret** created on that registration under **Certificates & secrets**. Note its value at creation time, it is shown once.
    - The **Directory (tenant) ID** and the **Application (client) ID** of the registration.
    - Microsoft Graph **application** permissions, granted for the operations you intend to use:

      | Graph permission | Unlocks |
      |---|---|
      | `Mail.Read` | Folder, message, search and attachment reads |
      | `Mail.ReadWrite` | The reads above, plus drafts, updates, move, copy and soft delete |
      | `Mail.Send` | `sendMail`, `sendDraft`, `replyMessage`, `replyAllMessage`, `forwardMessage` |
      | `MailboxSettings.Read` | `getMailboxSettings` |
      | `Calendars.Read` | Calendar and event reads (Builder surface) |
      | `Calendars.ReadWrite` | Calendar reads, plus create, update, delete and meeting responses |

    - **Admin consent** granted for those permissions by a Global Administrator or Privileged Role Administrator.
    - The email address or user object ID of the mailbox the connector should target.

    <Note>
      Grant only what you use. `Mail.Read` plus `MailboxSettings.Read` is enough for a read-only installation. `Mail.ReadWrite` already covers every read, so you do not need `Mail.Read` alongside it.
    </Note>

    <Note>
      Optional: to let the `listGrantedPermissions` instruction report what Microsoft actually granted, also grant `Application.Read.All` or `Directory.Read.All` with admin consent. Without one of them the instruction returns `Could not read the configured Azure app service principal. Grant Application.Read.All or Directory.Read.All application permission with admin consent, then retry.`, or reports permissions as `unknown`.
    </Note>
  </Tab>

  <Tab title="Delegated mode">
    - The same Microsoft 365 tenant and Entra application registration, with a **client secret**. The delegated flow sends `client_secret` during the token exchange, so the registration must be a confidential client and the redirect URI must be registered under the **Web** platform.
    - A **redirect URI** added to the registration, pointing at the `oauthCallback` webhook of the workspace that hosts **Outlook MCP**:

      ```text
      <api-url>/workspaces/<workspace-id>/webhooks/oauthCallback
      ```

      Replace `<api-url>` with your environment's platform API URL, for example `https://api.studio.prisme.ai/v2` on production, and `<workspace-id>` with the identifier of the workspace hosting Outlook MCP.

    - Microsoft Graph **delegated** permissions matching the scope string the connect flow requests:

      ```text
      openid profile email offline_access Mail.Read Mail.Send Mail.ReadWrite MailboxSettings.Read User.Read
      ```

    - Either the tenant allows end users to consent to those delegated permissions, or an administrator grants consent once for the whole tenant.
    - Every end user needs an Exchange Online licence on their own account.

    <Note>
      The same application registration can serve both modes. Only the **permission type** differs: application permissions for application mode, delegated permissions for delegated mode.
    </Note>

    <Warning>
      The delegated scope string requested at connect time does not include `Calendars.Read` or `Calendars.ReadWrite`. Calendar instructions therefore work in application mode only, unless a maintainer changes the scope string in the Outlook MCP workspace configuration and every user reconnects.
    </Warning>
  </Tab>
</Tabs>

## Configure the connector

Perform these steps as a workspace builder with the `editor` role on the workspace.

<Steps>
  <Step title="Install Outlook App">
    In your workspace, open **Apps**, search for **Outlook App**, and install it. The instance is named `Outlook App` by default; that name is the DSUL prefix you call later, for example `Outlook App.listMessages`.
  </Step>
  <Step title="Fill in the Outlook App configuration">
    Open the app instance configuration and set the fields you need:

    | Field | Key | Purpose |
    |---|---|---|
    | **Azure Client ID** | `clientId` | Application (client) ID of the Entra registration. |
    | **Azure Client Secret** | `clientSecret` | Client secret value. Stored as a password field. |
    | **Azure Tenant ID** | `tenant` | Directory (tenant) ID. |
    | **Default User ID** | `defaultUserId` | Mailbox targeted when a call passes no `userId`. Email address or user object ID. Application mode only. |
    | **OAuth Connect URL** | `oauthConnectUrl` | Page URL returned to users who must connect their Microsoft account. Used as a fallback when the caller sends no connect URL header. |
    | **Enabled Microsoft Graph scopes** | `enabledScopes` | Allowlist of Graph scopes. Any instruction whose scope is not enabled is refused before Microsoft is called. |

    The stock configuration binds `clientId`, `clientSecret`, `tenant` and `defaultUserId` to the workspace secrets `azureClientId`, `azureClientSecret`, `azureTenant` and `defaultUserId`, so store the real values in **Secrets** rather than typing them into the configuration form.
  </Step>
  <Step title="Restrict the connector with enabledScopes">
    `enabledScopes` accepts any of `Mail.Read`, `Mail.ReadWrite`, `Mail.Send`, `MailboxSettings.Read`, `Calendars.Read` and `Calendars.ReadWrite`. Leave it empty to enable all six.

    Every instruction checks this list first. A refused call returns `error: true`, `scopeDenied: true` and a message naming the missing scope, and the workspace emits an `outlook.scope.denied` event carrying the tool name, the required scopes and the enabled scopes. No Graph call is made.

    A second app instance with a narrower list is a supported way to expose a read-only surface next to a full one. For example, install **Outlook App** a second time under the name `OutlookNoSend` with `enabledScopes` set to `Mail.Read`, `Mail.ReadWrite` and `MailboxSettings.Read`: `OutlookNoSend.sendMail` is then refused while `OutlookNoSend.listMessages` keeps working.

    Select **Save**. The change applies to the next call; no republish is required.
  </Step>
  <Step title="Configure Outlook MCP, for the MCP surface only">
    If agents will call the connector as tools, the workspace hosting **Outlook MCP** needs its own configuration under **Outlook Configuration**:

    | Field | Key | Purpose |
    |---|---|---|
    | **Azure Client ID** | `outlook.clientId` | Application (client) ID. |
    | **Azure Client Secret** | `outlook.clientSecret` | Client secret value. |
    | **Azure Tenant ID** | `outlook.tenant` | Directory (tenant) ID. |
    | **Default User ID** | `outlook.defaultUserId` | Default target mailbox for application mode. |
    | **MCP API Key** | `outlook.mcpApiKey` | Key that MCP clients must present on `tools/call`. |

    These bind to the workspace secrets `azureClientId`, `azureClientSecret`, `azureTenant`, `defaultUserId` and `mcpApiKey`. The delegated OAuth client (`oauth.clientId`, `oauth.clientSecret`, `oauth.tenant`) reuses the same three Azure secrets, and the requested scope string is the one listed under [Delegated mode](#delegated-mode) in the prerequisites.
  </Step>
</Steps>

## Connect a Microsoft account in delegated mode

End users connect once from the `connect-outlook` page hosted by the Outlook MCP workspace. The page is reachable at `<pages-url>/connect-outlook`, where `<pages-url>` is the pages URL of that workspace.

<Steps>
  <Step title="Open the connect page">
    Sign in to Prisme.ai first. The page requires an authenticated session; without one the OAuth webhook answers HTTP `401` with `Authentication required. Please log in to Prisme.ai first.`

    If the delegated client is not configured, the page shows `OAuth is not configured. Contact the workspace administrator.` instead of a button.
  </Step>
  <Step title="Select Connect with Microsoft">
    When the page loads, it generates a PKCE code verifier and challenge (S256) and a CSRF `state`, stores both in the user scope, and builds the Microsoft authorization URL. The **Connect with Microsoft** button links straight to `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize`.
  </Step>
  <Step title="Sign in and consent">
    Sign in with your Microsoft account and approve the requested permissions. Microsoft redirects back to the `oauthCallback` webhook of the Outlook MCP workspace.
  </Step>
  <Step title="Let the callback store the tokens">
    The callback validates `state`, exchanges the code with the PKCE verifier at `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token`, and stores:

    - `outlook_delegated_token`: the access token, as a user-scoped platform secret, with a time to live equal to `expires_in`.
    - `outlook_refresh_token`: the refresh token, as a user-scoped platform secret, with a time to live of `7776000` seconds (90 days).
    - `user.outlook.oauth`: metadata only, holding `expiresAt`, `tokenType`, `scope` and `authMethod: delegated`.

    The callback also deletes any previously stored client credentials for that user, so a person is connected through exactly one method at a time. It then emits `outlook.oauth.connected` and returns you to the connect page.
  </Step>
  <Step title="Verify the connection">
    The connect page shows `Successfully connected — you can now use Outlook with your personal permissions.` and then `Connected — delegated access is active.` on subsequent visits, alongside a **Disconnect** button. This is the observable success state to check before reporting a problem elsewhere.
  </Step>
</Steps>

When the access token nears expiry, the connector exchanges the stored refresh token for a new one without user interaction, and stores a rotated refresh token if Microsoft returns one. Tokens are held as platform secrets and never written into user metadata.

<Note>
  Message subjects, body content, body previews and attachment bytes are registered as interaction secrets before any event is emitted, so platform events show redacted values and keep only identifiers visible.
</Note>

    ## Usage as App

    Call the installed app instance from DSUL using its instance name as prefix. Every instruction accepts an optional `userId` (application mode only) and returns a metadata envelope containing `operation`, `structuredData` and display hints.

    ### Mail instructions

    | Instruction | What it does | Required arguments | Graph scope |
    |---|---|---|---|
    | `listMailFolders` | Lists mail folders with total and unread counts. `includeHiddenFolders` adds hidden folders, which are excluded by default. | none | `Mail.Read` or `Mail.ReadWrite` |
    | `getMailFolder` | Reads one folder by ID or well-known name. | `folderId` | `Mail.Read` or `Mail.ReadWrite` |
    | `listMessages` | Lists message summaries with `top`, `skip`, `filter`, `orderBy`, `search` and `select`. Defaults to the `inbox` folder. | none | `Mail.Read` or `Mail.ReadWrite` |

    | `listAttachments` | Lists attachment metadata without content bytes. | `messageId` | `Mail.Read` or `Mail.ReadWrite` |

    | `getMailboxSettings` | Returns time zone, language, automatic replies and working hours. | none | `MailboxSettings.Read` |
    | `sendMail` | Sends a message. `saveToSentItems` defaults to `true`. | `message` with `subject`, `body` and `toRecipients` | `Mail.Send` |
    | `sendDraft` | Sends an existing draft, which moves to Sent Items. | `messageId` | `Mail.Send` |
    | `replyMessage` | Replies to the sender, with `comment` or a full `message` override. | `messageId` | `Mail.Send` |
    | `replyAllMessage` | Replies to every original recipient. | `messageId` | `Mail.Send` |
    | `forwardMessage` | Forwards a message, with an optional `comment`. | `messageId`, `toRecipients` | `Mail.Send` |

    | `updateMessage` | Updates `isRead`, `importance`, `categories` and `inferenceClassification` on any message, and body or recipients on drafts. | `messageId` | `Mail.ReadWrite` |
    | `deleteMessage` | Soft-deletes, moving the message to Deleted Items. | `messageId` | `Mail.ReadWrite` |
    | `moveMessage` | Moves a message. The message gets a new ID at the destination. | `messageId`, `destinationId` | `Mail.ReadWrite` |
    | `copyMessage` | Copies a message, leaving the original in place. | `messageId`, `destinationId` | `Mail.ReadWrite` |

    | Instruction | What it does |
    |---|---|

    ### DSUL examples

    List the ten most recent unread messages in the inbox:

    ```yaml
    - Outlook App.listMessages:
        userId: user@example.com   # application mode only, ignored in delegated mode
        folderId: inbox
        top: 10
        filter: "isRead eq false"
        output: messages
    ```

    Send an email. Note that recipients, subject and body live inside the `message` object:

    ```yaml
    - Outlook App.sendMail:
        userId: user@example.com
        message:
          subject: Meeting follow-up
          body:
            contentType: HTML
            content: "<p>Thank you for the meeting today.</p>"
          toRecipients:
            - emailAddress:
                address: recipient@example.com
        saveToSentItems: true
        output: result
    ```

    Search messages with KQL:

    ```yaml
    - Outlook App.searchMessages:
        userId: user@example.com
        query: "from:john subject:project"
        top: 20
        output: results
    ```

    Reply with a short comment:

    ```yaml
    - Outlook App.replyMessage:
        userId: user@example.com
        messageId: '{{messageId}}'
        comment: "Thanks for the update."
        output: result
    ```

    Read this week's agenda, occurrences expanded:

    ```yaml
    - Outlook App.getCalendarView:
        userId: user@example.com
        startDateTime: "2026-06-01T00:00:00Z"
        endDateTime: "2026-06-08T00:00:00Z"
        timeZone: Europe/Paris
        top: 50
        output: agenda
    ```

    ## Usage as MCP

    The Outlook MCP workspace exposes a JSON-RPC 2.0 endpoint. `initialize`, `notifications/initialized` and `tools/list` answer without a key; `tools/call` requires the configured API key.

    ### Endpoint

    ```text
    <api-url>/workspaces/<workspace-id>/webhooks/mcp
    ```

    Replace `<api-url>` with your environment's platform API URL, for example `https://api.studio.prisme.ai/v2` on production, and `<workspace-id>` with the identifier of the workspace hosting Outlook MCP.

    ### Attach the endpoint to an agent

    <Steps>
      <Step title="Open the tools configuration">
        In your Knowledges project, go to **Advanced > Tools**, select **Add**, then the **MCP** tab.
      </Step>
      <Step title="Paste the endpoint URL">
        Enter the endpoint URL shown above.
      </Step>
      <Step title="Add the credential headers">
        Fill the **Headers** field with the header set matching your chosen mode.

        Application mode, where the connector performs a client-credentials exchange and targets the mailbox named by `userId` or by the workspace default:

        ```json
        {
          "mcp-api-key": "<your-mcp-api-key>",
          "azure-client-id": "<your-client-id>",
          "azure-client-secret": "<your-client-secret>",
          "azure-tenant": "<your-tenant-id>"
        }
        ```

        Delegated mode, where the connector uses the calling user's stored OAuth tokens:

        ```json
        {
          "mcp-api-key": "<your-mcp-api-key>",
          "auth-mode": "oauth"
        }
        ```

        The API key value must match the **MCP API Key** configured on the Outlook MCP workspace.
      </Step>
      <Step title="Verify the tool list">
        Send a `tools/list` request, or open the tool picker, and confirm the 18 mail tools listed below appear. Then run `listMailFolders` as a safe read-only check before enabling any write tool.
      </Step>
    </Steps>

    <Warning>
      The `auth-mode` header set to `oauth` **forces** delegated mode and disables every fallback. If the calling user has no stored delegated token, the call fails immediately with `OAuth authentication required. Please visit the following URL to connect your Microsoft account:` followed by the connect URL. It never falls back to client credentials.
    </Warning>

    ### Credential resolution order

    Outlook App resolves credentials in this order:

    1. The `auth-mode` header set to `oauth`, which requires a stored delegated token for the calling user and has no fallback.
    2. An `authorization` header carrying a `Bearer` Microsoft Graph access token, used as-is.
    3. The `azure-client-id`, `azure-client-secret` and `azure-tenant` headers, exchanged for an application token.
    4. Stored delegated OAuth tokens for the calling user, refreshed automatically when expired.
    5. Per-user credentials previously stored by `configureOutlook`.
    6. The workspace configuration credentials, backed by the `azureClientId`, `azureClientSecret` and `azureTenant` secrets.

    Steps 3, 5 and 6 all end in a client-credentials exchange whose result is cached as a user-scoped platform secret named `outlook_cc_token`, with a 300 second safety margin subtracted from the token lifetime.

    ### Mailbox targeting

    - **Application mode**: the `userId` tool argument selects the mailbox, falling back to the credentials stored by `configureOutlook`, then to `defaultUserId`. If none resolves, the call fails with `userId is required for mailbox operations. Provide userId in arguments, call configureOutlook, or set defaultUserId in config.` Accepted formats are a user principal name such as `user@example.com` or a user object ID.
    - **Delegated mode**: `userId` is ignored and every call targets `/me`, the mailbox of the connected user.

    ### Available tools

    Every tool accepts the arguments of the matching Builder instruction, plus `outputFormat`. Calendar operations are not exposed here.

    | Tool | Arguments beyond `userId` and `outputFormat` |
    |---|---|
    | `listMailFolders` | `includeHiddenFolders` |
    | `getMailFolder` | `folderId` |
    | `listMessages` | `folderId`, `top`, `skip`, `filter`, `orderBy`, `search`, `select` |
    | `getMessage` | `messageId`, `includeHeaders`, `bodyType` |
    | `searchMessages` | `query`, `folderId`, `top`, `skip`, `orderBy` |
    | `listAttachments` | `messageId` |
    | `getAttachment` | `messageId`, `attachmentId` |
    | `getMailboxSettings` | none |
    | `sendMail` | `message`, `saveToSentItems` |
    | `sendDraft` | `messageId` |
    | `replyMessage` | `messageId`, `comment`, `message` |
    | `replyAllMessage` | `messageId`, `comment`, `message` |
    | `forwardMessage` | `messageId`, `toRecipients`, `comment` |
    | `createDraft` | `subject`, `body`, `toRecipients`, `ccRecipients`, `bccRecipients`, `importance` |
    | `updateMessage` | `messageId`, `isRead`, `importance`, `categories`, `inferenceClassification`, `subject`, `body`, `toRecipients`, `ccRecipients`, `bccRecipients` |
    | `deleteMessage` | `messageId` |
    | `moveMessage` | `messageId`, `destinationId` |
    | `copyMessage` | `messageId`, `destinationId` |

    A call to any other tool name returns `Tool not found: <name>`.

    ### JSON-RPC examples

    List unread inbox messages:

    ```json
    {
      "name": "listMessages",
      "arguments": {
        "userId": "user@example.com",
        "folderId": "inbox",
        "top": 10,
    ```

    Send an email:

## Verify the setup

Run these checks in order. Each one has an observable result, so a failure tells you which layer to fix.

| Check | How | Expected result |
|---|---|---|
| Scope gate | Call `getOAuthScopes` from Builder | Returns the effective scope string and the enabled scope list you configured |
| Azure grant, application mode | Call `listGrantedPermissions` from Builder | Lists the application permissions granted on the registration, without `unknown` entries |
| Delegated connection | Open `<pages-url>/connect-outlook` as an end user | The page shows `Connected — delegated access is active.` and a **Disconnect** button |
| Read path | Call `listMailFolders`, or the equivalent MCP tool | Returns folders with total and unread counts for the intended mailbox |
| Mailbox targeting | Call `getMailboxSettings` | Returns the time zone and language of the mailbox you expect, not of another user |
| Negative access | In application mode, call `listMailFolders` with a `userId` outside the allowed group | Fails with `Access denied. Check permissions.` once an application access policy is in place |
| Write path | Call `createDraft`, check the draft in Outlook, then `deleteMessage` | The draft appears in Drafts, then moves to Deleted Items |

## Restrict application mode to one mailbox

This section applies to application mode only. Delegated mode is already limited to the connected user's own mailbox and needs no policy.

Application permissions reach every mailbox in the tenant. To scope the Entra application to a single mailbox, apply an application access policy in Exchange Online.

```powershell
# 1. Connect to Exchange Online
Connect-ExchangeOnline

# 2. Create a mail-enabled security group holding only the target mailbox
New-DistributionGroup -Name "OutlookMCP-Allowed" -Type Security -Members user@example.com

# 3. Restrict the Entra application to that group's mailboxes
New-ApplicationAccessPolicy -AppId "<your-azure-client-id>" `
  -PolicyScopeGroupId "OutlookMCP-Allowed" `
  -AccessRight RestrictAccess `
  -Description "Restrict Outlook connector to a single mailbox"

# 4. Verify
Test-ApplicationAccessPolicy -AppId "<your-azure-client-id>" -Identity user@example.com
# Expected: Granted
```

<Warning>
  These commands are general guidance and policy changes take time to propagate across Exchange Online. Follow [Microsoft's mailbox access limitation guide](https://learn.microsoft.com/en-us/graph/auth-limit-mailbox-access) for the authoritative syntax and propagation behaviour.
</Warning>

## Troubleshoot

### Credentials not configured

```text
Credentials not configured. Options: 1. Pass Authorization Bearer token header 2. Pass Azure-Client-Id, Azure-Client-Secret, Azure-Tenant headers 3. Configure app-level credentials
```

No credential source resolved. The Microsoft Entra admin or the workspace builder fixes this. Set `azureClientId`, `azureClientSecret` and `azureTenant` in the workspace secrets, or send the three Azure headers on the request, or call `configureOutlook` once for the calling user. Verify with `listMailFolders`.

### OAuth authentication required

```text
OAuth authentication required. Please visit the following URL to connect your Microsoft account:
```

The request forced delegated mode but the calling user has no stored delegated token. The end user fixes this by opening the connect URL returned alongside the message and selecting **Connect with Microsoft**. Verify that the connect page shows `Connected — delegated access is active.`

### OAuth session expired, please re-authorize

```text
OAuth session expired
```

The refresh exchange failed, usually because the refresh token passed its 90 day lifetime or was revoked in Entra. The end user reconnects from the connect page. If the message instead reads `OAuth configuration is incomplete (tenant/clientId/clientSecret unresolved). An administrator must fix the workspace secrets.`, a workspace administrator must repair the `azureTenant`, `azureClientId` and `azureClientSecret` secrets, which resolved empty.

### Token exchange failed, or refresh failed

```text
Token exchange failed: <error_description>
Refresh failed: <error> - <error_description>
```

Microsoft rejected the authorization code or the refresh token, and the connector forwards its description verbatim. The Microsoft Entra admin reads the `AADSTS` code in the description against [Microsoft's sign-in error code reference](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes). Expired client secrets, missing user consent and a tenant identifier that does not match the registration all surface here. After fixing the registration, the end user reconnects.

### Authentication failed or token expired

```text
Authentication failed or token expired.
```

Microsoft Graph answered HTTP `401`. In application mode, verify the client ID, secret and tenant, and confirm the secret has not expired. In delegated mode, reconnect from the connect page.

### Access denied, check permissions

```text
Access denied. Check permissions.
```

Microsoft Graph answered HTTP `403`. Either admin consent is missing on the required Graph permission, or an application access policy excludes the target mailbox. The Microsoft Entra admin grants consent or adds the mailbox to the allowed security group, then waits for propagation. Verify with `getMailboxSettings` on that mailbox.

### The tool is disabled, it requires the Microsoft Graph scope

```text
The "sendMail" tool is disabled: it requires the Microsoft Graph scope Mail.Send, but the Outlook app configuration only enables: Mail.Read, Mail.ReadWrite, MailboxSettings.Read. An administrator must add the required scope to the "Enabled Microsoft Graph scopes" (enabledScopes) app configuration, then users must reconnect their Microsoft account.
```

This is the `enabledScopes` allowlist refusing the call before Microsoft is contacted, and the workspace emits `outlook.scope.denied`. The workspace builder adds the scope to **Enabled Microsoft Graph scopes** and saves, or routes the call to a fuller app instance. In delegated mode, users then reconnect so consent covers the added scope.

### userId is required for mailbox operations

```text
userId is required for mailbox operations. Provide userId in arguments, call configureOutlook, or set defaultUserId in config.
```

Application mode resolved no target mailbox. The workspace builder sets **Default User ID**, or the caller passes `userId`. This message never appears in delegated mode, which always targets `/me`.

### Unexpected response from Microsoft Graph

```text
Unexpected response from Microsoft Graph: the message list is missing. This indicates an authentication or connectivity problem, not an empty folder.
```

Graph returned no message array. Treat it as an authentication or connectivity failure rather than an empty mailbox, and re-run the credential checks in [Verify the setup](#verify-the-setup).

### Rate limited

```text
Rate limited. Please wait and retry.
Rate limited. Retry after <n> seconds.
```

Microsoft Graph throttled the tenant with HTTP `429`. Retry after the delay Microsoft reports, and reduce `top` or the call rate in scheduled automations. The connector adds no throttling of its own.

### Delegated authentication is not yet implemented

```text
Delegated authentication is not yet implemented. Use auth mode 'application' or omit the header.
```

A request set the `azure-auth-mode` header to `delegated`. That header belongs to the shared Microsoft Graph Auth layer and does not select this connector's delegated OAuth mode. Remove it and set the `auth-mode` header to `oauth` instead.

### MCP API key errors

```text
API key not configured. Generate one from the API Key page.
Missing mcp-api-key header. Add header "mcp-api-key" with a valid API key.
Invalid mcp-api-key. Check that the API key value is correct.
```

These JSON-RPC errors (code `-32001`) come from the MCP router on `tools/call`. The workspace builder sets the **MCP API Key** on the Outlook MCP workspace, and the agent builder copies the same value into the MCP headers. `initialize` and `tools/list` keep answering without a key, so a working tool list does not prove the key is right.

## Disconnect, rotate and remove

- **A user disconnects**: on the connect page, select **Disconnect**. This deletes the `outlook_delegated_token`, `outlook_refresh_token`, `outlook_cc_token` and `outlook_client_secret` user secrets, clears the `user.outlook.oauth` and `user.outlook.credentials` metadata, and emits `outlook.oauth.disconnected`. The page then shows the connect button again. The same action is available by emitting the `disconnectOAuth` event.
- **An administrator revokes a user**: revoke the user's sessions or refresh tokens in Microsoft Entra ID. The next connector call fails with a re-authorization message pointing at the connect page.
- **Rotate the client secret**: create the new secret in Entra, update the `azureClientSecret` secret in every workspace that holds it, and save. Application mode picks up the new secret once the cached `outlook_cc_token` expires. Delegated connections keep working until their refresh token is used, then need the updated secret to be in place.
- **Offboard a user**: have them disconnect, or revoke their Entra sessions, then remove their access to the workspace. Delegated tokens are user-scoped, so they stop resolving once the account is disabled.
- **Reduce the surface without uninstalling**: empty out the write scopes in **Enabled Microsoft Graph scopes** and save. Every write instruction is refused immediately, with no Graph call.
- **Remove the connector**: uninstall the **Outlook App** instance from the workspace, delete the `azureClientId`, `azureClientSecret`, `azureTenant`, `defaultUserId` and `mcpApiKey` secrets, remove the MCP endpoint from any agent that references it, and delete the redirect URI and the client secret from the Entra registration.

## Migrate to the Outlook connector

Plan the move to the [Outlook](/apps-store/marketplace/connectors/outlook) connector for any installation that is still growing. The differences that shape the migration:

| Topic | Outlook (legacy) | Outlook |
|---|---|---|
| Tool shape | 18 flat mail tools | Six entity tools driven by an `action` argument, covering mail, calendar and contacts |
| Credentials at call time | Azure client ID, secret and tenant passed as request headers, or a forced `auth-mode` header | Tenant app-instance context, no credential headers |
| OAuth client | One client per installation, registered by each customer | Central client registered once by the platform maintainer, or a tenant client |
| Calendar | Builder surface only | Available on both surfaces |
| Agent authorization | None beyond the API key | Per-agent allowlist |

Migration outline: install the Outlook connector in the target workspace, connect the accounts through its own flow, rewrite DSUL calls and agent instructions against the entity tools, verify with read-only operations, then remove the legacy installation as described in [Disconnect, rotate and remove](#disconnect%2C-rotate-and-remove).
