The Jira app provides read/write access to [Atlassian Jira](https://www.atlassian.com/software/jira) through the official platform REST API and Agile 1.0 (Jira Software). It supports both **Jira Cloud** (platform REST API v3) and **Jira Data Center 10.3** (platform REST API v2); the `deployment` setting selects the API routes and is chosen independently from the authentication method. It can be consumed two ways: as a remote MCP server that **Agent Creator** agents call as tools, or as a Builder app whose instructions you call directly from DSUL. The MCP surface groups every operation into **seven entity tools** (`issues`, `search`, `projects`, `users`, `metadata`, `agile`, `attachments`), each driven by an `action` argument, and runs in the **tenant app-instance context** (it resolves the installing workspace's own credentials and gates which agents may call it).

Pick the authentication mode from the outcome you need, not from what is easiest to set up:

| Mode | Provider identity | Use it when |
|------|-------------------|-------------|
| `oauthCentral` | The invoking end user | Recommended. A platform maintainer registers one Atlassian 3LO app for the whole platform; each workspace installs the connector and each user signs in with their own Atlassian account. Nothing to register per workspace. |
| `oauth` | The invoking end user | You must keep the Atlassian OAuth app under your own tenant's control. You paste your own Client ID and Secret in the configuration app; users sign in against your client (authorization code with PKCE, 3LO). |
| `apiToken` | One shared Atlassian account | Unattended automations with no interactive sign-in. HTTP Basic with an Atlassian account email plus an API token. Every call is attributed to that single account. |
| `accessToken` | Whoever owns the token | A caller-managed token is already available and is used as-is with no exchange. On Data Center this is where a Personal Access Token goes (sent as `Bearer`). |
| `oauth1` | The invoking end user | Data Center only, where OAuth2 is unavailable. A Jira Application Link signs each request with a shared consumer key and RSA private key, plus an access token each user obtains from that Application Link. |

<Warning>
  `apiToken` and `accessToken` are **shared service identities**: every agent and every user of the workspace acts as that one Atlassian account, Jira audit logs attribute all writes to it, and its project permissions become the blast radius of the whole connector. Prefer `oauthCentral` or `oauth` whenever a human triggers the action. Selecting `oauth1` on a Cloud deployment fails with `oauth1 is supported only with deployment=dataCenter.`
</Warning>

## Prerequisites (Atlassian side)

- An **Atlassian Jira Cloud** site (`https://yoursite.atlassian.net`) or a **Jira Data Center 10.3** base URL (an absolute HTTP or HTTPS URL, optionally with a context path such as `/jira`, and without credentials, query string or fragment), plus an account with permission on the projects you intend to use.
- For the OAuth2 modes: an **OAuth 2.0 (3LO) app** registered in the [Atlassian Developer Console](https://developer.atlassian.com/console/myapps/), with the **Jira platform REST API** added and the scopes below granted.
- For the `apiToken` mode: an **Atlassian account email** plus an **API token** generated at [Atlassian API Tokens](https://id.atlassian.com/manage-profile/security/api-tokens). On Cloud you also supply the **site** (`yoursite.atlassian.net`); on Data Center the configured base URL is used instead.
- For the `oauth1` mode (Data Center only): a **Jira Application Link** configured with a consumer key and an RSA public key, so each user can issue themselves an access token.
- The base URL is resolved automatically: the OAuth2 and `accessToken` modes call `https://api.atlassian.com/ex/jira/{cloudId}` on Cloud (the `cloudId` is discovered from the granted site through `GET https://api.atlassian.com/oauth/token/accessible-resources`); the `apiToken` mode calls `https://{site}.atlassian.net` directly. On Data Center every mode calls the configured base URL.

### OAuth scopes

On Cloud, the scopes requested by default are the **classic** Jira platform scopes, which cover every platform operation (issues, search, projects, users, metadata, attachments):

```text
read:jira-work
write:jira-work
read:jira-user
manage:jira-project
manage:jira-configuration
offline_access
```

On a Data Center OAuth2 client the default scope list is instead:

```text
READ WRITE
```

The connector requests exactly the scopes stored in the **Scopes** field of the configuration app, so that field is the effective grant: it can narrow what the Atlassian app exposes, never widen it.

<Warning>
  **Agile boards, sprints and backlog need a different, fully-granular OAuth app; they do not work with the classic scopes above.** The Jira Agile 1.0 API (the `agile` tool) only accepts the **granular** Jira Software scopes (`read:board-scope:jira-software`, `write:board-scope:jira-software`, `read:sprint:jira-software`, `write:sprint:jira-software`), and Atlassian rejects a token that also carries a classic scope. Enabling Agile therefore requires migrating the *entire* Atlassian app to granular scopes (roughly 30 to 40 scopes covering all platform operations too), which is incompatible with the simple classic setup. With the default classic scopes, the seven `agile` operations are not usable. This is an Atlassian platform limitation, not a connector limitation; see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup) for the trade-off.
</Warning>

### Jira Data Center differences

When `deployment` is `dataCenter`, the connector rewrites every `/rest/api/3/` route to `/rest/api/2/`, applies the route overrides below, and adapts request bodies. Agile operations stay on `/rest/agile/1.0` for both deployments.

| Operation | Cloud route | Data Center route and arguments |
|-----------|-------------|----------------------------------|
| `searchJql` | `POST /rest/api/3/search/jql` | `POST /rest/api/2/search`. `nextPageToken` is stripped from the body; page with `startAt` instead. |
| `listProjects` | `GET /rest/api/3/project/search` | `GET /rest/api/2/project`. Only `expand` is forwarded, so `query`, `startAt`, `maxResults` and `orderBy` are ignored. |
| `searchUsers` | `GET /rest/api/3/user/search` | `GET /rest/api/2/user/picker`. Only `query` and `maxResults` are forwarded. |
| `getUserByAccountId` | `GET /rest/api/3/user` | `GET /rest/api/2/user` with `username`, `key` or `expand`. An `accountId` argument is sent as `username`. |
| `findAssignableUsers` | `GET /rest/api/3/user/assignable/search` | `GET /rest/api/2/user/assignable/search` with `username`, `project`, `issueKey`, `startAt`, `maxResults`. A `query` argument is sent as `username`. |
| `listPriorities` | `GET /rest/api/3/priority/search` | `GET /rest/api/2/priority`. No pagination arguments. |

Body adaptations applied on Data Center:

- Atlassian Document Format (ADF) values are flattened to plain text for `createIssue` and `updateIssue` descriptions and for `addComment` bodies, because REST API v2 expects wiki-markup strings.
- `assignIssue` sends `name` instead of `accountId`.

Data Center OAuth2 uses the instance endpoints `{baseUrl}/rest/oauth2/latest/authorize` and `{baseUrl}/rest/oauth2/latest/token`, with a form-encoded token request. Cloud uses `https://auth.atlassian.com/authorize` and `https://auth.atlassian.com/oauth/token` with a JSON token request.

<Note>
  A **central** (platform-wide) client can only be an OAuth2 client, as described in [When to use a central client](/apps-store/marketplace/connectors/central-oauth#when-to-use-a-central-client). If the platform maintainer stores a Data Center OAuth1 profile as the central profile, workspaces that select `oauthCentral` cannot resolve it: the connection status reports `unsupported_central_auth_mode`. Data Center OAuth1 must be configured per workspace with the `oauth1` mode.
</Note>

  **Goal:** two one-time tasks: (1) configure the shared **central Atlassian OAuth client** so every workspace lets its users sign in with their own Atlassian account, and (2) expose Jira as a reusable **capability** in AI Governance so agent builders can pick it without pasting endpoint URLs.

  ## 1. Configure the connector

  The procedure is the standard one documented in [Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client), including the role you need on the core workspace ([Before you begin](/apps-store/marketplace/connectors/central-oauth#before-you-begin)). The Atlassian-specific values are below.

  <Steps>
    <Step title="Register the OAuth 2.0 (3LO) app at Atlassian">
      In the [Atlassian Developer Console](https://developer.atlassian.com/console/myapps/), create an app → **Authorization > OAuth 2.0 (3LO)**, and set the **Callback URL** to the `jira-next` core workspace callback:

      ```text
      <api-url>/workspaces/slug:jira-next/webhooks/oauthCallback
      ```

      (For example `https://api.studio.prisme.ai/v2/workspaces/slug:jira-next/webhooks/oauthCallback` on production; `<api-url>` is the production API URL. Copy the exact URI from the connector's configuration app, which renders it for you.) This single URI serves every workspace, and it is **not** the per-instance URI a tenant-owned client uses; see [Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls) for the difference. Then under **Permissions**, add the **Jira platform REST API** and enable the scopes listed in [OAuth scopes](#oauth-scopes). Note the **Client ID** and **Secret** from **Settings**.
    </Step>
    <Step title="Choose classic or granular scopes, and decide about Agile">
      Atlassian enforces **classic XOR granular scopes per product** in the developer console: the classic scopes (`read:jira-work`, `write:jira-work`, `read:jira-user`, `manage:jira-project`, `manage:jira-configuration`) do **not** appear in the granular list and cannot be mixed with granular Jira Software scopes on the same token.

      - For the 29 platform operations (issues, search, projects, users, metadata, attachments), keep the **classic** scope set. Simple, recommended.
      - To additionally enable the `agile` tool (boards, sprints, backlog), you must migrate the app to a **fully-granular** set (every platform scope plus `read:board-scope:jira-software`, `write:board-scope:jira-software`, `read:sprint:jira-software`, `write:sprint:jira-software`), because the Agile API rejects a token that also carries any classic scope. This is verbose and is the only way to use Agile.

      <Warning>
        The connector requests exactly the scopes set in its **Scopes** field (the central scopes entered in step 3, overridable per workspace), **not** whatever is enabled on the Atlassian app. Enabling more scopes in the Atlassian developer console has no effect until you also add them to the connector's Scopes field. Conversely the Scopes field can never grant a permission the Atlassian app does not expose.
      </Warning>
    </Step>
    <Step title="Enter the credentials through the configuration app">
      Open the central `jira-next` workspace and launch its **Configuration app** at `<studio>/apps/jira-next` (for example `https://studio.prisme.ai/apps/jira-next`), also linked as **Configuration app** on the installed instance. Switch to the maintainer view, paste the **Client ID**, **Client Secret** and the **Scopes**, then save. The app stores the profile in the core workspace secret `jiraNextCentralOAuth`; do not edit Studio's raw Secrets by hand.

      The Atlassian client secret never leaves the `jira-next` workspace: installed connectors read only the non-secret fields (mode, deployment, base URL, client ID, scopes) and every token exchange is proxied through the core `centralTokenExchange` webhook. See [How the client secret stays in the core workspace](/apps-store/marketplace/connectors/central-oauth#how-the-client-secret-stays-in-the-core-workspace) for the two endpoints involved and the role checks applied on save.

      <Note>
        **One Atlassian OAuth app can serve both Jira and Confluence.** A single Atlassian app (one Client ID/Secret) can have both the Jira platform REST API and the Confluence API enabled. Each connector requests **its own** Scopes, so Jira can stay on classic scopes while Confluence uses its required granular scopes on the very same app; point both connectors' config apps at the same Client ID/Secret and give each its own Scopes field.
      </Note>
    </Step>
    <Step title="Tell workspaces to use the central client">
      Each consuming workspace selects auth mode **`oauthCentral`** in the connector configuration app (no client id or secret to enter on their side). Hand them [Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace); their users then start the connection from that same app.
    </Step>
  </Steps>

  Verify the result with [Verify the central client](/apps-store/marketplace/connectors/central-oauth#verify-the-central-client), and handle secret rotation, scope changes and withdrawal with [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client).

  ## 2. Declare the capability in AI Governance

  Generic connectors (broad tool surfaces meant to be shared across many agents, like Jira) are best exposed as a named **capability** in AI Governance. Agent builders then enable that capability on their agents instead of pasting a raw MCP endpoint.

  Publish it with [Publish the connector to the Capabilities catalog](/apps-store/marketplace/connectors/declare-capability#publish-the-connector-to-the-capabilities-catalog), or author the entry yourself with [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance). Name the capability **Jira**, point its MCP server URL at the connector's **MCP Endpoint**, and set its **Scope** to:

  ```text
  context_id,agent_id,user_id
  ```

  The `agent_id` in the scope is what lets the connector identify and authorize the calling agent.

  **Smoke-test the result.** From an agent that has the capability, in a workspace configured for `oauthCentral`, call the `users` tool with `action: myself`. The first call for an unconnected user returns `Jira is not connected for this user.`; connect once from the configuration app, then call it again and confirm it returns your own `accountId` and `displayName`. Subsequent calls reuse the stored token and refresh it automatically.

  <Warning>
    Declaring the capability makes the connector **available**; it does not by itself authorize a specific agent, as explained in [Availability is not authorization](/apps-store/marketplace/connectors/declare-capability#availability-is-not-authorization). This connector follows the **tenant-context model**: which agents may actually call it is gated per-workspace by the **authorized-agents allowlist** in the configuration app (see [Workspace builder (DSUL)](#workspace-builder-dsul)). There is also **no OAuth auth-config JSON** to attach in Governance; connect, status and disconnect are handled by the connector's own webhooks, wired automatically on install.
  </Warning>

  <Warning>
    Publishing the **core** `jira-next` endpoint to the catalog is not the same as publishing a workspace endpoint. Once a central Atlassian client is stored, the core endpoint short-circuits the per-agent allowlist and accepts every calling agent; the per-user Atlassian sign-in becomes the only gate. Read [Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint) before publishing it.
  </Warning>
</Accordion>

    ## Agent builder

    **Goal:** let an agent you build in Agent Creator read and act on Jira through MCP tools.

    <Note>
      Before an agent can call the connector, a *Workspace builder* must have installed and configured the Jira app in a workspace (see [Workspace builder (DSUL)](#workspace-builder-dsul)), and, for the central OAuth mode, a *Platform admin* must have provisioned the shared OAuth client (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup)).
    </Note>

    This connector runs in the **tenant app-instance context**: your agent is authorized two ways at once: it is identified by the `agent_id` that Agent Creator injects through the capability *Scope*, and that agent must appear in the connector's **authorized-agents allowlist** (managed in the configuration app). The Atlassian token itself is resolved server-side from the configured auth mode, so the agent never handles a credential.

    There are two ways to wire it up. Pick based on how much isolation you need.

    ## Option A: Enable the shared capability from the catalog

    The fastest path: a *Platform admin* has already published a **Jira** capability (see [Platform admin (Governance): one-time platform setup](#platform-admin-governance-one-time-platform-setup), §2), so you just pick it from the catalog.

    <Steps>
      <Step title="Open your agent in Agent Creator">
        Open the agent you want to extend and go to its capabilities / tools.
      </Step>
      <Step title="Add the Jira capability">
        Browse the capability catalog, select **Jira**, enable it and save the agent. The MCP endpoint URL and the *Scope* (`context_id,agent_id,user_id`) are already wired by the admin; nothing to paste, and because the shared instance holds the central credentials it accepts every agent, so there is no allowlist step on your side ([Agent authorization on the core endpoint](/apps-store/marketplace/connectors/central-oauth#agent-authorization-on-the-core-endpoint)).
      </Step>
      <Step title="Connect an Atlassian account (OAuth modes)">
        The first tool call by an unconnected user returns `Jira is not connected for this user.` and points to the configuration app. Connect there once, then retry the call. The `apiToken` and `accessToken` modes need no per-user sign-in.
      </Step>
    </Steps>

    <Note>
      Convenient, but your agent runs against a **shared, platform-managed instance**: its Atlassian credentials are owned by someone else and the instance accepts every agent that is granted the capability. Prefer Option B for anything beyond quick experiments.
    </Note>

    ## Option B: Run it from your own workspace (recommended)

    For production agents, install the connector in **your own workspace** and point the agent at *that* workspace's MCP endpoint.

    <Warning>
      **Prefer this mode for security.** Because the MCP runs in *your* app-instance context, the Atlassian credentials, the per-user OAuth tokens and the authorized-agents allowlist are all **scoped to your workspace**, not shared platform-wide. You decide exactly which agents may call it and which Atlassian account or auth mode backs them, and a misconfiguration elsewhere can never expose your data. The shared catalog capability (Option A) is a broad surface many agents can reach; your own workspace is an isolated, least-privilege boundary.
    </Warning>

    <Steps>
      <Step title="Install and configure the connector in your workspace">
        Follow [Workspace builder (DSUL)](#workspace-builder-dsul): install **JiraNext** in your workspace, open its **Configuration app**, choose the auth mode and connect an Atlassian account.
      </Step>
      <Step title="Allowlist your agent">
        In that workspace's config app, open **Authorized agents**, tick your agent and save. Selecting **Install capability** on the agent's row does the allowlisting and the wiring in one action: see [Install the capability on one agent](/apps-store/marketplace/connectors/declare-capability#install-the-capability-on-one-agent).
      </Step>
      <Step title="Add the MCP capability to your agent">
        If you did not use **Install capability**, add a capability on your agent pointing at **your workspace's MCP Endpoint** URL, set its **Scope** to the value below, and save the agent.

        ```text
        context_id,agent_id,user_id
        ```

        The `agent_id` is what lets the connector identify and authorize your agent; without it, every call is rejected with `The calling agent could not be identified, so it cannot be authorized.` This *Scope* is separate from the Atlassian OAuth scopes; see [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).
      </Step>
      <Step title="Connect an Atlassian account (OAuth modes)">
        Start the connection from the configuration app, or trigger a tool call and follow the error message it returns.
      </Step>
    </Steps>

    ## Brief the agent in its system prompt

    Whichever option you pick, wiring the capability is not enough: the agent must know the MCP exists and when to use it. Copy-pasteable starter:

    ```text
    You have access to the Jira MCP server (tools: issues, search, projects, users, metadata, agile, attachments). Each tool takes an `action` argument. Use `search` (action `jql`) to find issues, `issues` (action `get`) to read one by key (e.g. PROJ-123), and `issues` create/update/delete/assign to manage them. To move an issue, call `issues` getTransitions then doTransition. Rich text (description, comment body) uses Atlassian Document Format (ADF), and users are referenced by `accountId` (resolve with the `users` tool). Before creating an issue, discover the required fields with `metadata` createmeta then createmetaFields. Confirm with the user before any create, update, delete, assign or transition.
    ```

    <Note>
      **Legacy AI Knowledge agents** (no native MCP picker): add the connector under **Advanced > Tools > MCP** and paste the **MCP Endpoint** URL. The agent still has to be allowlisted in the config app and its identity propagated so the connector can read its `agent_id`. See [Declare the capability manually in AI Governance](/apps-store/marketplace/connectors/declare-capability#declare-the-capability-manually-in-ai-governance).
    </Note>

    <Note>
      **Restricting to read-only (least privilege).** Jira tools cover both reads and writes (create, update, delete, assign, transitions, comments). The requested OAuth scopes **are** the grant, so the connector only obtains what the **Scopes** field in the configuration app asks for (see [OAuth scopes](#oauth-scopes)). To allow only read access, set a read-only scope list:

      ```text
      read:jira-work read:jira-user offline_access
      ```

      (Drop `write:jira-work`, `manage:jira-project` and `manage:jira-configuration`.) With central OAuth (`oauthCentral`) you do **not** create your own Atlassian client: keep `oauthCentral` and just enter the read-only scopes; your tenant scope overrides the platform default (the central app must expose those read scopes). Write calls are then rejected by Atlassian with `403`. Note this is set at the workspace level; a workspace editor can widen it again, and a provider-side restriction (a read-only Atlassian account or permission scheme) is the only hard guarantee. For the `apiToken`, `accessToken` and `oauth1` modes, restrict at the provider instead by backing the connection with a Jira account that has read-only project permissions.
    </Note>

    ## Available Tools

    Each tool takes an `action` argument selecting the concrete operation, plus the per-action parameters. An unknown entity, a missing `action` or an unknown `action` returns an error listing the accepted values.

    | Tool | Description |
    |------|-------------|
    | `issues` | Jira issues. Actions: `get`, `create`, `update`, `delete`, `assign`, `getTransitions`, `doTransition`, `getComments`, `addComment`, `getEditMeta`. Rich text uses ADF; users by `accountId`. |
    | `search` | Search issues with JQL (`POST /rest/api/3/search/jql`). Action: `jql`. Token-based pagination via `nextPageToken`. |
    | `projects` | Jira projects. Actions: `list`, `get`, `components`, `versions`, `statuses`. |
    | `users` | Jira users (identified by `accountId` on Cloud, `username`/`key` on Data Center). Actions: `search`, `get`, `myself`, `assignable`. |
    | `metadata` | Discover fields, types and create metadata. Actions: `fields`, `issuetypes`, `priorities`, `statuses`, `createmeta`, `createmetaFields`. |
    | `agile` | Jira Software boards, sprints and backlog (Agile 1.0). Actions: `boards`, `getBoard`, `boardIssues`, `sprints`, `getSprint`, `sprintIssues`, `backlog`. **Requires a fully-granular Jira Software OAuth setup** (see [OAuth scopes](#oauth-scopes)). |
    | `attachments` | Issue attachments. Actions: `getMeta`, `delete`, and `add` (rejected inline; upload binaries via Jira directly). |

    ## Output Formats

    Every tool accepts an `outputFormat` argument that controls the MCP response shape:

    - **`verbose`** (default): human-readable text optimized for LLM consumption
    - **`structured`**: machine-readable JSON in `structuredContent`
    - **`both`**: both the text and the structured content

    Two limits keep responses inside the agent's context window: `maxResults` is clamped to the range 1 to 100 on every paginated operation, and arrays in the response are capped at 100 items, with a truncation marker appended that tells the agent to narrow the query.

    ## Tool Details

    ### search

    ```json
    {
      "name": "search",
      "arguments": {
        "action": "jql",
        "body": {
          "jql": "project = DEV AND status = \"In Progress\" ORDER BY updated DESC",
          "maxResults": 25,
          "fields": ["summary", "status", "assignee"]
        }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | `jql`. |
    | `body` | Yes | Search request `{ jql, maxResults (at most 100), nextPageToken, fields: [..], expand }`. Always pass `fields` to limit the payload. |
    | `body.nextPageToken` | No | Cursor from a previous response to fetch the next page (the legacy `startAt` is not used on Cloud). On Data Center the cursor is stripped and `startAt` is used instead. |

    ### issues

    ```json
    {
      "name": "issues",
      "arguments": {
        "action": "create",
        "body": {
          "fields": {
            "project": { "key": "DEV" },
            "issuetype": { "name": "Task" },
            "summary": "Implement new feature",
            "description": {
              "type": "doc",
              "version": 1,
              "content": [
                { "type": "paragraph", "content": [{ "type": "text", "text": "Detailed description here." }] }
              ]
            }
          }
        }
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `get`, `create`, `update`, `delete`, `assign`, `getTransitions`, `doTransition`, `getComments`, `addComment`, `getEditMeta`. |
    | `issueIdOrKey` | For everything but create | Issue id or key, e.g. `DEV-123`. |
    | `body` | For create/update/assign/doTransition/addComment | Jira JSON body. Create/update use `{ fields }` (or `{ update }`); assign `{ accountId }`; doTransition `{ transition: { id } }`; addComment `{ body: <ADF doc> }`. On Data Center, ADF values are flattened to plain text and `accountId` is sent as `name`. |
    | `fields` | No | `fields` query param (comma-separated list, or `*all`) for `get`. |
    | `expand` | No | `expand` query param. |
    | `startAt` / `maxResults` | No | `getComments` pagination. `maxResults` is clamped to 100. |
    | `deleteSubtasks` | No | `delete` only: `"true"` to delete subtasks. |
    | `notifyUsers` | No | `update` only: `"false"` to suppress notification mail. |

    ### metadata

    ```json
    {
      "name": "metadata",
      "arguments": {
        "action": "createmetaFields",
        "projectIdOrKey": "DEV",
        "issueTypeId": "10002"
      }
    }
    ```

    | Parameter | Required | Description |
    |-----------|----------|-------------|
    | `action` | Yes | One of `fields`, `issuetypes`, `priorities`, `statuses`, `createmeta`, `createmetaFields`. |
    | `projectIdOrKey` | For createmeta/createmetaFields | Project id or key. |
    | `issueTypeId` | For createmetaFields | Issue type id (from `createmeta`). |
    | `startAt` / `maxResults` | No | `priorities` pagination on Cloud. Data Center returns the full priority list without pagination. |

    Resolve a custom field's technical id (`customfield_…`) with `metadata` `fields`, then confirm it is on the create screen for that project + issue type with `createmeta` → `createmetaFields` before passing it in `issues` create/update.

    ### agile

    ```json
    {
      "name": "agile",
      "arguments": {
        "action": "sprintIssues",
        "sprintId": "42",
        "jql": "assignee = currentUser()",
        "fields": "summary,status",
        "maxResults": 50
      }
    ```

    | Parameter | Required | Description |

    | `action` | Yes | One of `boards`, `getBoard`, `boardIssues`, `sprints`, `getSprint`, `sprintIssues`, `backlog`. |
    | `boardId` | For getBoard/boardIssues/sprints/backlog | Agile board id. |
    | `sprintId` | For getSprint/sprintIssues | Sprint id. |
    | `type` / `name` / `projectKeyOrId` | No | `boards` only: filter by board type (`scrum`, `kanban`, `simple`), name or project. |
    | `state` | No | `sprints` only: `future`, `active` or `closed`. |
    | `jql` / `fields` | No | Optional JQL filter and comma-separated field list (boardIssues, sprintIssues, backlog). |

    <Warning>

With the default **classic** scopes, every `agile` action fails with an Atlassian scope error.

    ## Workspace builder

    **Goal:** install the connector in a workspace, configure authentication and the agent allowlist, and call Jira operations from your automations.

    ## Installation

    Jira follows the standard connector installation flow: [Install the app](/apps-store/marketplace/connectors/install-in-workspace#install-the-app), then [Configure credentials in the configuration app](/apps-store/marketplace/connectors/install-in-workspace#configure-credentials-in-the-configuration-app), then [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector) and [Copy the MCP endpoint](/apps-store/marketplace/connectors/install-in-workspace#copy-the-mcp-endpoint). The Jira-specific values are:

    | | Value |
    |---|---|
    | App name in the **Apps** catalog | **JiraNext** |
    | Workspace secret holding the auth profile | `jiraNextAuth` |
    | Workspace secret holding the agent allowlist | `jiraNextAuthorizedAgents` |
    | Per-user OAuth refresh token secret | `jrnRefresh_<userId>` |
    | Capability **Scope** | `context_id,agent_id,user_id` |

    Installing the app provisions those secrets, binds them to the instance configuration, and stores both the configuration app URL and this instance's own OAuth callback URL, as described in [What installing provisions](/apps-store/marketplace/connectors/install-in-workspace#what-installing-provisions). The flow is idempotent and re-runs on every reconfiguration.

    ## Configuration

    | Field | Description |
    |-------|-------------|
    | **Configuration app** | Read-only, auto-populated on install. Open this link to configure authentication (mode + credentials), connect an Atlassian account (OAuth modes), and manage the authorized-agents allowlist. |

    The configuration app drives everything; the app instance itself has no per-field credential form. From it you pick a `deployment` (`cloud`, the default, or `dataCenter` with its base URL) and one of the auth modes below.

    | Auth mode | What you provide | Best for |
    |-----------|------------------|----------|
    | `oauthCentral` | Nothing but the **Scopes** you want to narrow to; then start the connection ([Select the central client in a workspace](/apps-store/marketplace/connectors/central-oauth#select-the-central-client-in-a-workspace)) | Workspaces on a platform where a maintainer set up the central Atlassian client. Cloud or Data Center OAuth2. |
    | `oauth` | Your own Atlassian **Client ID + Secret** and **Scopes**, registered against this instance's own callback URI, given after this table | You manage your own Atlassian OAuth app |
    | `apiToken` | Atlassian **account email** + **API token**, plus the **site** (`yoursite.atlassian.net`) on Cloud | A single shared service identity, no interactive sign-in |
    | `accessToken` | A pre-minted Atlassian **access token** (a Data Center Personal Access Token goes here) | Short-lived or caller-managed tokens |
    | `oauth1` | Data Center **base URL**, Application Link **consumer key** and **RSA private key**; each user then submits their own Application Link access token | Data Center instances without OAuth2 |

    In `oauth` mode, the redirect URI to register at Atlassian is this instance's own callback, not the core one:

    ```text
    <api-url>/workspaces/slug:<your-workspace-slug>/webhooks/<app-instance-slug>.oauthCallback
    ```

    The configuration app renders the exact value for your instance; copy it from there rather than assembling it by hand. Do not register the core `jira-next` URI here: that one belongs to the central client only, and mixing the two breaks sign-in on both sides ([Callback URLs](/apps-store/marketplace/connectors/central-oauth#callback-urls)).

    <Note>
      Credentials are provisioned into the workspace's Secrets by the install flow and resolved server-side, so no automation ever receives a raw token. The agent allowlist (**Authorized agents**) gates which Agent Creator agents may call the MCP endpoint; enabling the allow-all option stores `*` in the allowlist and disables the per-agent gate entirely, with the consequences described in [The allow-all wildcard](/apps-store/marketplace/connectors/install-in-workspace#the-allow-all-wildcard). The OAuth **Scopes** field is what the connector actually requests (see [OAuth scopes](#oauth-scopes)); set a read-only list there to restrict writes.
    </Note>

    ## Available Instructions

    Every instruction resolves credentials from the workspace configuration and returns the raw Jira REST payload, or `{ error }` with an explanatory message when authentication or the API call fails. Operations are grouped by resource; the MCP server exposes the same operations behind the seven entity tools (see [Agent builder (Agent Creator)](#agent-builder-agent-creator)).

    ### Issues

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `getIssue` | Fetch one issue by `issueIdOrKey` (e.g. `DEV-123`); narrow with `fields`, `fieldsByKeys`, `expand`, `properties`. | `{ id, key, fields: { summary, status, … } }` |
    | `createIssue` | Create an issue from `body.fields` (`{ project, issuetype, summary, … }`; ADF for rich text). | `{ id, key, self }` |
    | `updateIssue` | Edit an issue by `issueIdOrKey`; `body` = `{ fields }` or `{ update }`. `notifyUsers: "false"` suppresses mail. | Empty (HTTP 204) |
    | `deleteIssue` | Delete an issue by `issueIdOrKey`; `deleteSubtasks: "true"` to cascade. | Empty (HTTP 204) |
    | `assignIssue` | Set the assignee by `issueIdOrKey`; `body` = `{ accountId }`. | Empty (HTTP 204) |
    | `getTransitions` | List the available workflow transitions for an `issueIdOrKey`. | `{ transitions: [{ id, name, to }] }` |
    | `doTransition` | Move the issue by `issueIdOrKey`; `body` = `{ transition: { id } }`. | Empty (HTTP 204) |
    | `getComments` | List comments on an `issueIdOrKey`; page with `startAt`/`maxResults`. | `{ comments: [{ id, body, author, created }], total }` |
    | `addComment` | Add a comment to an `issueIdOrKey`; `body` = `{ body: <ADF doc> }`. | `{ id, body, author, created }` |
    | `getEditMeta` | Editable-fields metadata for an `issueIdOrKey`. | `{ fields: { <fieldId>: { required, schema, … } } }` |

    ### Search

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `searchJql` | Run a JQL search; `body` = `{ jql, maxResults (at most 100), nextPageToken, fields: [..], expand }`. | `{ issues: [{ id, key, fields }], nextPageToken }` |

    ### Projects

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `listProjects` | List/search projects (paginated on Cloud); `query`, `startAt`, `maxResults`, `orderBy`, `expand`. | `{ values: [{ id, key, name }], total, isLast }` |
    | `getProject` | Get a project by `projectIdOrKey`. | `{ id, key, name, projectTypeKey, lead }` |
    | `getProjectComponents` | List a project's components by `projectIdOrKey`. | `[{ id, name, lead }]` |

    | `getProjectStatuses` | List the issue-type statuses of a project by `projectIdOrKey`. | `[{ id, name, statuses: [{ id, name }] }]` |

    ### Users

    | Instruction | Description | Returns |
    |-------------|-------------|---------|
    | `searchUsers` | Find users by name/email fragment `query`. | `[{ accountId, displayName, emailAddress }]` |

    | Instruction | Description | Returns |

    | `listBoards` | List boards; filter by `type`, `name`, `projectKeyOrId`. | `{ values: [{ id, name, type }], isLast }` |

To list an issue's attachments, call `getIssue` with `fields` including `attachment`.

## Verify the connection

Run these checks after configuring the connector and before letting an agent write to Jira. Each one is independent of the setup screens. They are the Jira instance of the generic checks in [Verify the installation](/apps-store/marketplace/connectors/install-in-workspace#verify-the-installation); run the non-allowlisted-agent check from there as well, and [Verify the capability](/apps-store/marketplace/connectors/declare-capability#verify-the-capability) once an agent is wired.

<Steps>
  <Step title="Confirm the runtime identity">
    Call the `users` tool with `action: myself` from the agent, or run `JiraNext.getMyself: {}` from an automation. The response returns the `accountId`, `displayName` and `emailAddress` of the account Jira actually sees. In the OAuth modes this must be the signed-in user; in `apiToken` and `accessToken` modes it is the shared service account, and every write in the workspace will be attributed to it.
  </Step>
  <Step title="Run a read-only query">
    Call `search` with `action: jql` and a narrow query such as `project = DEV ORDER BY updated DESC`, passing `fields` to limit the payload. Issues are returned only for projects the resolved identity can browse.
  </Step>
  <Step title="Check that unauthorized access is blocked">
    Call `projects` with `action: get` on a project key the account must not see. The call fails with `Resource not found while getProject.` or `Forbidden while getProject.` instead of returning data.
  </Step>
  <Step title="Check the write path last">
    Only once the reads behave as expected, create a throwaway issue with `issues` `create` in a test project, confirm it appears in Jira under the expected reporter, then delete it with `issues` `delete`. If the connector is scoped read-only, the write is rejected by Atlassian with `403` and the tool returns `Forbidden while createIssue.`
  </Step>
</Steps>

## Revoke, rotate and remove

The generic procedures are in [Rotate credentials and uninstall](/apps-store/marketplace/connectors/install-in-workspace#rotate-credentials-and-uninstall), and, for the platform-wide client, [Rotate and revoke the central client](/apps-store/marketplace/connectors/central-oauth#rotate-and-revoke-the-central-client). What is specific to Jira:

- **Disconnect one user.** The connector deletes that user's stored OAuth2 **and OAuth1** tokens and the workspace-scoped copy of their refresh token. To also revoke the grant at Atlassian, the user must remove the app's access from their Atlassian account settings; that is the only provider-side guarantee.
- **Offboard a user.** Disconnect them before their Prisme.ai account is removed. Their refresh token is stored under a workspace secret named `jrnRefresh_<userId>`, which the disconnect flow deletes.
- **Rotate the central client secret.** Generate a new secret in the [Atlassian Developer Console](https://developer.atlassian.com/console/myapps/), then re-enter the Client ID and Secret in the maintainer view. Refreshes fail until the stored value matches the one Atlassian expects; users reconnect once if Atlassian invalidated their grants.
- **Rotate an API token or access token.** Replace the value in the configuration app. No user re-consent is required because the `apiToken` and `accessToken` modes have no per-user connection.
- **Revoke an agent's access.** Untick the agent in **Authorized agents**, or clear the allow-all option. The next call is rejected with `This agent is not authorized to use this connector.`
- **Uninstall.** Uninstalling does not delete the workspace secrets the install flow provisioned (`jiraNextAuth`, `jiraNextAuthorizedAgents`) or the per-user `jrnRefresh_<userId>` secrets; delete them from the workspace **Secrets** to purge the stored credentials, and remove any **Jira** entry from the Capabilities catalog ([Remove or update a capability](/apps-store/marketplace/connectors/declare-capability#remove-or-update-a-capability)).

## Error Handling

Atlassian responses are normalized into one message per status, with the failing operation name and a compact detail extracted from the Jira error body (`errorMessages` and `errors`, or `error` and `error_description` for token endpoints).

| HTTP code | Returned message |
|-----------|------------------|
| `400` | `Bad request while <operation>: <detail>` Invalid JQL, malformed body, or a field value Jira cannot parse. |
| `401` | `Authentication failed while <operation>.` The Atlassian token is missing, expired or revoked. The user must reconnect (OAuth modes). |
| `403` | `Forbidden while <operation>.` Insufficient OAuth scope (for example a write with read-only scopes), or the account lacks permission on the project. |
| `404` | `Resource not found while <operation>.` The issue, project, board, sprint or attachment id does not exist or is not visible to the account. |
| `429` | `Throttled by Jira while <operation>. Wait and retry.` |
| `500` | `Jira server error while <operation>.` Transient; retry shortly, no reconnection needed. |
| Other | `Error <status> while <operation>: <detail>` |

### Common Issues

**"This agent is not authorized to use this connector."**: The calling agent is not in this instance's allowlist. Tick it in **Authorized agents** in the configuration app: [Authorize the agents that may call the connector](/apps-store/marketplace/connectors/install-in-workspace#authorize-the-agents-that-may-call-the-connector).

**"The calling agent could not be identified, so it cannot be authorized."**: The MCP capability *Scope* does not declare `agent_id`, so Agent Creator never injects the agent identity. Set the Scope to `context_id,agent_id,user_id`, then allow the agent in the config app: [What the Scope means](/apps-store/marketplace/connectors/declare-capability#what-the-scope-means).

**"Jira is not connected for this user."**: No per-user OAuth token. Start the connection from the configuration app (OAuth modes), or use the agent's connect action.

**"Jira token refresh failed (…)"**: The stored refresh token was revoked or expired. The connection is dropped automatically and the connection status reports the user as disconnected; the user must reconnect from the config app.

**"Jira OAuth is not configured."**: Neither a tenant Atlassian client nor the central platform client is available. Set the OAuth client ID and secret in the config app, or ask the platform maintainer to provision the central OAuth client from the core workspace ([Configure the central client](/apps-store/marketplace/connectors/central-oauth#configure-the-central-client)).

**"apiToken mode requires email, apiToken and site."**: The `apiToken` profile is incomplete. Fill the account email and API token, plus the site on a Cloud deployment.

**"No access token configured."**: The `accessToken` mode is selected but no token is stored. Paste the token (or the Data Center Personal Access Token) in the config app.

**"oauth1 is supported only with deployment=dataCenter."**: OAuth1 was selected on a Cloud deployment. Switch the deployment to `dataCenter`, or choose an OAuth2 mode.

**"Jira OAuth1 is not connected for this user."**: The Application Link access token is missing for this user. Open the connection popup and paste the token issued by the Jira Application Link; it is validated with a signed request before being stored, and the previous token is kept if validation fails.

**"Invalid Jira Data Center baseUrl (…)"**: The base URL is not an absolute HTTP or HTTPS URL, or it carries credentials, a query string or a fragment. Enter the bare instance URL, optionally with a context path such as `/jira`.

**Connection status reports `unsupported_central_auth_mode`**: The central profile is a Data Center OAuth1 profile, which installed workspaces cannot resolve. Configure `oauth1` directly in the workspace instead of `oauthCentral`.

**Agile calls fail with an Atlassian scope error**: The `agile` tool needs a fully-granular Jira Software OAuth app; it cannot run on a token that carries classic scopes. Either migrate the Atlassian app (and the connector **Scopes** field) to the fully-granular set, or avoid the `agile` operations. This is an Atlassian platform limitation. See [OAuth scopes](#oauth-scopes).

**A list stops at 100 items**: `maxResults` is clamped to 100 and array responses are capped at 100 items so a large payload cannot exhaust the agent's context. Narrow the request with `jql`, `query`, `fields` or `startAt` and page through the results.
